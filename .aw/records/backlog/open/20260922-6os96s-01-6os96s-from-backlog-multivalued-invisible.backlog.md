## Workflow history
- 2026-09-22 created (aw backlog): Found while executing plan 8u6770 (planprio Order 02, the Priority/Work-Kind inheritance backfill). THE DEFECT: both regexes that read the field are anchored single-token. releases._ITEM_FROM_BACKLOG_RE is '(?m)^- From-Backlog:\s*(\S+)\s*$' and check_engine._META_FROM_BACKLOG_RE is '(?m)^- From-Backlog:[ \t]*(\S+)[ \t]*$'; on the line '- From-Backlog: dstnso, 8hx3g3' BOTH return None because the trailing ', 8hx3g3' defeats the end anchor. MEASURED at HEAD d84791a0 on pending plan nmlx47 (hostdedup Order 02), the ONE plan in the corpus carrying two source ids: check_engine.find_from_backlog_artifacts('dstnso') returns three plans and NOT nmlx47, find_from_backlog_artifacts('8hx3g3') returns EMPTY, and _from_backlog_carrier_index reports nmlx47 as a carrier for NEITHER id. WHY IT MATTERS, and it is worse than a cosmetic parse miss: the carrier index is exactly what AGENTS.md's close-legitimacy predicate consults to let a release-blocking backlog item close 'done' on the grounds that a plan carrying '- From-Backlog: <id6>' plus the same '- Blocks-Release:' inherited its gate. A multi-valued field is therefore a handoff that LOOKS recorded in the plan and is INVISIBLE to the gate, so evaluate_blocking_close would refuse a legitimate close (fail-closed, benign) while check.live-bug-ungated would flag an item whose carrier genuinely exists (a false positive that trains people to ignore the rule), and check.from-backlog-dangling reports NOTHING at all rather than flagging an unparseable value (measured: 0 findings). It also silently shrinks a backfill population: plan 8u6770 E-01 had to EXCLUDE nmlx47 and report it, because resolving the field honestly is impossible without deciding which of two sources to inherit from. SCOPE: decide first whether the field is single-valued (ipd_schema.META_FROM_BACKLOG's comment says 'single-valued' twice) or multi-valued in fact (one plan in the corpus and its own authors clearly intended two). If single-valued, the readers must FLAG a comma-bearing value via check.from-backlog-dangling rather than silently matching nothing, and nmlx47 needs a decision about which id to keep. If multi-valued, both regexes plus every carrier reader must split on commas, and the two 'single-valued' schema comments must be amended. Do NOT fix this by loosening only one of the two regexes: they are read by different surfaces (aw check's cross-tree sweep and the carrier index) and a divergence between them would make the gate and the checker disagree about the same file.
