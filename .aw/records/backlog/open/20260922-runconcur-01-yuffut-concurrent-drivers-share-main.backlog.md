## Workflow history
- 2026-09-22 created (aw backlog): OBSERVED 2026-09-22: two 'aw oc run ... --unattended' processes were live in the SAME checkout at once (pid 2065001 on sets graduate/migleftover/orchprobe/reaskscore/revladder/roleadv/runnerlayer/runtrailwire/runviewdisc/setterguard/specsweep, and pid 2245533 on commitguard/compinert/finidem/laneorph/nopush/planprio/retrywire/runghostid/runverdict/setidhard/stalecrit/stopcrash). Both integrate verified lanes to main. CONCRETE HARM MEASURED, not hypothetical: while a human was validating a hand-merge of the other run's stranded lanes, pid 2065001 advanced main by 5 commits (landing fduoj4), which silently invalidated an already-completed full-suite validation and forced the whole integration to be rebuilt and re-run against the new tip. The near-miss is worse than the cost: a merge prepared against the old tip would have REVERTED fduoj4's pending/ -> executed/ move, because the stale side still held that plan in pending/. This is the same class of stale-snapshot hazard the runner already guards for its OWN lanes via the stale-base check, but nothing arbitrates BETWEEN two drivers. Additionally, 8u6770's pending-plan backfill touched 10 plan files that the OTHER driver still had queued or running, so landing it could have conflicted with work in flight; the human had to compute that overlap by hand to decide what was safe to merge. A FIX SHOULD decide the intended policy and then enforce it mechanically rather than by operator discipline: either (a) REFUSE to start a second unattended driver in a checkout that already holds a live driver.lock whose pid is alive (the lock and the liveness probe both already exist -- driver.lock records 'pid=' and the run viewer already projects abandoned-vs-live from it), naming the live run and its selectors in the refusal; or (b) SERIALIZE the integration step alone behind a repo-level lock so two drivers may execute in parallel but never merge concurrently, re-resolving main's tip inside the lock. Whichever is chosen, 'aw host capabilities' or the run's startup banner should state it, because today an operator cannot tell from any output that a second driver is even present.
