It carries the QUESTION the retirement left open, which the spec's own 4.2 retirement paragraph now points at: whether to build the one mechanism that is actually a boundary. WHY OS-LEVEL IS THE ONLY CANDIDATE, measured in 4h7tt0's E-02 candidate table: every cheaper mechanism has a concrete evasion. A pre-push hook falls to 'git push --no-verify' and is deletable by the agent it constrains. A remote-less clone falls to 'git push <literal-url> HEAD'. A push-denying credential falls to any other credential in the environment (netrc, SSH agent socket, env token, authenticated gh). A driver-side helper such as git_commit_helper.offer_commit falls to invoking git directly, and inferring support from its presence is FORBIDDEN IN WRITING at host_sandbox_profile.py:109-115. A config flag falls to the agent rewriting the file. Only kernel-level refusal of the syscall cannot be evaded from inside. WHAT BUILDING IT WOULD MEAN: an OS-level sandbox denying push-capable network routes and withholding remote credentials, exposed as a PROBED supports_deny_push in spec 25kzda 5.2's host capability contract, probed BY ATTEMPT exactly as supports_os_sandbox is. The attempt-not-inspect rule is non-negotiable and has a measured justification in host_sandbox_profile's module docstring: on the development host every signal said 'sandbox available' while 'unshare -Umr true' failed with Operation not permitted, so a presence probe would have granted hard mode on a host that could not enforce it. Only after such a probe exists may a finding code be reintroduced in 4.2. SIZE AND POSTURE: the source backlog item d07nz2 calls this a security-boundary design of 1o4eif magnitude that should not be picked up casually, and it needs a spec-level decision before any code. Priority is low DELIBERATELY: nothing is unsafe today, because supports_deny_push is declared False and never probed, so the capability fails CLOSED. This is a missing capability, not a live hole.
