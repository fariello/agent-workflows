## Workflow history
- 2026-09-22 created (aw backlog): Found while executing plan 8u6770 (planprio Order 02) on the four 'reviewed' plans it backfilled. THE DEFECT is the composition of two shipped behaviours, neither of which is a bug alone. FIRST, 'aw ipd set <same-status> <id6> --priority P --work-kind K' appends a workflow-history line even though nothing transitioned; without --message its text is the outright false 'status set to approved' (measured in a throwaway copy on plan 5e4sb6), and with --message the prose is truthful but the leading STATUS TOKEN is still the plan's current status. SECOND, plan_readiness.is_review_history_entry decides a history record IS a review record by scanning that token for a review word, which is the defect backlog ycg597 already records for the general 'aw set' case. COMPOSED, a purely metadata write onto a 'reviewed' plan emits '- <date> reviewed (aw set): <note>', which becomes the NEWEST review record and shadows the real one. MEASURED at HEAD d84791a0 on plans 2s0iym, yv4tb1, r9uvwc and ingpvc: plan_readiness.newest_verdict returned ('positive', <the real /plan-review line>) for three of them and ('neutral', ...) for the fourth BEFORE the write, and returns polarity None with MY bookkeeping line for all four AFTER it. WHAT MAKES THIS MORE THAN ycg597: the consequence is demonstrably NOT benign once the Readiness field is absent, which is the state AGENTS.md REQUIRES a freshly authored plan to be in ('when AUTHORING, OMIT the field'). Driven with '- Readiness:' stripped from the same two files, is_plan_review_approved(2s0iym) returns True BEFORE the write and False AFTER it: a metadata-only backfill flipped the auto-approve predicate's answer on a plan that had a positive review. The four live plans are unharmed ONLY because each still carries an explicit '- Readiness: go-pending-approval' that the predicate consults first, so this is benign-by-luck exactly as ycg597 says, and the luck runs out on any plan following the current authoring contract. SCOPE: ycg597 owns the discriminator fix (the actor field already differs, '(aw set)' versus an agent/model string). What is NOT covered there and belongs here: a FIELD-ONLY no-op write should not emit a review-shadowing record at all, either by writing no history line when no status changed and no --message was supplied, or by tagging a bookkeeping line with an actor/status form no verdict reader can mistake for a review. Cross-reference x6tk1u, which records the same setter DISCARDING a --message on the backlog path, so the two paths disagree about what a no-op transition records.
