## Workflow history
- 2026-09-30 note (aw backlog): CORRECTION to the creation note above, which was filed on an imprecise measurement and is wrong in two ways; the defect is real but its mechanism and symptom differ. FIRST, the symptom: 'aw sanitize --json' writes NOTHING to stdout (stdout is the empty string, exit 0); the line 'No local leaks found.' goes to STDERR, not stdout as the note claimed. So a parsing caller does not read prose where JSON was promised, it reads nothing at all, which is the quieter and more misleading failure. SECOND, the mechanism: the clean path does NOT 'return before reaching' the renderer. The root cause is in the CLI dispatcher cli._run_check_local_leaks, which builds an explicit passthrough argv for leak_sanitizer.main and forwards --history, --max-commits, --wheel, --staged, --warn, --agent, --fix, --yes and --dry-run but NEVER forwards --json. leak_sanitizer.main's own machine branch is correct and tests 'if ctx.is_agent or ctx.is_json', so the engine would honor --json if it ever received it; the flag is consumed by the outer parser (it is on the shared 'common' parent) and then dropped on the floor. Verified by contrast: 'aw sanitize --agent' emits a well-formed aw.agent/v1 record on stdout. The bug classification and the 'next' gate stand, and the likely fix is one forwarding line, plus a test asserting every advertised machine flag on this subcommand reaches the engine (the generalizable defect is a hand-maintained passthrough list, so other forwarded leaves may drop flags the same way and are worth auditing in the same pass).
- 2026-09-30 created (aw backlog): Found authoring plan 9yd6tx (backlog 7tixnq) as its F-13. Measured: 'aw sanitize --json' on a clean tree emits exactly 'No local leaks found.' and exits 0; json.loads on that output raises. The --json flag is declared on the subcommand (it appears in the command's own --help usage line) and the repository's output contract documents --json as a full structured JSON representation, so a caller that trusts the advertised flag gets a parse error rather than a payload. leak_sanitizer.main does build a CommandResult and route it through select_output plus get_renderer(ctx).emit for its machine path, so the structured path EXISTS; the clean path appears to return before reaching it. Filed as a bug rather than a chore because the user-perceptible impact is a crash in any script that parses the documented surface, and because the flag is advertised; gated on next per the every-live-bug-gates-the-next-release policy. Not fixed in 9yd6tx because that plan's scope is what the --json payload CONTAINS (home-path redaction in CommandResult.to_dict), not which code paths reach a renderer at all; 9yd6tx explicitly asserts on rendered payloads instead of delegating to the sanitizer precisely because the sanitizer cannot see command stdout anyway.
