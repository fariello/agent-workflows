This item's original text claimed 'a merge prepared against the old tip would have REVERTED fduoj4's pending/ -> executed/ move, because the stale side still held that plan in pending/'. THAT IS FALSE and is retracted. The maintainer challenged it and direct measurement settled it: three throwaway repositories were built with main moving a plan pending/ -> executed/ while a lane forked from the older base. (1) Lane EDITS the file at its old pending/ path: git reports 'CONFLICT (modify/delete): pending/plan.md deleted in HEAD and modified in lane'. (2) Same but with bodies similar enough for rename detection: git follows the rename and reports 'CONFLICT (content): Merge conflict in executed/plan.md'. (3) Lane does NOT touch the plan and edits only an unrelated file: the merge SUCCEEDS and the plan REMAINS in executed/, because a side that changed nothing about a file cannot revert it. So a stale side either conflicts LOUDLY or leaves the transition intact, and there is no conflict-free path that silently un-executes a plan. WHAT SURVIVES, unchanged and still measured: the wasted-work cost. The peer driver advanced main mid-validation twice, forcing two full rebuilds and re-runs of the suite, and a prepared --ff-only publish refused with 'Not possible to fast-forward'. Also unchanged: a peer driver is INVISIBLE in every operator-facing output, so deciding what was safe to merge required reading both runs' state.json by hand. THIS WEAKENS THE JUSTIFICATION AND IS STATED PLAINLY: this item is worth fixing for wasted operator and machine time and for peer invisibility, NOT on the strength of a record-corruption risk that git demonstrably prevents. MAINTAINER DECISION 2026-09-22: policy (b), serialize the integration step only, so two drivers may execute in parallel but never publish concurrently. Plan vddpml's OQ-01 is answered accordingly. A FOLLOW-ON QUESTION THE MAINTAINER RAISED remains open and is the more important half: how a NON-RUNNER actor (a human, or an agent like this one integrating by hand) is expected to honor that serialization, and how it is enforced rather than merely documented.

CONCRETE HARM MEASURED, not hypothetical: while a human was validating a hand-merge of the other run's stranded lanes, pid 2065001 advanced main by 5 commits (landing fduoj4), which silently invalidated an already-completed full-suite validation and forced the whole integration to be rebuilt and re-run against the new tip. The near-miss is worse than the cost: a merge prepared against the old tip would have REVERTED fduoj4's pending/ -> executed/ move, because the stale side still held that plan in pending/. This is the same class of stale-snapshot hazard the runner already guards for its OWN lanes via the stale-base check, but nothing arbitrates BETWEEN two drivers. Additionally, 8u6770's pending-plan backfill touched 10 plan files that the OTHER driver still had queued or running, so landing it could have conflicted with work in flight; the human had to compute that overlap by hand to decide what was safe to merge. A FIX SHOULD decide the intended policy and then enforce it mechanically rather than by operator discipline: either (a) REFUSE to start a second unattended driver in a checkout that already holds a live driver.lock whose pid is alive (the lock and the liveness probe both already exist -- driver.lock records 'pid=' and the run viewer already projects abandoned-vs-live from it), naming the live run and its selectors in the refusal; or (b) SERIALIZE the integration step alone behind a repo-level lock so two drivers may execute in parallel but never merge concurrently, re-resolving main's tip inside the lock. Whichever is chosen, 'aw host capabilities' or the run's startup banner should state it, because today an operator cannot tell from any output that a second driver is even present.
