WHY IT MATTERS RATHER THAN BEING COSMETIC: it is a FALSE RED in exactly the situation the repository most depends on a true reading. The integration gate's trust signal is a full-suite exit code, and an agent validating in a lane sees this failure, so the agent must either mis-report its own work as breaking a test it never touched, or spend a turn diagnosing an inherited variable, or (worst) learn to wave away red tests as 'probably environmental'. It also interacts with the gate-answer mechanism: a lane whose only failure is this one gets escalated to the agent for adjudication, spending a paid model turn on a question with no real subject. LIKELY FIX, for whoever takes it: build the expected environment from an explicit base rather than inheriting os.environ for this assertion, or pop the opencode-owned keys before comparing, so the test measures what the policy WROTE rather than what the ambient process happened to carry. Sibling precedent worth reading first: backlog 8kttqq is the same CLASS of defect (a test that consults ambient filesystem state and trips over a gitignored local directory), so a fix here should check whether other tests in this family inherit process state they should not.
