## Round 1

All claims re-measured at HEAD `51ffe3f4` in an isolated lane worktree. The target plan was committed and
byte-identical to the driver's staged input, so the pre-review snapshot was correctly skipped per Step 1.
Structural preflight `aw ipd lint --phase author` reported `conforming` before review and
`--phase review-finalize` reported `conforming` after the revisions.

THE DEFECT IS REAL, THE EVIDENCE REPRODUCES, AND THE PLAN'S DIAGNOSIS IS CORRECT. That matters to establish
first, because everything below is about how the fix could go wrong rather than whether it is needed. I
re-read both cited `state.json` records through the repository's own `attention._resolve_runs_repo_root`
rather than trusting the prose: `ld8lb3` and `65cuw0` both ended `merge-refused` with
`integration_failed_combined_red`, both carry a `completed` baseline, both carry `measured: True` (so these
are genuine measured reds, not harness faults), and in both the post-merge failing SET is byte-identical to
the baseline's single id while the passing count rose by exactly the tests each lane adds. F-1's central
asymmetry also holds, re-derived by AST rather than by the plan's line-range grep, which would have expired:
`make_integration_validation_runner` spans 244 lines and contains zero occurrences of `baseline`, and `passed`
comes from `bool(getattr(result, "passing", False))` alone. F-4 is true and slightly understated: all THREE
call sites pass `item`, `attempts` is never stripped from a preserved item, and both the
`attempt["suite_baseline"]` write and the `val_runner` construction sit inside `execute_item_core` with the
write strictly first.

THE DOMINANT FINDING IS THAT THE PROPOSED SUBTRACTION IS THE COMPARISON THAT ALREADY INVERTED THIS
REPOSITORY'S INTEGRATION GATE ONCE, and the plan as authored walked into the same hole in a different
function. `tests/test_suite_adjudication.py::TheExitCodeIsTheAuthorityAndNotTheList` exists for that
incident and describes it in terms: plan `32ij2j` "compared failing SETS as a subset and derived them from an
always-empty string, so every lane passed including one that broke everything", and the same always-empty
read was ALREADY SHIPPED in `oc_runipd.run_suite_check` until `h5pyqa` repaired it. That file calls the
anti-inversion case "the single most important case here, because it is the one that was shipped wrong". The
hole is reachable unchanged in the new location: E-01 as written answers `no-regression` whenever
`merged_ids - baseline_ids` is empty, and an extractor that yields `()` on a genuinely red run makes that set
empty, so a tree that broke everything would integrate. The plan's own gate says "a fix here that made the
gate MORE permissive in any other case would be worse than the defect it removes" - which is exactly right
and is why this is a BLOCKER rather than a caution.

A SECOND, INDEPENDENT WAY THE SUBTRACTION LIES IS THE TRUNCATION CAP, and it needs no extractor bug at all.
`oc_runipd.extract_suite_failures` returns at `SUITE_FAILURE_LINE_LIMIT` (40) in FIRST-SEEN order, while
`pyproject.toml` `addopts` carry `-n auto --dist=worksteal` plus random ordering, so two runs of the SAME red
tree can retain DIFFERENT 40-line subsets. Measured: 60 identical pre-existing failures reported in reverse
order by the second run yield 20 FALSELY NEW ids, i.e. a fabricated regression on a tree nothing changed.
That direction is over-refusal and so is not a safety hole, but it would make the fix unreliable precisely on
the badly-red trees it is meant to help.

A THIRD FINDING CAME OUT OF CORRECTING A FIGURE, which is why the figure was worth correcting. The plan
asserts base commit `301a1d8fbc15` for both refused items; measured, `65cuw0`'s baseline is pinned to
`ee20e831f5f1`. So a single run contained two items with DIFFERENT baselines - and the factory caches
`{passed, reason, measured}` under `cache[tree_id]`, keyed on the merged TREE and served wholesale to any
item reaching it. Once the verdict becomes relative to a per-item baseline, an unmodified cache can serve a
comparison computed against another item's baseline. Raised as OQ-03 with both fixes priced.

TWO SMALLER CORRECTIONS OF OVERCLAIM. `h90ij1`, offered as a third instance, carries TWO post-merge failures,
one of them genuinely new, so it would STILL refuse after this fix - correctly; it is evidence the defect
recurs, not a case the fix rescues. And the residual error's SIGN was left for a reviewer to derive: because
`start_suite_baseline` pins the baseline to a COMMIT rather than a branch (deliberately, "if a human or
another agent merges to main mid-turn"), a failure introduced by main advancing is absent from the baseline,
counted new, and refuses. Over-refusal is today's behavior and recoverable by hand, so the fix's residual
error has the safe sign - which is the single most reassuring fact about this change and was unstated.

Verified TRUE and left standing: F-3's count lines verbatim; F-6's cascade; the deferral of `c74dm7` and
`iv4n2c` (both live on disk, and `validation_runner_for` confirmed inert - declared once, called never);
OQ-02's unknown-refuses answer, which is the correct discipline and is now extended to three further unknown
shapes; the two declared `Scope-Paths`; and V-04's list of pre-existing `post_merge_revalidation` keys, which
matches the shipped record exactly (`cached`, `failures`, `measured`, `merged_files`, `passed`, `reason`,
`skipped`, `tree`).
