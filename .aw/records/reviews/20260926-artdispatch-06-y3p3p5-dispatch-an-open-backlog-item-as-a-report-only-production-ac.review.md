## Round 1

Re-verified at lane HEAD `8ef40273`. Every authored claim was re-derived by DRIVING the real setter
and the real checkers on a scratch repository rather than by reading source, and that choice is what
produced the two HIGH findings: both defects are invisible in the source and only appear when the
calls are made in the order the plan specifies.

THE ROOT CAUSE OF BOTH HIGH FINDINGS IS ONE MISTAKE: THE PLAN TRUSTS THE SETTER TO ENFORCE THINGS IT
DOES NOT. `check_engine.evaluate_blocking_close` branches on the DESTINATION status (`if target_status
== "graduated" and blocks_release: return CloseVerdict(True, "ok", ...)`), so it says nothing about
where the item came from. Two consequences follow, each measured end to end.

First, `BACKLOG-GRADUATE-LEGITIMACY`'s clause "the item was NOT set `done`" is unfalsifiable as the
plan wrote it. The authored order is: agent turn, handoff commit, runner's `--status graduated`, THEN
the LEGITIMACY check reading "its status is not `done`". But `--status graduated` is legal from `done`,
so the runner's own call MOVES the item out of `done/` before the check looks. Driven in that exact
order on a scratch gated item: the agent's `aw backlog set done <id6>` exits 0 and lands the item in
`done/`; the runner's `aw backlog set <id6> --status graduated` exits 0 and lands it in `graduated/`;
the file then reads `- Status: graduated` and the clause PASSES. Spec `z7nbn1` 5.5c's "the item ends
`graduated`, never `done`" would have been asserted by a check that cannot fail for it. The fix is
structural, not a stronger check: the runner captures the item's status BEFORE its own transition,
refuses to transition from anything but `open`, and passes that prior status into the verifier.

Second, the rollback cannot run. The plan's E-03 restored the item with `aw backlog set <path>
--status open` using the path captured at dispatch, but the setter MOVES the file, so that path names
nothing once the item is in `graduated/`. Driven: `aw backlog set: no such item: <open/ path>`, exit 2,
item still in `graduated/`. So a post-transition `BACKLOG-CROSS-TREE` or `BACKLOG-GRADUATE-LEGITIMACY`
finding would leave the item stranded as `graduated` with no valid handoff while the run reported that
it had contained the failure, and because `aw attention` maps `graduated` to `active`, the item also
drops out of the `ready` set a human works from. The same id6 selector on the same item exits 0.

A THIRD CORRECTION IS TO THE PLAN'S OWN FINDINGS TABLE, and it matters because the plan cited it as
settled prior art. F-3 claimed `check_engine.check_release_gates` "already implements the cross-tree
findings" and listed `check.orphaned-live-blocker` among them. It does not: that function composes
exactly `check_engine.RELEASE_GATE_RULES`, and two of the four classes `25kzda` 4.9's
`BACKLOG-CROSS-TREE` row requires are reached only through other entry points. Measured: an `open`
gated item with a pending `From-Backlog` carrier yields `[]` from `check_release_gates` and
`['check.orphaned-live-blocker']` from `release_gate_warnings`; a produced plan carrying `From-Spec:
nosuch` yields `[]` from `check_release_gates` and `['check.from-spec-dangling']` from
`check_from_spec_dangling`. A verifier built on the authored premise would have reported a clean
cross-tree on both defects, which is the failure mode that matters most for a check whose entire job is
to catch them.

The plan's SHAPE is sound and its verifier decomposition is good, which is why this is a revision
rather than a REPLAN. What it lacked was the measured behavior of the one tool it delegates its most
important guarantee to.
