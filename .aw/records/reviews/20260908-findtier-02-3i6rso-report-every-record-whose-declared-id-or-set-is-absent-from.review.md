THE ROUND'S CENTRAL RESULT: THE PLAN PROPOSES BUILDING SOMETHING THAT IS HALF-BUILT, AND DOES NOT
CITE IT. `check.id6-identity-slot` is registered and implemented, and its documented rule (a) already
says a file declaring a frontmatter `- Id:` must carry that id6 in its filename slot - which is E-01
and E-02's comparator. More importantly it already SOLVES the sub-problem this plan would have had to
solve blind: distinguishing a real id6 from a slug word that merely looks like one, by testing
membership in the set of all declared ids. Measured, that rule flags 2 files and covers ZERO of the
ten, because it exempts filenames with no id6 slot - precisely the legacy population. So the gap this
plan fills is REAL but NARROW, and the correct shape is to extend or sit beside that rule and reuse
its discriminator. Writing a second identity comparator would give the repo two definitions of "is
this a real id6" that can drift, which is the defect the existing rule was written to prevent. That is
now E-06, the plan's new first design decision.

WHY THAT MATTERS CONCRETELY RATHER THAN AESTHETICALLY: the naive discriminator mis-buckets a record
this plan lists among its own ten. `parse_clustered` reports the legacy name
`20260817-1357-01-assess-bugs-leftover-remove-dataloss.ipd.md` as CONFORMANT with `id6='assess'`, and
`assess` is six lowercase alphanumerics so `ID6_RE` accepts it. A classifier that trusts the parsed
slot therefore reads that file as modern-grammar and would place it in the genuine-drift bucket - the
one the plan says deserves prominent escalation - when it is plainly a legacy name whose real declared
Id is `wvlk84`. The existing rule's `declared_ids` test is what avoids this.
