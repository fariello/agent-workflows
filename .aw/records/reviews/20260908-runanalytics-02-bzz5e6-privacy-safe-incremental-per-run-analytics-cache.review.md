## Round 1

Reviewed at HEAD `f6a71427`. Structural preflight `aw ipd lint --phase author` conformed BEFORE semantic
review (exit 0, `outcome: clean`), and `--phase review-finalize` conformed after the revisions. Note the
linter EARNED its keep mid-review: the E-item split tripped `IPD-I304` (stale `Highest E allocated`) and
three `IPD-I303` bijection errors, all repaired, which is exactly the class of drift a hand-check misses.

WHAT THE PLAN GETS RIGHT, and it is the substance. The privacy analysis is genuinely good: it separates
"raw" as UNSUMMARIZED METRIC FACTS from "raw" as SOURCE RECORDS, which is the distinction most such plans
elide, and it insists the same projected facts feed every downstream consumer rather than letting report,
query, export and submission each grow a weaker sanitizer. The closing refusal to call the cache
"anonymous or safe for public release" is the right honesty and rare. The freshness reasoning is correct
where it matters most: directory mtime cannot establish freshness because a resumed run reuses its
directory, which is the actual failure mode. And the required-cases list is genuinely falsifiable.

THE PRINCIPAL FINDING IS SIZING, AND THE COUNT-BASED LINT CANNOT SEE IT. E-02 as authored named SIX
independent deliverables in one item (freshness decisions, stable-source reuse, incomplete-run rechecks,
locking, atomic replacement, corruption recovery) spanning at least four unrelated test surfaces, and
E-03 bundled a consumer-facing observability contract with five test families. `aw ipd lint` reported
conforming and the density advisory `IPD-Z602` was silent on all three items, which I verified by calling
`ipd_schema.e_item_density_advisory` on each rather than inferring it from the clean lint. The decisive
evidence that this is a template rather than a judgement: EVERY ONE of the Set's ten children carries
exactly three E-items. A privacy boundary and a locking protocol do not happen to be the same size as a
CLI and a documentation pass. Split into six items against the plan's own stated right-sizing rule.

THE CONVENTIONS SECTION POINTED AT THE WRONG LOCK API, which is the finding most likely to have produced
broken code. The plan said to use `filelock`'s "established locking approach". True about the dependency,
wrong about the approach: `platform_lock` is the package's single lock authority, exists so no other
module depends on a lock backend directly, and is enforced by a guard test that fails on a top-level
`import fcntl` anywhere in the affected modules. Its docstring records three properties a direct
`filelock` caller would get wrong, and one of them is severe: `filelock` MUST NOT be used to PROBE a
holder, because its POSIX backend opens with `O_CREAT | O_TRUNC`, so a FAILED acquire destroys the record
of the live holder that just refused. A cache probing for contention with `filelock` would corrupt the
very diagnostic it was reading. Also non-re-entrancy is deliberate, and a second `acquire()` on the same
`filelock` object SUCCEEDS via a per-object counter, which is a silent mutual-exclusion failure.

A SHIPPED DETECTOR ALREADY COVERS MOST OF THE FORBIDDEN SET AND THE PLAN NEVER MENTIONED IT.
`leak_sanitizer` (re-exported as `local_leaks`, driven by `aw sanitize --agent`) detects home paths,
handles, hostnames, remotes and secret-shaped strings. Measured: `scan_text` over a string containing a
real home path and username returned `home-path` and `handle`, both at `fail`. This matters twice. It is
the correct INDEPENDENT read-side oracle, so V-04 now requires the detector be run over the produced
cache AND a control run proving the same detector flags those canaries in raw form, because "clean" and
"not looking" are otherwise indistinguishable. And it means a second sanitizer here would fork a module
whose own docstring says it exists to keep ONE code path.

ONE DIRECTIONAL HAZARD WORTH MORE THAN ITS SEVERITY. The Findings section enumerates a thorough forbidden
set, and a thorough denylist is an invitation to implement a denylist, which passes every test written
from that same list and fails on the first field nobody imagined. The plan's own E-01 said "allowlist", so
the intent was right; the risk was that the most detailed prose in the document pointed the other way.
The forbidden list is now explicitly labelled a TEST CORPUS, and the gate says plainly that filtering
known-bad keys instead of passing known-good ones is a stop condition.

"NO OPEN QUESTIONS" WAS NOT TRUE, and both gaps were resolvable from repository evidence rather than by
asking, so they are recorded as decisions. Where the hash salt lives was required by the plan's own
Findings and specified nowhere; resolved to the gitignored analytics subtree, with `.aw/config/local.json`
rejected because a salt is not a user-visible setting and with the disposability of the cache making a
salt that outlives its data the wrong default. And what happens on lock contention was unaddressed;
resolved to a recorded SKIP rather than a wait, because `platform_lock` documents that exactly one caller
may block and an analytics cache is the weakest imaginable candidate to become the second, since a skip
costs a rebuild while a hang costs the operator their run.

TWO SET-WIDE AUTHORING PATTERNS, recorded because they will recur in the eight unreviewed siblings. The
gate carried NO execution contract at all (no scope fence, no path-scoped commit / never-push, no
paste-actual-output rule, no lifecycle move), and Order 01's review found the identical omission. And four
escaped backtick pairs rendered as literal backslashes, where Order 01's review found six. Both are
mechanical and both are fixed here, but whoever reviews Orders 03 through 10 should expect them.

ONE TENSION I CHECKED RATHER THAN LEAVE FOR EXECUTION: approved spec `kw5y2s` enumerates a
`state/runtime/cache/` class, while this Set sites the analytics cache under the runs root. That is
defensible (the analytics tree describes the run corpus and inherits its disposability) and it is Order
01's decision, not this child's, so no amendment is forced; the plan now says so and says to STOP rather
than relocate or edit the spec if execution concludes otherwise.

AND THE PLAN'S OWN THESIS WAS DEMONSTRATED ON THIS REVIEW, ACCIDENTALLY. Pasting the measured `scan_text`
result into the plan WITH ITS LITERAL INPUTS made `aw sanitize --agent` FAIL on the plan file itself, with
`home-path` and `handle`. I reworded it and re-ran to clean. That is worth more than the embarrassment: E-06
seeds exactly such canaries into fixtures, so a committed test corpus of real-shaped secrets is a leak that
ships. The detection engine's own convention is the model ("Sensitive literals are assembled from fragments
in the engine module, never here"), and E-06 and F-10 now carry that requirement plus the instruction to run
the sanitizer over the TEST tree, not only the cache.

WHY APPROVE WITH REVISIONS RATHER THAN OPEN QUESTIONS. Nothing here required a human decision: the sizing
fix follows the plan's own rule, the lock and sanitizer corrections are settled repository facts, and both
unmade decisions were answerable from existing evidence and are recorded as such. No BLOCKER or unfixed
HIGH remains.
