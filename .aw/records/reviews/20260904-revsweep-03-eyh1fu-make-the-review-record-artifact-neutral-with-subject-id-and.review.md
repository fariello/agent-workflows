## Round 1

All claims verified at HEAD `024ab067`. The target plan was committed at `0ee800f4` and unchanged, so
the pre-review snapshot was correctly skipped. `aw ipd lint` conforming at `--phase author` before
review and again at `--phase review-finalize` after revisions.

THE PLAN'S PREMISE IS EXACTLY RIGHT, and it is worth saying plainly because the rest of this review is
about what the plan missed rather than about whether it should exist. `render_review` hardcodes
`- Plan-Id:` at `review_findings.py:353`, `check_review_dangling` builds its `known` set from
`_iter_plan_ipds` alone (`check_engine.py:2477-2480`), and the recovery text tells the author to
"correct the Plan-Id ... or retire the review". A spec review really is rejected by the repository's
own checker. F-3's observation that the FILENAME grammar already generalizes also holds, which
correctly bounds the change.

TWO FINDINGS WOULD HAVE TURNED THIS "NEUTRAL RENAME" INTO A SILENT REGRESSION.

PR-001 is the one I would not have wanted to discover after execution. The subject field has a SECOND
consumer the plan never mentions. `_review_index` reads the same `_REVIEW_PLAN_ID_RE` and maps subject
id6 to review files, and it backs four call sites implementing `check.review-finding-unescalated`
(severity `error`, wired into two `aw ipd lint` checkpoints) and `check.review-decision-unescalated`.
Repoint only the dangling check and the index is keyed on a field no record carries: it returns empty,
and every dependent rule takes its documented "nothing reviewed: every plan is the (a) absent case"
early return. The result is that unfixed HIGH and BLOCKER findings would stop gating anything, with no
error and no output, which is precisely the hole the `revgate` Set was built to close. The plan's own
Scope says "every consumer", so this is an omission rather than a disagreement, but the omission is
load-bearing: it is the difference between a rename and a regression in a release gate.

PR-002 is a cost the plan accounted for incorrectly rather than missed. E-03's decision to make an
absent `Subject-Type` a parse error is CORRECT and I kept it; F-7's reasoning about defaulting hiding a
migration bug is sound. But a parse error is a `Diagnostic`, and `plan_gating_blocks` case (b) treats
any diagnostic as BLOCKING on the explicit ground that "a file that exists but cannot be trusted is an
error, not an absence". That predicate is consumed by both host runners, `/exec-set`'s Set compiler,
`aw check`'s escalation evaluator, and `plan_readiness.approval_refusals`, where a typed gating
finding is documented as having no override at all "because the whole point is that no flag should be
able to turn 'do not build this' into 'executable'". So a single record left unmigrated does not merely
read as dangling: it blocks its plan's approval and its dependents' execution, unfixably, until the
record is repaired. All 36 records parse with zero diagnostics today, so every instance of this failure
is manufactured by this change. E-03 and E-04 must therefore be one atomic commit, or strictly
ordered, and the plan now says so.

FOUR SMALLER CORRECTIONS, each of which would have cost the executor time or produced a false claim.

Two E-05 instructions rested on premises that are simply not true (PR-003). `Plan-Id` greps to ZERO in
`.aw/system/workflows/`, so the plan-review bodies do not instruct an agent to write the record's front
matter, the cited `plan-review.md:178-185` says only "using the same columns", and the deliberate-parity
concern does not arise at all. Meanwhile the REAL documented contract, `.aw/records/reviews/README.md:155`,
which literally displays `- Plan-Id: <id6 of the reviewed plan>`, was demoted to a conditional "check and
update if". I inverted both: the workflow bodies leave the fence, the README enters it.

The plan's own advisory-severity verification was unsound (PR-004). V-03 asked to confirm
`check.review-dangling` is still advisory "by exit code, not by reading the rule's declaration".
`drift_exit_code` exempts only `info`, so a `warning` drives exit 1 as well, and `check_engine.py`
carries a comment written expressly against this misreading: "DO NOT READ `warning` AS 'cannot fail
anything' (measured, not assumed)". An executor following V-03 literally would either have concluded the
rule had been promoted, or worse, changed something to make the exit code match.

The corpus count is a moving target and the plan hardcoded it (PR-005). The spec says 34, the plan says
35, I measured 36, and one of those 36 is the review record this Set produced for its own sibling plan
an hour earlier. A validation asserting equality against a literal will fail for a reason that has
nothing to do with the change.

`tests/test_selector_resolver_matrix.py` writes a `- Plan-Id:` fixture and was missing from Scope-Paths
(PR-006), so the plan declared a fence excluding a file it must edit.

ONE FINDING SOFTENS A CLAIM RATHER THAN ADDING WORK (PR-007). F-5 said the `reviews.py` contract "will
become false prose". I verified the resolver's regex: `_FRONT_MATTER_ID_RE` matches `- Id:` exactly and
rejects both `- Plan-Id:` and `- Subject-Id:`. So the prose's CONCLUSION, that an id6 selector does not
match a review's front matter and matching happens by filename, remains true after the rename. Only the
field name in it is wrong. That distinction matters because the obvious "fix" would be to rewrite the
paragraph as though front-matter matching now works, which would be a new false claim.

Finally, recorded for the approver rather than as a defect (PR-008): the source spec `6m4kow` is still
`to-review`. A plan may be authored from a spec under review, and its sibling `5slbpi` is in the same
position, but it means approving this plan implicitly ratifies R-01 through R-05.

Zero findings were deferred and zero left open, so nothing required escalation as a blocking question.
OQ-01 (rename the gating predicates or correct their prose) stays non-blocking, and I strengthened its
recorded default with the measurement that was missing: renaming reaches five call sites, two of them in
the two highest-contention modules in the repo, so it would breach this plan's own fence.

Baseline measured so a later regression is attributable: the four review test modules are `161 passed`
at `024ab067`.
