THE PLAN'S PRESCRIBED FIX WAS A DATA-LOSS DEFECT WORSE THAN THE ONE IT REPAIRS, and that is the
substance of this review. E-03 instructed the executor to write all four fields from the destination
name, rendering `model` as the empty string when `R.parse_name` returns `model=None`, reasoning by
analogy from `research_cmd.build_frontmatter`'s `model_str = model if model else ""`. That analogy fails
because `build_frontmatter` is a CREATOR (where `None` means the author supplied no model) while the
applier is an UPDATER (where a facet-less name means only that the NAME omits the model). Spec
`agents-artifact-organization` Section 4.4 states that `<model>` is "present ONLY when authorship
disambiguation matters, and always ALSO recorded in frontmatter (`model:`) so provenance is queryable
even when omitted from the name", so a facet-less name beside a populated `model:` is the spec's
SANCTIONED NORMAL CASE. I built the plan's prototype exactly as specified and ran it against a record in
that shape: it wrote `model: `, destroying provenance that exists nowhere else, while claiming to fix a
spec violation. This is strictly worse than the defect being fixed, because a stale `set:` is a
RECOVERABLE wrong value the fixed verb can repair, whereas an erased `model:` is unrecoverable.

I did not stop at the finding. I derived the corrected mechanism (omit the key when `parsed.model` is
falsy, which works because `update_frontmatter_fields` only rewrites keys it is GIVEN), measured that
every other property the plan claims still holds under it, and measured that the correction closes no
legitimate use: `R.normalize_model` rejects `-`, `''` and `none`, so no CLI path can request a model be
CLEARED, and `plan_set_assign` passes `parsed.model` through unchanged. So the plan is repaired in place
rather than replanned, and the repair is pinned by a new test rather than by prose.

The plan also relied, without stating it, on the research tree being exempt from the writer's markdown
normalization; without that exemption its byte-identical body assertion would fail on any record whose
delivered formatting is unnormalized. That is TRUE here and now recorded (F-18).
