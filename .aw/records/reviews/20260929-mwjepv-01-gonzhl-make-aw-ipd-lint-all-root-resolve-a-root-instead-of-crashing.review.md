Reviewed at HEAD `dfb500e3` in an isolated review lane. The plan file was committed and byte-identical to the

THE PLAN'S CENTRAL JUDGEMENT IS CORRECT AND I VERIFIED IT RATHER THAN ACCEPTING IT. The backlog item asks for
a one-line repair (take the first element of the list). The plan refuses to stop there, on the argument that
the repair alone converts a loud crash into a silent `error=0` at exit 0 over a tree that was never read. I
reproduced every step of that argument independently: the crash text and exit 2 are exactly as F-01 states;
`parse_args(["ipd","lint","--all","r1"]).path` is `['r1']` while bare `--all` is `[]`; `_iter_plan_files` on a
root containing a real plan at `.aw/records/plans/pending/bad.md` returns `[]`; the resolved base is
`~/.aw/projects/<handle>/records/plans` with `is_dir()` False; and `resolve_project_context` gives
`records_backend=home` from `builtin_defaults` for that root against `repository` from
`project_durable_config` for this one. F-04's claim that the legacy `.agents/plans` rung still works is also
true (that root IS found today), which is what makes the defect specific to the modern layout. Spec
`ipd-structure-and-linting` says what the plan quotes it as saying, at Section 10: "The tool MUST distinguish
a conforming result from inability to run. An internal failure MUST never be reported as a passing lint." So
the plan's expansion beyond the item is justified, not gold-plating, and E-02 is correctly ordered first.

F-05 through F-08 all verified. The existing `ExitCodeTests._run` does build a `Namespace` with `path=None` and
both `--all` tests do call `self._run(all=True, path=str(root))` with a STRING, and both build `.agents/`
layouts, so neither the crash nor the false pass could have been caught. `gate_ipd_lint` does pass no
positional. `command_surface`'s `ipd lint` declaration does carry `exit_contract=(0, 1, 2)`. No `.spec.md`
mentions `--all` or a repo-root positional. `LIVE_SAFE_LEAVES` is read only as a membership test
(`is_live = decl.command in LIVE_SAFE_LEAVES`) and appears in no other test module, so its argv list really
does drive nothing.

WHAT REVIEW FOUND. Two serious problems, both discovered by probing the MECHANISM the plan prescribes rather
than by reading it, and both of the same family as the defect the plan exists to close.

THE FIRST (PR-801/PR-802) is that E-03's refusal as written would have created a NEW false answer. E-03 told
the executor to refuse when "E-02's ladder found no base", but E-02 as authored still returned a bare LIST,
from which base absence is not recoverable. I measured what that list actually distinguishes: an unconfigured
root gives base `is_dir()` False and `[]`; a CONFIGURED root whose `.aw/records/plans/pending/` exists and is
empty gives base `is_dir()` True and also `[]`. The first is an inability to run. The second is a legitimate
empty population and the correct answer for a fresh repository. An executor implementing E-03 against `[]`
would exit 2 on a healthy repo, trading this plan's false PASS for a false FAILURE. E-02 now returns a
discriminated result, E-03 refuses on base ABSENCE explicitly and never on emptiness, E-05 gains case (g) to
pin the empty-but-located root at exit 0 both before and after, and the gate carries a paragraph naming the
overshoot by name. This is the finding that most changes the plan.

THE SECOND (PR-804) is that the plan asserted the bare-`--all` path stays "BYTE-UNCHANGED" and that is false
in general. The defaulted `"."` flows through E-03's new refusals like any other root, so a bare `--all` in a
directory that is not a project moves from exit 0 to exit 2. I measured it: in an empty non-project cwd the
base resolves out-of-tree, `is_dir()` is False, and the base-absence refusal would fire. The release gate is
genuinely unaffected, but for a reason the plan did not give (`gate_ipd_lint` passes `cwd=repo_root`, a tree
that HAS a plans tree), not because the code path is untouched. Left standing, an executor would have written
a test pinning an invariant that does not hold and then either weakened the refusal or hardcoded around it.

Also found and fixed: a leak the plan's own V-03 could not have caught (PR-803), because `to_agent_record`
OMITS `summary` entirely while `to_dict` carries it verbatim, so checking only `--agent` proves nothing; the
shipped `not a file:` refusal already prints `"summary": "not a file: /home/<user>/nope.md"` under `--json`,
and E-03's new refusals take a caller-supplied root. Two stale live-artifact figures (PR-805): `error=1`/six
diagnostics is now `error=3`/seventeen over three different plans one day later, and the 943 plan-count
baseline is 1033, which is precisely the drift the re-derivation convention exists for. A citation to F-06 for
an "only such leaf in this CLI" claim F-06 does not make and whose survey was never run (PR-806). And an
execution gate missing the scope-fence declaration wording and the conditional finalize ownership (PR-807).

WHAT I DELIBERATELY DID NOT DO. I did not fix the pre-existing `--json` summary leak in the sibling
`not a file:` arm, and I recorded that decision in the plan's Deferred section with its reason rather than
silently passing over it: it is outside the `--all` arm this plan touches, the disclosed string is the path the
caller just typed, and `agent_schema` already refuses it on the machine-consumed `--agent` surface. I also did
not re-open OQ-01 (refuse 2+ roots rather than loop). Its reasoning is sound and rests on a real discriminator
I checked: `artifact_adopt` does refuse a second value on a `nargs="*"` positional at exit 2 naming the count,
`aw install` and `workflow_cli` do loop, and the difference really is that the looping verbs emit per-target
sections while `ipd lint --all` emits one flat `counts:` line no reader could decompose.

The bare suite at review HEAD is `3246 passed, 2 skipped` with no plan-related failure. `aw check plans`
reports 26 findings across the pending corpus and NONE on this plan.
