## Round 1

All claims verified at HEAD `9079a6e3`. The target plan was committed and unchanged, so the
pre-review snapshot was correctly skipped per Step 1. Structural preflight
`aw ipd lint --phase author --agent` reported `conforming` (exit 0) BEFORE review and again at
`--phase review-finalize` after the revisions.

EVERY ONE OF THE PLAN'S FIVE FINDINGS HOLDS, and I re-derived each rather than trusting it. F-1,
F-3 and F-4 I reproduced exactly: a probe over `engine.parse_manifest(engine.resolve_source_root(None))`
returns 63 rows, 46 classifying `POLICY_SKILL_ENTRY_POINT` and the same 17 classifying
`POLICY_GENERATED_COMMAND` in the same order the plan lists; `V1_HOSTS` is `("opencode", "codex")`
and `HOST_FEATURE_ROLE_MAP["antigravity"]` is the single `runner_template` row. F-2's mechanism is
right too: `engine.generate_shim_members` writes `shims[f"{shim_dir}/aw.md"]` for each of
`COMMAND_SHIM_DIRS`, which is `(".opencode/commands", ".claude/commands")` and has no Antigravity
entry, so `/aw` genuinely does not exist for that host.

The plan's ARCHITECTURAL CHOICE is also correct and is the best part of it. `engine._build_skill_members`
is the sole install seam for skills and it takes only `generate_adapter_bundle(...).skill_files()`, so
appending one package inside the bundle inherits manifest recording, idempotent skip-unchanged, prune
and manifest-driven uninstall with no engine change. I verified the prune path specifically, because a
new package that prune does not know about would be deleted on the next install:
`collect_target_framework_files` recurses the whole `resolve_skills_dir(target_layout)` tree and
`prune_stale` computes `desired = set(body_members) | set(shim_members.keys())` where the caller passes
`generated_members = {**shim_members, **skill_members}`, so the router is in `desired` and survives.

THEN I RAN THE PRESCRIPTION, and two of its three mechanical instructions do not work. This is the
core of the review and it is why the plan could not have been executed as written.

FIRST, THE DIGEST IS A CONSTANT (PR-601). E-01 says to compute the digest "with
`workflow_profile.semantic_digest` over the sorted `(command, body)` pairs of the manifest rows". I
drove exactly that. `semantic_digest` hashes `semantic_view`, and `semantic_view` reads only
`manifest.id`, `manifest.risk`, `manifest.mutation_boundary`, `evidence.requirements`,
`evidence.validations`, `step_packets` and the scope fence. `body`, `description` and `lens` are all
absent from that projection by DESIGN (its docstring says transport is "deliberately excluded"). So a
`{"manifest": {"id": "aw", "rows": <all 63 rows>}}` compile and a `{"manifest": {"id": "aw", "rows":
[]}}` compile hash to the SAME `f08e4bbedf20...`. The router would ship a digest that never changes
when the manifest changes, which is the exact opposite of what a parity signal is for, and no V item
as written would have caught it (V-01 only asserts `validate_skill_package(pkg) == []`, and a constant
digest validates fine). Worth noting this is not a new defect the plan introduces: the SHIPPED
`compute_workflow_semantic_digest` has the same property, since I confirmed two workflows differing
only in `body`, `description` and `lens` hash identically. But the router is a NEW artifact and must
not be born with it, and fixing the shipped per-workflow digest is a different concern with 46 emitted
files behind it, so I scoped the fix to the router and filed the shipped case as a Deferred carrier
rather than widening this plan.

SECOND, A BACKTICKED MANIFEST PATH FAILS VALIDATION (PR-602). E-01 requires the body to "read
`<workflows_dir>/index.md`" and E-04(d) asserts `validate_skill_package` returns `[]`. Those two
cannot both hold in the obvious rendering. `validate_skill_package` scans the router for every
`` `...` `` span and reports `router references resource '<x>' not in package` for any span containing
`/` that is not a declared resource. I built the package exactly as E-01 describes and got precisely
that finding on `.aw/system/workflows/index.md`. The `@`-prefixed form passes (the check skips spans
starting with `@`), which is also the form the shipped `build_skill_package` and `aw_dispatcher_shim`
already use, so the fix is to mandate `@<path>` unbackticked and to state WHY, so an executor
reformatting for looks does not silently re-break it.

THIRD, `disabled_skill_still_invocable` IS AN UNSTATED CONTRACT THE ROUTER MUST MEET (PR-603). It
requires `explicit_invocation` to start with `read and execute ` and to contain
`.aw/system/workflows/` or `.agents/workflows/`. E-01 never mentions the field, and
`validate_skill_package` does NOT catch an empty one: I drove a package with
`explicit_invocation=""` and got `[]` findings while `disabled_skill_still_invocable` returned False.
So the plan's own V-01 would pass on a router that fails the disable-safety predicate, and
`security_hardening.check_skill_least_privilege` (which composes `validate_skill_package` with
`check_authority_not_inlined`) would not catch it either. The field is now specified with its exact
required form and V-01 asserts the predicate directly.

ON THE VERB LIST I FOUND THE PLAN'S SELECTION CORRECT BUT ITS BUDGET UNSTATED (PR-604). The
`not engine.is_concern_catalog_row(w)` filter yields 25 rows, and I confirmed all 17
generated-command workflows are inside that 25, so the router does reach every workflow that has no
skill of its own, which is the plan's whole reachability argument. But rendering those 25 with their
manifest descriptions is 9752 bytes against a `DEFAULT_SKILL_MAIN_BUDGET_BYTES` of 8192, so a router
built the natural way OVERFLOWS and `validate_skill_package` fails it. Names alone are 377 bytes and
fit with room to spare. E-01 now says names-only with the measured numbers, so the executor does not
discover this by a failing assertion after writing the wrong renderer.

ON THE COLLISION GUARD, the plan is right that a guard is needed and right that no row collides today
(I confirmed `[w.command for w in wf if h._slugify(w.command) == "aw"]` is empty), but E-01 as written
guards the wrong population (PR-605). The hazard is not only a manifest row named `aw`: it is ANY row
whose slug collides with the router's package NAME, and the router is added to the same
`skill_packages` list whose packages all write into one `skill_dir`, so a collision silently
OVERWRITES one package's `SKILL.md` with the other's via `skill_files()`'s `files.update(...)`. The
guard is now stated as a check against the emitted package-name set, which is the thing that actually
collides.

ON RIGHT-SIZING: E-01 was doing too much (PR-606). It named the builder, the frontmatter, the digest,
the body renderer, the verb list, the resource file, the collision guard and the `__all__` export in
one item, and after the fixes above it also owes the explicit invocation and the byte budget. Two of
those sub-parts turned out to be independently WRONG, which is the diagnostic the right-sizing rule
asks about: it bundles multiple deliverables with different failure modes and needs several unrelated
V items. It is now E-01 (the package builder and its contract) and E-02 (the collision guard), with
the digest specified precisely in E-01 because it is one line once the scheme is right.

I ALSO STRENGTHENED WHAT E-03 DOES NOT SAY (PR-607). Adding `"skill": ROLE_ROUTER` to antigravity
changes more than a dict: `build_host_adapter` iterates `HOST_FEATURE_ROLE_MAP[host].keys()` as its
default candidate features, so the new key makes the adapter query the registry for `skill` and adds
it to `unverified_features` with reasons. I verified the registry has no antigravity record
(`query_capability(host="antigravity", ..., feature="skill")` -> `unverified`,
`No capability record found in registry.`), so the claim stays honest exactly as the plan says.
`host_adapters.build_support_table` iterates `supported | unverified`, so the generated support table
in `docs/host-adapters.md` GAINS a row showing antigravity/skill/router/unverified, which is a
documentation-visible effect the plan did not mention. I checked the one consumer of the supported
flag, `host_launchers.plan_launch`, and it keys on `advertises_supported`, so it keeps choosing the
`agy run` fallback and nothing starts claiming native skill dispatch. `is_v1` has NO consumer anywhere
in `agent_workflows/`, `tests/` or `docs/` beyond its own assignment, so flipping antigravity into
`V1_HOSTS` is metadata-only today. That is worth recording because it cuts both ways: the change is
safe, and it also buys nothing mechanical, so its value is the honest declaration rather than a
behavior change. E-03 now states all four of these.

THE GATE WAS THE WEAKEST SECTION (PR-608). Three sentences, no statement of what a human is approving,
no scope fence, no stop conditions, and an unconditional "Move to `executed/`" instruction with no
runner/executor ownership split. It is rewritten to the shape the workflow requires.

Two things I checked and found correct, recorded so a later reader does not re-derive them. OQ-02's
resolution is sound: skills are emitted unconditionally for every install (no `enabled_hosts` gate
reaches `_build_skill_members`), so gating only the router would be the inconsistent choice. And the
plan's decision not to emit standalone skills for the 17 command-only workflows (OQ-01) is right for a
reason the plan understates: `classify_discovery_policy` is consumed by `migration_compact` as well as
by the bundle, so changing it has a second caller's blast radius. Backlog `u0fmeu` carries
`- Blocks-Release: next` and the plan correctly inherits it; `Work-Kind: feature` on both, so the
every-live-bug rule does not apply.
