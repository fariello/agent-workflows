THE DEFECT IS REAL AND EVERY CENTRAL CLAIM REPRODUCES, which is worth stating first because everything below
is about how the FIX could go wrong rather than whether it is needed. Driven directly,
`classify_integration_refusal("merge-refused")` returns False, so the refusal is terminal on its first
attempt; the verdict `decide_integration_deferral` composes for it does contain "it asserts a real failure of
the work", and it is composed IDENTICALLY for every cause, so for a cross-run adjacency conflict the sentence
an operator reads is simply false. Both documented cases are provably cross-run races:
`git merge-base --is-ancestor f9a37808 f763be8c` and `git merge-base --is-ancestor 908db905 d1d6b6eb` both
exit nonzero. F-7, the plan's load-bearing negative result, also re-measured and held: `merge-tree
--write-tree 97255449 f9a37808` still reports `CONFLICT (content): Merge conflict in
agent_workflows/completion.py`, the reverse direction conflicts identically, and `908db905` against
`d1cc184f` conflicts in `agent_workflows/runner_shared.py`. So automatic resolution really is off the table
and reporting-and-routing really is the available deliverable. Both hand resolutions are also independently
corroborated: the merge commit bodies of `f38aeb4b` and `5c25bcd0` each record keeping BOTH sides and why
dropping either would have broken the tree.

THE DOMINANT FINDING IS THAT THE PLAN'S TAXONOMY IS TWICE THE SIZE OF WHAT CAN ACTUALLY HAPPEN. The plan
counts SIX gate causes from the constants in `orchestrate_isolation` and asks E-03 to write cause-specific
verdict text across them. Driving the gate exactly as `integrate_lane_branch` calls it - a single lane,
`merge_order=[id6]`, `integration_base_commit=handle.base_commit`, no `declared_scope`, and a `LaneOutcome`
that `build_lane_outcome` hard-codes to `STATUS_COMPLETED` with `per_lane_validation_passed=True` - produced
`integrated_passed` on a green runner, `integration_failed_combined_red` on a red one, and
`integration_failed_conflict` only when the lane's own diff carried conflict markers. The other four each
require an input this path cannot supply: `_MISSING_LANE` needs a `merge_order` id absent from a map built
from that id, `_STALE_BASE` needs the two base commits to differ when both are `handle.base_commit`,
`_SCOPE_VIOLATION` needs a truthy `declared_scope`, and `_LANE_FAILURE` needs a lane status the builder
cannot emit. Authoring verdict text for those four would ship dead code carrying a claim no test could ever
exercise, which is the same species of defect as a hand-written attestation: evidence-shaped output for
something that did not happen. Fixed by stating the three-cause reality with its proof and routing an
unexpected cause to today's wording, which is the fail-closed direction.

THE SECOND STRUCTURAL FINDING IS THAT THE PLAN'S OWN CITED PRECEDENT DOES NOT TRANSFER, and the plan leans on
it heavily (its conventions section calls it "THE PRECEDENT THIS PLAN FOLLOWS"). `revalidation_was_unmeasured`
works because `make_integration_validation_runner` CLOSES OVER `item` and can write
`item["post_merge_revalidation"]`. The function that knows the cause does not:
`integrate_lane_branch(repo, handle, id6, validation_runner, *, host_label, run_checked, action_kind)`
receives neither `item` nor `state`, so at the conflict arm there is no sink to write to. That is the actual
difficulty of E-01 and the plan did not name it. Priced rather than decided: embedding the cause in the
reason string and parsing it at `record_integration_refusal` (which does receive `item`) touches no signature;
widening the returned tuple touches ELEVEN unpack sites across four files, two of them undeclared, and both
per-host wrappers are pinned to an exact signature by a test whose docstring is "no wrapper may expose the
injected parameter"; a module-level side channel is refused outright, since this module is driven concurrently
and a global would cross-attribute one item's cause to another.

A THIRD FINDING IS THAT E-02's PREDICATE WAS UNSOUND ON THE INPUT GIT ACTUALLY PRODUCES. Adjacency-only means
"both sides ADD and neither modifies a line the other wrote", and deciding that requires knowing what the
BASE said. Measured on `xipfy1`'s real conflict via its three index stages: with `--diff3` the single hunk is
7 ours lines, 0 base lines, 10 theirs lines, and the empty base section is exactly the evidence the predicate
needs. With git's DEFAULT two-way style the same conflict has no base section at all, so "both added" is
indistinguishable from "both replaced the same base lines". `merge.conflictStyle` is unset both locally and
globally in this repository, so the default is what a naive implementation would meet. The failure direction
is the dangerous one: a wrong `adjacency-only` tells a resolver a semantic conflict is safe to keep-both.

A FOURTH FINDING CAME OUT OF TESTING THE MECHANISM OQ-01 ALREADY "RESOLVED" TO. That answer says the peer
commit is available from "`git log` over the conflicting path". On this plan's own `xipfy1` case that yields
`f2410f75`, an integrate commit for the unrelated lane `65cuw0`, while the commit that actually wrote the
conflicting hunk is `908db905`, recoverable with `git log -S` on a line the hunk added; nine commits touched
that path in the window. For `92u0v9` exactly one commit touched the path, which is why the naive form
happened to be right there and must not be generalized from. A confidently-named wrong peer is worse than
UNKNOWN, because it spends a resolver's attention reading the wrong lane's work.

never mentioned: `test_the_terminal_verdict_NAMES_the_condition_instead_of_listing_four` requires the literals

Verified TRUE and left standing: F-1, F-2, F-4, F-5, F-8 as written; the deferral of `tgyfs2` and `vddpml`

### Decisions

ONE ACT IN THIS REVIEW HAD A SIDE EFFECT BEYOND EDITING THE PLAN, and it is called out here so a
reader does not have to infer it from a row: repairing PR-009 required a real carrier for F-9, so this
review CREATED a tracked backlog record,

carrying `Work-Kind: bug` and therefore `Blocks-Release: next` (mandatory for a live bug under this
repository's own rule, not a choice I made). A maintainer who disagrees has three cheap moves: KEEP it,
RE-TIER it (`aw backlog set ... --blocks-release -`, or reclassify the work-kind), or DELETE it and
accept that F-9 lives only in this review record - in which case the `- Carrier: i597pz` line in the
plan's `## Deferred` section needs re-pointing, and nothing else in plan `87apfx` depends on the choice.

D-6 AND D-7 ARE JUDGED `Reversible: yes`, AND THE JUDGEMENT WAS CORRECTED DURING THIS REVIEW rather
than asserted once. I first marked both `no` on the reasoning that a release gate other tooling reads
cannot be unmade, and `check.review-decision-unescalated` correctly flagged them as unescalated. Re-read
against the workflow's stated test - judge on the COST OF BEING WRONG, with `no` reserved for published
interfaces, data or file migrations, deletions, released artifacts, or anything another party may
already depend on - `yes` is the honest answer: the artifact is a records-tree file, no party outside
this repository can depend on it, and undoing it is one setter call or one file deletion. What made me
reach for `no` was the gate's VISIBILITY, not its permanence, and those are different properties. The
correction is recorded rather than quietly applied because the alternative routes were both dishonest:
writing `maintainer told` would have claimed a conversation that did not happen, and raising a
`Blocking: yes` question would have held a release-gated bug fix whose own findings are all FIXED
hostage to a decision about a different record.
