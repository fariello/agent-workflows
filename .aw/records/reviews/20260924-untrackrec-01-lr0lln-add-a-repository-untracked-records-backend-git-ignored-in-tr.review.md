## Round 1

The plan was committed and unchanged, so the pre-review snapshot was correctly skipped per Step 1.
Structural preflight `aw ipd lint --phase author --agent` reported `conforming` (exit 0) BEFORE review,
and `--phase review-finalize` reported `outcome: clean`, exit 0 after the revisions (two `IPD-Z602`
prose-density ADVISORIES remain on E-08 and E-12, each of which is genuinely one deliverable whose
text is long because it carries a measurement).

THE AUTHOR'S FOUR FINDINGS ALL HOLD, and I re-derived each rather than trusting the table. F-01 is
correct and is the load-bearing one: `resolve_project_context` ends its records-root selection with
`else:  # HOME`, so an unhandled backend silently lands in AW_HOME. F-02 reproduces exactly as
recorded - with `/records/` in `.aw/.gitignore`, `get_ignored_dirs` returns `.aw/records`,
`is_ignored_path` returns True for a pending plan, and a plans-dir-rooted scan still finds it, which is
precisely the repo-rooted-versus-subtree-rooted split the author described. F-03 is right about the
spec lineage (`20260809-2211-01` reads `Status: superseded`; `20260810-1447-01` reads `Status:
implemented`, `Canonical: true`). F-04 I verified by execution rather than by reading: with the value
present in `RECORDS_BACKENDS`, `resolve_record_routing` returned `repository-untracked`,
`allow_git_stage=False`, `commit_destination=None`, so no change is needed there.

THE DOMINANT FINDING IS PR-501, and it is a latent CRASH the plan would have walked into on its first
call. `record_producers.get_git_owner`'s second branch reads `elif "companion" in backend or backend ==
RecordsBackend.COMPANION_TRACKED.value:` and `RecordsBackend` has NO `COMPANION_TRACKED` member -
`COMPANION_TRACKED` is a `Placement`. Measured against real temp repos carrying a `project.json`:
`repository` returns `"target"` and `companion` returns `"companion"` (both short-circuit before the
bad attribute), while `home` raises `AttributeError: type object 'RecordsBackend' has no attribute
'COMPANION_TRACKED'`. The new value takes the same crashing path. So this is a PRE-EXISTING defect that
the feature turns from latent into reachable-on-the-happy-path, which is why the repair belongs in this
plan rather than a follow-up: shipping the backend without it ships a backend whose owner resolution
raises.

THE SECOND MATERIAL FINDING IS PR-502, and it is the one I would most want a human to see, because the
original E-04 would have REVERSED A USER'S OWN DECISION. `get_ignored_dirs` cannot tell WHY git reports
a path ignored. I built a temp repo whose ROOT `.gitignore` says `.aw/records/` and which has no AW
policy whatsoever: git reports `.aw/records` in the ignored set identically to the backend's own rule,
and the unconditional discard made `is_ignored_path` return False for a plan under it. A user who
deliberately excluded their records tree would silently have it scanned again, by a change made for an
unrelated backend they never selected. The fix is to gate the discard on the repo's RECORDED backend via
`read_project_identity`, which the docstring establishes as the one reader for that field and
deliberately distinguishes from `resolve_project_context` (which layers defaults and so always yields a
value). I also measured the cost, because this function runs about 30 times per command:
`read_project_identity` is ~1.5ms per call (45.3ms for 30) against 258.2ms for 30 `get_ignored_dirs`
calls, so an uncached read would add ~45ms to a command a human waits on - itself the threshold
AGENTS.md treats as a user-perceptible defect - hence the caching requirement in the item and the
negative-case assertion in V-08 without which the item is indistinguishable from the version this
finding rejects.

THE THIRD IS PR-503: the feature creates a SILENT HALF-STATE on any repo that already tracks records,
which is every repo installed with the default `repository` backend - that is, the overwhelmingly likely
place someone tries this flag. Measured: with `.aw/records/plans/pending/p.ipd.md` committed and
`/records/` then added to `.aw/.gitignore`, `git ls-files .aw/records` STILL lists the file and `git
status` still reports it modified (gitignore never untracks), while `git add` on a NEW record exits 1
with "The following paths are ignored by one of your .gitignore files: .aw/records". The result is a
repo with some records tracked, some untrackable, and no command that reconciles them - and the plan
deferred the migration flow, so nothing in scope would fix it. Refusing at policy validation is what
makes that deferral honest rather than a hole.

PR-504 is smaller but would have shipped a no-op. The placement override in `ProjectPolicy.__post_init__`
has to run unconditionally, because the existing code fills placements from the preset ONLY when they
are empty (`if not self.placements or not self.git_policies`), and `resolve_policy_noninteractive` -
the path a `--yes` install actually takes - passes `placements=pls, git_policies=gps` explicitly. An
override written inside that guard never executes on the primary code path, so the records placement
would stay `target-tracked` while every test that constructed a bare `ProjectPolicy` passed. V-04 now
demands both construction shapes.

PR-505 is an entry point that already lies. `aw setup` declares `--records-backend` with the same
`choices=[r.value for r in RecordsBackend]`, so the new value appears in its help the moment E-01 lands,
but `_run_setup` never calls `collect_policy_interactive` or `persist_project_policy` - it goes straight
to `_install_one` per discovered repo. The flag is accepted and ignored. That is pre-existing for the
three old values, where the consequence is mild (you get the default you probably wanted); for this one
the consequence is a TRACKED records tree while the user believes they chose an ignored one, which is
the exact outcome the feature exists to prevent. E-11 requires either wiring or an explicit refusal, and
names "the flag is accepted" as a non-outcome.

ON RIGHT-SIZING (PR-508). The count-based size lint passed and measures nothing about density. Original
E-05 named a `storage.py` branch, an `install_wizard` render line, and a `cli.py` warning across three
files with three unrelated test surfaces; original E-07 bundled a spec body edit with an `aw specs note`
invocation. Both are split. The plan is now 13 items against 8, still one concern, and the growth is
mostly the three surfaces above rather than decomposition.

TWO ROUTING GAPS I checked rather than assumed (PR-506). `storage.validate_storage_boundaries` refuses
an in-target path for `HOME`/`COMPANION`; `repository-untracked` is LEGITIMATELY in-target, so the
correct action is to leave it out of that tuple - but silently leaving it out looks like an oversight to
the next reader, so E-03 requires a comment stating the intent. `project_layout.materialize_project_layout`
does need the value added, or the in-tree records dir is never created. And one gap I checked and found
was NOT a gap: `artifact_core.git_mv` falls back to `shutil.move` when `git mv` fails, and it does fail
here (`fatal: not under version control`), so lifecycle transitions still relocate files under an ignored
tree. Recorded as F-09 so nobody "fixes" it.

PR-507 is a one-line trap with precedent in this exact file. The `/records/` presence test must be
LINE-ANCHORED, not a substring test, because the explanatory comment the item also writes contains the
substring `records/`. `_ensure_aw_gitignore` already carries this hazard explicitly for `/inbox/` ("the
presence test matches the pattern LINE only, never the substring `inbox/` that the explanatory comment
above it also contains"), so the failure mode is documented three lines from where the new code goes.

PR-509: the gate carried only three sentences and none of the required execution-contract elements. It
now states what a human is approving (naming the `get_ignored_dirs` edit's repo-wide blast radius and
the deliberate new refusal), carries a per-path scope fence stated as a DECLARATION for reconciliation
rather than a stop directive, the hard-MUST honesty rule naming the two items most exposed to faking
(V-02's pre-fix traceback and V-08's source mutation, both requiring a produced FAILURE), two genuine
stop conditions, and the lifecycle transition with conditional runner/executor ownership in place of the
original's bare "move to executed/".

Two baseline facts, checked so nothing here starts dirty. `aw check plans` reported
`check.ipd-uncarried-obligation` at `error` severity against this plan for its two unresolved open
questions; both are now resolved from evidence with `Carrier-Declined` reasons, and
`evaluate_durable_carrier` returns zero findings for the plan afterwards. The source item `hsixiz`
carries no `- Blocks-Release:` and is `Work-Kind: feature`, so the every-live-bug-gates-the-release rule
does not apply and no gate handoff is owed.
