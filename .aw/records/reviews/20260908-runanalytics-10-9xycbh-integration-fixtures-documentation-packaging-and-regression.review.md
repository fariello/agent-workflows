## Round 1

Reviewed at HEAD `5fe992aa`. Structural preflight `aw ipd lint --phase author` conformed BEFORE semantic review
(exit 0, `outcome: clean`), and `--phase review-finalize` conformed after the ten-item split and the rewritten
V-item bijection. This is the eleventh and last plan in the Set.

METHOD, AND IT IS WHY THIS REVIEW FOUND A BLOCKER THE OTHER TEN DID NOT HAVE IN THIS FORM. This plan's entire
product is PROOFS. So rather than reading its test list for completeness, each proof was RUN in a probe repo to
see whether it could fail. The first one could not. Everything else followed from executing the packaging,
install, docs-gate, index-verb and corpus surfaces rather than reading about them.

THE BLOCKER: THE PRIVACY PROOF WOULD HAVE PASSED WITH EVERY CANARY PRESENT. The orchestrator `5lxvl3` mandates
that this child's sanitizer scan CONSUME `aw sanitize --agent` rather than reimplement detection, and that
instinct is correct (P8/P11, one engine, no second detector). But the MECHANISM does not work here.
`leak_sanitizer.scan_working_tree` enumerates `git ls-files` through `_tracked_files`, and `.aw/records/runs/` is
gitignored at `.aw/.gitignore:14`, so every cache, report, agent output, export and receipt this Set produces is
invisible to that walk. Probe-verified: a repo whose `.aw/records/runs/analytics/facts.json` contained a
fail-severity home path AND prompt text scanned `{"outcome":"clean","exit":0,"findings":0}`, while `scan_text`
over the identical bytes returned `home-path` and `handle` at FAIL. Pointing the CLI at the analytics directory
as its own root reports clean too, because `git ls-files` is empty there, and `--staged` cannot help because
these artifacts are never staged. So the Set's self-declared highest-risk requirement was to be validated by a
command that cannot read the files in question, on the one child that owns acceptance for the whole feature. A
proof that cannot fail is worse than no proof, because it is reported as assurance. The fix keeps the
single-source rule intact and changes only the ENTRY POINT: consume `build_ruleset` + `scan_text` over artifact
CONTENT, and pair every detector check with a control run proving it flags a planted positive.

THE MIRROR-IMAGE FINDING, WHICH BITES IN THE OPPOSITE DIRECTION. `tests/fixtures/run_analytics/**` is TRACKED
(`git check-ignore` exits 1), so it IS in `_tracked_files` and the named `local-leaks` CI job scans it.
Probe-verified: a fixture holding a seeded home path returns `home-path` and `handle` at fail severity. So the
same asymmetry that makes the output tree unscannable makes the fixture tree fail-closed, and a committed
literal canary breaks a named CI job. Sibling `ixis0c` already carries the correct rule; the plan that OWNS the
corpus did not.

WHAT THE PLAN GETS RIGHT AND KEEPS. The 33-scenario enumeration is genuinely good work: it is specific,
falsifiable in shape, and covers the mutation axes (resumed, added, removed, corrupt-among-valid, interrupted
publication, concurrent writers) that are exactly where an incremental cache breaks. The insistence that every
failure return to the OWNING CHILD rather than being patched here is the right discipline for an integration
plan and is preserved verbatim. The refusal to commit real user data is correct and is now strengthened rather
than merely restated. And the documentation list is the most complete in the Set.

FOUR MEASUREMENTS THAT CHANGED WHAT THE PLAN MUST DO. FIRST, "no live run corpus in this checkout" is FALSE, as
the orchestrator's review already recorded and this plan still asserted: 135 runs, 1976 files, 272.3 MB, drivers
`oc_runipd.py` 120, legacy `runipd.py` 13, `ipdrunner.py` 2, Agy ZERO. So scenario 2 cannot be corpus-validated
at all, and scenario 3 "mixed-runner corpus" would be satisfied entirely by OpenCode lineage unless the two
legacy generations become their own scenarios, which is where the repository's REAL historical schema drift
lives. SECOND, the isolated install cannot be a test: `pip install` of the built wheel with `--no-index` FAILED
on `filelock>=3`, so it needs the network, which the plan's own rules forbid, and CI's `wheel` job already
performs that exact proof on three operating systems. THIRD, the performance budgets are mandated against
documents that do not exist: no numeric time, memory or size threshold appears anywhere in the eleven plans, so
the honest posture is measure-and-publish, not a retroactive gate invented at acceptance time. FOURTH,
`aw plans index --check` is a usage error; the real verb is `aw index plans --check` and it EXITS 1 TODAY on a
pre-existing `stale-index` that pending plan `yvvf98` exists to remove.

THE CONTRADICTION WITH TWO REVIEWED SIBLINGS. "Execute all 33 mandatory scenarios" plus "all Set completion
criteria have durable evidence" cannot both hold as authored, because Order 06 now REFUSES four required
analyses as under-powered (n=3 to 6) and refuses model comparison at 1.1 percent identity coverage, and Order 07
renders a refusal panel instead of a chart. An executor reading this plan literally would either report five
false failures or, far worse, manufacture five numbers from refusals. A documented refusal is now an accepted
passing outcome, and a synthetic-fixture code-path exercise may never be reported as a corpus-level finding.

THE DOCS GATE THE PLAN PUT ITSELF UNDER WITHOUT NAMING. Declaring `docs/**` in `Scope-Paths` subjects this plan
to `tests/test_docs.py`, which is NOT `slow`-marked and therefore runs in the bare suite it requires. It asserts
`docs_check.check_docs_dir(docs/)` returns ZERO findings across three checks (no em or en dash, every relative
link resolves, every top-level `aw` verb known), and it is at zero today, so any new finding is attributable.
Two useful specifics were measured: only the FIRST token after `aw` is checked, so `aw runs analyze` passes while
a top-level typo fails; and the dash rule is a USER-FACING prose rule that binds README and docs and explicitly
does NOT bind this IPD. Conversely the doc-index completeness the plan implies does NOT exist as a gate: three
shipped docs are unlinked from `docs/README.md` today and nothing fails.

ON SIZING. Three E-items for the widest scope in the Set, and the orchestrator's own blocking OQ-01 names this
plan's E-03 explicitly among the four densest items ("the 33-scenario acceptance matrix plus performance,
sanitizer, offline, suite, lint and diff"). `aw ipd lint --phase author` conformed and
`ipd_schema.e_item_density_advisory` returned `None` for all three, so nothing mechanical catches it. Nine
siblings were already split for the identical reason, leaving this the last unsplit child. Split into ten across
four groups.

WHY APPROVE WITH REVISIONS DESPITE A BLOCKER. The Fix Bar turns on Remediation Risk, not severity. The blocker's
remedy is bounded, local and mechanical: call a different entry point on the SAME engine and add a control run.
That is Medium risk with a clear verification path, well below the Medium-High threshold that would justify
deferral, and it needs no human decision. All six open questions were settled by probe, execution or by reading
a reviewed sibling, and each is recorded as a decision with its rejected alternatives. No finding is left OPEN
or DEFERRED, so nothing needs escalation as a blocking question.

TWO NOTES FOR THE MAINTAINER, BOTH SPANNING PLANS. First, the leak-sanitizer's tracked-files-only scope is a
real gap beyond this Set: any tool that writes into a gitignored tree is unscannable by `aw sanitize`, and this
is the second Set-level assumption about that module to fail under measurement (the first being `ixis0c`'s
one-of-twelve coverage). A backlog item for a content-scan entry point, or at minimum a docstring stating the
tracked-only scope, would stop the next consumer making the same assumption. Second, the orchestrator's OQ-01 is
now moot in practice: all ten children have been re-cut into finer E/V items within their existing boundaries,
which is exactly the option (b) the reviewer recommended, so that question can be closed as resolved by the
reviews rather than awaiting a separate decision.
