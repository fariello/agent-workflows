THE PLAN'S OWN FINDINGS ALL HOLD, and its headline mechanism works. I re-derived each rather than
trusting the table. `commit_review_lane_output` has exactly ONE product call site, the
`if is_review and wt_handle is not None:` branch of `runner_shared.execute_item_core` (a grep across
`agent_workflows` finds the definition and that one caller, and nothing in `tests/` touches it at all).
The commit carries no trailers. Its only traces are `attempt["review_lane_commit"]` and the
`review-lane-output-committed` event, and `.aw/.gitignore` does ignore `records/runs/`, so those traces
genuinely do not survive the run directory. `git log --all --grep="record the review of"` returns
nothing. And the proposed composition works as specified: I built the real message with
`run_item_trailers("run-test", "rvc001")` plus `AW-Committed-By: driver`, committed it, and
`git interpret-trailers --parse` returned all three trailers, so `AW-Committed-By` (a key this
repository has never used) parses fine.

THE DOMINANT FINDING IS PR-501, and it inverts the plan's value proposition rather than merely adding
work. A git trailer is an IMMUTABLE ownership claim; `run_item_trailers`' own docstring is explicit
that "their value is exactly that a later reader can TRUST them, and a fabricated one makes a false
ownership claim permanent". But the commit this plan proposes to label can carry ANOTHER turn's files.
The mechanism is structural, not exotic: the sweep lane is ONE tree shared by every review of the run
(`acquire_review_sweep_lane`: "the ONE lane every review turn of this run shares"; retirement is the
coordinator's and happens at run end), the function stages whatever `git status --porcelain` reports,
and a hook refusal returns `None` while LEAVING those paths staged - git then reports them `A `, so the
next turn's `porcelain` read still includes them. I measured it end to end in a temp repo: turn 1 for
`aaa111` with a refusing `pre-commit` hook returned a `None` sha and left two files staged; turn 2 for
`bbb222` then committed FOUR files under subject `review(oc): record the review of bbb222`. Adding
trailers to that commit would permanently attest that run R, item `bbb222`, owns two files a different
review wrote. That is strictly worse than the untrailered commit the plan set out to improve, which is
why E-02/E-03 now precede the trailer item and why the plan says in terms that the ordering is
load-bearing.

PR-502 is smaller but hits four of the plan's own assertions at once. `git status --porcelain`
collapses an entirely untracked DIRECTORY to a single entry, and an entirely untracked `.aw/` tree is
exactly what a first-use lane has. Measured: `commit_review_lane_output` returned `('.aw/',)` for a
commit whose real content was `.aw/records/plans/pending/x-rvc001-p.ipd.md`. That one value is what
E-01 was going to assert on, what E-06's `<n> path(s)` count and path list report to the operator, and
what lands in `attempt["review_lane_committed_paths"]`. So the plan's new operator line would have
said "the driver committed 1 path(s)" and named a directory. E-04 now owns it, and E-01's fixture
commits a `pending/` directory in the initial commit so the collapsed shape is not silently pinned as
normal.

PR-503 is a validation that would have proven nothing. E-01 said to put the refusing `pre-commit` hook
"in the worktree's git dir". Verified against git 2.43.0: a hook in a worktree's OWN git dir
(`.git/worktrees/<name>/hooks/`) is NEVER RUN - `git rev-parse --git-path hooks` resolves to the
COMMON dir - so the commit SUCCEEDS and the case asserting `(None, (<path>,))` fails for the wrong
reason, or worse, an executor "fixes" the assertion to match. The in-tree precedent already says this:
`tests/test_git_commit_helper.py::_install_hook` writes to `repo/".git"/"hooks"` and its docstring
gives the reason ("which the isolated worktree also runs"). V-01 now additionally requires the
executor paste `git rev-parse --git-path hooks` from inside the fixture worktree, because "the hook
case passed" is indistinguishable from "the hook never ran".

PR-504 is a summary that drops the very fact it exists to report. E-04 (now E-07) selected items by
"latest attempt carries `review_lane_commit`". But `execute_item_core` appends a NEW attempt dict per
turn (`item.setdefault("attempts", []).append(attempt)`), and a review whose integration is refused is
re-attempted by the deferral ladder (`reattempt_deferred_integrations`, called from the top of the
dispatch loop, with the review-action adapter pair wired by `i4ak5n`). So a driver commit recorded on
attempt 1 becomes invisible to a latest-attempt read as soon as attempt 2 exists - a silent drop in
the one report the plan adds for visibility. Now an any-attempt scan, following
`finish_integrated_review_item`'s established `for attempt in reversed(item.get("attempts") or [])`
shape, with the reason recorded on the item.

PR-505 is `aw check plans` failing on this plan TODAY. `evaluate_durable_carrier` returns one
`error`-severity drift: OQ-01 is `Status: open` and owes a TYPED carrier, and the prose sentence
"Backlog `wtaxvk` remains open as the carrier of this decision" satisfies nothing - `ipd_schema`'s

Added `- Carrier: wtaxvk` to OQ-01 and typed carriers to the two review-added Deferred rows;
`evaluate_durable_carrier` now returns zero drifts on this plan, and `aw check plans` went from 14

explicitly so nobody reads a new trailer key as binding either code.
