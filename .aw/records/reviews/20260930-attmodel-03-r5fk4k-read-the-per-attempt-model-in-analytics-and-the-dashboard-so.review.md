FIVE THINGS DID NOT HOLD, AND THREE OF THEM WOULD HAVE SHIPPED A DEFECT.

The most serious is PR-001. E-02 asserted that the unclaimed-session-file branch "has no attempt to read, so
it legitimately keeps the run-level value" and told the executor to write that into a comment. Measured, that
branch parses the filename, derives `id6` and attempt number, and does
`base = by_item_attempt.get((id6, number))`, so when an attempt exists but its log was not claimed it REUSES
that attempt's base; and it derives a `role` from the same filename that can be `verify` (I executed the regex
against both `...-attempt-1-verify.jsonl` and `...-verify-attempt-1.jsonl`). So the plan instructed the
executor to leave the F-01 defect alive in exactly one branch, and to document the excuse. The same item was
headed "A THREE-SITE CHANGE AND MUST HIT ALL THREE" while naming two sites, so the executor could not have
known what was missing. A second defect sits at the same site: the `(unrecorded, <host>)` substitution runs
ONCE on the run-level value before any row exists, so moving the value per row without moving the
substitution silently changes an output the shipped `test_unrecorded_model_is_labeled_per_host` asserts over
every row.

PR-002 is the one that would have broken the Set's own deliverable. E-04 told the executor to build the
`model_comparison` population "from the same entries the surrounding analyses already use". Measured, neither
source is attempt grain: cache `entries` carry run-level `metric_facts` with no attempt list at all, and
`rows` holds exactly one `phase: "aggregate"` row per run plus up to four per-run PHASE rows whose attempt
figures are ACCUMULATED into buckets. Passing either would publish a coverage figure on a 135-run denominator
against a baseline that records "2 of 179 attempts", which is precisely the incomparability the plan's own
OQ-02 says must not happen, and it would happen silently. The remedy was available in the same function and
the plan had not noticed it: the per-phase block already loops over `item["attempts"]` after opening each
`state.json`, so attempt grain is constructible there.

PR-003 and PR-004 are design gaps rather than wrong facts. The dashboard already emits a third role
(`gate-answer`, present in the shipped fixture's own assertion alongside `main` and `verify`, with `recovery`
reachable by the same pattern), so E-01's two-role chain would have forced real rows into a guess; and E-01
left its own central invariant ("three readers must not each invent one") as an execution-time choice between
one function and duplicated accessor data, with the fallback explicitly permitting duplication. PR-005 is
narrower: an attempt-grain fact is NEVER `Phase.VERIFY` (I executed it: `_phase_of` yields only `REVIEW` or
`EXECUTE`, and `attempt_phase` adds only `RECOVERY`), so E-03's "the attempt's phase decides the role" can
never select the verify chain. That shape is correct and the fix was to SAY so, plus forbid adding a second
attempt-grain fact, which would change the `RunFacts` shape that `INGEST_SCHEMA_VERSION` exists to track.
