## Round 1

All claims verified at HEAD `ed3f8db7`. The target plan was committed at `0ee800f4` and unchanged, so
the pre-review snapshot was correctly skipped. `aw ipd lint` conforming at `--phase author` before
review and again at `--phase review-finalize` after revisions.

THE PLAN'S JUSTIFICATION IS THE STRONGEST IN THE SET AND EVERY PART OF IT VERIFIED. `TRANSITION_AUTHORITY`
carries entries for `->approved`, `->implementing`, `->implemented`, and `->deferred`, and none for
`->reviewed`, so a spec really can be set `reviewed` with no evidence at all while the equivalent claim
on a plan is policed. All three of F-3's corruption modes are real: `/plan-review` REQUIRES writing
`- Readiness:` onto its subject, it hand-edits `- Status:`, and its structural preflight is both IPD-only
and guarded by "For each eligible plan that is an agent-executable IPD", which means on a spec the gate
would silently SKIP and an executor would read that as a pass. Both documentation claims are present and
false. F-8's broken status filter reproduced exactly: `aw find specs --status draft`,
`--status to-review`, and the unfiltered call each return all 27 specs.

ONE FINDING IS THE MOST CONSEQUENTIAL I FOUND ANYWHERE IN THIS SET, AND THE PLAN DOES NOT MENTION IT.

PR-001. Filing the first spec-subject review record does not merely make spec review possible; it
ACTIVATES a live gate on spec approval that is already fully wired. `aw specs set approved` calls
`plan_readiness.approval_refusals`, which consults `review_findings.plan_gating_blocks` keyed on the
artifact's `- Id:` bullet, and specs carry `- Id:`. Nothing about that path is hypothetical. It is inert
today for exactly one reason: no review record names a spec, so the lookup always misses. `specs.py`
says so itself, in a comment that predicts this very moment: the verdict half "ACTIVATES BY ITSELF if a
spec-review artifact type is ever added". So the first spec review carrying an unfixed finding at or
above the configured threshold (default `high`) will refuse that spec's approval, through a refusal
`plan_readiness` documents as having no override "because the whole point is that no flag should be able
to turn 'do not build this' into 'executable'". A record that merely fails to PARSE blocks approval too,
since any diagnostic counts as blocking.

I kept this as intended behavior rather than asking for it to be suppressed, because it is precisely the
integrity the plan exists to create and the codebase clearly anticipated it. But an undisclosed
no-override gate is the kind of thing a maintainer meets at the worst possible moment, so it now has to
be tested in both directions and reported in plain language.

TWO FINDINGS CORRECTED CLAIMS THAT WERE MATERIALLY FALSE, both in the plan's favor in one sense and
against it in another.

PR-002. F-9 asserts that a new workflow name "BREAKS REVIEW-ENTRY RECOGNITION" because `_REVIEW_PREFIX`
is the literal `/plan-review`, and requires evidence that `/spec-review` entries are recognized. That is
wrong: `is_review_history_entry` accepts a record whose STATUS TOKEN is in `_REVIEW_WORDS`
(`reviewed`, `re-reviewed`, `review`, `re-review`) OR whose text starts with the prefix. I verified that
a `- ... reviewed (oc): /spec-review round 1; APPROVE` record is recognized, and so is the setter's own
`- ... reviewed (aw set): status set to reviewed`. An executor chasing F-9 would have widened a literal
that did not need widening. The genuine hazard is the mirror image and is now recorded: because a bare
setter status line already qualifies as a review record while stating no verdict, the question worth
proving is WHICH record `newest_verdict` actually reads.

PR-003. F-7 says there are zero specs at `to-review`. There is now one, and it is `6m4kow`, this plan's
own source spec. That converts "use a fixture" from tidy advice into a live trap: the most convenient
end-to-end demonstration available to an executor is to review the spec that authorizes the plan, with
the tool the plan builds. It is circular, it writes to the maintainer's in-flight artifact, and by
PR-001's gate a BLOCKER finding in that review would block `6m4kow`'s own approval. The fence now names
it explicitly, and says plainly that reviewing `6m4kow` is legitimate work but not this plan's
self-validation.

THREE SMALLER CORRECTIONS. PR-004: E-03 told the executor to correct `.opencode/commands/spec.md`
directly, but that file's description is copied verbatim from the manifest row and the installer
generates shims from the manifest table, so the manifest is the single edit and the shims are
regenerated; there are also two shim families, so "the shim" is not one file. PR-005: the plan requires
`aw workflow check-generated` unconditionally, but `plan-review/` has no `_generated/` projection, so
that check is N/A for the package most likely to be touched and demanding it invites a vacuous pass.
PR-006: the population figures moved again (27 specs, 38 review records), which does not change any
conclusion but is worth correcting since this Set keeps producing the artifacts it counts.

Zero findings were deferred and zero left open. OQ-01 (workflow shape) stays non-blocking and owned by
E-01, and I added the one measurement it lacked: the three plan-specific obligations sit at
`plan-review.md:113-133`, `:377-398`, and `:487-496`, all load-bearing requirements rather than optional
prose, in a 601-line body duplicated across two files held in parity, so generalizing means six
conditional sites. That is evidence, not a decision; E-01 still owns it. OQ-02 was already resolved as
requiring a record, and I confirmed the reasoning holds.

Size assessment `exception` is honest and correct, and I left it. E-02 authors a workflow body and E-04
adds a lifecycle gate bearing on 27 specs; PR-001 arguably makes the blast radius larger than the plan
claimed, which strengthens rather than weakens the case for the `exception` label.
