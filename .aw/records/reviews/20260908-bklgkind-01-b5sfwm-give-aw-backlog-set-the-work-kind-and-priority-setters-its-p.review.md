proven by execution rather than accepted: driving `status_set.run_set_command` with `work_kind` and
`priority` on an already-`open` item rewrote both metadata lines and reported the status `unchanged`, so
F-5's "parser change only" is exactly right; driving `backlog.run_set` with the identical namespace left
both lines at their old values, so F-6's "this spelling needs a writer" is exactly right too. The fork
itself is real, and the plan located it correctly even though its discriminator is `--status` PRESENCE
rather than a positional status. The hoisting mechanism in `apply_status_change` is as described, keyed on
`getattr(args, ..., None) is not None` with no same-status early return, which is genuinely why the plan
twin persists on a no-op. F-1 and F-2 both re-confirmed by running `--help`: neither flag exists, and the
backlog item's premise that `Priority` already works is indeed wrong, so E-02's widening is justified and
correctly flagged as over-scope for deliberate acceptance. F-10 is right about the stale declaration. The
`_SetArgs` namespace really does lack both attributes. The vocabularies really are single-sourced. And the
plan's instinct to demand a failing-before test, to insist both spellings be demonstrated separately, and
to name the no-op case as the one the defect was hit on are all correct and were strengthened rather than
replaced.

WHAT THIS ROUND CHANGED ABOUT THE PLAN'S SHAPE. Nothing about its diagnosis, scope, or sequencing, and one
thing about its safety. The plan reasoned by analogy from `aw ipd set`, which is the right instinct for a
consistency fix and is wrong in exactly one place: on a plan those two fields are optional, and on a
backlog item they are required. So the flag vocabulary the plan copied includes a value (`-`) whose effect
here is to produce a record the repository's own checker rejects, and the plan's E-06 would have pinned
that with a test while its own validation section forbade the resulting diagnostic. That contradiction is
internal to the plan and only surfaced by running the clear and then running the checker. The second
correction has the same flavour: the plan reached for a plausible implementation (mutate the item, let the
renderer emit it) without noticing that the function it is editing already solves the identical problem
the other way, ten lines from where the new code goes. Both are cheap to fix and neither threatens the
plan. The lesson worth carrying is that a consistency fix must check which properties are shared and which
are deliberately asymmetric, because the repository already had a test class named for that asymmetry.
