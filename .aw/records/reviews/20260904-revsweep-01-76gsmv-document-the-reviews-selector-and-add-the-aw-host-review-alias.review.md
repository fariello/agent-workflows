THREE FINDINGS CHANGED WHAT THE PLAN WILL PRODUCE, not merely how it reads.

PR-001 is the one that would have defeated the plan's own goal. E-02 named the DRIVER's implicit-`start`
shim as the implementation site for the alias. But the spelling the plan promises is `aw oc review`, and
that resolves at the `cli` host-subcommand layer, which rejects it today with
`invalid choice: 'review'` before any argv reaches `oc_runipd.main`. A rewrite placed only inside the
driver's `main()` would have made `aw oc runipd review` work, which it ALREADY does as the bare
selector, and left the spelled surface unreachable. The plan could therefore have been executed,
self-validated against a V-02 that only compared namespaces, and shipped without delivering the command
the maintainer asked for. This is the same failure shape the plan warns about one paragraph earlier
("a test proving the alias runs would also pass if the alias had forked"), reappearing one level up.

PR-002 is the safety finding. The plan treated `--action` as plumbing and E-03 as "pure wiring", but the
runner derives its action from status: `action_for` returns `execute` for `approved` AND `reviewed`, the
queue builder calls it unconditionally, and under `--full-auto` a `reviewed` plan carrying an approving
`- Readiness:` is auto-cleared to `auto-approved` and EXECUTED. So a `--action` that is accepted and
ignored, which is exactly what "register it minimally" invites, turns `aw oc review <approved-id6>` into
a command that executes a plan while the operator typed the word "review". Spec 2.6 forbids precisely
that. The plan's thin-alias principle is what makes this dangerous rather than safe: an alias with no
logic of its own inherits whatever the canonical path does, and the canonical path executes.

PR-003 is an exit-code defect the plan CREATES rather than inherits, which is why it became an E-item
instead of a deferral. An empty sweep raises `DriverError` and `main` maps that to exit 2, so "nothing
needs review" reports as a failure. Spec 2.4a property 3 declares the opposite normatively. Before this
plan that path required a magic bareword nobody knew; after it, `aw oc review` is the advertised
everyday command and the HEALTHY repository state is the one that fails. Adding the fix widens the plan
by one behavior change, which I would normally refuse in a documentation plan, and the justification is
recorded in the Scope check rather than assumed.

TWO PROCESS FINDINGS worth naming separately.

PR-008 was learned the hard way during this review: `aw oc runipd reviews` is not a read-only probe. Two
exploratory invocations LAUNCHED REAL AGENT SESSIONS against the repository's live `to-review` plans
(runs `run-20260904T225556Z-2946616` and `run-20260904T230648Z-3028816`, each starting a `/plan-review`
turn on this very plan). No tracked file was modified and both runs died with their parent shell, but
the plan's own validation instructions invited exactly that mistake by asking for `--help` output and
alias comparisons without ever saying "do not run the sweep bare". The execution contract now says it
explicitly, and every V-item requires `--prepare-only` or a fixture.

PR-007 records that the oc line citations had already drifted about 38 lines because `818uru`
restructured the module between authoring and review. The plan's execution contract already says to
locate sites by symbol, so no edit would have landed wrong; the citations were refreshed anyway, because
a reader who measures at a stale line and finds unrelated code cannot tell whether the plan describes a
different tree.

Zero findings were deferred and zero left open, so nothing required escalation as a blocking question.
The plan's OQ-01 (verb spelling) was already non-blocking with a recorded default; I confirmed the
reasoning holds, including that the collision it worries about is real (`aw reviews` exists as a
read-only record-reporting noun at `cli.py:2254`), and it needs no maintainer round trip.
