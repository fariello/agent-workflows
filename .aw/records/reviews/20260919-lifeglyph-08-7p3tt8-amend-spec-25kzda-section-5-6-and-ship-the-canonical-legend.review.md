THE FINDINGS FALL INTO THREE GROUPS. One item was ORDERED TO RUN AFTER THE PLAN IT EXISTS TO UNBLOCK.
Two items had NO OWNER ANYWHERE IN THE SET and this is the last child, so they would have vanished with
it. And several places asserted a number or a deliverable that measurement contradicts.

**1. E-05 was seven hops downstream of the plan it unblocks (PR-801, BLOCKER).** E-05 was added to write
the `uonrjg` Section 7.2 `integration-deferred` row that sibling `udgilu` needs. I computed dependency
depth from every `lifeglyph` plan's `- Item-Dependencies:`:

```text
z8ddk0  depth 0
n4xq3l  depth 0    2xz59a depth 0
udgilu  depth 1  <- needs the row
pow5sj  depth 2
bn026f  depth 3
f9t5hz  depth 4
9zvl2w  depth 5
qdd5jq  depth 6
7p3tt8  depth 7  <- was going to write it
```

`oc_runipd.queue_sort_key` puts `dependency_depth` FIRST, so `udgilu` dispatches six items before this
one. `udgilu`'s E-03 requires the mapping, its E-06's A2 assertion over `runner_shutdown.KNOWN_ITEM_STATUSES`
fails without the spec row, and its V-03 demands "the `git diff` of the spec's Section 7.2 row added in
the same change". So as sequenced, `udgilu` would execute with the row still absent and either fail its
own V-03 or write an unspecified mapping into the canonical module, which is exactly the drift its OQ-02
was raised to prevent. I measured the underlying gap too: importing the enum gives 15 members, and
`integration-deferred` occurs ZERO times in `uonrjg` while every other member occurs at least once.

I did NOT fix this by moving the child to depth 0, which would have broken the Set's own "SPEC AMENDMENT
LAST" invariant (E-01's "no second table remains" claim is only true after `qdd5jq` deletes them).
Instead E-05 became a VERIFY-AND-REPAIR item with both branches specified and different evidence
demanded on each, and the `uonrjg` path is now DECLARED in `- Scope-Paths:` while being expected to show
no diff, so `aw ipd finalize`'s `--scope-ack` turns "the row was already correct" into an acknowledged
claim rather than silence.

**2. Two obligations had no owner in the entire Set (PR-803, PR-804).** Section 9.2 has two halves: a
legend MUST be available in command help, and one SHOULD be shown once in a view with three or more
stages. `bn026f`'s review explicitly handed the showing rule to the converting children, yet
`grep -rn "three or more\|shown once"` across all ten `lifeglyph` plans matches `bn026f` ALONE; none of
`f9t5hz`, `9zvl2w` or `qdd5jq` mentions it. So the one file that recorded the rule also declined to
implement it and nobody picked it up. Separately, `docs/cli-human-guide.md:13-19` tells users piped
output is `aw.agent/v1` JSONL as a hard cutover; that is false today (measured: `aw status` piped emits
prose) and the maintainer RETRACTED the promise on 2026-09-10 (`yaxr4i` OQ-01, Option B), but `yaxr4i`
E-05 declares only `docs/cli-output-contract.md` and its Deferred section names this file only under the
OPPOSITE ruling, so the retraction never reaches the file this plan is already editing.

**3. E-03 read as authoring a second legend renderer (PR-802).** "Ship ONE canonical legend ... reachable
from command help", with `agent_workflows/cli.py` in scope and no mention of `bn026f`, is most naturally
executed by writing a fresh legend in `cli.py`. But `bn026f` E-03 already ships one generated from
`lifecycle_style`'s table, and `bn026f`'s own review (its F-06) split the work by name: renderer there,
placement here. A second legend would be precisely the duplicate table this Set exists to delete, and
E-04's drift guard would then have to retrofit it.

**The stage count was wrong in four places (PR-805).** Section 5's table parses to 20 data rows, and the
spec's own D13 and Section 7.2 `ran` commentary each reject "a new 21st stage", which only parses at 20.
This plan said "the 21 stages" twice and "a 22nd stage" twice. Sibling `udgilu` carries the same
correction as its F-05 and named this file. I removed the count rather than correcting it: E-04's guard
asserts COVERAGE of the shared table, which makes any literal unnecessary and drift-proof.

Suite baseline at review HEAD, run bare: `1 failed, 7305 passed, 3 skipped, 2 xfailed in 115.84s`. The
one failure is a PRE-EXISTING parallel-run flake,
`tests/test_runner_backlog_close.py::ShutdownReportOnInterrupt::test_sigint_produces_the_report_and_exits_130`
(a `subprocess.TimeoutExpired`); the same class re-run in isolation gives `7 passed in 1.49s`. Recorded
in the plan's Step 0 so the executor compares against reality rather than a green expectation. Note
sibling plans cite different baselines (`qdd5jq` 7468, `bn026f` 8369) taken at different HEADs.
