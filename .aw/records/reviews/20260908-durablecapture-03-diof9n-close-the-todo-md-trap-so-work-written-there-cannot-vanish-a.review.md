## Round 1

Reviewed at HEAD `024f4256`. `aw ipd lint --phase author --agent` CONFORMING before semantic review and
`--phase review-finalize --agent` CONFORMING after every revision. Claims were re-measured in an isolated
worktree by IMPORTING the modules, APPLYING the proposed changes, and RUNNING the prescribed commands,
not by reading source.

THE PLAN'S CORE DIAGNOSIS IS CORRECT AND SURVIVED RE-MEASUREMENT WHOLE. `TODO.md` is in `SCAN_ROOTS`,
`_classify_tree("TODO.md")` returns `None`, and `attention.scan` drops it with no drift because the
unclassified branch requires a `.agents/` prefix; the same silent drop holds for `DECISIONS.md`,
`README.md` and `ARCHITECTURE.md`. The attention-tier spec really does predict the defect verbatim at
`:102-103`. Both deferred specs still carry `Gate-Kind: artifact` / `Gate-Ref: TODO.md`. `TODO.md`
appears at exactly nine places in `whatnext.md`, and the plan is right that most are WRITE instructions
rather than a source pointer. Its F-6 correction (that `i6015i` is EXECUTED and deliberately left the
workflow alone) is accurate and well argued. The author also deserves credit for the pre-review
amendment that corrected a false reversion claim; that instinct was right, and the finding below is that
the correction landed on the wrong conclusion, not that correcting was wrong.

TWO FINDINGS CHANGE WHAT EXECUTION MUST ACTUALLY DO, and both required running the plan rather than
reading it.

FIRST, E-05 CANNOT WORK AS WRITTEN (PR-001). I changed the `engine.py:1151` sentence and ran
`python3 -m agent_workflows install . --yes`. The new wording NEVER reached `AGENTS.md`, on the first
install or the second (`grep -c` returned `0` both times). The generator was correct, since
`agents_managed_sections()` emitted a `pointer` section whose body DID contain the new text; the merge
discarded it. `_apply_section_consent` preserves the on-disk body whenever a per-section hash is
recorded and the on-disk body does not match it, and at HEAD `AGENTS.md#aw:pointer` IS recorded
(`a9deb5a1...`) while the on-disk body hashes to `8baff639...`. The section is therefore ALREADY
drift-frozen before this plan touches anything, so every install preserves stale text and drops the
regeneration. This INVERTS the plan's own amendment, which concluded "the drift-preserving path is the
one a real install takes" as a reassurance and asserted the manifest "records ZERO managed sections":
the `managed_sections` key is indeed empty, but the load-bearing hash lives under `files`, which is what
the predicate reads. The amendment corrected a real error and replaced it with the opposite error.

SECOND, THE GATES DO NOT VALIDATE THE WAY THE PLAN SAYS, AND THE TRUTH IS WORSE (PR-002). The Concern
states these gates "VALIDATE (the file exists)". An `artifact` ref is matched against a pure shape regex
and is never resolved against the filesystem: `validate_gate_ref('artifact','NOSUCHFILE.md')` is True,
and when I renamed `TODO.md` away entirely `aw check specs --agent` still reported `conforms` with 0
findings. So the reason these gates went stale unnoticed is not that the file kept existing; it is that
nothing ever checks. That raises the bar on E-03 rather than lowering it, because no tooling will detect
a repointed gate going stale either, and it demotes "aw check specs clean" from an acceptance signal to
a near-worthless one.

Three further findings are operational hazards the plan would have walked into: `aw install` stages
roughly 100 unrelated files, modifies `.aw/config/project.json`, and COMMITS unprompted, which is
genuinely dangerous in this shared checkout (PR-003); the stated suite baseline was stale in a way that
would have excused a real regression (PR-004); and `install_agents_pointer`, cited twice including in
the amendment, does not exist (PR-005).

The remaining three findings are about work the review could simply do: the spec-sync reading (which
resolved twice in the plan's favor and needs no amendment), OQ-01 (removal, measured clean), and OQ-03
(exempt by design, with the exemption required to be a closed named set so a fourth root-level file
still fails).

No BLOCKER. Eight findings, all FIXED, none deferred. OQ-02 is deliberately left open because it needs a
maintainer status call, which is the correct disposition rather than a gap; it was sharpened by PR-002
so the executor now knows the carrier choice is the only safeguard.
