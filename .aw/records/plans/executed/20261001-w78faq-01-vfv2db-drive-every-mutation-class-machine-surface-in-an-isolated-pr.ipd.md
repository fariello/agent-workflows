Of 78 in-parser mutation leaves, 17 carry `--dry-run`, 22 carry `--apply`, 7 carry only `--yes`, and 32 carry none of the three. `aw ipd scaffold --help` states the polarity plainly: "Dry-run (preview) by default; pass --apply to write." So a harness that appended `--dry-run` would be rejected by most leaves and would silently APPLY on the 32 bare ones.
- `mutation_gate` IS DECLARED AND CONSUMED BY NO PRODUCTION CODE, the same inert-field shape `f36de0` found in `agent_record_kind`. `rg mutation_gate` outside `command_surface.py` returns two hits, both test assertions (`tests/test_prompts_new.py`, `tests/test_host_capability_extension.py`). Its five values (`none`, `dry_run_default`, `confirmation`, `auth_floor`, `policy`) distribute over this universe as 35 / 25 / 12 / 6 / 0, and it does NOT predict drivability: of the eleven broken leaves, four are `none`, five are `dry_run_default` and two are `confirmation`. So E-02 must compute the universe from the class-and-kind predicate and classify the residue by MEASURED blocker, not by gate.
- `aw install . --yes` FULLY BOOTSTRAPS A PROJECT IN A TEMP DIRECTORY, which is what makes the fixture possible at all. Verified: exit 0, and the resulting tree carries `.aw/{config,records,state,system,workflow-artifacts}` plus a `.gitignore` and `AGENTS.md`. It COMMITS only when git has an identity (see F-14); given one, the fixture starts from a known HEAD with `.aw/config/` untracked, which is the baseline E-03's isolation checks compare against.
- `validate_agent_record` REJECTS HOME-STYLE PATHS (`_HOME_PATH_RE`) BUT NOT `/tmp` PATHS, so the schema cannot be the guard against the `storage detach` leak of a temp-project path. Verified: a well-formed record carrying `/tmp/.../proj` in `evidence` returns `[]` (F-15).
- `aw install . --yes` NEEDS A GIT IDENTITY TO COMMIT. Without one it exits 0 with the changes staged and HEAD unborn (F-14); the fixture must set a local identity.
- A SUBPROCESS WHOSE CWD IS OUTSIDE THE CHECKOUT IMPORTS THE INSTALLED PACKAGE, which in a worktree is another tree (F-13); the arm must pin `PYTHONPATH` to `REPO_ROOT`.
- `EXEMPTION_REGISTRY` KINDS ARE A CLOSED, TESTED SET: `tests/test_command_surface_declarations.py::test_zero_unreachable_command_declarations` asserts `reason_kind in ("sanctioned_raw", "known_broken", "not_runnable")` for the allow-set, and the read arm subtracts every key of `EXEMPTION_REGISTRY`, so mutation exemptions live in their own registry. The repository's existing precedent is to assert path absence in the TEST, which `f36de0`'s non-project case does for `/home/`.
- STDIN MUST STAY `DEVNULL` OR THE SUITE HANGS. `run_cli` already routes stdin from `DEVNULL`, and `storage init` and `storage attach` prompt for confirmation; with DEVNULL they decline non-interactively and exit 0, which is the behavior under test. `docs/cli-output-contract.md` Section 1.2 names this the asymmetric safety ladder.
- `oc update-models` IS DISPATCHED BY FORWARDED ARGV, NOT BY NAMESPACE, which makes it the one leaf in E-04 whose fix is shaped like `f36de0`'s hook-gate threading rather than like a handler edit. `cli._dispatch` rebuilds a `forwarded` list from selected attributes (`config`, then the truthy subset of `apply`, `dry_run`, `no_backup`, `allow_insecure`) and calls `oc_models.run(forwarded)`; `--agent` is not among them, so the flag cannot reach the handler at all until it is threaded.
- A LEAF'S MODULE IS NOT PREDICTABLE FROM ITS NAME, so E-04's targets were resolved by following each dispatch branch. The two `research` leaves in this universe land in DIFFERENT modules (`research index` -> `research_index.run_index`, `research promote` -> `research_archive.run_promote`), and `normalize-lanes` has no handler function whatsoever, living as an inline branch of `cli._dispatch`. An executor who greps for `_run_<leaf>` will find nothing for three of the eleven.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Open questions

### OQ-01: Should this plan carry `- Blocks-Release: next` when the backlog item it graduates is `Work-Kind: followup` with no gate?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY RULE PLUS MEASUREMENT, toward carrying the gate. The item was filed as a coverage followup predicting a latent hole; measurement found eleven ALREADY-SHIPPED broken machine surfaces (F-03), which is a different artifact. AGENTS.md's release-gate section states that an artifact whose `- Work-Kind:` is in the gating set (default `bug`) MUST carry `- Blocks-Release:` while it is live, and its perceptibility test is user-visible impact: an agent piping `aw include --agent` into a JSON parser gets an exception rather than a record, which is perceptible and not an invisible inefficiency. So `bug` is the honest classification and the gate follows from it mechanically. THE COUNTER-ARGUMENT IS REAL AND IS WHY THIS IS RECORDED: inheriting a gate the item does not carry could look like inventing one, which the production contract forbids ("If the item has none, do not invent one"). The distinction is that this is not INHERITANCE but the gate the plan's own `Work-Kind` requires, and the three nearest precedents agree: `f36de0` carries `bug` + `next` for the same defect class on the read surface, and `eeiytw` carries `bug` + `next` for literally the same missing-payload shape on two other leaves. A maintainer who judges the eleven leaves tolerable in a release should clear the field explicitly rather than leave the classification wrong.

### OQ-02: Should the fixture give each leaf its own clone, or share one installed project across the arm?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED BY MEASURING BOTH, toward clone-per-leaf. A probe drove ten of the eleven broken leaves against ONE shared installed project and the tree was dirtied ZERO times (F-05), so sharing is tempting and would cost 2.41s total instead of about 3.6s. IT IS STILL WRONG, for a reason the probe cannot see: those leaves do not write TODAY, and the arm exists precisely to keep running as handlers change. The moment one does write, a shared tree turns one leaf's output into another leaf's precondition, and because `pyproject.toml` `addopts` leaves `pytest-randomly` enabled, test ORDER varies per run, so the failure would present as an intermittent flake rather than an honest red. The cost of avoiding that is about 1.2s of `copytree` across the arm, which is not a budget worth trading a deterministic suite for. The install is still done ONCE as a session-scoped template, so the expensive half is amortized either way.

### OQ-03: Should `storage init` and `storage attach` report `skipped` when a confirmation is declined non-interactively, or should they refuse with `cannot-run`?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED TOWARD `skipped` WITH `complete: false`, decided by a constraint this plan already holds fixed rather than left to the executor. Measured (F-09): both leaves exit 0 today while printing a confirmation prompt and a `SKIP` line to stdout. BOTH READINGS OF THE CONTRACT ARE ARGUABLE, which is why this is recorded rather than assumed. For `skipped`: `docs/cli-output-contract.md` Section 1.2's asymmetric safety ladder treats declining a confirmation non-interactively as the CORRECT outcome rather than an error, so the record should describe a non-event; `skipped` is in `agent_schema.VALID_OUTCOMES`, and Section 4's anti-greenwashing rule is satisfied precisely because `complete` is false, so nothing claims the work happened. For `cannot-run` at exit 2: a consumer asked for work that did not occur and arguably needs a nonzero code to notice it, which is what Section 11.4 prescribes for a refusal.
  WHAT DECIDES IT IS E-04's OWN BYTE-IDENTICAL REQUIREMENT, which is not negotiable within this plan: the human path including its EXIT CODE must not change, and these leaves exit 0 for a human today. `cannot-run` at exit 2 would therefore either violate that requirement or introduce a machine-versus-human exit divergence. Such a divergence is not unprecedented here (`attention`'s deliberate 3-versus-2 split, recorded in `f36de0`'s conventions), but it is a DELIBERATE contract retraction that belongs in its own reviewed change, not a side effect of a conformance sweep. So `skipped` is the only mapping consistent with the constraints already written, and E-04 states it as the required mapping.
  NO DURABLE CARRIER IS OWED, because nothing outstanding survives this plan: the mapping is DECIDED here, implemented by E-04, and V-04 requires the emitted record be pasted with `complete` shown false and the outcome shown to be in `VALID_OUTCOMES`. If a reviewer prefers the exit-2 reading, that is a change to E-04's stated mapping plus an explicit amendment of its byte-identical requirement, which is a review decision on this plan rather than deferred work to track elsewhere.
