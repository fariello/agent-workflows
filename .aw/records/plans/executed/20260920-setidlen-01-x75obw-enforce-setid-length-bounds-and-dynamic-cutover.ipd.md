- Finding: PR-403

THE DIRECTIVE, as this plan records it: "the cutover date must not be a hardcoded calendar date in the Python source code; it must be stamped into `.aw/config/project.json` dynamically". OPTION (b) WAS REJECTED AS ACTIVELY WORSE, not merely less literal: stamping the CURRENT install date would set every existing repository's boundary to today, permanently grandfathering every long setid that already exists, which is the exact outcome the install-history search was built to prevent. ### OQ-04: When a setid spans artifacts with different dates, which date decides grandfathering?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: THE ARTIFACT'S OWN DATE, per finding. Resolved from repository evidence rather than deferred, because the shipped check shape settles it. A setid is a SHARED label, so "the setid's date" is not a quantity that exists: measured at review, `backlog-medhigh-260819` (22 chars) spans 8 artifacts, `assess-documentation` (20) spans 6, and `agent-comms-broker` (18) spans 3, with different dates. But every `Drift` finding is LOCATED AT A FILE (`location=file:line`), and both cutover precedents already compare a cutover against the individual artifact's own date (`_spec_requires_id6` uses the filename's leading `YYYYMMDD`; `carrier_severity_for_plan` uses the plan's own `- Date:`). So the rule evaluates PER ARTIFACT: a post-cutover artifact adopting a long setid is flagged even when pre-cutover siblings share that setid, and those siblings stay silent. THE CONSEQUENCE IS INTENDED AND MUST BE DOCUMENTED: one long setid can be simultaneously grandfathered on an old artifact and refused on a new one, which is precisely what stops the corpus going red while still preventing new long setids. Note this also means a NEW artifact may NOT join an existing long-setid topic after the cutover, which is a real usability cost; state it in the spec amendment rather than letting an author discover it.
