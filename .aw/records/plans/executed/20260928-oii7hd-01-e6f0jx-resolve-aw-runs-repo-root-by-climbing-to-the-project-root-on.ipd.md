## Goal

Make `aw runs` work from any subdirectory of a project, the way every other repo-scoped `aw` verb already does, by resolving its repo root through `project_context.resolve_verb_repo_root` on all four sites that currently resolve against the process's current directory. The operator-visible result: `aw runs <run-id>` from `tests/` or `docs/` shows the run instead of answering `error: no run matched target '<id>'`, and `aw runs analyze` writes its report inside the project instead of into a separate machine-local records root.

## Project conventions discovered (Step 0)

- `project_context.resolve_verb_repo_root` IS the repository's answer to this problem and it already exists. Its docstring states the contract: an explicit `--dir` is honored verbatim with no climb, otherwise CLIMB from cwd via `find_project_root` "so the verb works from any subdirectory, git-style", else fall through to cwd. This plan adds no new mechanism; it routes four stragglers through the existing one.
- `find_project_root` climbs for a `.aw/` or legacy `.agents/` marker and requires a DURABLE child (`system`/`records`/`config`) via `_is_project_marker`, so a stray runtime `.aw/` under `.aw/state/` is not mistaken for a root. git presence is deliberately NOT a marker.
- THE SAME DOCSTRING RECORDS A KNOWN, DELIBERATE GAP this plan must not mistake for its own business: only `aw attention` and `aw ipd board` pair the resolver with `is_project_dir` and emit `no_project_message`; every other caller takes the cwd fallback SILENTLY. It says explicitly that whether the silent callers should all guide is a separate design question and that the note "does not license converting them on the way past". OQ-04 honors that boundary.
- ONE `aw runs` LEAF ALREADY CLIMBS, which is why the surface is internally inconsistent rather than uniformly cwd-relative: `run_cli._projection_dir` (serving `aw runs decisions` and `aw runs questions`) calls `resolve_verb_repo_root(getattr(args, "dir", None))`. Measured on the fixture, `aw runs decisions <id>` names the SAME absolute projection path from the subdirectory and from the root. So this plan's target state already has a working precedent inside the very module it edits.
- `state_root` derives the runs root from the resolved PROJECT CONTEXT (`resolve_project_context(target_repo=...)`), not by composing `<repo>/.aw/records/runs` literally. That is precisely why a cwd-relative root is not merely a missing climb but a redirection: from `sub/deeper/` it resolves to a `~/.aw/projects/<name>-<hash>/records/runs` context, a wholly different records root, which is what makes `discover_run_dirs` return zero runs and what makes the analytics writer publish outside the repository.
- `discover_run_dirs` searches THREE roots: `state_root(repo_root)` (resolved, absolute) plus the literally composed `repo_root / ".aw" / "runs"` and `repo_root / ".agents" / "runs"`. The mix of a resolved root and two composed ones is what makes the emitted `run_dir` shape depend on WHICH root matched, which is the observable side effect E-01 must decide about.
- `resolve_target_runs_detailed` is the viewer's resolver and `repair` calls it; it matches a target against a run directory NAME (exactly or as a substring) and then against the setid FIELDS via `_state_setids`. `repair_run` additionally requires `state.json`. These two conditions together are what `_classify_absent_target` reproduces, and `d91i3e` V-02 measured the second as load-bearing.
- The viewer never renders a path RELATIVE to `repo_root`: `grep -n "relative_to" agent_workflows/run_viewer.py` returns zero hits. So changing the root's spelling cannot alter any human-rendered relative path; the only shape exposure is the `run_dir` field carried into `--json`/`--agent` by `asdict`.
- `run_analytics_cli._repo_rel` DOES render paths relative to the repo root, and Section 9 plus the user rules require repo-relative rather than absolute output there. That is the surface where the wrong root becomes a visibly wrong, `../`-laden path in the payload.
- MACHINE OUTPUT MUST NOT CARRY A HOME PATH, AND THIS SURFACE ALREADY VIOLATES THAT TODAY. `agent_schema._HOME_PATH_RE` matches `/home/<name>` and `/Users/<name>`, `normalize_repo_path` exists to keep a payload repo-relative, and the repository ships `aw sanitize` as the deterministic authority. `d91i3e` E-03 already forbade printing a resolved absolute path into a suggestion on this same command for exactly this reason (its D92 note). Measured at HEAD: `validate_agent_record` on the viewer's `--agent` payload for a canonical-root run already returns `Unsanitized absolute home path in field 'run_dir'`, and `run_dir` is the ONLY field in the payload carrying one. That pre-existing violation is what makes OQ-02 answerable from evidence rather than a maintainer judgement.
- THE VIEWER'S LIST PAYLOADS ARE NOT `aw.agent/v1` RECORDS, which bounds how far the previous convention can be pushed. `run_viewer` imports `agent_schema` and calls `assert_valid_agent_record` at exactly ONE site, the unresolvable-target refusal; the run/summary payloads are bare dicts printed by `json.dumps`. So the validator's verdict on `run_dir` is evidence about intent, not a gate these payloads currently pass. Do not claim conformance for them, and do not convert them here (the same distinction `d91i3e` F-16 drew for `run_cli`).
- MEASURE EXIT CODES UNPIPED. Recorded repeatedly in this repository after a piped `$?` produced a false finding; this plan's own first measurement of `aw runs show` read `EXIT=0` through a pipe while the real code was 2.
- Run records are gitignored, so a test on this surface MUST build a fixture (`tests/test_run_viewer.py` header; `_build_viewer_fixture` is the shape to follow). `tests/test_run_viewer.py` also arms a process-wide audit hook to catch a regression read of the live tree.
- THE TEST FILES `d91i3e` NAMES NO LONGER EXIST. `tests/test_run_recovery_cli.py`, which that plan calls "the `e6b9kt` regression suite" and instructs a future author to extend, was deleted in `19313eed` ("trim test suite from 9,136 to under 2,000 tests"). Measured at HEAD: `TestLedgerResolutionAndWrongFormatVerdict` exists nowhere in `tests/`, and the ONLY remaining reference to `resolve_ledger_path` in the whole test tree is one analytics-exclusion assertion in `tests/test_run_viewer.py`.
