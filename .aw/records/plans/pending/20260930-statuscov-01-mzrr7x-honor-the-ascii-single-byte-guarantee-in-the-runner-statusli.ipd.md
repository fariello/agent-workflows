# IPD: Honor the ASCII single-byte guarantee in the runner statusline box, which emits block glyphs and ignores AW_ASCII_ONLY

- Date: 2026-09-30
- Kind: child
- Concern: `docs/cli-human-guide.md` tells a user that Unicode glyphs "degrade to ASCII ... when you set `AW_ASCII_ONLY=1` or `FORCE_ASCII=1`", and spec `uonrjg` Section 9.4's THIRD contract bullet requires "guaranteed single-byte alignment in ASCII mode". THE RUNNER STATUSLINE HONORS NEITHER. Measured at authoring HEAD `c2b3a3c1f`: with `AW_ASCII_ONLY=1` set, `term.should_unicode()` correctly returns False, yet `Statusline.render_line()` still emits nine distinct non-ASCII code points (`╭ ─ ┬ ╮ ╰ ┴ ╯ │ █`), because the chain from the environment variable to the box is broken in THREE independent places: the runners construct `render_stream.Palette(should_color(...))` with NO `use_unicode` argument, so the flag `Palette` already carries defaults True (0 of 11 `Palette(...)` sites in either runner pass it); `Statusline.__init__` takes no `use_unicode` parameter and `Statusline._render_lines_unlocked` never forwards one, so even a correctly-built palette could not reach the renderer; and `format_statusline_lines` drops the flag when it calls `format_progress_bar`, which has no ASCII branch AT ALL. The last link makes even the EXPLICIT `use_unicode=False` path non-conforming: a caller who asks for ASCII still gets U+2588 at every progress state except `0/N`, measured leaking at all ten of `current_idx` 1 through 10. The consequence on a real non-UTF-8 console is visible rather than theoretical: `term.ensure_encodable_stdio` deliberately leaves such a stream with `errors="replace"`, so the box renders as rows of `?` instead of degrading to the `+---+` form the function already knows how to draw.
- Scope: Repair the three broken links so the ASCII mode the code already implements is reachable, and give `format_progress_bar` the ASCII branch it lacks. IN: a `use_unicode` parameter on `format_progress_bar` with an ASCII fill that preserves the current visible width exactly and keeps a started run distinguishable from an un-started one and an incomplete run from a complete one (F-12); forwarding `use_unicode` from `format_statusline_lines` to that call; a `use_unicode` source on `Statusline` derived from the `Palette` it is already given; the runner-side `Palette` constructions that feed a statusline, so `term.should_unicode` reaches them; and a behavioral regression module asserting ASCII-mode purity. OUT: every other column, label, width computation and pad in `format_statusline_lines` (plan `it6tpj` owns those and this plan must not collide), `render_run_summary_table`'s own identical leak (same root cause, its own carrier), the ambiguous-width half spec Section 9.4 declines to guarantee, the ANSI palette, and which columns exist.

## Goal

Make the ASCII degradation path the repository already DOCUMENTS and SPECIFIES actually reachable for the runner statusline, so `AW_ASCII_ONLY=1`, `FORCE_ASCII=1`, or a non-UTF-8 stream encoding produces the `+---+` box the renderer can already draw instead of nine kinds of Unicode the console cannot encode.

Give `format_progress_bar` the ASCII fill it has never had, at IDENTICAL visible width AND without collapsing the two boundaries a reader interprets from a progress bar (started versus not, complete versus not, F-12), so the one remaining glyph inside an otherwise-ASCII box stops leaking and so a caller who explicitly asks for `use_unicode=False` is told the truth.

Leave a behavioral regression guard behind, because this defect is invisible to the entire existing suite: no test in the tree calls `format_statusline_lines`, `format_statusline`, or `Statusline` at all.

### Task group 1: give the progress bar an ASCII form

- [ ] E-01 ADD A `use_unicode: bool = True` PARAMETER TO `render_stream.format_progress_bar` AND AN ASCII FILL BRANCH, keeping the signature backward-compatible by defaulting to the current behavior. The function today has NO ASCII path: it always builds its fill from `"█"` plus the `_FRACTIONAL_BLOCKS` eighths table, so there is no flag to honor and nothing for a caller to select (F-02 link 7).
  THE ASCII BRANCH MUST PRESERVE VISIBLE WIDTH EXACTLY, and this is the one hard constraint. The bar sits inside a padded column, so a fill that is one character shorter shifts the box. Authoring proposed: round the fraction to whole cells (`full = int(round(frac * width))`) and emit `"#" * full + " " * (width - full)`, which drops the eighths resolution ASCII cannot express while keeping the total cell count at `width`. Width parity is confirmed across `0/10`, `1/10`, `3/10`, `5/10`, `10/10`, `79/80` and the `0/0` degenerate case: the ASCII and Unicode bars report the SAME `term.visible_width` at every one (F-05).
  BUT DO NOT SHIP `int(round(...))` AS WRITTEN: IT CREATES TWO USER-VISIBLE COLLISIONS THE UNICODE BAR DOES NOT HAVE (F-12, measured at review). Rounding to whole cells makes `79/80` render `[##########]`, BYTE-IDENTICAL to `80/80`, so a run at 99 percent looks FINISHED; and it makes `1/80`, `3/80` and `4/80` all render `[          ]`, byte-identical to `0/80`, so a run that has started looks UN-STARTED. The shipped Unicode bar distinguishes every one of those states through the eighths table, so this would be a NEW wrong answer introduced by a bug fix, on the same user-perceptible-impact test that earns this plan its `bug` classification and its release gate. Losing eighth-cell RESOLUTION is unavoidable in ASCII and is fine; collapsing the "started" and "complete" BOUNDARIES is not, because those are the two readings an operator actually takes from a progress bar.
  SO CLAMP THE BOUNDARIES. A measured conforming shape is floor-plus-clamp: `full = int(frac * width)`, then `if frac > 0 and full == 0: full = 1` (a started run shows at least one cell) and `if frac < 1.0 and full == width: full = width - 1` (an incomplete run never shows a full bar). Verified at review to keep every bar at exactly `width` cells and to render `100%` -> `[##########]`, `99%` -> `[######### ]`, `4%` -> `[#         ]`, `0%` -> `[          ]`. Any other shape is acceptable if it holds the same two boundary properties AND the width parity; what is NOT acceptable is bare `round()`, and V-01 now requires the boundary cases as evidence rather than only the parity table.
  DO NOT CHANGE THE UNICODE BRANCH. Authoring measured the proposed rewrite BYTE-IDENTICAL to today's output across every `current`/`total` combination for totals 0, 1, 7, 10, 80 and 1000 (zero differences). That identity is what makes this safe to land, and V-01 demands it be reproduced rather than assumed.
  PICK THE FILL CHARACTER FROM ASCII ONLY, and state which you chose. `#` is authoring's measured choice; `=` or `*` are equally conforming. What is NOT conforming is any `_FRACTIONAL_BLOCKS` member, every one of which is non-ASCII.

## Project conventions discovered (Step 0)

- THE ASCII CONTRACT IS ALREADY WRITTEN AND THIS PLAN ONLY MAKES IT REACHABLE. Spec `uonrjg` (`approved`, `Blocks-Release: next`) Section 9.3 states "When Unicode is disabled by `AW_ASCII_ONLY=1`, `FORCE_ASCII=1`, or stream capability, the exact ASCII fallback in section 5 replaces the Unicode grapheme", and Section 9.4's third bullet requires "guaranteed single-byte alignment in ASCII mode". So E-04 consumes an existing detector at the call site rather than adding detection to a renderer.
- `Palette` ALREADY CARRIES `use_unicode` and already consults it for lifecycle glyphs, so E-03 reads an existing field rather than introducing a parallel flag. This is why the fix needs no new public surface.
- THE ASCII BOX-DRAWING PATH ALREADY EXISTS in `format_statusline_lines`, which selects `+`/`-`/`|` under `use_unicode=False`. The leak is the ONE embedded glyph the function does not control, which is why this plan is small.

- RUN THE SUITE BARE (`python3 -m pytest`). `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal` and the slow/livecorpus deselection; `-n0` makes it several times slower, a second `-q` suppresses the summary line this plan requires be pasted, and `-p no:randomly` disables order randomization.
