## Open questions

### OQ-01: Should the duplicate rule report one finding per repeated key, or one finding per item?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED AT AUTHORING - one finding PER REPEATED KEY, naming the key and the count. `validate_item` already emits several independent findings for one item (a single fixture can drift `priority-invalid` and `kind-invalid` together), and `Drift` carries one `location`/`rule`/`detail` triple, so a single aggregate finding would have to pack the key list into `detail` where no consumer can read it. Per-key also makes the `--agent` tab-separated surface actionable: one record per thing to fix. The cost is that an item with three doubled keys reports three findings, which is correct rather than noisy, since each needs a separate edit.

### OQ-02: Should `backlog.gate-summary-unexpected` be a distinct id, or should the existing `backlog.gate-unexpected` widen to cover the summary?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED AT AUTHORING - a DISTINCT id, while the `has_gate` PREDICATE widens. Two reasons, both mechanical. First, `backlog.gate-unexpected`'s detail reads "gate fields present on a non-blocked item" and its remediation is to delete the `Gate-Kind`/`Gate-Ref` pair; a reader whose item carries only a summary would hunt for lines that do not exist. Second, `doctor.build_remediation` dispatches on SUBSTRINGS of the rule id (`if "summary-unsafe" in rule`, `if "setid-collision" in rule`), so a distinct id can later carry its own remediation while a widened one cannot be distinguished. The specs tree is not a counterexample: `specs.validate_spec` does reuse one `attention.gate-forbidden` id for all three fields, but it is reporting a spec-tree contract whose gate fields are a single indivisible block, and this plan is not obliged to copy a coarser choice.
