## Goal

Make a run whose `state.json` holds an unreadable queue entry still PRINT its summary table, so the closing census of work that actually completed survives instead of being lost to an exception. The entry gets a visible row and a counted bucket, never a silent omission, so a corrupted state file cannot read as a shorter and cleaner run than it was.

THE GUARDS ARE FAIL-CLOSED IN THE PRECISE SENSE THE SIBLING PRECEDENT FIXES. `runner_shared.no_turn_was_attempted` documents the direction this Set inherits: "a malformed entry (anything that is not a mapping) returns False, since an unreadable entry cannot be shown not to have run". Applied here that means an unreadable entry is never counted as COMPLETED work and never admitted to the `COMPLETED` outcome word, because either would manufacture a success for an entry nobody can read.

THE FIX IS TWELVE GUARD SITES ACROSS FIVE FUNCTIONS IN ONE MODULE, NOT ONE GUARD, and that is the finding that shapes the plan rather than a scope choice. After guarding the site the backlog item names, the same input raises again from `dispatchable_work_total` -> `item_is_dispatchable_work`, then from each of FIVE outcome-ladder comprehensions (the `interrupted`, FAILED and BLOCKED tests plus the TWO separate success tuples), then from the diagnostics loop (F-03). A plan that guarded only the named site would report a fix while the table still failed to render.

THE COUNT IS CONFIRMED AND ONE ITEM'S SUMMARY OF IT WAS WRONG (PR-102, F-19). F-03's enumeration was re-measured at review and is accurate, including its separate entries for the two success-tuple comprehensions. E-05's own summary of those same sites called them "the four outcome-ladder comprehensions" while parenthetically naming five things, collapsing the two byte-identical success tuples into one - and review staged that reading and watched it still crash. The count is stated here because it is the plan's headline argument for why a single guard is insufficient; the correction is to the INSTRUCTION, not to the measurement.

The bytes of every well-formed run's table must not move: each guard adds a branch reachable only by an input that currently raises.

### OQ-01: The item asks what a malformed entry should RENDER as. Should it get a counted row, or be skipped with a caveat?

FIRST, it makes the table LIE BY ARITHMETIC: the body row count and the `Progress:` status census would sum to fewer entries than the queue holds, so a corrupted state file would read as a shorter, cleaner run than it was. That is the manufactured-disposition direction `EXIT_MALFORMED_ENTRY_TOKEN`'s own comment was written to avoid ("so it can never be confused with something a driver persists"), and it contradicts the in-source guarantee that the table renders "one ROW per matched artifact ... - Status: resolved
- Owner: opencode
