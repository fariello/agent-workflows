# IPD: Render a malformed queue entry as an honest row so the run summary table survives instead of crashing

- Date: 2026-09-29
- Kind: child
- Concern: `render_stream.render_run_summary_table` raises `AttributeError` on a queue entry that is not a mapping, so a run whose durable `state.json` holds one loses its whole closing summary table. It is the SECOND statement of both hosts' `run_queue` exit tails, and it is also reached by `aw <host> run status`, by `--prepare-only`, and by the interrupt/SIGTERM and `DriverError` paths, so the same input costs an operator the run's only rendered census of what happened.
- Scope: Make `render_run_summary_table` render a COMPLETE table for a queue holding a non-mapping entry, by giving that entry its own honest ROW and its own counted status bucket rather than dropping it, and by guarding the SEVEN other measured per-entry read sites the same input reaches (the `run_order` sort key, the row loop, the four outcome-ladder comprehensions, and the diagnostics loop) plus the four `render_stream` helpers that crash on it (`item_is_dispatchable_work`, `activity_for_item`, `_interrupt_reason_of`, `format_generated_next_actions_summary_block`). NOT `run_viewer.load_run_summary` (F-14, filed nowhere; reported, not fixed). NOT any well-formed entry's row, count, outcome word, or byte.

## Goal

Make a run whose `state.json` holds an unreadable queue entry still PRINT its summary table, so the closing census of work that actually completed survives instead of being lost to an exception. The entry gets a visible row and a counted bucket, never a silent omission, so a corrupted state file cannot read as a shorter and cleaner run than it was.

THE GUARDS ARE FAIL-CLOSED IN THE PRECISE SENSE THE SIBLING PRECEDENT FIXES. `runner_shared.no_turn_was_attempted` documents the direction this Set inherits: "a malformed entry (anything that is not a mapping) returns False, since an unreadable entry cannot be shown not to have run". Applied here that means an unreadable entry is never counted as COMPLETED work and never admitted to the `COMPLETED` outcome word, because either would manufacture a success for an entry nobody can read.

THE FIX IS TWELVE GUARDS ACROSS FIVE FUNCTIONS IN ONE MODULE, NOT ONE GUARD, and that is the finding that shapes the plan rather than a scope choice. After guarding the site the backlog item names, the same input raises again from `dispatchable_work_total` -> `item_is_dispatchable_work`, then from each of four outcome-ladder comprehensions, then from the diagnostics loop (F-03). A plan that guarded only the named site would report a fix while the table still failed to render.

The bytes of every well-formed run's table must not move: each guard adds a branch reachable only by an input that currently raises.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- THE FAIL-CLOSED DIRECTION IS ALREADY THIS REPOSITORY'S POLICY FOR THIS EXACT INPUT, and the backlog item cites it: `runner_shared.no_turn_was_attempted`'s docstring enumerates three deliberate fail-closed properties, one of which is verbatim "a malformed entry (anything that is not a mapping) returns False, since an unreadable entry cannot be shown not to have run". This plan adopts that direction rather than inventing one.
- THE GUARD BELONGS IN THE FUNCTION THAT OWNS THE READ, NOT IN ITS CALLERS. Executed plan `w7e3e3`'s OQ-02 resolved this for the sibling predicate with three evidenced reasons (the contract is written on the predicate; several callers can drift; the sibling `no_turn_was_attempted` guards inside itself). E-04 applies it to the four helpers. E-03 and E-05 are NOT counterexamples: those reads happen in `render_run_summary_table`'s OWN body and reach no other function.
- THE SKIP-VERSUS-COUNT DISTINCTION IS DRAWN ON WHAT A SURFACE CONTRACTS TO DESCRIBE, which is the in-tree rule sibling plan `0kh97v` states for the report and which this plan follows for the table: a CENSUS surface (the table body, the `Progress:` status counts) must account for every entry, while a CONDITIONAL surface (the diagnostics block, the stranded-work section, the generated-next-actions block) skips it because each is conditional on per-entry evidence a non-mapping entry cannot carry. `runner_shared.render_zero_work_notes` already opens its loop with `if not isinstance(item, Mapping): continue` for exactly that reason, and is the one queue reader in its family that did not crash.
- A STATUS TOKEN OUTSIDE THE OWNER ENUMS IS THE CORRECT SHAPE HERE, not a gap. `lifecycle_style`'s resolver has a documented rung for "a KNOWN family with an unrecognized status" returning `unknown` plus a diagnostic, and the spec's Section 7.2 table ends with a row for exactly that case ("stale projected `abandoned?` or another inference | unknown"). Two shipped tokens (`abandoned?`, `queued?`) already live in `_RUNNER_ITEM_PAIRS` mapped to `unknown`, so the stage exists and is reachable.
- `render_stream` MAY NOT IMPORT `runner_shared`, and the module header says why: `runner_shared` imports `render_stream`, so an import reaching back would cycle. The header records that only `term` and `lifecycle_style` are permitted first-party imports beyond `run_selection_policy`, guarded by an allowlist. The new token is therefore defined HERE and not shared with `0kh97v`'s report token (F-12).
- ASSERT ON OBSERVABLE BEHAVIOR, never on code structure (`AGENTS.md`, GUIDING_PRINCIPLES P16). E-01's tests call the renderer and assert on returned lines, cells, row counts and outcome words; none reads source text, counts callers, or pins a docstring.
- THE BOX IS MEASURED, SO A NEW CELL WIDTH IS NOT FREE. `render_run_summary_table` derives `col_widths` from the widest cell per column, so the new Status token widens the Status column for a malformed run only. Two pending plans (`4taj2e`, `it6tpj`) are rewriting exactly these measurements to visible columns; E-01's assertions must therefore be on CELL CONTENT and ROW COUNT, never on byte-exact box width, or this plan's tests will collide with theirs (F-15).

## Open questions

### OQ-01: The item asks what a malformed entry should RENDER as. Should it get a counted row, or be skipped with a caveat?

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE as COUNT AND RENDER, never silently omit, and it needs no maintainer ruling because the repository has already ruled on the underlying direction in an adjacent surface. SKIPPING IS REJECTED for three evidenced reasons. FIRST, it makes the table LIE BY ARITHMETIC: the body row count and the `Progress:` status census would sum to fewer entries than the queue holds, so a corrupted state file would read as a shorter, cleaner run than it was. That is the manufactured-disposition direction `EXIT_MALFORMED_ENTRY_TOKEN`'s own comment was written to avoid ("so it can never be confused with something a driver persists"), and it contradicts the in-source guarantee that the table renders "one ROW per matched artifact ... INCLUDING an item with zero attempts" (F-09). SECOND, the honest option costs nothing downstream, which was measured rather than assumed: the token resolves cleanly through the shared lifecycle resolver to `unknown` with a diagnostic and styles without raising (F-13), and the table's column widths are derived per-render so a wider Status cell reflows the box rather than breaking it (F-10). THIRD, a "caveat" is the weaker form of the same information: a sentence tells a reader that SOMETHING was unreadable, a counted row tells them HOW MANY and WHERE in the queue. The COUNT-versus-SKIP line is then drawn on what each surface CONTRACTS to describe, which is the same rule sibling plan `0kh97v` states for the report: the CENSUS surfaces (table body, status counts) must account for every entry, while the CONDITIONAL surfaces (diagnostics block, stranded-work section, generated-next-actions block) skip it because each is conditional on per-entry evidence a non-mapping entry provably cannot carry. `runner_shared.render_zero_work_notes` already implements exactly that skip, so the conditional half is an in-tree ruling too.

### OQ-02: Should the new status token be added to `lifecycle_style._RUNNER_ITEM_PAIRS` so it resolves to a real stage instead of `unknown`?

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED as NO, LEAVE IT UNMAPPED, from spec text and measurement rather than preference. `unknown` is not a fallthrough here, it is the CORRECT answer: the stage's own defined meaning is "State cannot be determined safely", which is precisely true of an entry nobody can read, and spec `uonrjg` Section 7.2's final row already provides for "another inference" resolving that way, with two shipped tokens (`abandoned?`, `queued?`) mapped to `unknown` for the analogous reason that an inference is not a durable state. Mapping the token to any REAL stage would be the collapse Section 5 exists to forbid: `done` or `ready` would paint an unreadable entry as work in a known condition, and `failed` or `blocked` would assert a disposition nobody measured. Enum membership is separately wrong: `runner_shutdown.KNOWN_ITEM_STATUSES` is read by Phase 0's ledger-coherence check, so adding it would make a shutdown check treat a renderer's placeholder as a driver-written status. The one thing that had to be verified rather than argued is that leaving it out breaks no test: criterion A2's assertion is `owner_enum <= mapped_keys` and its docstring explicitly forbids tidying it into an equality ("do not delete an unreferenced mapping row to make one pass"), and the resolver's unrecognized-status rung is itself covered by existing tests, so an unmapped token is a supported case (F-13).
