# IPD: Report a repeated research front-matter key instead of silently honoring the last one

- Date: 2026-10-02
- Kind: child
- Concern: `research_contract.parse_frontmatter` is a hand-written line splitter (`key, _, val = line.partition(":")` assigning into a dict), so a REPEATED key is collapsed with silent LAST-WINS semantics and no reader of the YAML dialect can tell a one-key block from a two-key one. Measured in this lane at HEAD `86934a144`: `parse_frontmatter("---\na: 1\na: 2\n---\n")` returns `{'a': '2'}`. On a real doc whose legitimate line reads `status: todo` and whose injected later line reads `status: reference`, every consumer reports the LATER value: `validate_frontmatter` returns `[]`, `_scan_docs` indexes `status='reference'`, `check_drift` returns `[]`, `attention._research_record` reports `native_status='reference'` with `attention_class='done'`, and `selectors._read_status` returns `reference`. An injected `blocks-release: next` reaches `attention` as `blocks_release='next'` and `releases._declared_blocks_release` as `'next'`, so the smuggled gate FUNCTIONS. The one bound worth recording is that a duplicated `id:` IS caught, by a DIFFERENT rule for a different reason (`research_index._doc_entry` cross-checks `fm.get("id")` against the id6 in the FILENAME, yielding `name-frontmatter-mismatch: id aaaaaa != name m8zg5y`), and even that fails when the LAST `id:` matches the filename: a block carrying `id: aaaaaa` then `id: m8zg5y` indexes clean at zero drift. Nothing cross-checks `status`, `blocks-release`, `priority`, `outcome` or `kind`, which is the actual gap.
- Scope: Add ONE repeated-key drift rule over the research tree's fenced-YAML front matter, emitted from `research_index.check_drift` (so it surfaces through `aw research index --check` and `aw check research --all`), registered in `check_engine.RULE_REGISTRY` at `error`, and covered by behavioral tests in `tests/test_research_index.py`. Judge the RAW TEXT of the leading `---` block, because the collapsed mapping `parse_frontmatter` returns structurally cannot carry the evidence. Agree with the sibling bullet-tree rule `backlog.metadata-bullet-repeated` (executed plan `7ohskw`) on the `-repeated` naming and the `error` severity, so one defect class has one vocabulary across the two dialects. OUT, each for a stated reason: changing `parse_frontmatter`'s RETURN CONTRACT or its last-wins behavior (five production modules consume it and a contract change is a different, larger deliverable; OQ-01 records the alternatives); any WRITE-PATH guard (pending plan `deftzy` closes the research write paths that can create a duplicate, and this rule is the complement that catches a HAND EDIT no write-path guard can see); the unsafe-descriptive research rule (pending plan `xnogdl`, backlog `cvxbbu`); and extending the rule to any other tree (no other records tree uses the fenced-YAML dialect: all 127 fenced-YAML docs under `.aw/records/` are research docs).

## Goal

Make a repeated key in a research document's front matter a named, fail-closed finding instead of a silent contradiction, so a hand edit (or a future write-path bug) that leaves two `status:` lines in one block is reported rather than resolved in favor of whichever line happens to be last. After this plan the research tree's YAML dialect has the repeated-metadata rule the bullet dialect already got in `7ohskw`, under the same `-repeated` naming and the same `error` severity, so one defect class reads as one defect class across both.

## Open questions

### OQ-01: Should `parse_frontmatter` itself change, rather than a checker rule being added over it?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED AT AUTHORING - a CHECKER RULE, with the reader left alone, and the Deferred row carries the same decision for a reader who looks there first. Three options were measured. (a) Make `parse_frontmatter` REFUSE a duplicated block (return `None`): rejected, because `None` means "no valid front matter" to all five consumers, so an offending doc would become `frontmatter-missing`, be DROPPED from the manifest by `_doc_entry`, and freeze manifest regeneration via `run_index`'s drift refusal - a strictly worse outcome than a reported-but-readable record, and the same mechanism `xnogdl` F-06 measured. (b) Widen the RETURN TYPE so callers can see the raw key order: rejected as this plan's work, because it changes a signature five production modules and seven test files consume, and `selectors._read_yaml_scalar`'s bounded-header read is documented as safe BECAUSE of the current `None` contract; that is a refactor with its own review, not a side effect of adding a rule. (c) Leave the reader and add a rule that walks the raw text: CHOSEN, because the duplication is visible in the TEXT the scan has already loaded (F-10 measures the cost as negligible), the record stays readable and indexed, and the remedy is a one-line human edit the finding names. A reviewer who prefers (b) can say so without disturbing E-02, since the rule's walk would survive the signature change unchanged.

### OQ-02: One finding per repeated key, or one per offending document?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED AT AUTHORING - one finding PER REPEATED KEY, naming the key and the count, matching the sibling `backlog.metadata-bullet-repeated` which resolved the identical question the same way. `check_drift` already emits several independent findings for one document (a doc can carry both `dangling-consumed-by` and `adopted-without-consumer`), and `Drift` carries one `location`/`rule`/`detail` triple, so an aggregate finding would have to pack the key list into `detail` where the `location<TAB>rule<TAB>detail` agent record cannot structure it. Per-key also makes the agent surface actionable: one record per thing to fix. The cost is that a doc repeating three keys reports three findings, which is correct rather than noisy, since each needs a separate edit. E-04 case 5 pins the granularity.

### OQ-03: Should the rule also flag a repeated key whose two values AGREE?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED AT AUTHORING - YES, flag it, and the rule deliberately does not compare values. Three reasons. First, the defect is the AMBIGUITY, not the disagreement: a block with two agreeing `status:` lines is one hand edit away from disagreeing, and `research_cmd.update_frontmatter_fields` rewrites BOTH lines (F-09) while `research_archive._rewrite_status_in_text` rewrites only the LAST, so the same doc's duplication resolves differently depending on which verb touches it next. Second, a value comparison would have to decide what "agree" means for a list value (`topic: [a, b]` versus `topic: [b, a]`), which is a normalization question this rule has no business answering. Third, the sibling rule flags an agreeing pair too (its E-02 expected outcome names "two `- Blocks-Release:` bullets (agreeing or not)"), and the two dialects agreeing is the point of matching the naming and severity. E-04 case 1 uses disagreeing values because that is the harmful shape; a reviewer wanting the agreeing case pinned explicitly can ask for a ninth case at no cost to the implementation.
