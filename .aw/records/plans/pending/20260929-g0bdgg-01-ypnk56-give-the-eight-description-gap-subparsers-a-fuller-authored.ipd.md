## Project conventions discovered (Step 0)

- TWO ROUTES EXIST AND THE TABLE WINS ONLY WHERE IT CLAIMS A PATH, which is the single most important convention here and was RECORDED BACKWARDS AT AUTHORING (corrected at review; see F-3 and OQ-01). `cli._DESCRIPTIONS` is a dict keyed by FULL COMMAND PATH, and `cli._apply_descriptions` walks every subparser assigning `_DESCRIPTIONS.get(path)` only when that lookup is truthy. `_build_parser` calls it LAST, after every `add_parser`, so a table entry overrides an inline `description=` FOR A PATH THE TABLE CLAIMS, and does nothing whatsoever for a path it does not. Measured census at HEAD: 94 visited paths are served by the table, 183 carry an inline description only, and 6 (the `upgrade-test` leaves) carry none. The inline kwarg is therefore the MAJORITY convention for a leaf and the table serves mostly parents; OQ-01 chooses inline on that basis.
- AN ARGPARSE ALIAS SHARES ONE PARSER OBJECT, and the table already documents the consequence. The comment above the `show` entry records that `todo` was DELETED as a key because an alias "shares the SAME parser object as its canonical name, so `_apply_descriptions` (which walks every `choices` key) would let whichever alias it visited LAST overwrite the canonical description for all four spellings", and that declaring only the canonical key is "both the smaller change and the correct one". `config`/`conf` is that same situation, which is why this plan writes one key and not two.
- THE CONTRACT IS `len(desc) > len(help)`, NOT MERELY "non-empty". `SubcommandDescriptionTests.test_every_subparser_has_fuller_description` reports three distinct modes: `empty description`, `description not longer than help (N <= M)`, and `description equals help`. `config unset` fails the SECOND, which is why it already has prose and still fails.
- THE CONTRACT'S ORIGIN IS AN EXECUTED PLAN, so this is a regression rather than a new rule. Executed plan `3e70cv` (clianx-01) E-06 gave "every subparser a `description=` (distinct from the short `help=` one-liner)" covering "all 51 subparsers", and its V-06 evidence records the walk passing with "0 problems". The surface has since grown past what that plan covered.
- THE GAP WAS INVISIBLE BY MARKER, not by luck. `tests/test_cli.py` is module-marked `pytestmark = pytest.mark.slow` (its comment: "Heavy subprocess/install suite; excluded from the fast default run"), and `pyproject.toml` `addopts` carries `-m 'not slow and not livecorpus'`. So evidence for this plan needs `-o addopts=""` or `-m slow`. Backlog `xuc9v0` (done) and plan `4petcj` (executed) exist for exactly this invisibility, and `4petcj` added the advisory CI step whose comment names `g0bdgg` among the four owning items.
- A NEW TEST FILE DEFAULTS TO VISIBLE. Executed plan `baxbdh` set the precedent, and pending sibling `g1w58u` restates it: a new file is default-visible and pays the slow mark only where an install is genuinely required. This plan's test needs neither an install nor a subprocess.
- PYTHON 3.14 ARGPARSE COLORIZES `--help`. `tests/test_cli.py::AlphabeticalHelpTests` carries an `_ANSI` strip with the comment that "Python 3.14's argparse colorizes `--help` by default when the output stream is a TTY, so `format_help()` embeds `\x1b[...m` codes".
