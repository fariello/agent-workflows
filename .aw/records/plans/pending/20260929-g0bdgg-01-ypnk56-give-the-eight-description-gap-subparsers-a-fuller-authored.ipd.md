## Project conventions discovered (Step 0)

- THE AUTHORING ROUTE IS A TABLE, NOT A KWARG, and this is the single most important convention here. `cli._DESCRIPTIONS` is a dict keyed by FULL COMMAND PATH, and `cli._apply_descriptions` walks every subparser assigning `_DESCRIPTIONS.get(path)` when truthy. `_build_parser` calls it LAST, after every `add_parser`, so a table entry overrides an inline `description=`. Measured census at HEAD: 94 visited paths are served by the table, 183 by an inline kwarg only. Both routes are live, so the choice is a real decision and is recorded in OQ-01.
- AN ARGPARSE ALIAS SHARES ONE PARSER OBJECT, and the table already documents the consequence. The comment above the `show` entry records that `todo` was DELETED as a key because an alias "shares the SAME parser object as its canonical name, so `_apply_descriptions` (which walks every `choices` key) would let whichever alias it visited LAST overwrite the canonical description for all four spellings", and that declaring only the canonical key is "both the smaller change and the correct one". `config`/`conf` is that same situation, which is why this plan writes one key and not two.
- THE CONTRACT IS `len(desc) > len(help)`, NOT MERELY "non-empty". `SubcommandDescriptionTests.test_every_subparser_has_fuller_description` reports three distinct modes: `empty description`, `description not longer than help (N <= M)`, and `description equals help`. `config unset` fails the SECOND, which is why it already has prose and still fails.
- THE CONTRACT'S ORIGIN IS AN EXECUTED PLAN, so this is a regression rather than a new rule. Executed plan `3e70cv` (clianx-01) E-06 gave "every subparser a `description=` (distinct from the short `help=` one-liner)" covering "all 51 subparsers", and its V-06 evidence records the walk passing with "0 problems". The surface has since grown past what that plan covered.
- THE GAP WAS INVISIBLE BY MARKER, not by luck. `tests/test_cli.py` is module-marked `pytestmark = pytest.mark.slow` (its comment: "Heavy subprocess/install suite; excluded from the fast default run"), and `pyproject.toml` `addopts` carries `-m 'not slow and not livecorpus'`. So evidence for this plan needs `-o addopts=""` or `-m slow`. Backlog `xuc9v0` (done) and plan `4petcj` (executed) exist for exactly this invisibility, and `4petcj` added the advisory CI step whose comment names `g0bdgg` among the four owning items.
- A NEW TEST FILE DEFAULTS TO VISIBLE. Executed plan `baxbdh` set the precedent, and pending sibling `g1w58u` restates it: a new file is default-visible and pays the slow mark only where an install is genuinely required. This plan's test needs neither an install nor a subprocess.
- PYTHON 3.14 ARGPARSE COLORIZES `--help`. `tests/test_cli.py::AlphabeticalHelpTests` carries an `_ANSI` strip with the comment that "Python 3.14's argparse colorizes `--help` by default when the output stream is a TTY, so `format_help()` embeds `\x1b[...m` codes". Any assertion on rendered help must strip first.
- THE COMPLETION GENERATOR WALKS THE SAME TREE. `completion.introspect_cli_tree`'s docstring says it "Models the recursion on `cli._apply_descriptions`", but it reads `help`, not `description` (no `.description` reference exists in `completion.py`), so a description-only change cannot alter a generated completion script. E-05 still runs its tests, because the claim is worth proving rather than asserting.
- `upgrade-test` IS A GRADUATED TOOL with its handlers in `agent_workflows/upgrade_rehearsal.py` (`cmd_list` through `cmd_clean`), dispatched from `cli` by a name-to-handler map. The parent parser has an inline `description=` and an `epilog` of examples; only its LEAVES lack descriptions. Its own `tools/aw_upgrade_test.py` still carries the original `build_parser`, whose top-level description the `cli` parent reuses verbatim.
- A PLAN THAT CHANGES USER-VISIBLE BEHAVIOR ADDS ONE `- Fixed:` LINE to `CHANGELOG.md` `## 2.0.0 (pending)`, and `CONTRIBUTING.md` forbids em and en dashes in user-facing prose. Help text a human reads IS user-facing.
- TESTS MUST ASSERT OBSERVABLE BEHAVIOR, NEVER CODE STRUCTURE: no `inspect`, `ast`, regex, or substring search over production source, and no symbol or key censuses (AGENTS.md execution contract; GUIDING_PRINCIPLES P16).
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Open questions

### OQ-01: Should the seven descriptions be added as `_DESCRIPTIONS` table entries, or as inline `description=` kwargs on each `add_parser` call?

- Blocking: no
- Status: resolved
- Owner: this plan's author
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE, and the question is real rather than rhetorical because BOTH routes are live in the file (94 paths served by the table, 183 by an inline kwarg only, F-3) and the routes are not equal in effect: `_build_parser` calls `_apply_descriptions` LAST, so a table entry OVERRIDES an inline kwarg for the same path. Driven and confirmed by injecting a table value and seeing it win on the leaf. USE THE TABLE, for three reasons that all rest on measured facts rather than taste. FIRST, PRECEDENCE SAFETY: if a later author adds an inline `description=` to one of these `add_parser` calls (the more obvious-looking spelling), an inline-only fix would be SILENTLY OVERRIDDEN by any table key that later claims the path, whereas a table entry cannot be beaten by an inline kwarg. Putting the authored prose on the winning side removes a whole class of silent-no-op regression. SECOND, THE ALIAS COMMENT LIVES IN THE TABLE: the `config`/`conf` hazard that makes this fix seven strings instead of eight is already documented in `_DESCRIPTIONS` (the deleted `todo` key comment), so the reasoning and the code that depends on it stay in one place, which is P8. THIRD, FAMILY LOCALITY: every other `config *` description is already a table key (`config`, `config exclude`, `config exclude add`, `config exclude list`, `config exclude rm`), so an inline `config unset` would split one family across two mechanisms for no gain. THE HONEST COST, stated because it is a real downside and not zero: the prose then sits far from the `add_parser` call it describes, which is precisely the drift risk that let `upgrade-test`'s leaves ship with no description at all. E-04's default-visible guard is the mitigation, since it fails if any of the seven loses its description regardless of which mechanism a future author reaches for. NOTE the parent `upgrade-test` parser keeps its existing inline `description=` untouched: no table key claims that path, it is not among the eight reported defects, and moving it would be unrequested churn.

### OQ-02: Is `config unset`'s existing description wrong, or merely too short, and does the fix therefore replace it or extend it?

- Blocking: no
- Status: resolved
- Owner: this plan's author
- Resolution or deferral rationale: RESOLVED BY DRIVING THE COMMAND. The existing text ("Remove a configuration variable, restoring its default or absent state.") is ACCURATE but 71 characters against an 88-character help, so it fails the `len(desc) > len(help)` contract while stating nothing false. So the fix EXTENDS rather than corrects: keep the accurate core and add the behavior a reader needs. What to add was decided by MEASUREMENT, not plausibility, and that mattered: a natural-sounding draft asserted that `config get` "exits nonzero for an unset variable, so a script can tell unset from empty", which driving REFUTED (F-6): a recognized-but-unset key exits 0 printing nothing, and only an UNRECOGNIZED key exits 2. Shipping that draft would have put a false claim in user-facing help text and invited a script to branch on an exit code that never arrives. The measured facts worth stating instead are that unsetting an absent variable is a no-op rather than an error, that an unrecognized name is refused with exit 2 naming the valid keys, and that the write lands in the same config file `config show` names. This is also why E-03 requires every string to be grounded in a read handler or a driven command: the `upgrade-test` leaves carry the same hazard, since a safety caveat invented from a command's NAME rather than its code would be worse than no caveat at all.
