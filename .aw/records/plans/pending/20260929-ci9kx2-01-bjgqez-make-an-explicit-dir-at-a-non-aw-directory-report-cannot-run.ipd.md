# IPD: Make an explicit --dir at a non-AW directory report cannot-run instead of silent exit 0

- Date: 2026-09-29
- Kind: child
- Concern: `aw attention --dir <a directory that is not an AW project>` prints NOTHING to either stream and exits 0, and `aw ipd board --dir <same>` prints a green `✓ CLEAN  no plans found` and exits 0. Both no-project guidance branches are gated on `not explicit_dir` (`attention.run` and `cli._run_plans`), so passing the flag SKIPS the guidance entirely: the operator who was most explicit about where to look gets the least information, plus a success exit code. Exit 0 asserts "clean, nothing needs attention" about a directory the tool never surveyed, so a wrapper or CI step reading `$?` concludes the board is clean. Measured at HEAD `283b3c92` as finding F-17 of IPD `quqyc4`, which characterized rather than fixed it because changing the guard changes a published exit-code contract and deserved its own scope decision.
- Scope: Make an explicitly named directory that is not an AW project a CANNOT-RUN on both verbs, on every output surface, instead of a silent success. IN: dropping the `not explicit_dir` gate at the two guard sites so the existing no-project branch is reached when `--dir` names a non-project; teaching `no_project_message` to phrase the explicit-`--dir` case (it must say the DIRECTORY GIVEN was checked and NOT suggest `--dir <repo>` as the remedy, which the operator just used); extending the branch to the two surfaces that currently bypass it (`attention --check`, which returns a fail-closed-valid 0, and `ipd board`'s human path, which has no `--check`); and a regression test pinning the whole matrix. OUT: converting the other `resolve_verb_repo_root` callers that take the cwd fallback silently (a separate design question `project_context` explicitly declines to settle), changing the no---`--dir` behavior on either verb, changing the 3-vs-2 human/machine exit-code split, widening `agent_schema` to admit exit 3, and any change to what `is_project_dir` or `find_project_root` count as a project.

## Goal

Make an explicitly named non-AW directory a loud cannot-run on `aw attention` and `aw ipd board`, on every output surface, so a success exit code never asserts "clean" about a tree the tool did not survey. The fix reuses the no-project branch that already exists for the no---`--dir` case; the work is removing the gate that skips it, phrasing the message correctly for an operator who did pass `--dir`, and closing the two surfaces that bypass the branch entirely.

### OQ-01: Should an explicitly named non-project directory exit nonzero, given that changes a published exit-code contract?

- Blocking: no
- Status: resolved
- Owner: executor
- Finding: F-01, F-04, F-07, F-13
- Resolution or deferral rationale: RESOLVED, YES, AND THIS IS THE DECISION THE ITEM DELIBERATELY LEFT OPEN. The item records that `quqyc4` declined the fix because "changing that guard changes WHICH INPUTS produce a cannot-run, i.e. it changes a published exit-code contract (docs/cli-output-contract.md section 3) for a flag that other callers may rely on. That deserves its own scope decision." This plan is that scope decision, so it must be argued rather than assumed.
  THE REPOSITORY'S OWN CONTRACT ALREADY REQUIRES THE NEW BEHAVIOR, which makes this less a contract change than a contract correction. Section 3 assigns 2 to "fatal execution errors preventing domain inspection"; Section 11.4 states handlers "MUST NEVER ... return exit code `0` on fatal failure"; and the Anti-Greenwashing Invariant states a record "MUST NEVER report a positive outcome (`clean`, `ok`, `conforms`) for work that was `skipped`, `partial`, `unverified`, or `cannot-run`". Today's `--check --agent --dir <non-project>` emits `outcome:"clean","verified":true,"exit":0` about a tree it never surveyed (F-07), which violates the last of those outright. The attention spec independently requires `--check` to fail closed with 2 for could-not-run. So the old 0 is not a contract this plan breaks; it is a contract the code was already breaking.
  THE COMPATIBILITY RISK IS REAL BUT NARROW AND MEASURED. F-13 establishes that NO in-tree caller passes `--dir` to either verb (`aw status` reads attention in process, and the only constructed `--dir` in the package belongs to the `gemini` CLI), so nothing inside the repository changes behavior. The exposure is external wrappers, and for those the change is the POINT: a wrapper reading `$?` currently concludes "clean" for a directory that was never surveyed, which is the defect. A wrapper that legitimately wants "tell me if this directory has a board" gets a clearer answer from a nonzero exit plus guidance than from a false 0.
  WHY NOT ASKED OF THE MAINTAINER: the repository answers it. Three published rules and one implemented spec all point the same way, the in-tree blast radius is measured at zero, and the item itself already proposes exit 3 as the LIKELY FIX, so the maintainer's recorded inclination matches. The one judgement embedded here, that correcting a false success is worth a behavior change for external callers, is surfaced plainly in the approval gate so a maintainer can overrule at approval. The item's suggested FLAT 3 is nonetheless corrected to the established 3/2 human/machine pair, because a flat 3 is unemittable on the machine surface (F-04).

### OQ-02: Should the explicit-`--dir` message be a new string, or the existing one reused verbatim?

- Blocking: no
- Status: resolved
- Owner: executor
- Finding: F-06, F-08
- Resolution or deferral rationale: RESOLVED: REUSE THE FUNCTION, CHANGE THE REMEDY SENTENCE, via E-01's `explicit` switch. The item's LIKELY FIX says to "emit the same guidance (naming the DIRECTORY GIVEN, which no_project_message now accepts as a parameter)", and reusing the function is right: the `start_dir` parameter already exists for exactly this purpose, and the git-root install offer already works for an explicit directory (F-08).   THE REPLACEMENT SENTENCE MUST STATE THE NO-CLIMB RULE, and F-06 is why this is substantive rather than cosmetic. An operator who does not know that rule cannot diagnose their own command from a message that only says "no project here". Stating it converts the message from a complaint into a diagnosis. A DEFAULTED keyword is preferred over a second function so the git probe, the verb string and the directory interpolation are not duplicated, and so no existing caller's bytes change.
