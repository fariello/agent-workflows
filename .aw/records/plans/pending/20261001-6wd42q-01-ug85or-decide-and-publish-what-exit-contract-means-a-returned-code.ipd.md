# IPD: Decide and publish what exit_contract means: a returned-code contract that excludes signal-derived codes, pinned by the universal 130 floor

- Date: 2026-10-01
- Kind: child
- Concern: `command_surface.CommandDeclaration.exit_contract` CALLS ITSELF "NORMATIVE" AND NOWHERE SAYS WHAT IT ENUMERATES, SO TWO READINGS ARE BOTH DEFENSIBLE AND THE FIELD CANNOT BE AUDITED. The dataclass docstring reads "Normative contract declaration for a single CLI command or parser leaf" and the field carries no comment of its own. Does it enumerate EVERY integer the process can return, or only the codes the command's own normal return path produces? The question is not academic: the two readings differ on 162 of the 163 declarations, and nothing in the repository picks one. `docs/cli-output-contract.md` Section 3 names the field as "each command's normative declaration" without saying what populates it; no spec under `.aw/records/specs/` mentions `exit_contract` at all; and the three gates that shipped in `tests/test_exit_contract_conformance.py` (executed plan `1mnit8`) each assert MEMBERSHIP of one observed code in the tuple, which is true under both readings and so discriminates neither.
  THE BACKLOG ITEM FRAMES THE QUESTION CORRECTLY AND ITS TWO LOAD-BEARING FACTS BOTH REPRODUCE. Measured at HEAD `95fbd0667`: `oc_runipd.main` and `agy_runipd.main` each return `143 if is_sigterm else 130` from their `except KeyboardInterrupt` arm, both verbs declare `exit_contract=(0, 1, 2)`, and across all 163 declarations ZERO enumerate `130` or `143` (F-01, F-02). The item is also right that answering one way obliges a tree-wide addition while answering the other obliges one sentence where the field is defined, and right that it is LOW RISK.
  BUT THE ITEM'S PREMISE THAT THIS IS A TWO-VERB ASYMMETRY IS FALSE, AND THAT FALSIFICATION IS WHAT DECIDES THE QUESTION. The item says 130/143 "are OBSERVABLE on the two driver verbs", implying the drivers are special. They are not. `cli.main`'s own `except KeyboardInterrupt` arm returns `130`, and `cli.main` is the single entry point every one of the 162 declared leaves reaches (`pyproject.toml` `[project.scripts]` binds all three console names to `agent_workflows.cli:main`). MEASURED BY SIGNAL, not by reading: SIGINT to a real `python3 -m agent_workflows doctor`, `check` and `next` subprocess returned `130` from all three, and an in-process `cli.main` with `_dispatch` patched to raise `KeyboardInterrupt` returned `130` for two different verbs, as did an `EOFError` (F-03). So `130` is a UNIVERSAL FLOOR, reachable on essentially the whole surface, and the "enumerate every reachable integer" reading obliges adding it to 162 declarations, not to two.
  AND THE ITEM'S PAIRING OF 130 WITH 143 IS WRONG IN A WAY THAT MATTERS, BECAUSE THE TWO CODES ARE NOT THE SAME KIND OF THING. On a plain `aw` verb SIGTERM is NOT a returned code at all: the same probe that returned `130` for SIGINT returned `Popen.returncode == -15` for SIGTERM, meaning `WIFSIGNALED`, the process died of the signal, and the `143` an operator sees is the SHELL's `128 + 15` rendering of a death the process never chose (confirmed: `bash -c '... kill -TERM ...; wait'` reports `143` for the same condition `Popen` reports as `-15`). `143` becomes a RETURNED code only where something converts the signal first, which is exactly what the drivers do via `render_stream.install_exit_signal_handler` raising `KeyboardInterrupt("Terminated by SIGTERM")` (measured: with the handler installed a SIGTERM'd process returns `143` with `WIFEXITED`; without it, the identical process reports `-15`). A field enumerating integers the PROCESS returns therefore cannot list `143` for 160 of 162 leaves even in principle (F-04, F-05).
  THE REPOSITORY ALSO ALREADY CONTAINS A COUNTER-EXAMPLE THAT REFUTES "EVERY REACHABLE INTEGER" OUTRIGHT. `aw pwatch` installs its own `signal.signal` handlers raising `SystemExit(0)` and returns **0** on both SIGINT and SIGTERM (measured), while declaring `(0, 1, 2)`. So the signal-derived code is not even constant across the surface: it is `130` almost everywhere, `0` on `pwatch`, `143` on the two drivers under SIGTERM, and not-a-return-code at all elsewhere. A field that claimed to enumerate every reachable integer would have to encode all four shapes, and would still be wrong the moment a verb installed a handler (F-06).
  WHY THE ANSWER IS "RETURNED CODES FROM THE COMMAND'S OWN PATH", AND WHY THAT IS A DECISION THIS PLAN CAN TAKE ON EVIDENCE. Three shipped mechanisms already presuppose it. (1) `agent_schema.validate_agent_record` caps a `result`/`summary`/`error` record's `exit` at `(0, 1, 2)` and `render_jsonl_record` refuses to render otherwise, and the interrupt path emits NO agent record at all (measured: `doctor --agent` and `check --agent` interrupted mid-run exited `130` having written ZERO bytes to stdout), so the exit-parity rule in `docs/cli-output-contract.md` Section 4 has nothing to pair `130` with. (2) All three shipped gates in `tests/test_exit_contract_conformance.py` derive an observed code from a NORMAL invocation (an argparse usage error, a `--help`, a live safe read) and never from a signal. (3) Executed precedent `ck0vya` and pending `u28vqb` both correct a tuple by measuring the verb's own return path. The field is therefore ALREADY a returned-code contract in practice; this plan writes that down and pins it, rather than inventing a new rule (F-07, F-08).
  WHY `chore` AND NOT `bug`, ON THE REPOSITORY'S OWN PERCEPTIBILITY TEST. `AGENTS.md` requires USER-PERCEPTIBLE impact for `bug`. Nothing a user runs produces a wrong answer or waits longer: every signal exit code stays exactly as it is, the declarations change not at all under the adopted answer, and no shipped consumer branches on the field. The harm is to a future auditor who cannot tell what the field promises. The item's `chore` classification is correct and preserved, and no release gate is invented (the item carries none).

### OQ-01: Does `exit_contract` enumerate every integer the process can return, or only the codes the command's own return path produces?

- Blocking: no
- Status: resolved
- Owner: none
