# IPD: Normalize every execution-report cell the run viewer parses, so a backticked verify cell cannot silently lose the [verified] badge

- Date: 2026-09-28
- Kind: child
- Concern: `run_viewer.load_run_summary`'s report-table fallback parse strips backticks for FOUR of the eight columns it reads (id6, Set, Action, Last session) and takes the other four verbatim, then compares the verify cell to the bare string `verified` in `run_viewer.format_step_line` and `run_viewer.render_steps_table`. ## Goal

Make the run viewer's report-table reader treat all eight of its columns alike, so no future producer can silently lose a badge by writing a value in backticks, and so the "keep this column BARE" instruction that two shipped comments give a future author stops being load-bearing. No rendered byte changes for any report a shipped host actually writes: both hosts already emit the verify cell bare, and this plan proves that by measurement rather than assuming it.

## Open questions

### OQ-01: Should the tolerance live at the parse boundary, or should the three comparison sites compare case- and markup-insensitively (the item's second suggestion)?

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE as the PARSE BOUNDARY, and the item's alternative is rejected for a measured reason rather than a stylistic one. There are THREE comparison sites, not one (`format_step_line`'s `verified` badge, its `failed` badge, and `render_steps_table`'s `verified`/`unverified`/`verify-failed`/`failed` mapping), so a comparison-site fix must be written three times and would leave the other three unnormalized columns broken regardless: F-04 measures that `position`, `attempts_count`, `status` and `counts` are ALSO corrupted by the same input, and no amount of tolerance at the verify comparison repairs those. Three copies of a tolerance rule is precisely how the current asymmetry arose, and the repository's two existing precedents both normalize at the READ (`check_engine._identity_declared_values`, `selectors._normalize_yaml_scalar`). Case-insensitivity is separately declined: `verify_disp` is a closed lowercase enum of three values that the runner itself writes (F-11), so no case variant can arrive from a shipped producer, and accepting one would widen what counts as `verified` - the same fail-closed reasoning `runner_shared.normalize_verdict` records when it refuses to accept `VERIFIED: except for the three failures below` as a pass.

### OQ-02: The fallback parse splits on every pipe, so a cell containing a backticked pipe would shift columns. Should this plan adopt the backtick-aware splitter the repository already has?

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED as NO, from the producer's own column vocabulary. `runner_shared.write_report` writes exactly eight cells whose values are a position integer, an id6, a setid, an action token, a status token, one of three `VERIFY_DISP_*` values, an attempt count and a session id - none of which can contain a pipe, and all of which are generated rather than authored. The backtick-aware splitter (`ipd_set_plan._split_table_row`, reached from `runner_shared.child_table_rows`) exists for a genuinely different corpus: HAND-AUTHORED orchestrator child tables, where `setgraph` E-01 measured three live orchestrators containing a backticked pipe and one row splitting into 12 cells instead of 4. Adopting it here would change how every historical report parses in order to defend against a value no producer can emit, which is a wider change with no measured defect behind it - and `child_table_rows`'s own docstring records that `parse_declared_child_orders` was deliberately LEFT on the naive split for exactly this reason (its cell 0 is identical under both, so a plan about something else must not move it). Recorded as a known bound in `## Scope check` rather than silently skipped.
