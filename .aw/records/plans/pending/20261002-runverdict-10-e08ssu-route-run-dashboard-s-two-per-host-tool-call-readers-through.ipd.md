## Goal

Two modules independently encode the same per-host fact: on OpenCode a tool call is a `tool_use` event whose `part.tool` names the tool, whose `part.state.input.command` carries a `bash` command and whose `part.state.status == "error"` marks a failure; on Antigravity it is a `step_update` of `step_type == "tool"` whose `tool_name` names the tool, whose `tool_info.parameters.CommandLine` carries a `run_command` command and whose `state == "ERROR"` marks a failure. `verifier_corroboration.extract_session_commands` holds one copy and `run_dashboard._oc_line`/`_agy_line` hold the other. Nothing signals when one is updated for a new host event shape and the other is not.

This plan makes ONE module own that key knowledge. It does so in the shape the measurements permit rather than the shape backlog `2mjfo7` proposed: a new per-line primitive `tool_call_from_event` in `verifier_corroboration` that classifies one decoded event into a normalized record carrying tool name, host, command text, file path, duration and error flag, with `extract_session_commands` and both dashboard readers driving it from their own existing single pass. The dashboard keeps its aggregation, its token reads and its timestamp bookkeeping; only the per-host key access moves.

The plan also closes the three disagreements the duplication has already produced. They are measured, not predicted: the two modules return different answers today for a whitespace-padded tool name, for a whitespace-only command string, and for two of the four tool names `verifier_corroboration` treats as delegation. Unifying the reader without choosing a single answer for each would preserve the divergence inside one function, which is worse than the duplication because it would then be invisible.
