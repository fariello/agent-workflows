## Project conventions discovered (Step 0)

- A PROBE MUST ATTEMPT, NOT INSPECT, and this module publishes the measured counterexample in its own docstring section "WHY THE PROBE EXECUTES INSTEAD OF INSPECTING": every inspected signal (two sysctls, both binaries present) said "sandbox available" on a host where `unshare -Umr true` actually failed, so inspection would have granted hard mode and failed OPEN. The `HostSandboxCapabilities` docstring states the rule as "A field may only be set True by code that actually executed a probe for it." - AN UNPROBED CAPABILITY CLAIMS NOTHING. Every field on `HostSandboxCapabilities` defaults False, and a capability with no probe reports not-supported WITH THE REASON RECORDED in `probe_notes` rather than supported-by-assumption (`probe_runner_safety_capabilities`, and `_DECLARED_UNENFORCED` for the one field that is deliberately never probed). - THE SIBLING FIX IS THE TEMPLATE, and it is executed: plan `qul11h` (`.aw/records/plans/executed/20260928-plsx3r-01-qul11h-...ipd.md`) fixed the OTHER half of this same identity branch by adding `_probe_session_resume`, wiring it before the platform gate, deleting the identity line, and pinning a true/true/false triple. - RUN THE SUITE BARE. `python3 -m pytest` is already quiet, parallel and fast-scoped via `addopts`; adding `-n0` makes it several times slower, a second `-q` suppresses the very summary line the execution contract requires pasting, and `-p no:randomly` disables the order randomization that surfaces order-dependence bugs.

### OQ-02: Should the probe assert the argv requests a structured stream, assert the renderer parses one, or both?

- Blocking: no
- Status: resolved
- Owner: none

### OQ-03: What is the probe's NEGATIVE control, given that an unparseable line renders a fallback line rather than `None`?

- Blocking: no
- Status: resolved
- Owner: opencode/its_direct/pt3-claude-opus-5-1m-us (reviewer)
- Resolution or deferral rationale: RESOLVED AT REVIEW FROM A DEMONSTRATION, and recorded because the authored answer was wrong and would have inverted the probe. USE A WELL-FORMED NON-TOOL EVENT, and assert the positive case CONTAINS THE TOOL NAME. THE DEMONSTRATION, run against both real renderers at review HEAD `d449f3d2`: an unparseable line returns a DIM FALLBACK LINE from both (`render_agy_event("not json at all", pal)` -> `'  not json at all'`; `render_event("not json at all", pal)` -> `'not json at all'`), because each has a `json.JSONDecodeError` branch that echoes the line rather than returning `None`. A WELL-FORMED NON-TOOL event returns `None` from both (`{"type": "totally_unknown", "part": {}}` and `{"event": "step_update", "step_update": {"state": "DONE", "step_type": "thinking"}}`). The tool lines are `'❯ bash:  {"command": "pytest -q"}'` and `'❯ bash:  pytest -q'`, both containing `bash`, which the junk fallback does not. WHY THE WELL-FORMED CONTROL IS THE RIGHT ONE ON THE MERITS AND NOT MERELY THE ONE THAT WORKS: the capability being probed is SCHEMA AWARENESS (can this host's code turn ITS OWN tool events into something a consumer uses), and a passthrough would echo a well-formed unknown event just as it echoes junk. So `None` on a well-formed non-tool event is exactly the property that separates a parser from a passthrough, whereas junk handling tests only the decoder's error path. ALTERNATIVES REJECTED: (a) asserting the junk line is falsy, which is FALSE for both hosts; (b) asserting merely that the tool event renders non-empty, which the junk fallback also satisfies and which would therefore pass on a host with no schema awareness at all; (c) using the empty string as the control, which does return `None` from both but proves nothing, since returning `None` for no input is not evidence of parsing. REVERSIBLE: yes, the control is a test input and can be changed later at no cost.
