- Concern: The three home-path detection regexes are stated TWICE, character for character, with no shared constant and nothing that fails when one copy drifts. Measured in this lane at HEAD `d248dd5df`: `agent_schema._HOME_PATH_RE` states them as ONE fused alternation, while `leak_sanitizer._FAIL_PATTERNS` states the same three bodies as three separately named rules (`home-path`, `users-path`, `windows-home`). A drift that loosens one leaves the other still passing, so the repository would report clean on exactly the surface that stopped detecting.
- Scope: IN: introduce a single stdlib-only leaf datum module naming the three home-path classes once (pattern body plus the cheap required-substring prefilter each needs), and derive BOTH existing surfaces from it with ZERO change to any pattern byte, any rule name, or any rule ORDER; add a cross-module agreement test that is SENSITIVE to divergence (perturbing the datum must move both derived surfaces together, and a corpus differential must fail if either copy drifts). OUT: the REWRITE patterns on either side, namely `agent_schema._REDACT_WINDOWS_HOME_RE` / `_REDACT_POSIX_HOME_RE` / `_REDACT_USERS_HOME_RE` and `leak_sanitizer._HOME_ANY_RE` / `_USERS_ANY_RE`, whose bodies DELIBERATELY differ from the detectors (they carry capture groups and lookaheads and intentionally drop the placeholder exemptions, because a rewrite must neutralize a path the detector is content to ignore) and which `tests/test_json_surface_leak_posture.py` already pins against the detector; the five NON-home rows of `_FAIL_PATTERNS` (`vc-home`, `private-repo`, `other-account`, `session-id`, `handle`) and their `_REQUIRED_RULE_SUBSTRINGS` entries, which encode maintainer-specific fragments unrelated to home paths; `run_analytics_privacy.pseudonymize_paths`' own path regexes, which pseudonymize rather than detect and answer to a different contract; the per-rule severity model, allowlists, and config gating in `build_ruleset`; and any change to WHICH inputs are detected.

## Goal

Make the three home-path detection classes ONE datum that both leak-detection surfaces derive from, so a future fix to the detection of a home path cannot land on one surface and silently miss the other. The observable behavior of both surfaces is unchanged by construction: this plan removes a drift mode, it does not change what is detected.

## Project conventions discovered (Step 0)

- P8 (single source of truth) is the governing principle, and this repository already applies it to THIS EXACT ENGINE. `agent_workflows/local_leaks.py` exists only as a re-export shim whose docstring says the detection engine was unified into `leak_sanitizer` so every surface keeps working "with ONE code path and no double-reporting (P8, single source of truth)". So unifying a duplicated leak datum is the established move here, not a novel one.
- Both modules are STDLIB ONLY at module scope, which is what makes a shared leaf module safe. `agent_schema` imports only `json`, `os`, `re`, `pathlib`, `typing` and has zero intra-package imports; `leak_sanitizer` imports only `os`, `re`, `socket`, `subprocess`, `sys`, `zipfile`, `dataclasses`, `pathlib` at module scope and DEFERS its `renderers` / `result_types` imports into `main` specifically to avoid a cycle. A new leaf module with no intra-package imports therefore cannot create a cycle for either consumer.
- A module carrying these pattern literals does NOT need a sanitizer exemption, and this is already proven in production rather than assumed. `leak_sanitizer._ALLOWED_PATHS` exempts only `tests/test_packaging.py`, `tests/test_local_leaks.py`, `tests/test_leak_sanitizer.py`, `agent_workflows/local_leaks.py` and `agent_workflows/leak_sanitizer.py`. `agent_workflows/agent_schema.py` is NOT exempt and already carries the fused literal today while the repository scans clean, because the `home-path` rule requires `[A-Za-z0-9._-]+` after `/home/` and a regex literal continues with `(`, which that class cannot match. Confirmed directly: scanning a candidate module body through `build_ruleset` + `scan_text` returned no findings.
- Rule NAMES and rule ORDER are both load-bearing and must survive untouched. The names are pinned by `tests/test_leak_sanitizer.py`, `tests/test_local_leaks.py` and `tests/test_artifact_adopt.py`, consumed as keys by `leak_sanitizer._REQUIRED_RULE_SUBSTRINGS`, and reported to an operator by `run_analytics_export`, which reads `getattr(leak_sanitizer, "_FAIL_PATTERNS", {}).keys()` to say WHICH categories were checked. Order matters because `scan_text` appends findings while iterating `ruleset.fail.items()`, and tests compare ordered finding lists; the three home rules are the FIRST three insertions in `_FAIL_PATTERNS` and must remain so.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Deferred / out of scope (with reason)

- The five rewrite/redaction patterns on both sides (F-07): their bodies differ from the detectors ON PURPOSE and unifying them would change behavior rather than restructure it. Their detector agreement is already pinned by `tests/test_json_surface_leak_posture.py`.
  - Carrier-Declined: This is a SCOPE BOUNDARY, not deferred work, so there is nothing for a carrier to own. These patterns are not copies of the detectors and no drift mode exists between them: they differ by capture group, lookbehind, lookahead, and by deliberately dropping the placeholder exemptions, because a rewrite must neutralize a path a detector is content to ignore. Their agreement with the detector is ALREADY pinned by `HomePathRedactionAgreementTests`, so no coverage gap is being left behind. Unifying them would require changing what gets neutralized, which needs a behavior argument this plan does not make; should a reviewer want that, it is a new plan with its own evidence, not an obligation this one owes.
- The five non-home `_FAIL_PATTERNS` rows and their prefilter entries: they encode maintainer-specific fragments assembled at runtime and have nothing to do with home paths. Folding them into a home-path datum would be a worse grouping than the one that exists.
  - Carrier-Declined: Nothing is outstanding: these rows are CORRECTLY placed where they are and this plan asserts no defect in them. `vc-home`, `private-repo`, `other-account`, `session-id` and `handle` are assembled from maintainer-specific fragments and are not duplicated anywhere, so they are outside the duplication this plan removes. Naming a carrier would record a future obligation that does not exist.
- `run_analytics_privacy.pseudonymize_paths`' path regexes: they pseudonymize for an analytics cache rather than detect for a gate, their own docstring says they are "NOT a substitute for the allowlist", and they intentionally match `~/` paths and a different terminator class.
  - Carrier-Declined: Not a duplicate and not a defect, so no carrier is owed. These patterns answer a DIFFERENT contract (pseudonymize for an analytics cache, never gate a commit), their own docstring disclaims being a substitute for the allowlist, and their bodies differ substantively: they match `~/` paths the detectors ignore and use a different terminator class (`[^\s:,;'\")\]}]+`). Unifying them with a detector datum would break the pseudonymizer's purpose.
- Promoting the shared datum to a PUBLIC (non-underscore) API, or deprecating `agent_schema._HOME_PATH_RE` in favor of it: both are importer-visible changes, and the symbol has out-of-scope importers (`cli`, `run_cli` prose, `tests/test_json_surface_leak_posture.py`, `tests/test_agent_schema_paths.py`). This plan keeps every existing name working.
  - Carrier-Declined: A rejected alternative, not pending work. This plan deliberately keeps every existing name working, so there is no follow-up to schedule: renaming or deprecating `_HOME_PATH_RE` would be a gratuitous importer-visible change with no benefit to the drift mode being closed, and the underscore surface is the correct one for an internal datum two sibling modules share.

## Open questions

### OQ-01: Extract one shared constant, or only add a cross-module agreement test?

- Blocking: no
- Status: resolved
- Owner: plan author
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE: do BOTH, because F-01 makes the refactor half nearly free and F-08 shows neither half is sufficient alone. The backlog item framed this as a refactor traded against a cheaper pin. That trade does not survive measurement. The refactor is NOT the expensive option here, because the duplication is byte-identical (F-01: `rebuilt == fused` -> `True`), so the derivation is a pure string join that changes no pattern byte, no rule name and no rule order, and there is no behavior delta to negotiate. P8 and the `local_leaks` precedent (Step 0) settle the direction: this repository already unified this engine's duplicated surfaces behind one code path for exactly this reason. The test's job in the combined shape is therefore different and worth paying for: it pins the DERIVATION and proves MUTATION SENSITIVITY, rather than restating the patterns.
