# IPD: Record a level-3 checkpoint stop instead of crashing on a missing exit_code, and pin the handler bodies that no test executes

- Date: 2026-09-19
- Kind: child
- Concern: A level-3 stop, the feature whose whole purpose is to wind a run down CLEANLY at an observed safe boundary, CRASHES the runner with an unhandled `AttributeError` instead of recording the stop. MEASURED 2026-09-19 at HEAD `ecdd348f` by running `aw oc run setidfix` and letting a level-3 stop fire: `runner_stop.StopAtCheckpoint` was raised correctly at `oc_runipd.run_opencode`, and the handler for it in `runner_shared.execute_item_core` then died on `attempt["exit_code"] = stop.exit_code` with `AttributeError: 'StopAtCheckpoint' object has no attribute 'exit_code'`.
  THE DEFECT IS A TYPO-CLASS MISTAKE WITH AN OUTSIZED CONSEQUENCE, WHICH IS WHY IT IS WORTH A PLAN. `StopAtCheckpoint.__init__` takes ONLY a `CheckpointObserver` and sets ONLY `self.observer`; its attribute surface is `observer` plus `Exception`'s own.
  AND THE SAME BUG SITS IN THE LEVEL-4 HANDLER TWENTY-ONE LINES ABOVE, which this plan originally asserted was correct. CORRECTED AT REVIEW 2026-09-19 by direct measurement, because the original claim was the plan's load-bearing scope boundary and it is false: `StopNowForce.__init__` takes `level`, `requester`, `events_seen`, `prior_completed_index`, `prior_completed_label` and sets exactly those five. It does NOT set `exit_code`. Measured: `sorted(vars(StopNowForce(level=4, events_seen=3)))` -> `['events_seen', 'level', 'prior_completed_index', 'prior_completed_label', 'requester']`, and `hasattr(..., 'exit_code')` -> `False`. So `runner_shared.py:11921` (`attempt["exit_code"] = stop.exit_code`, in the `except runner_stop.StopNowForce` branch) raises the IDENTICAL `AttributeError: 'StopNowForce' object has no attribute 'exit_code'`. BOTH deliberate-stop paths out of `spawn_executor` are broken, level 3 and level 4, by one copied line each. The fix is therefore two lines, not one, and the level-4 handler is IN SCOPE.
  WHAT THE OPERATOR ACTUALLY LOSES, and it is not merely a stack trace. The crash occurs AFTER `_record_checkpoint_stop` has run but BEFORE `save_state`, so the attempt is left un-persisted: `attempt["disposition"]`, `item["status"]` and the `stopped` record are never written, and the cleanly-stopped item is not marked `interrupted`. So a stop that the machinery correctly identified as safe is recorded as a crash, which is precisely the "fabricated disposition" outcome `runner_stop.deliberate_stop_exit_code` documents itself as existing to avoid. A resume then reads a state file that never learned the item stopped.
  THERE ARE FOUR DELIBERATE-STOP HANDLERS IN `execute_item_core` AND EXACTLY THE TWO SPAWN-PATH ONES ARE BROKEN, a distinction an implementer must not flatten. Enumerated and verified at review: the `spawn_executor` try-block has an `except runner_stop.StopNowForce` (`:11915`) and an `except runner_stop.StopAtCheckpoint` (`:11934`), and each assigns `attempt["exit_code"] = stop.exit_code` (`:11921`, `:11942`) from an exception that has no such attribute. The enclosing verify/reconcile block has its own pair (`:12164` force, `:12174` checkpoint); BOTH of those set `interrupt_reason`, record the stop, set the disposition, reconcile `item["status"]` through `reconcile_disposition(repo, item, run_dir, 1)`, and RE-RAISE, touching `exit_code` NOWHERE. So the verify/reconcile pair is already correct and must be left alone; the fix is to stop the two SPAWN-PATH handlers reading an attribute that does not exist.
  AND NOTHING WOULD HAVE CAUGHT IT, WHICH IS THE HALF WORTH FIXING PROPERLY. `tests/test_runner_stop_level3.py` is substantial and pins the exception's CONSTRUCTION well: it greps that `runner_stop.StopAtCheckpoint` appears in the drivers' source and asserts by REGEX that every raise site passes `checkpoint_observer` and not another object. A regex that proves the raise is well-formed says nothing about whether the catch can run.

## Goal

Make a DELIBERATE STOP do what it says: record the item as stopped with the level-correct disposition, persist that, and let the run wind down, instead of raising `AttributeError` from its own handler. Then close the gap that hid it, by executing the handler bodies in tests rather than asserting on their source text.

READ THE GOAL PRECISELY: this plan does NOT change WHEN a stop fires, WHICH level does what, what either exception carries, or the RUN-level exit code. It removes two impossible attribute reads and adds the coverage that would have caught them. The stop machinery's design is correct; its spawn-path bookkeeping is not.

SCOPE WIDENED AT REVIEW, FROM ONE HANDLER TO TWO. The plan was authored believing only the level-3 handler was broken and that level 4 was the working template it had been miscopied from. Measured, `StopNowForce` has no `exit_code` either, so `runner_shared.py:11921` crashes exactly as `:11942` does and BOTH deliberate-stop paths out of `spawn_executor` are dead. That is a strictly larger and strictly more valuable fix: level 4 is the emergency stop, so its failure mode is worse, and nothing in the suite touches either handler.

## Project conventions discovered (Step 0)

- `StopAtCheckpoint` AND `StopNowForce` CARRY DIFFERENT PAYLOADS, AND NEITHER CARRIES `exit_code`. Corrected at review: `StopAtCheckpoint.__init__(observer)` sets only `self.observer`; `StopNowForce.__init__` sets `level`, `requester`, `events_seen`, `prior_completed_index`, `prior_completed_label`. Measured with `vars()` on real instances. Their docstrings record that levels 3 and 4 share a TERMINATION mechanism and differ only in WHEN it is issued, so the payload difference is intentional and is not drift to be tidied; the `exit_code` reads in both spawn-path handlers are simply reads of nothing.
- `StopAtCheckpoint`'s CONSTRUCTOR NEEDS A REAL OBSERVER. It reads `observer.requested_level` to build its message, so `StopAtCheckpoint(None)` raises inside `__init__` (measured). A test must construct a `CheckpointObserver(detector=..., requested_level=3, ..., stop_at_checkpoint=True)`.
- THE DISPOSITIONS ARE CONSTANTS AND THEY DIFFER BY LEVEL: `runner_stop.STOPPED_DISPOSITION` is `'interrupted'` (level 3) and `runner_stop.FORCED_DISPOSITION` is `'unknown_outcome'` (level 4). Assert against the constants so a rename cannot silently pass, and do not expect the same value at both levels.
- THE RUN-LEVEL EXIT STATUS IS NOT THIS PLAN'S PROBLEM AND IS ALREADY CORRECT. `runner_stop.deliberate_stop_exit_code(statuses, *, success_states, stopped)` takes the WHOLE QUEUE and is called exactly once per host (`oc_runipd.py:6901`, `agy_runipd.py:3648`) with `exit_code_statuses(state["queue"])`. Its docstring's point (items left `queued` are ignored BECAUSE THEY NEVER RAN, spec `c4gd2h` A1/A4 require 0) concerns the RUN's code, not an attempt's. Do not call it per attempt.
- NOTHING READS `attempt["exit_code"]`. Measured at review across `agent_workflows/`: the only occurrences are the two writes this plan deletes. So this is a deletion, not a substitution.
- THE VERIFY/RECONCILE HANDLERS RE-RAISE ON PURPOSE. Both record the stop, reconcile the item's status, and `raise` so the driver's outer `except BaseException` routes to the shared reaper. `StopAtCheckpoint`'s own docstring states that raising is deliberate for exactly this reason (spec R5). Do not convert either to a swallow.
- A GREEN SUITE PROVED THE RAISE, NOT THE CATCH, IN TWO FILES. This is the transferable lesson and the reason E-04 exists: `test_runner_stop_level3.py` and `test_runner_stop_level4.py:749-752` both assert over SOURCE TEXT. Source-text assertions cannot detect a non-existent attribute on an exception, and the SAME defect shipped past both for that reason.
- THE ONE EXISTING END-TO-END STOP TEST REACHES THE WRONG HANDLER. `tests/test_runner_stop.py:922 test_verifier_stop` raises `StopNowForce` only on the verify turn, so it exercises the verify/reconcile handler and passes with both spawn-path handlers broken (verified: `1 passed`). Any new test that can pass without reaching the FIRST turn has reproduced this blind spot rather than closed it.
- BOTH DRIVERS RAISE AND BOTH DELEGATE THE HANDLING. `oc_runipd` and `agy_runipd` each raise `StopAtCheckpoint` and each carry their own thin `except runner_stop.StopAtCheckpoint`, while the substantive handling lives in `runner_shared`. So this is a ONE-PLACE fix that reaches both hosts, and no symbol may be added to `oc_runipd` for agy to import.
