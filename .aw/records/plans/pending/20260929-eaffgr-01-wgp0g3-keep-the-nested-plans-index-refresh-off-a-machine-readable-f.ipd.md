## Goal

Make `aw ipd finalize --json` and `aw ipd finalize --agent` emit ONLY their `aw.agent/v1` payload on stdout, on the success path as well as the refusal path, by having the transaction's fail-loud plans-index refresh derive its verdict from the pure `plans_index.check_drift` function instead of from `plans_index.run_index(check=True)`, whose human print branch has no way to know an outer command is emitting machine-readable output. Secondarily, stop DISCARDING the drift detail that check found: today it goes to stdout and reaches the structured payload nowhere, so a consumer that recovers the payload learns a refresh "did not converge" without learning which manifest or which rule.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- THE CONTRACT THIS BUG VIOLATES IS ALREADY WRITTEN DOWN, which is why this is a defect and not a preference. `docs/cli-output-contract.md` Section 7, "Stream Separation and Broken-Pipe Policy", states that stdout is "Reserved strictly for final structured results (the interactive human view or machine JSONL records)" and that stderr carries "interactive progress indicators, transient status updates". Section 11.2 adds the absolute form: "Progress cues MUST NEVER be written to `stdout`." A nested index verification's progress line is exactly such a cue.
- THE SEVERITY CONVENTION IS SHARED AND MUST NOT BE RE-DERIVED. `artifact_core.drift_exit_code` returns `1 if any(getattr(d, "severity", "") != "info" for d in drift) else 0`, so an `info` finding is advisory and does not fail a gate. `run_index`'s check branch already defers to it in BOTH arms, and its in-code comment records why a hardcoded `return 1` was wrong: a never-generated manifest (`check.stale-index-missing`, severity `info`) failed the gate on the human surface while `--agent` correctly returned 0 on the same tree (plan `yvvf98` E-02). E-01 therefore reuses `drift_exit_code` rather than testing `if drift`, which would resurrect precisely that bug.
- `plans_index.check_drift` IS ALREADY A PUBLIC-BY-USE PURE SEAM. `check_engine` calls it directly (`drift.extend(_pidx.check_drift(repo_root, dirs[0]))`), so consuming it from `ipd_lifecycle` follows an existing pattern. It stamps severities at the emitter via `check_engine.enrich_drift`, and its own comment explains that this is load-bearing rather than tidy: an un-enriched `Drift` carries `severity=""` and `drift_exit_code` fails the gate for anything not `info`.
- THE REFRESH IS SHARED BY TWO TRANSITION PATHS, so this fix lands on both at once. `_finalize_transaction` has exactly two callers, `finalize` and `retire_orchestrator`, and `ipd_lifecycle`'s own comment names `_refresh_plans_index_fail_loud` among the gates deliberately SHARED as code between them ("the gates that can be SHARED are shared as code"). That is the intended direction and needs no per-path work, but it does mean an executor must keep the orchestrator-retirement tests green, not only the finalize ones.
- THE PLANS MANIFESTS ARE GITIGNORED GENERATED VIEWS. `_pre_commit_phase_leaves_manifests_untouched` documents the invariant, and it is why a refresh failure is COMMITTED-INCOMPLETE with a mechanical local remedy (`aw index plans`) rather than a rollback. Nothing in this plan touches that.
- EXISTING TESTS SPY ON `_refresh_plans_index_fail_loud` AND CALL IT DIRECTLY, so its NAME and SIGNATURE are load-bearing. `tests/test_orchestrator_retirement.py` patches it to assert ordering (`["reconcile", "refresh"]`), patches it to raise, counts its calls to prove the rollback path never refreshes, and invokes `LC._refresh_plans_index_fail_loud(self.root)` directly to prepare fixtures. `tests/test_ipd_lifecycle_cli.py` patches it with `side_effect=RuntimeError("index boom")`. Keep the symbol and its `(repo_root: Path) -> None` shape exactly.
- THE SUITE RUNS BARE. `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow'`. Run `python3 -m pytest` with no added flags; use `-o addopts=""` only when per-test counts from a narrowed run are genuinely needed.

## Open questions

### OQ-01: Should the drift detail E-02 folds into the `RuntimeError` also be surfaced as separate structured `diagnostics` entries rather than appended prose?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: NO, append to the message. The structurally purer form is one `Diagnostic` per `Drift` in the payload's `diagnostics` list, and a consumer could then filter by `rule`. It is refused because reaching it means changing how `_finalize_transaction` builds its `FinalizeResult` findings and how `run_finalize` maps them into `Diagnostic` objects, for BOTH transition paths, which is a materially larger and riskier edit than the defect warrants, on the transaction that is the most load-bearing write in the toolkit. Appending to the message puts the information where an operator and a machine consumer both already read it: measured in F-08, `_finalize_transaction` interpolates this exception into the payload's `summary` AND into the `detail` of the `IPD-FINALIZE` diagnostic, so a one-line change in one function reaches both. REVERSIBLE: yes; a later plan can promote the appended text to structured diagnostics without undoing anything here.

### OQ-02: Is losing `plans index --check: clean` from HUMAN finalize output acceptable?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: YES, and it is an improvement rather than a regression, but it is flagged because it is the one change a human will SEE (F-10). The line reports the internal outcome of one step of a transaction whose own final line already reports the transaction's result (`finalized <id6> -> executed at <sha> (actor ...)`); a clean nested check carries no information the success line does not imply. The NON-clean case does not vanish: E-02 moves its content into the refusal message, where it is strictly more visible than a line above a payload. Raised here because a maintainer who relies on that line in a terminal should be able to object at review rather than after execution.

### OQ-03: Should E-02 render every drift finding, or only the ones that drove the nonzero verdict?

- Blocking: no
- Status: resolved
- Owner: reviewer (/plan-review 2026-09-30)
- Resolution or deferral rationale: RESOLVED: render ONLY the findings whose severity is not `info`, filtering with the same predicate `drift_exit_code` uses. Resolved from measurement rather than asked, and recorded as a decision because a reviewer chose it and the authored plan did not consider the question. THE MEASUREMENT THAT FORCED IT: a tree whose manifests were never generated yields two `check.stale-index-missing` findings at severity `'info'` and `drift_exit_code` returns **0**, so a tree can carry advisory findings while converging; on a tree that ALSO has a genuine mismatch, an unfiltered render would list all three and name two paths that are NOT the reason for the refusal. ALTERNATIVES REJECTED. (a) RENDER EVERYTHING, which is what the replaced print did: the print was not explaining a refusal, it was dumping a check's output, so inheriting its set inherits a mismatch between what the message says and why the verb failed. (b) RENDER NOTHING AND POINT AT `aw index plans --check`: that is HEAD's behavior and is the defect E-02 exists to fix (F-08). The chosen filter also keeps the message and the verdict provably consistent, because both read the same field through the same test. REVERSIBLE: yes; a later plan could widen the rendered set without undoing anything here.
