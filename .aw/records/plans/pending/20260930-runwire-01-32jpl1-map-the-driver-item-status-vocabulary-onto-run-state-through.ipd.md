# IPD: Map the driver item status vocabulary onto run_state through one shared translation with no second state machine

- Date: 2026-09-30
- Kind: child
- Concern: The drivers write an item status roughly sixty times and NOTHING ever checks whether the write is a legal transition, because nothing knows which lifecycle position the item is in. `run_state` ships the answer and is unimported: it defines 11 states and NINETEEN legal edges with per-edge authority (enumerated in-process at lane HEAD `cedab274`: `pending->runnable`, `runnable->running`, `running->{performed,blocked,failed}`, `performed->verifying`, `verifying->{verified,correction_required}`, `correction_required->{runnable,pending}`, `failed->runnable`, `blocked->runnable`, `verified->complete`, plus six `*->cancelled`). Both drivers grep ZERO for `run_state`.
  THE MEASUREMENT THAT DECIDES THIS PLAN'S SHAPE, and it inverts the naive reading of the backlog item. `runner_shared.TERMINAL_STATES_CANONICAL` (14 tokens) and `run_state.ALL_STATES` (11 tokens) intersect in exactly ONE token, `failed`. Adding the driver's live tokens (`queued`, `running`, `partial`, `interrupted`, `dependency-blocked`, `failed-safely`) gives a 16-token driver set whose intersection with `run_state.ALL_STATES` is still exactly ONE, `running`. The reason is stated in the repository's own comment above `TERMINAL_STATES_CANONICAL` (the `statusvocab` block): "Every non-`executed` label names the refusing authority". So the driver's tokens are indexed on WHO REFUSED (`fail-gate`, `fail-begin`, `fail-lane`, `fail-verify`, `fail-depend`, `fail-merge`) while `run_state`'s are indexed on WHERE THE ITEM IS. THESE ARE DIFFERENT AXES, so this is a TRANSLATION problem, NOT a rename problem, and a plan that renamed driver tokens to `run_state` tokens would be wrong AND would break five readers.
  WHY A TRANSLATION IS NONETHELESS WELL-DEFINED, since disjoint token sets could equally mean "no mapping exists". Each driver token, though it names an authority, is reached from a KNOWN lifecycle position: `queued` is reached before dispatch and is `run_state`'s `runnable`; the driver's own `running` is `running`; `executed` is the end of a verified item and is `complete`; every `fail-*` token is a refusal recorded from a position the driver knows at the write site. The mapping is therefore many-to-one and total in one direction only (driver -> `run_state`), which is exactly what a check needs and is why this plan builds a one-way translation and NOT a bijection.
  THE COST IS ALREADY DOCUMENTED IN-TREE, which is what makes this a defect rather than tidying. `runner_shared`'s `retrywire` comment records that the driver carries a SECOND implementation of retry semantics while "`run_recovery.plan_retry` / `retry_budget_remaining` REMAIN THE INTENDED LONG-TERM HOME", adding "this repository normally refuses one"; it names the disjoint vocabularies as one of three reasons the shared layer is unreachable ("`plan_retry` raises `NoRetryableStateError` for any step not in `run_state.STATE_FAILED`/`STATE_BLOCKED`, and a driver queue item never holds either value"). Plan `1bfppy` had to decide from scratch which state a rejected verdict belongs in. Plan `fzxfph` measured that `run_state` has no token for three facts it needed and minted four reason codes.
- Scope: Add ONE shared, one-way translation from a driver item status to a `run_state` position in `runner_shared` (the module both hosts already share), and use it at the SINGLE shared persistence funnel to CHECK each status change against `run_state`'s legal transition table, recording the result. REPORT-ONLY: the check records an illegal transition and refuses NOTHING, because the driver's status writes have never been checked and the false-positive rate is unmeasured.
  EXCLUDES, and each exclusion has a measured reason. (1) NO TOKEN RENAMED, REMOVED, OR RE-SPELLED. `TERMINAL_STATES_CANONICAL`, `TERMINAL_STATUS_ALIASES` and `runner_shutdown.KNOWN_ITEM_STATUSES` must be member-identical after this change; `run_viewer`, `runner_shutdown`, `artifact_audit` and the attention mapping all read these tokens. (2) NO REFUSAL. See OQ-01; promoting the check to a gate is a follow-on that needs corpus evidence first. (3) NO LEDGER, NO `run_engine`, NO `run_recovery`. Those are unreachable without a substrate decision this plan is forbidden from taking (parent `i18yaz` OQ-01). (4) NO `verify_roles` WORK. Session independence and verifier authority are sibling Order 02 (`eow7p4`); this plan supplies the POSITION its authority check needs and stops there. (5) NO REQUEUE (`1bfppy` OQ-01).

## Goal

Give the shipped transition table something to check, by translating the driver's item status onto a `run_state` position once, in one place, and recording every illegal transition the drivers attempt - changing no token and refusing nothing.

### Task group 2: the check

- [ ] E-03 CHECK EACH STATUS CHANGE AGAINST `run_state`'s LEGAL TABLE AT THE ONE SHARED PERSISTENCE FUNNEL, recording the verdict on the item. Use `run_state.validate_transition` (the PURE validator returning a result with findings) and NOT `check_transition` (which RAISES): this check is report-only, and calling the raising form would convert a mapping defect into a wedged run.
  SITE IT IN `runner_shared.save_state`, WHICH IS THE ONE FUNNEL AND IS WHY THIS IS ONE EDIT AND NOT SIXTY. Measured: `save_state(run_dir, state)` is called 60 times inside `runner_shared.py`, and each host defines a two-line `save_state` wrapper that delegates to `runner_shared.save_state` supplying `write_report` (`oc_runipd.save_state`; find agy's by NAME). So every driver status write on both hosts passes through this one function with the full `state` in hand. THE REJECTED ALTERNATIVE, recorded because it is the obvious one: instrumenting each `item["status"] = ...` assignment site. Measured at 49 sites in `runner_shared.py` plus 4 in `oc_runipd.py` and 3 in `agy_runipd.py`, it would add per-host copies (the exact re-fork this Set exists to prevent) and would still miss any future site.
  THE PRIOR POSITION MUST COME FROM THE PERSISTED STATE, NOT FROM MEMORY. `save_state` sees the NEW status; the previous one must be read from what was last persisted for that item, so the function needs a per-item record of the last position it observed. Store it ON THE ITEM (a new key), so it survives a driver restart and a `resume`, which read `state.json` back. A module-level cache would be lost on restart and would silently stop checking - the failure mode that leaves wiring "present and inert", which this module's review-integration ladder comment records paying for once already.
  AN UNMAPPED TOKEN IS NOT AN ILLEGAL TRANSITION. When either side translates to `None`, record that the check was SKIPPED and why; do not record a violation. Conflating "no position defined" with "illegal edge" would report violations for every intentionally-unmapped token and destroy the signal this exists to produce.
  A FIRST OBSERVATION IS NOT A TRANSITION EITHER: when an item has no previously observed position, record the initial position and check nothing.
  AN UNCHANGED POSITION IS NOT A TRANSITION. `save_state` is called many times per item with the status unchanged, and `run_state.validate_transition('running', 'running', 'runtime')` returns `ST-ILLEGAL-TRANSITION` (measured at review: the table has no self-edges). So when the new position equals the last observed one, record nothing new and check nothing; otherwise every save would report a violation.
  CHECK REACHABILITY, NOT A SINGLE EDGE. THIS IS THE LOAD-BEARING DECISION (review PR-001, decision D-1). The driver writes a COARSE status sequence: it never writes `performed`, `verifying` or `verified`, so a successful item goes `queued`->`running`->`executed`, which translates to `runnable`->`running`->`complete`, and `running->complete` is NOT a legal edge (measured at review: `validate_transition('running','complete','runtime')` returns `ST-ILLEGAL-TRANSITION`; so do `running->correction_required` for `running`->`fail-verify` and `runnable->blocked` for `queued`->`fail-depend`). A single-edge check would therefore flag every successful item and contradict E-04's inertness property. The honest check for a driver that skips positions it never writes is: a transition is LEGAL when the target is REACHABLE from the source through `run_state`'s legal edges authorized for the actor `runtime` (the driver is the runtime; walk `run_state.get_legal_transitions`, keep the rules whose `authorized_actors` contains `runtime`, and call `run_state.validate_transition` on each hop of the found path so the finding codes stay `run_state`'s). Record the collapsed path (the intermediate positions skipped) on a legal result so a later reader can see how coarse the driver is. A transition is ILLEGAL when no such path exists; measured at review this is exactly leaving `complete` (for example `executed`->`queued`), going from `verified` backward, or entering `cancelled`. Report the illegal result with the `run_state` finding for the direct edge (`ST-TERMINAL-STATE` or `ST-ILLEGAL-TRANSITION`). The search is a few lines over an 11-node, 19-edge table and needs no `run_state` edit (that module is not in Scope-Paths).
  VIOLATIONS ACCUMULATE; THEY ARE NEVER OVERWRITTEN. Keep the last observed position and last verdict on the item, and APPEND each checked-illegal result to a per-item list, so a later legal save cannot erase the evidence OQ-01's promotion decision needs.
  THE CHECK MUST NEVER RAISE AND MUST BE PERSISTED IN THE SAME WRITE. Every driver write on both hosts passes through this function, so a bug here would wedge every run: wrap the whole check so any exception is recorded on the item as a check error and the save proceeds (the precedent is `_verdict_state`'s defensive arm, "never kill a run over a label"). Run the check BEFORE `atomic_write_json`, so the recorded verdict lands in the same `state.json` write as the status it judges. Leave `state["updated_at"]`, the `state.json` write and `write_report` otherwise unchanged.
  - Depends on: E-01
  - Expected outcome: `runner_shared.save_state` translates each queue item's status, skips an unchanged position, checks a changed one by `runtime`-authorized reachability through `run_state`'s legal edges (each hop confirmed with `run_state.validate_transition`), and records one of: checked-legal (with the collapsed path), checked-illegal (with the attempted `source->target` edge and the `run_state` finding code, appended to a per-item list), skipped-unmapped (with which side was unmapped), or initial. The prior position persists on the item so a restart keeps checking. The check cannot raise out of `save_state` and is persisted in the same write. NOTHING is refused and no existing field changes meaning.
