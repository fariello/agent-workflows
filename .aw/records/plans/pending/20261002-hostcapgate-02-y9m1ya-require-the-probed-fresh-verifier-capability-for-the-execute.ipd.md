# IPD: Require the probed fresh-verifier capability for the execute action and prove the refusal is reachable and correct

- Date: 2026-10-02
- Kind: child
- Concern: `supports_fresh_verifier_session` IS PROBED STRICTLY AND REQUIRED BY NOTHING. `host_sandbox_profile.ACTION_CAPABILITY_REQUIREMENTS` contains exactly ONE row, `ACTION_READ_ONLY`, whose `required` tuple is EMPTY, with the spec basis "Nothing this contract represents is required, so a read-only action is never refused by this gate". Verified in-process at lane HEAD `6310b3e4`: `ACTION_CLASSES == ('read_only',)` and `ACTION_CAPABILITY_REQUIREMENTS['read_only'].required == ()`. So the probe runs, produces a correct verdict, and no caller consults it for any mutating action.
  THE PROBE'S OWN DOCSTRING DESCRIBES THE CURRENT STATE AS THE FAILURE IT WAS WRITTEN TO PREVENT. It says the capability is "PROBED by attempt. The probe runs the real fresh-verifier contract twice and requires BOTH that distinct identities finalize AND that a reused identity is REFUSED, because a contract that never refuses enforces no separation while a caller believes verification was independent." That last clause is an exact description of the ACTION PREFLIGHT today: the separation is measured and then not required.
  THE SECOND HALF IS JUST AS EMPTY AND IS WHERE THE GATE ACTUALLY DIES. `runner_shared.RUNNER_ACTION_TO_CONTRACT_ACTION` is `{}` and `runner_action_contract_class` returns `None` for all three runner action names (`execute`, `review`, `plan`), measured in-process. Its comment says so outright: "This mapping is deliberately empty of production rows: it serves as the extension seam that successor plans (b7tlsh/oq05nc) will populate when a mutating action acquires a real capability requirement." So even a non-empty `required` tuple would gate nothing until an action class exists for `execute` and the runner maps onto it. BOTH halves must land together or the change is cosmetic.
  THE BACKLOG ITEM'S STATED BLOCKER IS CLEAR, AND I MEASURED IT RATHER THAN ASSUMING IT. The item says the work includes establishing "that hosts in real use actually pass the probe, or the row turns a working configuration into a refused one". Measured: `_probe_fresh_verifier_session()` returns `True` with the note "fresh-verifier separation enforced: a distinct-identity run finalized and a reused-identity run was REFUSED", and `detect_host_capabilities` reports `supports_fresh_verifier_session=True` for `opencode`, `antigravity` AND `scripted`. The probe is in-process and platform-independent (it drives `agy_verifier.run_fresh_verifier` against a built `verify_roles` packet, touching no kernel feature and no host binary), so it does not fail on macOS or Windows the way the Linux-only sandbox rungs do.
  WHY A ROW IS STILL A REAL POLICY CHANGE DESPITE THAT. A required capability REFUSES an action class on any host whose probe failed, and the refusal is per-item with dependents cascaded. The probe passing HERE is not the same as passing everywhere: it is gated on `plat == running_platform` inside `detect_host_capabilities`, so a descriptor requested for a platform the interpreter is not running on reports False and would refuse every execute item. That is the fail-closed direction, and it is correct, but it is a behavior change an approver must see stated rather than discover in a stalled queue.
- Scope: Make the strictly-probed fresh-verifier capability actually gate the runner's `execute` action, in the two places that each independently nullify it today: add an action class for a mutating execute with `supports_fresh_verifier_session` in its `required` tuple, and populate `RUNNER_ACTION_TO_CONTRACT_ACTION` so the runner's `execute` maps onto it. Then prove the refusal is REACHABLE (a failing probe refuses a real execute item, cascades its dependents and starts no session) and INERT on a passing host (a capable host's queue is byte-unchanged).
  THE ACTION CLASS MUST BE A NEW ONE, NOT `read_only`, and this is settled rather than open. `iot7hc` measured and recorded both reasons: `read_only`'s own `spec_basis` specifies "no agent session for a skip" while execute starts a session and mutates the repository, so the mapping would be a false classification; and `format_host_capability_finding` interpolates the action name verbatim into spec `25kzda`'s byte-exact operator message, so mapping execute onto `read_only` would render "action read_only" for an execute item. Its review recorded this as PR-102 (HIGH) and the plan was rewritten to the empty-mapping seam this plan now fills.
  SCOPE IS DELIBERATELY ONE CAPABILITY AND ONE ACTION. Only `supports_fresh_verifier_session` is required, and only for `execute`. `review` and `plan` keep the no-policy sentinel. The reason is that this capability is the one the backlog item names, it is the one whose probe is strict and passing, and widening to the other spec-listed guarantees would require either requiring `supports_commit_gateway` (declared-never-probed, so it refuses EVERY action on EVERY host) or inventing probes that do not exist.
  EXCLUDES: requiring `supports_commit_gateway` anywhere (it is permanently False by deliberate decision, so requiring it would refuse every execute item on every host); reinstating the `ACTION_REVIEW`/`ACTION_MUTATE`/`ACTION_CONTRACTLESS_PROMPT` constants that `01reg8` deleted on maintainer ruling `4h7tt0` OQ-02 (a new class for execute is not a restoration of those three, and this plan must not be read as reversing that ruling); building any probe; changing the descriptor plumbing (Order 01 owns it); and amending spec `25kzda` 5.2's action table, which is deliberately NOT narrowed and which this plan moves toward rather than changes.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- FAIL CLOSED, AND NEVER INFER A CAPABILITY FROM PRESENCE. `host_sandbox_profile`'s docstring records a measured counterexample and concludes "Inspection MEASURABLY LIES"; `_DECLARED_UNENFORCED` forbids inferring `supports_commit_gateway` from `git_commit_helper.offer_commit`'s existence, because "a helper the driver chooses to call is not a boundary an agent cannot evade".
- AN UNLISTED REQUIREMENT CAN NEVER FAIL, which is why `ActionRequirement.unrepresented` exists and must be filled: "Omitting it would make the action PASS because the requirement was never listed, which is fail-OPEN."
- REFUSALS GO THROUGH `render_stream.record_refusal`, the ONE refusal writer paired with the ONE reader. `iot7hc`'s review (PR-101, HIGH) measured that a bespoke durable key yields disposition `acted_on` with no reason, so the spec's reason code would reach no operator surface. The dispatch block already writes through it; nothing here should add a second writer.
- A REFUSAL MUST CARRY A REMEDY NAMING A POSSIBLE ACT, not just a prohibition: AGENTS.md records the measured failure mode that a prohibition-only gate gets complied with by DELETION.
- AN UNKNOWN ACTION RAISES RATHER THAN DEFAULTING. `UnknownActionError` exists "because guessing which requirement set an unknown action should get is how a mutating action silently receives the read-only policy". Adding a class must not weaken that.
- RUN THE SUITE BARE as `python3 -m pytest`; `addopts` already supplies `-q -n auto --dist=worksteal` and the marker deselection.
