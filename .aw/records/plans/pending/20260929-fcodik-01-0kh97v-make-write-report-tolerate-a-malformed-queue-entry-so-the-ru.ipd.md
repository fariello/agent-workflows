## Goal

Make a run whose `state.json` holds an unreadable queue entry still WRITE its `execution-report.md`, so the closing record of work that actually completed is preserved instead of being lost to an exception. Note precisely what is and is not lost today, measured at review (F-15): `save_state` persists `state.json` BEFORE calling `write_report`, so the durable state survives and the run stays resumable; what is lost is the report, plus whatever the propagating exception costs the caller. This plan restores the report and stops the raise; it does not repair state, because state was never damaged. This is the blocker plan `w7e3e3` deliberately did not fix and explicitly named as the reason it could not claim the closing report was restored (its own Under-scope paragraph cites `fcodik` by id).

THE FIX IS SEVEN GUARDS ACROSS FOUR FUNCTIONS IN TWO MODULES, NOT ONE GUARD. The backlog item names the counting loop, which is genuinely the first statement to raise; but after guarding it the SAME input raises six more times from six other reads, three of them in helpers called near the end of the same function body (F-02). A plan that guarded only the named site would report a fix while `write_report` still wrote nothing, which is the precise failure mode `w7e3e3`'s F-05/F-06 exist to prevent.

THE REPORTING CONTRACT IS THE DECISION THE ITEM LEAVES OPEN, and it is resolved here as COUNT AND RENDER, NEVER SILENTLY OMIT (OQ-01). A skipped row would make `- Counts:` disagree with the queue length and would let a corrupted state file read as a shorter, cleaner run than it was, which is the manufactured-success direction spec `c4gd2h` R22 forbids.

The bytes of every well-formed run's report must not move: each guard adds a branch reachable only by an input that currently raises.

## Project conventions discovered (Step 0)

- THE FAIL-CLOSED / SKIP DIRECTION IS ALREADY DECIDED IN THIS MODULE, by a helper `write_report` itself calls. `runner_shared.render_zero_work_notes` opens its queue loop with `if not isinstance(item, Mapping): continue`, and it is measurably the ONLY one of the four helpers that survives this input (F-04). So E-04 follows an in-tree ruling rather than choosing a policy, and the same reasoning is available verbatim in `runner_shared.no_turn_was_attempted`'s docstring ("a malformed entry (anything that is not a mapping) returns False, since an unreadable entry cannot be shown not to have run").
- CODE IS CITED BY SYMBOL, NOT BY BARE LINE OFFSET (spec `ipd-structure-and-linting` Section 10.2, advisory `IPD-C801`). This bites hard here: `runner_shared.py` is over 37000 lines and the backlog item's own measurement is already stale in its line references. This plan cites `runner_shared.write_report`, `runner_shared.render_transient_dependency_waits`, `runner_shared.format_verifier_evidence_section`, `runner_shared.format_generated_next_actions_section`, `runner_shared.render_zero_work_notes`, `lane_containment.format_preserved_lanes` and `run_viewer.load_run_summary` by name.
- A `runner_shared` RENDERER IS SHARED BY OBJECT IDENTITY, NOT BY COPY. `oc_runipd.write_report` and `agy_runipd.write_report` are three-line wrappers differing only in the injected `labels` (and OpenCode's extra `render_launch_identity`), so one fix in the shared body reaches both hosts and no per-host file enters `- Scope-Paths:`. `tests/test_runner_shared.py` already pins `save_state`'s delegation to each host's own `write_report`.
- THE SUITE RUNS BARE. `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow'`. A second `-q` would suppress the `N passed` line this plan's validation must paste, and `-n0` makes the run several times slower here.
- A NEW TEST FILE IS THE LOCAL CONVENTION FOR A CROSS-MODULE CONTRACT. Sibling plan `cup9r7` (from `3z91mq`) puts its guards' coverage in `tests/test_run_selection_policy.py` because its fence is one module; this plan's fence spans two modules and both hosts, and the repository has many single-contract files of exactly this shape (for example `tests/test_typed_queue_entries.py`, which exists), so E-01 adds one. The OTHER sibling plan, `165lkb` (from `s438xd`, added at review, F-13), independently adds `tests/test_run_summary_malformed_entry.py` for the same reason, which confirms the convention rather than duplicating it: the two file names are distinct and neither plan's fence names the other's test file.

## Open questions

### OQ-01: Should a malformed entry get its own counted status bucket and table row, or be omitted from the report with a stated caveat? The backlog item leaves this explicitly undecided.

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE as COUNT AND RENDER, never omit, and it needs no maintainer ruling because the repository has already ruled on the underlying direction. The item's FIX DIRECTION offers both options ("counted under its own bucket or omitted with a stated caveat"). OMISSION IS REJECTED for three evidenced reasons. FIRST, it makes the report LIE BY ARITHMETIC: `- Counts:` and the table would sum to fewer items than the queue holds, so a corrupted state file would read as a shorter, cleaner run than it was. That is the manufactured-disposition direction spec `c4gd2h` R22 forbids and that `EXIT_MALFORMED_ENTRY_TOKEN`'s own comment was written to avoid ("so it can never be confused with something a driver persists"). SECOND, a distinct bucket is actually AVAILABLE, which is not obvious and was measured: `canonical_terminal_status` passes the token through unchanged (F-07), and the downstream report-table parser accepts it and counts it (F-06), so the honest option costs nothing downstream. THIRD, the "stated caveat" half of the omission option is the weaker form of the same information: a caveat sentence tells a reader that SOMETHING was unreadable, while a counted row tells them HOW MANY and WHERE in the queue. The distinction between COUNTING and SKIPPING is then drawn on evidence rather than taste: the queue-census surfaces (`- Counts:`, the table) MUST account for every entry because their contract is to describe the whole queue, while the four CONDITIONAL sections (dependency blocks, transient waits, verifier evidence, generated actions, preserved lanes) skip it because each is conditional on per-entry evidence a non-mapping entry provably cannot carry, and all of them already document returning `[]` when nothing applies. `render_zero_work_notes` already implements exactly that skip (F-04), so the conditional half of the answer is also an in-tree ruling.

### OQ-02: `write_report` is also called by `save_state` on every state save and by the `report` subcommand, not only on the exit tail. Does that change this plan's fence?

- Blocking: no
- Status: resolved
- Owner: opencode
- Resolution or deferral rationale: RESOLVED as NO CHANGE TO THE FENCE, but a correction to the plan's STATED MOTIVE, which is why it is recorded rather than dropped. The measurement (F-03) shows the item's framing is narrower than the defect: the item describes losing "the closing report", but `runner_shared.save_state` ends with `write_report(run_dir, state)`, so a malformed entry makes every state save raise from the moment it appears, and both hosts' `report` subcommand raises too. The fence does not move because the FIX is the same one either way: all three callers reach the identical shared body, so guarding that body fixes the exit tail, the mid-run saves and the subcommand together, with no additional file and no additional guard. What DOES change is what this plan may claim and what it must test: E-01 therefore asserts the `save_state` path explicitly rather than only the direct call, because a test that exercised only the exit-tail caller would leave the more frequent path unpinned, and the Concern and Goal state the wider blast radius rather than inheriting the item's narrower one. Note this also strengthens the `bug` classification the item already carries: a defect that fires on every save of an affected run, and that makes an operator's explicit `aw oc run report` command fail, is user-perceptible by any reading of the repository's perceptibility test.
