- Concern: `research_cmd.build_frontmatter` interpolates user-supplied values into a `---` fenced YAML block with no validation, and `research_cmd.plan_set_outcome` does the same through `update_frontmatter_fields`, so a newline in a value INJECTS real front-matter keys. Measured in this lane: `aw research new --summary $'legit\nstatus: reference\nblocks-release: next\npriority: high' --apply` exits **0** and writes a doc whose `research_contract.parse_frontmatter` returns `status='reference'`, `blocks-release='next'`, `priority='high'`, with `validate_frontmatter` returning `[]`, `aw check research --agent` reporting `"outcome":"conforms"`, `aw research index --check` reporting clean, and `aw attention --format json` reporting `"native_status":"reference","attention_class":"done","blocks_release":"next"` on a doc nothing promoted and nothing gated. The smuggled gate FUNCTIONS: `aw releases show next` lists the doc under `release-blockers (1)`. The item's own hypothesis that the YAML reader might surface a PARSE ERROR instead is measured FALSE for the key-shaped injection, because `parse_frontmatter` is a line-wise `key: value` splitter, not a YAML library, so an injected `status:` line becomes a real sibling key. Three further values carry the same hole (`--topic` on `new` and `new-comparison`, `--consumed-by` on `set-outcome`, `--date` on `new`), and `aw adopt` inherits all of it by calling `plan_new`.

Guard at the PLANNER (`plan_new`, `plan_new_comparison`, `plan_set_outcome`) rather than at the CLI handler, because `aw adopt` reaches `plan_new` directly and a verb-only guard would leave that path open (F-08). Bounded descriptive fields (`--summary`, and each `--topic` and `--consumed-by` TOKEN) get the full predicate. THE COVERAGE CLAIM IS ENUMERATED, NOT ASSERTED: `--kind`, `--model` and `--priority` already refuse through `normalize_kind`/`normalize_model`/`PRIORITIES`, `--slug` and `--set` are already safe through `R.kebab`, `--order` is an argparse `int`, `--to` on `promote`/`set-outcome`/`set-priority` is already enum-checked, and `add-model`'s tokens already match `^[a-z0-9-]+$`; so `--summary`, `--topic` and `--consumed-by` are the complete unguarded remainder of the research front-matter writer set (F-09). ## Goal

Make every research write path refuse a value that violates the Section 8.8 descriptive-field contract, so a creating or mutating verb cannot manufacture a research record carrying a status, a release gate, or a priority its author never wrote. The severe case is not cosmetic: a `--summary` newline currently writes a `status:` key that WINS `parse_frontmatter`'s last-wins race, so `aw attention` reports a native status nothing set, and a smuggled `blocks-release:` becomes a release blocker `aw releases show next` honors.

## Project conventions discovered (Step 0)

- THE PREDICATE IS ALREADY SHARED AND NEEDS NO CHANGE, so this plan adds CALL SITES only. `attention_contract.is_safe_descriptive` documents itself as "Section 8.8: a descriptive field is a single, bounded, control-char-free line". The defect is that the research write paths consult nothing.
- THE RESEARCH DIALECT IS A HAND-WRITTEN LINE SPLITTER, NOT YAML, and this is the single most important fact for sizing the defect. `research_contract.parse_frontmatter` walks lines between `---` fences, does `key, _, val = line.partition(":")`, and stores into a dict. Consequences: a duplicated key is LAST-WINS (`parse_frontmatter("---\na: 1\na: 2\n---\n")` returns `{'a': '2'}`), a line with no colon is SKIPPED, and `[a, b]` becomes a list. So an injected key is a real key and an injected DUPLICATE OVERRIDES the legitimate value. No YAML library is involved anywhere in this package (no `import yaml`).
- `plan_new` IS A SHARED PLANNER WITH TWO CALLERS, which is why the guard goes there and not in `run_new`. `research_cmd.run_new` is one caller; `artifact_adopt.plan_adoption` is the other, and it is the one that handles UNTRUSTED EXTERNAL TEXT by design.
- THE SIBLING TREE'S FIX IS ALREADY EXECUTED AND IS THE TEMPLATE. Plan `dtg7dz` (Set `a0s33b`, executed 2026-09-29) added `backlog._refuse_unsafe_descriptive`; pending plan `uz05bl` ports it to specs and releases and names THIS plan's backlog item as the carrier for "other trees' creating verbs".
- THE GOVERNING SPEC ALREADY FORBIDS THE OBVIOUS ALTERNATIVE. Spec `attention-registry-and-cross-tree-status` Section 8.8: "embedded newlines are rejected (a violation), not wrapped" and "Over-length values are a contract violation, not silently truncated". So sanitizing, wrapping or truncating at the write path is ruled out and refusal is the specified behavior.
- THE RESEARCH FRONT-MATTER SCHEMA IS SPEC-GOVERNED AND THIS PLAN DOES NOT TOUCH IT. Spec `agents-artifact-organization` Section 5.8 fixes the eleven-field block and calls it "the source of truth"; `research_contract.FRONTMATTER_FIELDS` is that list. A verb-side refusal changes no field, no order and no grammar.
- THE RESEARCH VERBS RETURN ERRORS AS TUPLES, NOT AS STDERR WRITES, which is the refusal shape to reuse: `plan_new` returns `(None, error)`, `plan_set_outcome` returns `(None, None, error)`, and `run_new`/`run_new_comparison` already render an `err` string through `_emit_new_error`'s `CommandResult(status="cannot-run", exit_code=2)` under `--agent`/`--json` and `print(f"error: {err}")` otherwise. So a planner-level refusal is machine-readable here already and needs no new plumbing.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- The suite is run BARE (`python3 -m pytest`); `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow and not livecorpus'`. Do not pass `-n0`, a second `-q`, or `-p no:randomly` (AGENTS.md).

## Open questions

### OQ-01: Should the guard live in the planners (`plan_new` etc.) or in the CLI handlers (`run_new` etc.)?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM MEASUREMENT: the PLANNERS, and this differs deliberately from the sibling `dtg7dz`/`uz05bl` decision to guard at the verb. The reason is that research's planner is NOT verb-private: `artifact_adopt.plan_adoption` calls `_rc.plan_new` directly, so a handler-only guard leaves `aw adopt` open, and F-08 measures `aw adopt` injecting both through its own `--summary` and through an untrusted drop's HEADING with no flag at all. The specs tree has no analogous second caller, which is why its plan could put the guard at the verb and this one cannot. The cost is that the refusal arrives as a tuple error rather than a direct stderr write, and that cost is zero here because both callers ALREADY render a planner `err` through their own machine-readable channel (`_emit_new_error` builds a `cannot-run` envelope under `--agent`, and `plan_adoption` returns `(None, err)` which `run_adopt` emits through `_emit`). Verified by stubbing a planner error and observing `plan_adoption` propagate it verbatim with no edit to `artifact_adopt`.

### OQ-02: Should every guarded value use the bounded mode, given the sibling needed an unbounded line-integrity mode for history messages?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM MEASUREMENT: YES, `bound_length=True` everywhere, because the research tree has no equivalent of the long history message that forced the sibling's asymmetry. ### OQ-03: Should `--slug` and `--set` be guarded too?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM MEASUREMENT: no, and this is a real answer rather than a deferral, because both are ALREADY SAFE BY CONSTRUCTION. Driven: `--slug $'legit\nstatus: active'` exits 0 and writes a file whose name carries the segment `legit-status-active` and whose CONTENT has no injected key, because `plan_new` passes both through `R.kebab` (strip pattern `[^a-z0-9]+`) and writes the kebabed form, never the raw value, into `set:`. ### OQ-04: Should the `--topic` and `--consumed-by` tokens be judged individually or as the joined rendered string?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: INDIVIDUALLY, on two grounds. Mechanically, the joined string is what `build_frontmatter` renders (`"[" + ", ".join(topic) + "]"`), so judging the join would make a 300-character bound a budget shared across every token, meaning adding a harmless fourth topic could retroactively refuse a record whose three existing topics were fine. Measured, the real population has no such pressure (max token length 25, max consumed-by token 6), so a per-token bound refuses nothing legitimate while a shared one introduces a coupling nobody asked for. Diagnostically, a per-token verdict can NAME the offending token, which a joined verdict cannot. The one thing a per-token check does not catch is a joined result that is over-bound while every token is within it; that is a length concern on a field no measured vector exploits, and it belongs with the checker carrier `cvxbbu` which judges the record as written rather than the input as supplied.
