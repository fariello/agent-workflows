# IPD: Make a duplicate aw CLI option definition fail loudly instead of silently replacing

- Date: 2026-09-28
- Kind: child
- Concern: `_AwArgumentParser.__init__` does `kwargs.setdefault("conflict_handler", "resolve")`, which puts EVERY parser in `agent_workflows/cli.py` on argparse's resolve handler. A duplicate option definition therefore SILENTLY REPLACES the earlier one instead of raising, and which definition wins (and so which `dest`, default and help text survive) is invisible at the registration site. This is not a theoretical concern: it already shipped a defect. Executed plan `p0l1to` recorded that declaring `--agent` on a `parents=[common]` subparser EMPTIED the shared repo-wide flag's `option_strings` in place, after which `aw attention` parsed with `agent=True` permanently on and `aw oc profile add --agent build` reported "unrecognized arguments". The workaround was to rename the new flag `--oc-agent`; the handler that made the failure silent was left in place, and `yaxr4i` re-measured it as a live latent hazard (its F-14) and filed this item.
- Scope: Remove the blanket resolve default so a duplicate option definition raises at parser build, and add a durable guard that keeps it removed. IN: the one-line policy change in `_AwArgumentParser.__init__` with its rationale comment, a guard test asserting the error handler is in force across every reachable parser in every builder plus a mutation proving a duplicate now raises, and correction of the one in-tree comment whose stated mechanism the change makes false. OUT: renaming any shipped flag (including reverting `p0l1to`'s `--oc-agent`), any change to what a flag MEANS or to any parser's option set, and the `agy_runipd` comments that discuss `resolve` as a hazard they deliberately avoid (those stay true).

## Goal

Make a duplicate option definition in the `aw` CLI a loud build-time failure instead of a silent replacement, so the class of defect that shipped once as `p0l1to`'s emptied `--agent` cannot recur undetected. The measured cost is one line plus a guard test; the measured risk is zero, because nothing in the tree currently collides.

### OQ-01: Should the blanket `resolve` be removed at all, and does it need a pre-cleanup stage first?

- Blocking: no
- Status: resolved
- Owner: executor
- Finding: F-01, F-02, F-03
- Resolution or deferral rationale: RESOLVED BY MEASUREMENT DURING AUTHORING, BY PERFORMING THE EXACT STEP THE ITEM PRESCRIBED. With no collision to fix, the conditional half of the item's question ("and if so, fix whatever...") has an empty body, and the removal is a one-line change.
  THE DECISION IS YES, ON THREE INDEPENDENT GROUNDS. First, the hazard is not hypothetical: it already shipped a defect that reached a user-visible wrong answer, `aw attention` parsing with `agent=True` permanently on (F-05), and `p0l1to` fixed the symptom by renaming a flag while leaving the silence in place. Third, the change is already proven against the whole suite: `2935 passed, 2 skipped` (F-02).
  WHY THIS WAS NOT SENT TO THE MAINTAINER: the repository answered it. The question is empirical (what is `resolve` hiding, and does removing it break anything), both halves were measured, and the repository execution contract directs an author to resolve from evidence and ask a human only where the repo genuinely cannot answer or the call is theirs. The one JUDGEMENT embedded here, that a duplicate definition should be a hard build-time failure, is the item's own premise and the other six builders' status quo; it is surfaced plainly in the approval gate so a maintainer can still overrule at approval.

### OQ-02: Is a hard build-time failure the right failure mode, given it breaks every command at once?

- Blocking: no
- Status: resolved
- Owner: executor
- Finding: F-05, F-06
- Resolution or deferral rationale: RESOLVED, AND RECORDED BECAUSE THE TRADEOFF IS REAL RATHER THAN OBVIOUS. A duplicate option definition under `error` raises `argparse.ArgumentError` while the parser is being BUILT, and `cli._build_parser()` runs for every invocation, so a collision would break EVERY `aw` command at once instead of just the subcommand that carries it. That is a genuinely worse blast radius per occurrence, and it deserves stating rather than glossing.
  IT IS STILL THE RIGHT MODE, for a reason the two options make plain when compared on DETECTION rather than on blast radius. A build-time raise is immediate, total, local to the offending registration, names the conflicting option string, and cannot reach a user: it fails in the author's own first test run. The alternative is what shipped: a silent replacement that passed review, passed the suite, and was found only when a user hit a wrong `--agent` default (F-05). A loud failure the author sees in seconds is strictly preferable to a silent wrong answer a user finds later, and the item was filed precisely to stop the latter.
  THE BLAST RADIUS IS ALSO BOUNDED BY THE GUARD AND BY THE STATUS QUO. E-02's test builds all seven parsers in CI, so a collision fails a test before it can ship; and the six other builders have always behaved this way, so this is not a new risk class for the package. There is no third option worth holding open: argparse offers only `error` and `resolve`, and a custom handler that logged a warning and resolved anyway would keep the silent-overwrite semantics while adding output nobody reads.
