## Project conventions discovered (Step 0)

- THE REPOSITORY'S MUTATION-SAFETY CONVENTION IS OPT-IN `--apply`, NOT `--dry-run`, which falsifies the backlog item's second proposed isolation strategy outright. Of 78 in-parser mutation leaves, 17 carry `--dry-run`, 22 carry `--apply`, 7 carry only `--yes`, and 32 carry none of the three. `aw ipd scaffold --help` states the polarity plainly: "Dry-run (preview) by default; pass --apply to write." So a harness that appended `--dry-run` would be rejected by most leaves and would silently APPLY on the 32 bare ones.
- `mutation_gate` IS DECLARED AND CONSUMED BY NO PRODUCTION CODE, the same inert-field shape `f36de0` found in `agent_record_kind`. `rg mutation_gate` outside `command_surface.py` returns two hits, both test assertions (`tests/test_prompts_new.py`, `tests/test_host_capability_extension.py`). Its five values (`none`, `dry_run_default`, `confirmation`, `auth_floor`, `policy`) distribute over this universe as 35 / 25 / 12 / 6 / 0, and it does NOT predict drivability: of the eleven broken leaves, four are `none`, five are `dry_run_default` and two are `confirmation`. So E-02 must compute the universe from the class-and-kind predicate and classify the residue by MEASURED blocker, not by gate.
- `aw install . --yes` FULLY BOOTSTRAPS A PROJECT IN A TEMP DIRECTORY, which is what makes the fixture possible at all. Verified: exit 0, and the resulting tree carries `.aw/{config,records,state,system,workflow-artifacts}` plus a `.gitignore` and a committed `AGENTS.md`. It also COMMITS, so the fixture starts from a clean worktree at a known HEAD, which is what lets E-03 assert isolation by comparing `git status --short` and `git rev-parse HEAD`.
- `validate_agent_record` DOES NOT REJECT AN ABSOLUTE PATH, so the schema cannot be the guard against the `storage detach` leak. Verified: a well-formed record carrying `/tmp/.../proj` in `evidence` returns `[]`. The repository's existing precedent is to assert path absence in the TEST, which `f36de0`'s non-project case does for `/home/`.
- STDIN MUST STAY `DEVNULL` OR THE SUITE HANGS. `run_cli` already routes stdin from `DEVNULL`, and `storage init` and `storage attach` prompt for confirmation; with DEVNULL they decline non-interactively and exit 0, which is the behavior under test. `docs/cli-output-contract.md` Section 1.2 names this the asymmetric safety ladder.
- `oc update-models` IS DISPATCHED BY FORWARDED ARGV, NOT BY NAMESPACE, which makes it the one leaf in E-04 whose fix is shaped like `f36de0`'s hook-gate threading rather than like a handler edit. `cli._dispatch` rebuilds a `forwarded` list from selected attributes (`config`, then the truthy subset of `apply`, `dry_run`, `no_backup`, `allow_insecure`) and calls `oc_models.run(forwarded)`; `--agent` is not among them, so the flag cannot reach the handler at all until it is threaded.
- A LEAF'S MODULE IS NOT PREDICTABLE FROM ITS NAME, so E-04's targets were resolved by following each dispatch branch. The two `research` leaves in this universe land in DIFFERENT modules (`research index` -> `research_index.run_index`, `research promote` -> `research_archive.run_promote`), and `normalize-lanes` has no handler function whatsoever, living as an inline branch of `cli._dispatch`. An executor who greps for `_run_<leaf>` will find nothing for three of the eleven.

### OQ-02: Should the fixture give each leaf its own clone, or share one installed project across the arm?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED BY MEASURING BOTH, toward clone-per-leaf. ### OQ-03: Should `storage init` and `storage attach` report `skipped` when a confirmation is declined non-interactively, or should they refuse with `cannot-run`?

- Blocking: no
- Status: resolved
- Owner: none

For `cannot-run` at exit 2: a consumer asked for work that did not occur and arguably needs a nonzero code to notice it, which is what Section 11.4 prescribes for a refusal.
  WHAT DECIDES IT IS E-04's OWN BYTE-IDENTICAL REQUIREMENT, which is not negotiable within this plan: the human path including its EXIT CODE must not change, and these leaves exit 0 for a human today. `cannot-run` at exit 2 would therefore either violate that requirement or introduce a machine-versus-human exit divergence.
