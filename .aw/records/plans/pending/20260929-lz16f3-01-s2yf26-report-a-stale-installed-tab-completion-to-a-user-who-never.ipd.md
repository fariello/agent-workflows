# IPD: Report a stale installed tab-completion to a user who never re-runs aw install or aw setup

- Date: 2026-09-29
- Kind: child
- Concern: An installed completion script is a frozen snapshot that NOTHING in the install or upgrade path regenerates, and the only surface that reports its staleness is reachable from exactly three call sites, all of them install/setup verbs. Measured in this worktree: `cli._completion_tip` is called from `cli._run_install`, `cli._install_all`, and `cli._run_setup` and from nowhere else (`grep -n "_completion_tip(term)" agent_workflows/cli.py` returns three hits, all inside those three functions). So the user who `pip install --upgrade`s and then only ever RUNS `aw` is never told, and that is the most common upgrade path for someone who installed once. Worse, the classifier that could tell them already exists and is already correct: `completion.installed_completion_state` returns `absent`/`current`/`stale` by byte comparison and was measured returning `stale` against this very checkout's installed script, so the missing piece is purely WHERE the question gets asked, not whether it can be answered.
- Scope: Ask the existing staleness question ONCE PER INSTALLED RELEASE VERSION from the one central place every invocation already passes through (`cli.main`), report it on STDERR through the one shared message constant, and add the read-only `aw completion status` verb that gives the notice an executable diagnostic. Gate the probe (not merely the print) behind a per-user stamp, because the probe costs ~50ms and putting that on every command would itself be a user-perceptible-inefficiency defect by this repository's own ruling. Suppress the notice for `__complete`, for the `completion` command family, for non-human output modes, for non-interactive invocations, and for a nonzero exit. EXCLUDES ever rewriting the user's completion file (maintainer ruled warn-only 2026-09-12, OQ-01 of plan `4y95tp`); EXCLUDES any change to `_completion_tip`'s three existing call sites or to its unconditional behavior there; EXCLUDES a runtime callback from the generated script (permanently excluded design constraint); EXCLUDES memoizing `cli._build_parser`; EXCLUDES removing the dead `cli._completion_configured` (see `## Deferred`).

## Goal

Make a stale tab-completion script reportable to the user who actually suffers from it: the one who upgraded the package and never ran `aw install` or `aw setup` again. Achieve it by moving WHERE the existing, already-correct staleness question is asked, not by building a second detector and not by touching the user's file.

The whole plan turns on one measured fact and one consequence. THE FACT: `completion.installed_completion_state` is already right, already read-only, and already returns `stale` for a drifted script, but its only production caller chain (`cli._completion_state` -> `cli._completion_tip`) is invoked from three install/setup functions and nowhere else. THE CONSEQUENCE: the fix is a placement problem, so the risky part is not detection but the blast radius of speaking up on every command. Four choices contain that radius, and each is a deliberate refusal rather than an omission. The notice goes to STDERR, so no command's stdout contract, golden, or `splitlines()` assertion can be perturbed and `source <(aw completion bash)` cannot be fed prose. It fires ONLY when the resolved output mode is human, so `--agent` and `--json` consumers are untouched. It fires ONLY when `term.is_interactive()` says a human is present, so CI, pipes, and the nested `aw` invocations both runners spawn stay silent. And it fires AT MOST ONCE PER INSTALLED RELEASE VERSION, which is what keeps the ~50ms probe off the hot path entirely rather than merely keeping the message quiet.

- THE CONTRACT THAT EXCLUDES THE BACKLOG ITEM'S THIRD OPTION IS A DOCSTRING PLUS A TEST, NOT A SPEC. `completion.py`'s module docstring describes "zero-runtime-dependency" generators that produce "self-contained" scripts, and the exclusion is enforced live by an assertion that greps a generated script for `__complete`, `$(aw `, `$(agentwf `, and backtick-`aw `. Plan `4y95tp` records the reason (interpreter startup on every TAB press, and breakage mid-upgrade) and labels it "A PERMANENT DESIGN CONSTRAINT, not postponed work".
- THE WARN-ONLY RULING IS THE CONSTRAINT THIS PLAN INHERITS UNCHANGED. Maintainer ruling 2026-09-12, recorded as OQ-01 of plan `4y95tp`, verbatim: "`aw install` should check and warn ... or similar", with the plan adding that "a warning asks, a rewrite assumes" and that user-scoped writes need consent. This plan therefore changes only WHERE the question is asked.
- TWO PER-USER SIDECARS ALREADY LIVE BESIDE `config.json` AND ESTABLISH THE PATTERN FOR A THIRD: `runner-profiles.json` via `runner_profiles.store_path` and `local-leaks-hints.json` via `leak_sanitizer.USER_HINTS_FILENAME`, both resolving through `config.config_dir()`. The reason to sit beside rather than inside is recorded in `runner_profiles.store_path`'s own docstring, and it was verified here: `config._ALLOWED_TOP_KEYS` is a five-element frozenset enforced on every load, and a new config key would additionally need an entry in `config.CONFIG_SCHEMA`, so a sidecar avoids four coordinated edits.
- A PROCESS GLOBAL, NOT AN ENVIRONMENT VARIABLE, IS THE HOUSE PATTERN FOR A PER-INVOCATION PRESENTATION DECISION, and `term.py` records why at both `_COLOR_OVERRIDE` and `_INTERACTIVE_OVERRIDE`: this package spawns nested `aw` invocations and an environment variable would be inherited by them. `cli.main` already restores two such globals in a `finally`, and its docstring explains that restoring the INHERITED value rather than `None` is itself a correctness fix.
- `Term` WRITES TO STDOUT BY DEFAULT AND EXACTLY ONE METHOD WRITES STDERR. `Term.__init__` sets `self.stream = stream or sys.stdout`, `Term.line` prints to `self.stream`, and `Term.status` composes `line`, so `status` is a stdout writer; only `Term.step_cue` defaults to `sys.stderr`. A stderr notice therefore requires binding `Term(stream=sys.stderr)` explicitly, and `run_analytics_cli` already does the equivalent by passing an explicit stderr stream to `step_cue`.
- `term.is_interactive` IS THE SINGLE ORIGINATING INTERACTIVITY DECISION and its docstring fixes the precedence as `--no-interactive` > `AW_NONINTERACTIVE`/`CI` > `--interactive` > stream detection, requiring BOTH an interactive stdin and a TTY output stream. Composing it rather than calling `isatty()` is mandatory here; `result_types.py` separately records the retracted claim that non-TTY implies agent mode, so TTY-ness must never be used to infer OUTPUT MODE, only human presence.
- THE COMPLETION TEST STYLE IS A REAL TEMP FILESYSTEM, NOT MOCKS. `_DropInFixture` in `tests/test_completion.py` builds a real temp `HOME` plus `XDG_DATA_HOME`/`XDG_CONFIG_HOME` and states the reason ("so `mkdir(parents=True)`, symlink creation, and the dotfile-untouched assertion exercise actual filesystem behavior"). Staleness is faked by installing for real and then editing the body while KEEPING `INSTALL_SENTINEL` intact, because a file without the sentinel is FOREIGN, a different state. Output is captured with `Term(stream=io.StringIO())`. Table-driven cases carry a trailing "why this row exists" string and accumulate failures into a list asserted equal to `[]` so every row reports.
- THE FILE-UNTOUCHED PROOF HAS AN ESTABLISHED SHAPE worth copying verbatim for E-05: compare both the bytes and the `(st_mtime_ns, st_size)` pair before and after, as the existing stale-warning test does.
- RUN THE SUITE BARE as `python3 -m pytest`; `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow'`. Adding `-q` compounds into `-qq` and suppresses the `N passed` line this plan's validation must paste.

## Proposed changes (ordered, validatable)

1. `completion.py` gains the per-user stamp (`NOTICE_STAMP_FILENAME`, `notice_stamp_path`, `read_notice_stamp`, `write_notice_stamp`), resolving through `config.config_dir()` and failing soft on every read and write error (E-01).
2. `completion.py` gains `notice_version_key()`, reducing `agent_workflows.__version__` to a release-plus-rc key via `versioning.parse_our_version` (E-02).
3. `cli.py` publishes the resolved output mode process-wide from `_dispatch` and restores the inherited value in `main`'s existing `finally` (E-03).
4. `cli.py` promotes the stale-completion wording to one shared constant, renders it from both surfaces, and calls a new six-gate `_maybe_notify_stale_completion` from `main` on the normal return path, probing only after all gates pass and reporting on stderr (E-04).
5. `cli.py` gains the read-only `aw completion status` verb, which writes nothing at all, including the stamp (E-05).
6. `README.md` documents the once-per-version stderr notice, the new verb, the refresh command, the never-rewrites guarantee, and the stamp path; one invalidated test docstring is corrected (E-06).

## Scope check

- Over-scope: none. Every E-item is required by the item's single defect. E-03 looks like unrelated CLI plumbing but is a strict prerequisite: without it the hook cannot tell a human invocation from a machine one, because `select_output` runs inside `_dispatch` and roughly a dozen forwarding paths return before it. E-05 is included rather than deferred because the notice makes a claim ("your script is outdated") that the CLI otherwise offers no way to inspect, and it costs one `choices` token plus one branch with no command-surface declaration change.
- Under-scope: THE NOTICE STILL CANNOT REACH A USER WHO IS NEVER INTERACTIVE. Someone who drives `aw` only from scripts, only with `--agent`/`--json`, or only in CI is deliberately never told, because every alternative is worse: prose on a machine-readable stream corrupts a consumer, and a notice a script cannot act on is noise. This narrows the gap from "never told unless you re-run install or setup" to "told once per version whenever you are at a terminal", which covers the upgrade path the item names as most common but is NOT a complete closure. Stated so a reviewer can weigh it rather than discover it.
- Under-scope: THE STAMP IS PER USER, SO ONE MACHINE SHARED BY TWO ACCOUNTS NOTIFIES EACH SEPARATELY, and a user with several shells is told about the DETECTED shell only. Both follow from existing decisions (`config.config_dir` is per user; `_completion_tip`'s docstring records that scoping to the detected shell exists so a bash user is never warned about zsh) and neither is changed here.
- Under-scope: `_completion_tip`'s THREE EXISTING CALL SITES KEEP WARNING UNCONDITIONALLY, ignoring the stamp. That is deliberate: a user who explicitly runs `aw install` or `aw setup` is asking about their setup and should always get the current answer. The consequence a reviewer should see is that the two surfaces can disagree about whether to SPEAK (never about the FACT, which E-04's shared constant guarantees).

## Open questions

### OQ-01: Should the notice have a first-class opt-out, or is once-per-version-on-stderr-when-interactive quiet enough?

- Blocking: no
- Status: open
- Owner: maintainer
- Carrier-Declined: NOTHING IS LEFT UNFIXED BY ANSWERING THIS EITHER WAY, so there is no defect to hand onward. The question is a matter of CLI-noise taste that only the maintainer can settle, and both answers are reachable without further work: "quiet enough" needs no change at all, and "too noisy" is satisfied by the documented stamp escape hatch or by the one-line kill switch named in the rationale below. A backlog item would assert an outstanding obligation that does not exist.
- Resolution or deferral rationale: RECOMMENDATION, PROCEED WITHOUT ONE. The notice already speaks at most once per installed release version, only when a human is at a terminal, only on stderr, and only after a successful command, so the lifetime cost to a user who ignores it is one line per upgrade. A `config.json` key would need four coordinated edits (`_ALLOWED_TOP_KEYS`, `CONFIG_SCHEMA`, normalize, and the reader) for that. A user who wants silence today can write the current `notice_version_key()` into the stamp, and E-06 documents the path so the escape hatch is discoverable. NOT BLOCKING because this is additive: a key can be added later without changing anything this plan builds. The genuinely maintainer-owned part is taste about CLI noise, which is why it is recorded rather than decided unilaterally; if the answer is "too noisy", the one-line kill switch is to stop calling the hook from `cli.main`, leaving the stamp, the verb, and the shared constant useful on their own.

### OQ-02: Should `aw doctor` also report completion staleness?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: NO, RESOLVED FROM REPOSITORY EVIDENCE rather than deferred. `aw doctor` is REPO-SCOPED (it resolves a `repo_root` and every probe takes it) while completion is a per-user, per-machine concern, so a per-user fact would be reported once per repo inspected, which is the exact once-per-repo duplication `_completion_tip`'s docstring already says to avoid. Adding a sixth probe would also cost a new dataclass, a new report field, a call site, an evidence entry, and a human-render section. `aw completion status` (E-05) is the right home because it is already host-scoped, and `aw host` establishes the precedent for a non-repo surface. Recorded because "put it in doctor" is the obvious first guess and a reviewer deserves the reason it was rejected.
