## Spec / documentation sync

`selectors.py`'s PRECEDENCE COMMENT BLOCK (`:52-58`) is the authoritative prose on what each match kind means and must gain a statement that tier 1 is a CANDIDATE FILTER which never changes the winner, and WHY (citing the frozen-precedence proof). Without that, the next reader will either reorder `_PRECEDENCE` and silently change which record wins, or extend the filter to kinds where it is pure overhead.

The filter's superset-only property must be stated AT THE CODE as an invariant, not left implicit: it may only remove files that cannot match; the union with the runtime-computed non-conforming-name set is what makes that true; and the records whose declared identity is absent from their bounded header are the standing counterexample. Record that the exception set is COMPUTED and must never become a hardcoded list (F-18), and that the token is matched against the WHOLE FILENAME rather than the parsed identity slot because `parse_clustered` reports `id6='assess'` for a legacy name whose real Id is `wvlk84` (F-16). Those sentences are what stop a future change from turning an optimization into a correctness bug.

`_read_setid` must carry a note that its backtick-bearing return value is PINNED by a characterization test and why: normalizing it flips `aw find research awoptimize` from four substring matches to one setid match, so the fix belongs at Order 02's report-only comparison site, not here (F-15). `_iter_paths`'s docstring already records that the text-free and text-bearing walks stay identical by construction; extend it to note the filter consumes it, so the relationship is findable from either end.

## Open questions

### OQ-01: Should tier 1 be a candidate filter or a precedence change?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: A CANDIDATE FILTER, decided by the proof the item itself inherited. `PrecedenceForcesFrontMatterReadsTests` demonstrates that `stem` and `substring` cannot be answered without first eliminating `setid` and `status`, both of which live in front matter, because one token can legitimately be both a Set id and a filename fragment. Reordering `_PRECEDENCE` would therefore change which record wins for existing queries, which is a matching-behavior change the item explicitly says needs sign-off. The filter shape captures most of the speed (it reduces how many files are opened) while leaving the winner determined by the frozen order, so it needs no sign-off and cannot silently change an answer. The cost is that the theoretical "zero opens" target is unreachable, which the item already recorded as unreachable anyway.

### OQ-02: May the filter ever remove a file that would have matched?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: NEVER; IT IS A SUPERSET-ONLY FILTER AND THIS IS A CORRECTNESS INVARIANT, not a quality goal. The nine records whose declared identity is absent from their filename are the standing counterexample: for an `id6` query, filtering by filename would drop `lus9ou`'s legacy-named plan and `25kzda`'s grandfathered spec, and the latter is cited constantly, so the tool would start failing on its most-referenced spec. E-03 therefore requires the filter either to be SKIPPED for kinds where a body-only match is possible, or to union filename candidates with a body pass over the exception set. E-05's corpus-wide differential is what proves the invariant held, and a hand-picked sample is explicitly insufficient.

### OQ-03: What if the display layer, not the resolver, dominates the cost?

- Blocking: yes
- Status: open
- Owner: maintainer
- Finding: PR-001
- Resolution or deferral rationale: MEASURED AT REVIEW, AND THE ANSWER IS YES: THE DISPLAY LAYER AND INTERPRETER STARTUP BOTH DOMINATE, SO THE FACTUAL QUESTION IS CLOSED AND WHAT REMAINS IS A PRIORITY DECISION ONLY THE MAINTAINER MAY MAKE. Decomposition of a ~450ms `aw find plans <id6>`: interpreter start plus `import agent_workflows.cli` ~115ms; resolver TOTAL ~42.5ms, of which traversal is ~29.5ms and IRREDUCIBLE by a filename filter; display `plans_index.scan_plans` ~113.6ms, re-reading all 616 records the resolver just read. The NET prize this plan can win is ~12.8ms, about 3% of the wait, while the display layer alone is 8.9x that and interpreter startup 9x. F-13 narrows it further: only the `id6` kind can benefit at all.
  WHY THIS IS NOW BLOCKING RATHER THAN AN EXECUTOR'S JUDGEMENT CALL. The plan authored this non-blocking on the premise that "the resolver improvement is real and safe regardless", and the safety half still holds. But the numbers invert the premise's second half: the plan's own Concern and Goal are performance claims, and at ~3% they no longer justify a change to the ONE resolver every verb and all ten record types route through (F-19). Executing it would spend a matching-engine change plus a corpus-wide differential to buy an improvement an operator cannot perceive. That is a scope-and-priority trade the maintainer owns, not the executor, so the plan must stop here rather than let an executor infer consent from a non-blocking flag.
  THE DECISION REQUIRED, in plain terms. Choose one: (A) EXECUTE AS NARROWED, accepting ~12.8ms for the correctness value that comes with it (the E-01 contract pins, the E-04 characterization test, and the F-16 discriminator hazard documented in code); (B) RE-SCOPE onto the real cost, a follow-up plan that stops the display layer re-reading the 616 records the resolver already read, which is ~114ms and roughly 9x this plan's prize; or (C) DEFER to `not-executed`, keeping only the correctness items as a small separate plan. E-02 carries an explicit abort condition so that even under (A) the executor cannot report a user-visible speedup that the measurement does not support.
  A NOTE ON (B), so it is not mistaken for a free win: the two readers are not trivially unifiable. `plans_index` and the resolver DELIBERATELY DISAGREE on 24 records, documented at `selectors.py:112-120`, where `_STATUS_RE`'s single-token `(\S+)` is called a matching-behavior CONTRACT that must not be "harmonized" without owning the change.
