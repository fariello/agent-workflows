# IPD: make a nested aw in a lane run the runner's own tooling, not the lane branch copy

- Date: 2026-08-29
- Kind: child
- Concern: Under worktree isolation the runner invokes nested `aw` with `cwd` set to the lane worktree and the command `[sys.executable, "-m", "agent_workflows", ...]`. Python prepends the cwd to `sys.path` for `-m`, so `agent_workflows` resolves to the LANE BRANCH's checked-out copy. A lane that legitimately edits `agent_workflows/` therefore has the runner execute that unreviewed, possibly mid-edit code to perform the very transition meant to gate it. PRECISION (review): this affects the nested invocations that actually run with the lane as cwd, which is `driver_finalize` and the `run_checked` helpers; `driver_begin` runs with `cwd=str(repo)` before any lane exists and is NOT affected. The original claim that "every lifecycle fix is void inside a lane" is overbroad; see the orchestrator `y0gg8o` for the owning correction.
- Scope: Pin every runner-spawned nested `aw` invocation to the tooling the RUNNER itself is running, in both drivers, and add a guard so the hijack cannot recur. Behavior of the nested verbs is unchanged; only which code implements them changes. Includes repairing the EXISTING half-pin in `run_checked` (measured inert) and explicitly classifying the bare-`aw` console-script fallbacks (measured immune), so exactly one definition of the pin exists and the guard tells the truth about every launch site. Excludes the host-agent `Popen` (the agent turn SHOULD run in the lane) and excludes any change to lane allocation or teardown.

## Goal

Make the tool the runner invokes be the tool the runner IS. Today a nested `aw` inside a lane silently runs the lane branch's version of the lifecycle machinery against the real repository, so a fix can be verified green in `main` and still not apply where it matters, and two lanes in one run can enforce different lifecycle rules depending on their base commits.

## Open questions

### OQ-01: `-P` / `PYTHONSAFEPATH` versus passing `--dir` and running from the main repo

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: CORRECTED AT REVIEW. The original resolution ("prefer `-P`") is INSUFFICIENT, not merely a preference: measured, `-P` alone resolves to the DEFAULT-PATH copy, which equals the runner's own only on an editable install, so a `-P`-only fix would silently run third-party code on a normal wheel install. The resolution is the TWO-PART POSITIVE PIN: `-P` (or `PYTHONSAFEPATH=1` on an interpreter without it) to remove the `''` cwd entry, PLUS the runner's own package root prepended to the child `PYTHONPATH` to select the runner's copy. Measured: neither part alone works, both together do (see Project conventions for all four combinations). The `--dir`-everywhere alternative remains rejected for the original reason: it fixes only the verbs that expose the flag and must be re-applied to every future call site, whereas the argv+env pin fixes one choke point and is guard-enforceable. `PYTHONSAFEPATH=1` is REQUIRED as a fallback, not optional, because `-P` needs 3.11 while `requires-python = ">=3.9"` and CI runs 3.9-3.14; the executor must state which mechanism shipped on which interpreters and evidence the fallback's equivalence on the floor version.

### OQ-02: Should a mismatch be fatal to the whole run or only to the item?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RUN-FATAL. Resolved at review rather than left to the maintainer, because the spec already classifies it and the repo already has the disposition vocabulary, so this is a reading of existing policy rather than a fresh risk appetite call. Spec `25kzda` section 1.4/A1 reserves `ABORT RUN` for repository-wide identity/type-ambiguity and integrity classes, and a tool-identity mismatch is definitionally one: it means the control plane executing EVERY item's lifecycle transition is not the code the runner believes it is, so the fault is not attributable to the item that happened to trigger the probe. Quarantining the item would be actively misleading, marking one item blocked while the remaining items continue to run under the same wrong control plane. Contrast with the item-local `dependency-blocked` disposition (oc_runipd.py:78), which is correct precisely because a dependency fault IS item-scoped. E-04 therefore aborts the run with a named diagnostic and a ledger record. If a maintainer later wants a softer posture, that is a change to spec `25kzda`, not an executor choice.
