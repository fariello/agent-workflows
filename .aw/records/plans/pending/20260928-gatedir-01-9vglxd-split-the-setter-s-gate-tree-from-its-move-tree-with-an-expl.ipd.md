## Goal

Let a caller of `aw backlog set --status done` state, in argv, that the item's file moves in one tree while its release gate is decided in another; and use that to make the runner's in-lane close gate against MAIN, which is what its own code comments already claim it does.

WHAT THIS GOAL DELIBERATELY DOES NOT CLAIM, because the distinction decides how it is validated. It does not make any release gate STRICTER in its rules: the three arms (HANDOFF, SATISFIED, DE-GATED) and their verdicts are untouched, and `check_engine.evaluate_blocking_close` keeps the signature it has. What changes is only WHICH tree a caller can point the existing predicate at. One observable consequence is nonetheless a tightening and must be stated plainly rather than discovered in review: after this plan a lane close that today passes on the lane's own view of its carriers will be decided against main, so an item with an unexecuted SIBLING carrier stops being closable from a lane. That is the defect being fixed, not a side effect, and E-06 proves the runner's ordinary single-carrier close still succeeds so the tightening does not become a regression.

## Project conventions discovered (Step 0)

- ONE SHARED PREDICATE BACKS THE SETTER, `aw check` AND THE HOOK, AND THAT IS DELIBERATE. `backlog.run_set`'s comment above the gate call says the predicate is "the SINGLE shared authority ... used by the setter, `aw check`, and the child-03 hook so they cannot diverge", and `AGENTS.md` states the same. This plan therefore changes only WHICH root is passed in, never the predicate, which is also why the backlog item calls the area high blast radius.
- THE `--status` SPELLING IS THE GATED ONE AND THE POSITIONAL SPELLING IS NOT. `close_backlog_item`'s docstring records this at length ("do not 'simplify' it back to the positional spelling") and it is measurable: `aw backlog set done <item>` exits 0 on a gated item with an unexecuted carrier and moves the file, because `cli.py` forks on whether `--status` was passed and routes the positional form to `status_set.run_set_command`, which never calls the predicate. Already filed as `mawwlc` and `le31pr`; named here so an executor does not mistake it for something this plan introduced or should fix.
- A SPECIFIC KNOB OVERRIDING A GENERAL ONE ALREADY HAS A SHIPPED SHAPE IN THIS REPO: `comms_acks._resolve_comms_dir` takes `--repo-root` and `--comms-dir` and returns the specific one when present, else derives from the general one. `--gate-dir` follows it. Note `--companion-dir` is NOT the precedent: that names a different repository, not a second view of the same one.
- THE TWO-TREE CONCEPT IS ALREADY MODELLED AT THE API LAYER, just not expressible through the setter's argv: `process_backlog_close` carries `repo` versus `write_repo`, records `"wrote_in": "lane" if isolated else "main"` on the queue item, and annotates the eligibility call "`repo`, never `write_repo`". This plan closes the gap between that model and the CLI.
- CONTROL STATE COLLAPSES TO THE CHECKOUT BUT RECORDS DO NOT. `ipd_lifecycle.checkout_control_root` deliberately maps every linked worktree's receipts, locks and journals to the main tree's `.aw`, while `backlog._resolve_backlog_root(repo_root)` and `check_engine._iter_plan_ipds(repo_root)` compose `repo_root/".aw"/records/...` directly and so DO see the lane's own records. That asymmetry is why a lane's view of a carrier's bucket differs from main's at all, and an executor must not "fix" this plan by routing records through `checkout_control_root`.

## Open questions

### OQ-01: Should `set_records.close_on_answer` get the same split, since it has the identical one-root coupling?

- Blocking: no
- Status: resolved
- Owner: reviewer
- Resolution or deferral rationale: RESOLVED AGAINST, from repository evidence, and recorded because a reviewer scanning for completeness will find the site and should see it was priced rather than missed. `close_on_answer(repo_root, backlog_path)` calls `evaluate_blocking_close(repo_root, ...)` and then moves the item under `_backlog._resolve_backlog_root(repo_root)`, so it has exactly the defect this plan fixes in `run_set` (F-09). It is nonetheless not worth fixing here for three reasons in descending strength. FIRST, IT HAS NO SECOND TREE: the function takes one `repo_root`, and its callers (the question-promotion path) have no lane concept, so a `gate_root` parameter would be dead surface with no caller to exercise it and no test that could do more than assert a default. SECOND, UNEXERCISED SURFACE IS WHERE DIVERGENCE COMES FROM, which is the failure mode this repository keeps hitting and the reason the close predicate is shared in the first place; a second untested split is a second place for the two roots to drift. THIRD, THE RISK IT WOULD MITIGATE IS NOT PRESENT: the permissive direction F-02 measures requires a lane-shaped tree, and nothing calls this function from a lane. Non-blocking because the fix is additive and the shape is established by E-03/E-04, so a future lane-side caller copies it in one change. THE HONEST COST OF THE DEFAULT: the repository keeps two instances of one coupling, and a reader of `close_on_answer` gets no hint that the question was considered, which F-09 exists to remedy.

### OQ-02: Should the `backlog_blocking_close_gate` pre-commit hook take a gate root too?

- Blocking: no
- Status: resolved
- Owner: reviewer
- Resolution or deferral rationale: RESOLVED AGAINST, and the reasoning is different from OQ-01's rather than the same argument reused. The hook's root is NEITHER knob: `check()` falls back to `Path(".")` and `main()` calls it with no argument, while `engine.create_backlog_close_gate_hook` generates the entry with `pass_filenames: false` / `always_run: true` and no `--dir` (F-10). THE COUPLING IS VACUOUS THERE, because pre-commit runs hooks with cwd at the repository root, so the move tree and the gate tree are necessarily the same tree and there is no split to express. Adding a knob would therefore change nothing observable while adding a way to misconfigure a gate. WHAT A REVIEWER SHOULD WEIGH AGAINST THIS, stated because it is a real gap this plan is choosing not to close: the hook has NO dedicated test (a grep of `tests/` for `backlog_blocking_close_gate` finds only a completion-classification assertion), so its behavior rests entirely on the rule it delegates to being tested. That is defensible for a three-line delegation and it is not nothing. It is recorded in F-10 rather than filed as an item, because filing one would assert a coverage gap with no measured defect behind it, and the portable authority for this rule is `aw check` plus CI rather than the local hook in any case. Non-blocking because nothing in E-03 through E-07 forecloses either a knob or a test later.

### OQ-03: Should `--gate-dir` become MANDATORY for the runner's in-lane close, or should gating against main become the default for every caller?

- Blocking: no
- Status: resolved
- Owner: reviewer
- Resolution or deferral rationale: RESOLVED AS AN OPT-IN KNOB WITH ONE OPTED-IN CALLER, which is the conservative half of a genuine design choice and a reviewer may legitimately want the other half. THE CASE FOR AN OPT-IN DEFAULT. A default that changed which tree the gate reads would change the verdict for EVERY caller at once, including `aw check`'s commit-scoped rule and the pre-commit hook, neither of which has a second tree to name, and F-08 measures that a naive main-side gate REFUSES the ordinary single-carrier lane close unless the citation is chosen correctly. Shipping that as a default is how you get the "would refuse EVERY close, forever, and would do so silently" outcome `evaluate_backlog_close`'s own docstring describes from the other side. So the knob defaults to `--dir` and exactly one caller opts in, under E-06's proof. THE CASE A REVIEWER MIGHT MAKE FOR THE OTHER ANSWER, stated fairly: an opt-in fix leaves the permissive arm reachable by anyone who passes `--dir <lane>` and forgets `--gate-dir`, which is precisely the mistake the runner made for months, and a knob that must be remembered is weaker than a default that cannot be forgotten. That is a real objection and the Scope check records it as deliberate under-scope. Non-blocking because the two are additive: a later plan can flip the default once E-06 has established what the ordinary close needs, whereas flipping it now would be changing a shipped gate's verdict on an unmeasured population.
