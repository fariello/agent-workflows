## Goal

Let a caller of `aw backlog set --status done` state, in argv, that the item's file moves in one tree while its release gate is decided in another; and use that to make the runner's in-lane close gate against MAIN, which is what its own code comments already claim it does.

WHAT THIS GOAL DELIBERATELY DOES NOT CLAIM, because the distinction decides how it is validated. It does not make any release gate STRICTER in its rules: the three arms (HANDOFF, SATISFIED, DE-GATED) and their verdicts are untouched, and `check_engine.evaluate_blocking_close` keeps the signature it has. What changes is only WHICH tree a caller can point the existing predicate at. One observable consequence is nonetheless a tightening and must be stated plainly rather than discovered in review: after this plan a lane close that today passes on the lane's own view of its carriers will be decided against main, so an item with an unexecuted SIBLING carrier stops being closable from a lane. That is the defect being fixed, not a side effect, and E-06 proves the runner's ordinary single-carrier close still succeeds so the tightening does not become a regression.

## Project conventions discovered (Step 0)

- ONE SHARED PREDICATE BACKS THE SETTER, `aw check` AND THE HOOK, AND THAT IS DELIBERATE. `backlog.run_set`'s comment above the gate call says the predicate is "the SINGLE shared authority ... used by the setter, `aw check`, and the child-03 hook so they cannot diverge", and `AGENTS.md` states the same. This plan therefore changes only WHICH root is passed in, never the predicate, which is also why the backlog item calls the area high blast radius.
- THE `--status` SPELLING IS THE GATED ONE AND THE POSITIONAL SPELLING IS NOT. `close_backlog_item`'s docstring records this at length ("do not 'simplify' it back to the positional spelling") and it is measurable: `aw backlog set done <item>` exits 0 on a gated item with an unexecuted carrier and moves the file, because `cli.py` forks on whether `--status` was passed and routes the positional form to `status_set.run_set_command`, which never calls the predicate. Already filed as `mawwlc` and `le31pr`; named here so an executor does not mistake it for something this plan introduced or should fix.
- A SPECIFIC KNOB OVERRIDING A GENERAL ONE ALREADY HAS A SHIPPED SHAPE IN THIS REPO: `comms_acks._resolve_comms_dir` takes `--repo-root` and `--comms-dir` and returns the specific one when present, else derives from the general one. `--gate-dir` follows it. Note `--companion-dir` is NOT the precedent: that names a different repository, not a second view of the same one.
- THE TWO-TREE CONCEPT IS ALREADY MODELLED AT THE API LAYER, just not expressible through the setter's argv: `process_backlog_close` carries `repo` versus `write_repo`, records `"wrote_in": "lane" if isolated else "main"` on the queue item, and annotates the eligibility call "`repo`, never `write_repo`". This plan closes the gap between that model and the CLI.
- CONTROL STATE COLLAPSES TO THE CHECKOUT BUT RECORDS DO NOT. `ipd_lifecycle.checkout_control_root` deliberately maps every linked worktree's receipts, locks and journals to the main tree's `.aw`, while `backlog._resolve_backlog_root(repo_root)` and `check_engine._iter_plan_ipds(repo_root)` compose `repo_root/".aw"/records/...` directly and so DO see the lane's own records. That asymmetry is why a lane's view of a carrier's bucket differs from main's at all, and an executor must not "fix" this plan by routing records through `checkout_control_root`.
- CITE CODE BY SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
