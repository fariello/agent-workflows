# IPD: Anchor the lane owner record on the checkout so an in-lane read cannot report a claimed lane unclaimed

- Date: 2026-10-01
- Kind: child
- Concern: Backlog `voxbcx` measured that two neighbouring state stores under `.aw/` anchor DIFFERENTLY. `ipd_lifecycle.receipt_dir` routes through `ipd_lifecycle.checkout_control_root` (which derives the main worktree from `git rev-parse --git-common-dir`), so a begin receipt written from a lane worktree lands in the ONE shared control store; that was deliberate, fixed under backlog `dh0uno`, whose docstring records the measured defect it closed ("an inner `aw` running inside a lane wrote its receipt/lock/journal to `<lane>/.aw/state/...` - a second control store the driver ... could not see and lane teardown then deleted"). `worktree_lease._owner_record_path` composes `repo_root / OWNERS_SUBDIR / "<lane>.json"` from the PASSED root with no such anchoring, so the same inner-`aw` invocation reads an empty store.

So a caller asking from the wrong anchor does not get an error, it gets the affirmative answer "this lane is unclaimed" - which is exactly the answer the `zwnjp3` E-08 liveness gate exists to PREVENT when a LIVE process owns the lane. Measured at authoring HEAD `faf47d81a` on a purpose-built checkout with a genuinely live third-party owner process (F-2): from the main checkout `lane_is_safe_to_adopt` returns `(False, 'owner pid <N> on <host> is LIVE')` and `lane_owned_by_other_live_process` returns `True`; from inside the lane the SAME two calls return `(True, 'no owner record; unclaimed')` and `False`. The gate inverts.
  THE ITEM'S `chore` CLASSIFICATION AND ITS NO-AFFECTED-CALLER CLAIM BOTH SURVIVE CHECKING, and this plan does not inflate them. The item says the claim "is the part most worth re-checking before acting" because it came from reading call sites rather than exhaustive execution; re-checked at authoring (F-4), every production consumer of an owner record still runs from the main checkout, and the ONE user-facing surface that reaches an owner read from a cwd-derived root (`aw <host> run integrate <id6>`, whose `--repo` defaults to `.`) is additionally protected TODAY by an unrelated accident: with the default `repository` records backend the lane's own runs root does not exist, so `iter_run_states(lane)` returns 0 states against 344 from the main tree and the verb refuses with "no recorded lane" BEFORE reaching the owner check. That accident is NOT a designed guard and does not hold for every configuration (F-5), which is why the item is worth fixing rather than closing, but it IS why no user is harmed today and why `chore` is the right kind.
- Scope: Remove the anchoring asymmetry the item measured, by routing the owner-record path through the SAME checkout anchor `receipt_dir` already uses, and make the "absent" versus "unreachable" distinction representable so the gate cannot silently answer "unclaimed" about a store it could not read. IN: anchoring `worktree_lease._owner_record_path` on the checkout; a behavioral regression test that drives a real `git worktree` and pins that the owner-record and liveness answers are IDENTICAL from the main tree and from inside the lane. ## Goal

Make the lane ownership store answer the SAME question identically no matter which worktree of a checkout asks it, so the `zwnjp3` E-08 liveness gate cannot be inverted by the caller's cwd, and so a store that cannot be read is never reported as a store with nothing in it.

Concretely, two changes to `agent_workflows/worktree_lease.py`:

1. `_owner_record_path` resolves against the CHECKOUT (the anchor `ipd_lifecycle.receipt_dir` already uses) instead of against the passed root, so `read_lane_owner`, `write_lane_owner`, `clear_lane_owner`, `lane_is_safe_to_adopt` and `lane_owned_by_other_live_process` all reach the one real store.
2. `lane_is_safe_to_adopt` stops treating an UNREACHABLE store as an empty one, so the distinction between "nothing claims this lane" and "I could not read the claim" is representable rather than collapsed into the adoptable answer.

READ THE SECOND HALF AS LOAD-BEARING, NOT AS A REFINEMENT. Anchoring alone would fix the one wrong path this item measured and would leave the failure CLASS open: `read_lane_owner` returns `None` for an unreadable record exactly as it does for an absent one, so any future wrong-anchor or permission failure still produces the affirmative "unclaimed". The item's own candidate (3) names this, and it is the half that makes the fix durable.

## Project conventions discovered (Step 0)

- THE CHECKOUT ANCHOR ALREADY EXISTS AND IS THE DECIDED ANSWER FOR THIS CLASS. `ipd_lifecycle.checkout_control_root` is "the single place that decides where that root lives, so a linked `git worktree` (a driver 'lane') and the main tree resolve to the SAME location", and its docstring records the measured defect that motivated it under `dh0uno`. Reuse it; do not write a second resolver.
- IT IS DELIBERATELY TOTAL, not raising, because its callers "were PURE path composition before `dh0uno`" and are called from loops and from error-message formatting; the docstring singles out `release_finalize_lock` running from a `finally:` as the case that matters most.
