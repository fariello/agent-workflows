- Kind: child

## Goal

Give the runner a STRUCTURED path to a refused finalize's findings, so the retryable/terminal classification keys on lint CODES rather than on diagnostic prose, and so a reworded `ipd_lint` message can no longer silently change which refusals are handed back to the agent. The change is confined to the ONE shared `driver_finalize` and the ONE shared classifier, so both hosts inherit it without a per-host edit.

- THE CLASSIFIER IS A POSITIVE ALLOWLIST AND MUST STAY ONE. `runner_shared.finalize_refusal_is_retryable` documents itself "FAIL-CLOSED IN BOTH DIRECTIONS", and both arms require EVERY finding line to be allowlisted, because spec `25kzda` Section 5.5 puts out-of-scope mutation first on its never-retry list and a rule matching ANY retryable finding would retry it. Every change here preserves that shape: an unrecognized code makes the message NOT retryable.
- THE HOST MUST NOT BE IMPORTED BY SHARED CODE. `runner_shared`'s docstring prohibits importing a runner, which is why `driver_finalize` takes `env_builder`/`argv_builder`/`labels` as injected parameters. E-01 adds no import and no new parameter.
- FINDING IDS ARE ALREADY NAMED AS CONSTANTS where a caller needs to branch. `ipd_lifecycle.FINDING_RECEIPT_NEVER_ISSUED`, `FINDING_RECEIPT_ALREADY_FINALIZED`, `FINDING_RECEIPT_STALE`, `FINDING_SCOPE_REDUCED_INVARIANT` and `FINDING_CONTRACT_REWRITE` exist precisely "so no one has to match refusal PROSE". The lint codes have the same shape as module constants in `ipd_lint` (`C_CHECKPOINT`, `C_EXEC_STATE`, `C_VALID_STATE`, `C_CROSS_STATE`), so this plan consumes existing names rather than minting new vocabulary.

## Open questions

### OQ-01: Should `driver_finalize` return the typed payload, or should the classifier re-derive structure from the message?

- Blocking: no
- Status: resolved
- Owner: opencode its_direct/pt3-claude-opus-5-1m-us
- Resolution or deferral rationale: RESOLVED FROM MEASUREMENT: the classifier re-derives, and `driver_finalize` keeps returning `tuple[int, str]`. The tempting design is to widen the return to `(rc, msg, payload)` or a NamedTuple so the structure flows forward explicitly. It is refused on blast radius, not on taste. F-16 enumerates six consumer families of `(fin_rc, fin_msg)` (`finalize_outcome`, `handle_finalize_refusal`, `finalize_retry_decision`, `finalize_with_lock_reattempts`, both execute-path arms, and `render_stream`'s legacy `finalize_refusal` reader), and F-15 measures that `_call_driver_finalize` calls `inspect.signature` on the function and that a test stub pins its current arity, so a widened contract forces coordinated edits across all of them plus their tests, inside a plan whose point is a two-file classifier fix. What makes the cheap route CORRECT rather than merely cheaper is F-04: the human message is a byte-exact serialization of the payload (`prefix + summary`, then `  {rule} {detail}` per diagnostic), verified by reconstructing it from real `--json` output and getting an exact match. So the code tokens the classifier needs are present in the message, and requesting `--json` in E-01 is what GUARANTEES they are present and well-formed rather than incidentally so. REVERSIBLE: yes, and it does not foreclose widening the contract later if a second consumer ever needs the payload.

### OQ-02: Should the code-keyed arm REPLACE the prose allowlist, or sit in front of it as the primary with prose as a fallback?

- Blocking: no
- Status: resolved
- Owner: opencode its_direct/pt3-claude-opus-5-1m-us
- Resolution or deferral rationale: RESOLVED: CODE FIRST, PROSE RETAINED AS FALLBACK, and the fallback is not timidity. Two measured reasons. FIRST, not every finding line carries a lint code: `finalize_precheck` emits its OWN strings for the receipt arms (`FINDING_RECEIPT_NEVER_ISSUED`, `FINDING_RECEIPT_STALE`, the reduction and rewrite invariants) with no `IPD-S4xx` token at all, so a code-ONLY rule would have to decide what to do with a codeless line; keeping prose as the fallback means such a line is judged exactly as it is today and the fail-closed direction is unchanged. SECOND, deleting the prose allowlist would delete the thing `test_the_allowlist_texts_are_the_ones_ipd_lint_ACTUALLY_EMITS` pins (F-10), and that test is genuinely useful: it is what would catch `ipd_lint` emitting a pre-transition diagnostic nobody classified. The composition is therefore strictly more permissive than prose alone in exactly one direction (a recognized code is admitted even if its wording changed) and never less, which is what closes F-02 without widening any never-retry class. E-04's total-coverage pin is what stops the fallback from becoming a silent hiding place for a new code. REVERSIBLE: yes.
