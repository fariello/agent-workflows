## Goal

Make the absence of a plan-to-spec edge VISIBLE at the moment it is introduced, and make it FIXABLE with a tool, so that spec acceptance-criteria coverage becomes computable for the specs that need it most instead of being silently unreportable.

Two halves, and the second is what makes the first legitimate. The DETECTOR (`check.plan-spec-link-missing`, `info`, PENDING-SCOPED) flags a plan in a `pending/` lane that cites a resolvable spec id6 in its `- Concern:`, `- Scope:`, or `- Scope-Paths:` front matter while carrying no `- From-Spec:`. The SETTER (`aw ipd set ... --from-spec <id6>`) gives that finding an executable recovery, closing the gap AGENTS.md names outright: "there is no `--from-spec` setter yet: write the field when authoring the plan."

WHY PENDING-SCOPED AND NOT COMMIT-SCOPED, since this reverses the authored design and the reversal is the point (review finding PR-501). An `info` finding from a COMMIT-SCOPED rule is observable by NOBODY, measured rather than argued. Its firing window is exactly the interval between `git add` and `git commit`: `check_status_untooled`'s mechanism fast-returns `[]` when nothing is staged under plans, so the rule is silent before staging and silent forever after the commit lands. Inside that window there are exactly three consumers and all three drop it. (1) `work_cmd._validate_plan_via_engine` (`work_cmd._validate_plan_via_engine`, whose body reads `continue  # advisory nudge, dropped silently`) `continue`s on `severity == "info"` with the comment "advisory nudge, dropped silently", so `aw commit` never prints it. (2) `check_commit_invariants` (`check_engine.check_commit_invariants`) composes exactly three named rules and the new one is not among them, so the pre-commit hook never reaches it. (3) CI runs `aw check plans` on a CLEAN tree (the `aw check plans (plan conformance; fail closed)` step in `.github/workflows/tests.yml`) where nothing is staged, so the rule fast-returns `[]`. A rule nobody can observe is worse than no rule, because it costs the code and the tests while delivering nothing. PENDING-SCOPING keeps F-03's unactionability fix intact (a terminal plan is never examined, so the 87 findings AGENTS.md forbids acting on never appear) while making the finding visible on EVERY `aw check plans` run for as long as the plan sits in `pending/`. The precedent to copy is therefore `check_ipd_draft_ready` (`check_engine.check_ipd_draft_ready`, whose body reads `if "pending" not in p.parts: continue`), the repository's other `info`-severity plan nudge, NOT `check_status_untooled`, which is `error`-severity and whose consumers exist precisely because an `error` blocks a commit. Measured equivalence of the live surface: the pending-scoped predicate reports the SAME 5 plans the commit-scoped one would have reported had anyone been able to see it.

## Project conventions discovered (Step 0)

- ADVISORY SEVERITY IS A DESIGN TOOL WITH AN EXACT MEANING, and `info` is the only non-failing tier. `artifact_core.drift_exit_code` returns 1 for any finding whose `severity` is not exactly `info`, so `warning` would fail the gate precisely as `error` does. The `check.spec-criteria-uncovered` registry comment states this outright and calls its own severity "load-bearing", adding that registration is not bookkeeping because an unregistered id falls back to `_DEFAULT_RULESPEC` at `error`. This plan's rule is a necessary-not-sufficient heuristic, so it must be `info` and must be registered.
- THE REPOSITORY HAS TWO ESTABLISHED ANSWERS TO "THE CORPUS IS FULL OF OLD VIOLATIONS", AND THE CORRECT ONE IS CHOSEN BY SEVERITY, NOT BY RECENCY. `check_status_untooled` COMMIT-SCOPES ("ONLY files changed in the commit are examined, so historical records are never touched") and is registered `error`, which is why it has consumers: an `error` refuses a commit, so the stage-to-commit window is exactly when it must speak. `check_ipd_draft_ready` instead scopes to `pending/` (`if "pending" not in p.parts: continue`) and is registered `info`, because an advisory nudge needs to be READABLE over the life of the artifact rather than blocking at one instant. This plan's rule is `info`, so it takes the second precedent. Choosing the first would have produced the invisible rule F-10 measures.
- THE KNOWN-SPEC-ID SET HAS ONE CORRECT CONSTRUCTION AND IT IS A UNION OF TWO AUTHORITIES. `check_from_spec_dangling`'s docstring records that `_iter_spec_records` walks the in-tree trees while `specs._existing_spec_ids` resolves through `record_producers.resolve_record_read_paths`, which in an externally-redirected project resolves OUTSIDE the repo; it reports verifying on a scratch repo that `_existing_spec_ids` was EMPTY while an in-tree spec plainly existed. Either source alone yields false positives on some real layout.
- `GUIDING_PRINCIPLES` P8 FORBIDS A SECOND MECHANISM FOR AN EXISTING QUESTION, and `check_from_spec_dangling` cites it by name ("a second mechanism for 'which spec ids exist' is precisely the drift GUIDING_PRINCIPLES P8 forbids"). Hence E-03 takes the id set as a parameter, E-02 reaches it through the same helper E-04 uses, and E-01 adds a field writer beside its twin rather than a parallel one.
- A TWIN IS A PRECEDENT FOR SHAPE, NOT A GUARANTEE OF CORRECTNESS, which is the lesson of findings F-11 and F-13. `releases.py` contains FIVE single-line metadata writers and they do NOT agree: `set_priority_line`/`set_work_kind_line` use `[^\n]*` and say so ("Tolerates any value so an existing malformed line is still replaced"), while `set_from_backlog_line`/`set_blocks_release_line` use `\S+` and duplicate the field on an empty value. `set_item_dependencies_line` documents choosing DIFFERENTLY from its siblings on anchor. So "mirror the twin exactly" is an unsafe instruction in this module; each axis (anchor, clearing, value tolerance, validation) must be chosen on its own evidence, which is what E-01 and E-02 now do.
- A SENTINEL VALUE IS NOT A LINK. `ipd_schema.source_link_is_absent` treats `None`, empty, and the absent sentinels (`-`, `none`, `unresolved`) as absent after stripping quotes; `check_spec_criteria_uncovered` already routes its `From-Spec` read through it. A rule reading the raw regex group alone would treat `- From-Spec: -` as a satisfied edge.
- TEST OUTCOMES, NOT CODE STRUCTURE (AGENTS.md, `GUIDING_PRINCIPLES` P16). Every test this plan adds drives a real function or a real CLI over a real temporary repository and asserts on returned findings, written file content, and exit codes. No test may read production source with `inspect`, `ast`, regex, or substring search, and none may assert a symbol census or a line count.
