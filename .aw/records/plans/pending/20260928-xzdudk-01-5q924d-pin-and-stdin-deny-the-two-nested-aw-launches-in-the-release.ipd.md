## Goal

Make the two release-readiness gates that shell out execute the release-review operator's OWN `agent_workflows` unconditionally, instead of whatever package happens to sit in the `repo_root` they were handed, and deny their children a terminal. Leave behind a test that fails if either the pin or the stdin denial is dropped, since the two guards that used to cover this class were deleted from the suite and nothing replaced them. No gate semantics change: a release verdict computed on a correct tree before this plan is identical after it.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`). The backlog item cites `release_readiness.py:158` and `:179`; both still resolve correctly at this HEAD, but this plan cites `release_readiness.gate_leak_scan` and `release_readiness.gate_ipd_lint` by name.
- THE SUITE RUNS BARE. `pyproject.toml` `addopts` supplies `-q -n auto --dist=worksteal -m 'not slow'`, so `python3 -m pytest` with no added flags is the contract. Do not add `-n0`, a second `-q` (which would suppress the `N passed` line this plan's validation requires), or `-p no:randomly`. Use `-o addopts=""` when per-test counts are genuinely needed.
- THE CANONICAL PIN HELPERS LIVE IN `runner_shared`, not in a driver: `runner_shared.pinned_child_env` and `runner_shared.pinned_module_argv`, under the section header `# ---- rununify: tool identity & child pinning ----`. `oc_runipd` and `agy_runipd` merely re-export them, so importing from either driver would make one host a de-facto library; `release_readiness` must import from `runner_shared`.
- THE DRIVERS INJECT THE HELPERS RATHER THAN IMPORTING THEM, via `env_builder=` / `argv_builder=` parameters on their shared `run_checked` wrappers, because `runner_shared` cannot import a host. That constraint does not apply here: `release_readiness` is a leaf module that nothing in the package imports, so a direct module-scope import is the simpler correct form and introduces no cycle (F-08).
- NO IMPORT CYCLE AND NO MEANINGFUL IMPORT COST. `runner_shared` does not reference `release_readiness` anywhere, and importing both together succeeds. `runner_shared` is a 36,346-line module costing about 70ms to import on top of `release_readiness`'s own 83ms; that is paid once per release-review invocation by a human-run gate that already spends about 1.2s per subprocess gate, so it is not user-perceptible (F-09).
- A SOURCE-READING GUARD IS THE WRONG SHAPE BY EXPLICIT PRECEDENT. Commit `80db6750` deleted 366 tests because they "read production SOURCE - parsing it with ast, reading `__file__`, or substring-searching it" and "None of them exercises the code". The deleted `tests/test_nested_tty_noninteractive.py` guard was exactly that shape, which is also why it never saw these two sites (they pass an inline list literal, and it matched on the first argument being NAMED `argv` or `cmd`). E-01's guard calls the gates instead.
- PYTHON 3.9 IS THE FLOOR (`requires-python = ">=3.9"`). `pinned_module_argv` already handles the version split internally (it adds `-P` only on 3.11+), so E-02 adds no version-sensitive construct; verified by parsing the patched module with `ast.parse(..., feature_version=(3, 9))`.
