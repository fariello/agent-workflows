# IPD: Make aw ipd lint --all <root> resolve a root instead of crashing, and stop it false-passing a repo it cannot see

- Date: 2026-09-29
- Kind: child
- Concern: `aw ipd lint --all <root>` crashes. `cli._build_parser` declares the positional as `nargs="*"`, so it arrives as a LIST, and `ipd_lint.run_lint`'s `--all` arm does `root = Path(getattr(args, "path", None) or ".")` on it. The `TypeError` is swallowed by that function's catch-all and surfaces as `error: lint failed to run: argument should be a str or an os.PathLike object where __fspath__ returns a str, not 'list'` at exit 2. The bare `--all` case works only because an empty list is falsy and `"."` is substituted, which is why the defect shipped: the documented default is the ONLY path exercised. BUT FIXING THE CRASH ALONE LEAVES A WORSE DEFECT STANDING, and that is this plan's central finding. Repair the `Path()` call and `--all <root>` stops crashing and starts SILENTLY REPORTING `error=0` AT EXIT 0 for a repository whose plans it never read, because `_iter_plan_files` resolves its base through `record_producers.resolve_record_path("plans", target_repo=str(root))`, whose `records_backend` for an unconfigured target repo defaults to `home` and returns a path under the CALLER'S `~/.aw/projects/<handle>/records/plans` that does not exist. Measured: a target repo containing one structurally-broken plan at `.aw/records/plans/pending/bad.md` yields `_iter_plan_files` = `[]`. A crash is loud and costs a human one confused minute; a clean exit 0 over zero files is a FALSE PASS, and spec `ipd-structure-and-linting` Section 10 states in terms that "The tool MUST distinguish a conforming result from inability to run. An internal failure MUST never be reported as a passing lint."
- Scope: Three changes to the `--all` arm of `ipd_lint.run_lint` plus the one helper it calls, and the regression tests that reach them THROUGH argparse rather than around it. IN: (1) accept the list, taking its single element, and REFUSE 2+ roots as `cannot-run`/exit 2 naming the count, following the shipped `artifact_adopt` precedent; (2) give `_iter_plan_files` an IN-TREE FALLBACK rung so a root whose resolved records base does not exist still finds `<root>/.aw/records/plans`, which is what converts the false pass into a real result; (3) REFUSE a root that is not a directory, and refuse a root under which no plans tree exists at all, rather than counting zero files as clean. Also IN: the `--all` help text, which currently promises "a repo root with --all" and is the documented behavior that does not work. OUT: the `nargs="*"` declaration itself (changing it is a CLI surface change with no defect behind it), `record_producers.resolve_record_path` and `project_context.resolve_project_context` (the `home` default is correct for their own callers and is not a defect), the non-`--all` multi-file arm (it handles the list correctly already), and the pre-existing `error=1` in this repository's own corpus.

## Goal

Make the one documented way to lint a repository other than the current directory actually lint it: `aw ipd lint --all <root>` must read `<root>`'s plans and report on them, refuse clearly when it cannot, and never report a pass for a tree it did not read.

Equally: close the false pass, not merely the crash. The item asks for a one-line repair (take the first list element). That repair is necessary and insufficient, because the code path it unblocks then resolves its records base OUT OF TREE and reports zero errors over zero files at exit 0. Shipping only the item's fix would convert a loud, honest crash into a silent wrong answer, which is the strictly worse outcome and the one the linter's own spec forbids by name.

## Project conventions discovered (Step 0)

- A LINTER MAY NOT REPORT A PASS IT DID NOT EARN. Spec `ipd-structure-and-linting` Section 10: "The tool MUST distinguish a conforming result from inability to run. An internal failure MUST never be reported as a passing lint", with `0` for no errors, `1` for conformance errors, and `2` for "invocation, parser, schema-loading, or internal-tool failure". The same spec's Section 10 also requires `aw ipd lint` to "make no model calls, require no network access, and perform no writes", which this plan preserves. The spec is silent on `--all` and on a repo-root positional (it writes only `aw ipd lint FILE`), and explicitly lists "precise CLI spelling" among details an implementation IPD may settle, so the arity decision in OQ-01 is this plan's to make and needs no spec amendment.
- REFUSING A SECOND VALUE ON A `nargs="*"` POSITIONAL IS THE SHIPPED PRECEDENT, AND IT NAMES THE COUNT. `artifact_adopt`'s command declares `paths nargs="*"` and refuses with `cannot-run` at exit 2 when `len(paths) > 1`, with a summary that begins by naming how many it is refusing and states that the verb takes exactly one; its `--help` epilog documents the refusal in the exit contract. `ipd_lifecycle` refuses an ambiguous selector the same way but NAMES THE CANDIDATES, which is the right shape when the values were resolved rather than typed.
- LOOPING OVER MULTIPLE ROOTS IS ALSO A SHIPPED PRECEDENT, WHICH IS WHY OQ-01 IS A REAL QUESTION. `aw install` loops over `targets nargs="*"`, printing a per-repo heading only when more than one was given, and `workflow_cli` loops over `path nargs="*"` package roots aggregating the worst exit code. Both are WRITE or per-package verbs whose output is naturally sectioned; `ipd lint --all` emits ONE flat `counts:` line, which is the asymmetry OQ-01 turns on.
- THE `cannot-run` IDIOM IS FIXED AND ALREADY PRESENT IN THIS FUNCTION. `ipd_lint.run_lint` uses it three times (unknown `--phase`, nothing to lint, and a path that is not a file): a `CommandResult` with `status="cannot-run"` and `exit_code=2`, emitted through `get_renderer(ctx).emit(res, ctx)` under `--agent`/`--json`, else a `print(f"error: ...")` and `return 2`. `result_types.CommandResult` derives `kind="error"`, `complete=False` and `verified=False` from `exit_code == 2` automatically, and `agent_schema` enforces that triple for an error record, so a refusal needs only those two fields set.
- `aw ipd lint --all --agent` IS A RELEASE GATE, so the bare-`--all` path is load-bearing beyond its own tests. `release_readiness.gate_ipd_lint` runs `["ipd","lint","--all","--agent"]` with no positional and sets `passed = proc.returncode == 0`. This plan must leave that invocation byte-identical, which is why E-03 keeps the zero-element case on `"."` rather than folding it into a new code path.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Deferred / out of scope (with reason)

- CHANGING THE POSITIONAL'S `nargs="*"` DECLARATION, for instance to a separate `--root` option or to `nargs="?"`. Refused because there is no defect behind it and it would break the sibling arm this plan does not touch: the same positional legitimately takes MANY values without `--all` (the multi-file lint added by `awlintmulti`), which `nargs="?"` cannot express, and introducing a `--root` option would leave the documented `--all <root>` spelling broken while adding a second way to say the same thing. The dual-meaning positional is unusual (F-06 notes it is the only such leaf in this CLI) but it is the shipped surface, and a surface change needs its own carrier and its own review.
  - Carrier-Declined: No obligation is created. The behavior a user observes is fixed by E-03 and documented by E-04; the declaration's shape is an internal style question with no user-visible symptom, so filing an item would create work whose only content is "consider a nicer spelling".
- CHANGING `record_producers.resolve_record_path` OR `project_context.resolve_project_context`. Refused because the `home` default is CORRECT for callers that mean a managed companion records tree, and F-03 shows it is a documented precedence outcome (`builtin_defaults`) rather than a bug. Altering it to prefer an in-tree path would change record RESOLUTION for every producer and consumer in the toolkit, including writers, on the strength of one read-only linter's needs. The specialization belongs in the linter's own helper, which is where E-02 puts it.
  - Carrier-Declined: Nothing durable is owed. The question "should an unconfigured repo resolve records in-tree" is a real design question, but it is a question about the RECORDS LAYOUT contract, not about this defect, and no observation here suggests the current answer harms any other caller.
- LINTING MULTIPLE ROOTS IN ONE `--all` INVOCATION. Refused on the reasoning in OQ-01: the output is one flat `counts:` line and one exit code with no per-root attribution, so aggregating two roots would produce a number a reader cannot decompose. A caller who wants two roots runs the command twice, which loses nothing.
  - Carrier-Declined: No obligation is created. ## Open questions

### OQ-01: With `--all`, should 2+ roots be refused or looped over?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE as REFUSE, which answers the explicit question the backlog item leaves open. Both shapes are shipped precedent here, so the decision turns on the OUTPUT, not on preference. `artifact_adopt` refuses a second value on a `nargs="*"` positional with `cannot-run` at exit 2 naming the count, and documents the refusal in its exit contract; `aw install` and `workflow_cli` instead LOOP over many targets. The discriminator is that both looping verbs emit per-target output (a per-repo heading, a per-package result) and aggregate a worst exit code over sections a reader can attribute, whereas `ipd lint --all` emits ONE flat `counts: conforming=N, quarantined=N, legacy=N, error=N` line and one exit code. Summing two roots into that line would give a reader a number they cannot decompose and an exit code they cannot attribute, which is a NEW honesty defect of the same family as the one this plan is closing. Refusing costs the caller a second invocation and nothing else. The refusal also names the count rather than enumerating the extra values, following `artifact_adopt`: the values were TYPED by the caller, not resolved, so echoing them back adds nothing (the `ipd_lifecycle` precedent enumerates candidates because those were resolved from a selector). A reviewer who prefers the loop should say so here; E-03 is the only item affected and the change would be small, but it must then also specify the per-root output that makes an aggregate count readable.

### OQ-02: Should the "no plans tree under this root" case be exit 2, or exit 0 with a message?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED as EXIT 2. Spec `ipd-structure-and-linting` Section 10 reserves `2` for "invocation ... failure" and requires the tool to "distinguish a conforming result from inability to run", and a root with no plans tree is precisely an inability to run: there is nothing to lint, so `error=0` asserts a property of a population that was never read. The same function already treats an analogous case this way, refusing "no IPD files to lint (none given and no pending plans found)" as `cannot-run` at exit 2 in its non-`--all` arm, so exit 2 here makes the two arms AGREE rather than inventing a rule. The counterargument considered and rejected: a caller scripting over many repositories might prefer exit 0 for an empty one, so as not to have to special-case it. Rejected because such a caller cannot currently distinguish "no plans" from "plans I failed to read", which is the exact confusion F-02 measures, and because the honest way to serve them is a future explicit flag rather than an ambiguous success. Note the consequence, which a reviewer should weigh: a caller who today runs `--all <root>` against an empty repo gets exit 0 and will get exit 2 after this plan. F-06 bounds that blast radius to zero in-repo callers, since the only in-repo `--all` invocations pass no positional and are unaffected.
