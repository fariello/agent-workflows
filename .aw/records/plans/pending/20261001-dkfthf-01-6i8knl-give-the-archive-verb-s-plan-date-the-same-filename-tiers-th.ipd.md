# IPD: Give the archive verb's plan date the same filename tiers the rename verb now has, so a plan with an unusable - Date: stops being shelved into the wrong shard and swept months early

- Date: 2026-10-01
- Kind: child
- Concern: `plans_archive._plan_date` READS THE FRONT-MATTER `- Date:` ALONE AND FABRICATES THE LITERAL `20260101` when it cannot parse one, and that fabricated date is load-bearing at TWO sites in the same module. MEASURED AT AUTHORING against this lane's source: `plans_archive._plan_date('- Id: abc123\n')` is `20260101`, and so is `plans_archive._plan_date('- Date: 2026-07-23 (fleshed 2026-07-26 from research)\n')`, the exact production string the one live casualty carries. (1) SHARD PLACEMENT: `plan_shard_move` files a terminal plan at `_shard_target(... _core.shard_for_date(plan_date) ...)`, and driving it on a throwaway repo put a plan named `20260714-grp-03-abc123-probe.ipd.md` with no `- Date:` line into `executed/202601` where its real date demands `executed/202607`. (2) SWEEP AGE: `sweep_candidates` ages a plan through `_age_days`, so the same plan, SIX DAYS OLD, was returned as a sweep candidate at the default `older_than_days=14` as of 2026-07-20, while an otherwise identical sibling carrying a good `- Date: 20260714` was correctly judged too young in the SAME call. That side-by-side contrast is the defect in one measurement: `_age_days('20260101', date(2026,7,20))` is `200.0` against the true `6.0`.
  THE SET-COHESION BRANCH DOES NOT SAVE IT, which matters because `sweep_candidates` has two branches and a reader may assume the set guard absorbs this. The guard is `min(set_ages[set_id]) >= older_than_days`, i.e. a set is swept only when its YOUNGEST member is old enough. Measured both ways: with a three-member set where ONE member's `- Date:` is unusable the fabricated age cannot drag the set in (the min is the youngest real age, so 0 of 3 were swept), but a SINGLE-MEMBER set whose own `- Date:` is unusable IS swept early, because the min is that same fabricated age; and a plan with NO `- Set:` line takes the per-member `else` branch and is swept early too. Eleven terminal plans in this corpus carry no `- Set:` line, so that branch is live and not theoretical.
  THE MISPLACEMENT IS PERMANENT AND SELF-CONCEALING, which is what makes this worse than a cosmetic wrong directory and is the finding that most changes the severity. `_at_disposition_root` returns True only when the path has exactly TWO components, so once a plan has been moved into `executed/202601/` a later `aw archive plans` on it returns `None` (measured: `plan_shard_move` on the landed file is `None`). There is no re-shard and no repair path, so a single archive run writes the wrong location permanently. And nothing reports it afterwards: `artifact_core.is_valid_shard_dirname('202601')` is `True`, because the name is a well-formed shard that is simply the WRONG one, and no `aw check` rule compares a plan's shard against its date (no `check.*shard` rule exists anywhere in the package).
  THIS IS THE SECOND COPY OF A FALLBACK ALREADY FIXED ONCE, and the fix did not reach here. Plan `949enf` added `plans_refs._preserved_date` and routed both `plan_set_assign` and `run_mv` through it, deliberately leaving this module alone (`949enf` OQ-02). `plans_archive._plan_date` is a SEPARATE definition with its own `if not m: return "20260101"` branch and no shared helper, so that fix changed this behavior by exactly nothing. Conversely `949enf` CANNOT be blamed for the shard and sweep harm: review of that plan withdrew its F-05 for precisely this reason and recorded that this item owns the consequence in full.
  THE LIVE CASUALTY IS IN THIS TREE AND IS MEASURABLY MIS-SHELVED TODAY. `.aw/records/plans/executed/20260101-instsafe-07-qrokie-clean-delta-and-tracking-modes-design-spec.ipd.md` carries `- Date: 2026-07-23 (fleshed 2026-07-26 from research)`, and `plan_shard_move` on it right now returns `executed/202601/...` where its real `20260723` demands `executed/202607/...`; by the fabricated date it reads 273 days old against a true 70. It is one file out of 1133 (corpus scan: 1132 usable `- Date:`, 1 malformed, 0 absent), so the live blast radius is one plan, and the defect is a live code path that any future unparseable date walks into.
- Scope: Give `plans_archive`'s plan-date resolution the SAME tiers `plans_refs._preserved_date` now has, so a plan whose `- Date:` is absent or unparseable is shelved and aged by the date its own FILENAME already records instead of by a fabricated constant. The tier order here is deliberately FRONT MATTER FIRST, then the clustered filename, then the legacy `YYYYMMDD-HHMM-NN` filename, then the historical `20260101` last resort; OQ-01 resolves that this INVERTS `949enf`'s order on purpose and measures why. Route both consumers (`plan_shard_move` and `sweep_candidates`) through the one resolver so the two sites cannot drift. Add the shard-placement and sweep-age regression coverage this module has never had, in `tests/test_plans_archive.py`. EXCLUDES: changing the `20260101` last-resort constant or making the archive verb REFUSE instead of falling back (OQ-02); repairing the one already-mis-shelved `qrokie` record or moving ANY committed plan (carried by `tf4jz5`); making `aw ipd lint` flag an unparseable `- Date:` value (carried by `5h8u3z`, plan `fqcax0`); adding an `aw check` rule for a shard that disagrees with a plan's date, or for a filename date that disagrees with metadata (carried by `mt6j1p`); `plans_refs.py`, `research_archive.py`, and `check_engine.py`, all of which stay byte-unchanged; and changing which plans are ELIGIBLE for archival (`_at_disposition_root`), the one-shot stickiness that makes a wrong shard permanent, or the shard grammar itself.

## Goal

Stop `aw archive plans` deciding WHERE a plan is permanently shelved, and WHETHER it is old enough to shelve, from a date that nothing in the plan ever asserted.

WHAT THIS GOAL CLAIMS, STATED NARROWLY because the sibling plan's goal had to be rewritten at review for claiming reach it did not have. This plan changes two decisions and only two: the monthly shard `plan_shard_move` picks, and the age `sweep_candidates` computes. It does NOT make any checker report a wrong date (`5h8u3z`, `mt6j1p`), does not repair the one record already mis-shelved (`tf4jz5`), and does not change which plans are eligible for archival at all. It is the exact consequence `949enf`'s review measured as unreachable from a filename fix and assigned here in full.

## Open questions

### OQ-01: Should the filename date outrank the front-matter `- Date:` here, as it does in `plans_refs._preserved_date`?

- Blocking: no
- Status: resolved
- Owner: author
- Resolution or deferral rationale: RESOLVED FROM MEASUREMENT AS **NO**, deliberately INVERTING the sibling fix's tier order, and this is the plan's one genuine design decision. Three reasons, each measured. (1) FRONT-MATTER-FIRST IS PROVABLY PURELY ADDITIVE: it changes only the no-match branch, and a replay over all 938 terminal plans gives 0 resolved dates changed (F-06). Filename-first would additionally change the result whenever a usable `- Date:` DISAGREES with the filename (measured: `- Date: 20260801` under a `20260716-` name gives `20260801` today and `20260716` under filename-first), which is a behavior change nothing asked for. (2) THE SPEC MAKES THAT DISAGREEMENT LEGITIMATE: the leading date is the SET's canonical date, so a regrouped member may correctly carry a filename date that is not its own, and `mt6j1p` exists precisely because whether such a disagreement is even reportable is undecided. An archive verb should not silently pick the set's date over the plan's own. (3) `949enf`'s REASON FOR INVERTING DOES NOT APPLY HERE, and the distinction is the whole point: a RENAME is PRESERVING a date it is about to rewrite, so it must not recompute it from a field whose failure mode is a fabricated constant; an ARCHIVE is merely READING a date to place a file, and it can safely prefer the plan's own assertion and fall back to the name. E-03 requires this recorded as a comment so a later reader does not "align" the two and reintroduce a change nobody requested.

### OQ-02: Should the archive verb REFUSE when no date is discoverable, instead of falling back to `20260101`?

- Blocking: no
- Status: resolved
- Owner: author
- Resolution or deferral rationale: RESOLVED as NO, out of scope, on the same reasoning `949enf` applied to its own copy and with a corpus measurement behind it. After this plan the constant is reached only when the front matter is unusable AND the filename matches NEITHER the clustered nor the legacy grammar; a scan of all 938 terminal plans finds 0 such files, so the residual path describes a genuinely undated artifact rather than a parse failure. Converting it to a refusal would change a public verb's failure mode, and it would do so MID-SWEEP, where `run_archive` is processing a batch and a raise would abandon the remainder; that is a contract and error-handling decision deserving its own plan, not a rider on a date-resolution fix. The honest residual risk is recorded rather than hidden: a future artifact type with a name matching neither grammar would still be shelved to `202601` silently, and nothing would report it (F-04).

### OQ-03: Should the resolver be shared with `plans_refs` rather than defined twice?

- Blocking: no
- Status: resolved
- Owner: author
- Resolution or deferral rationale: RESOLVED as NO, and the reason is substantive rather than a preference about duplication. The two resolvers have OPPOSITE tier orders by design (OQ-01), so `plans_refs._preserved_date` cannot be called from here without changing this module's behavior in exactly the way OQ-01 rejects. Sharing would therefore require a tier-order parameter, producing one function that does two things and hiding the asymmetry E-03 is required to document; and it would add an import edge (`plans_archive` -> `plans_refs`) that does not exist today, against the package's stated preference for imports flowing toward core. What IS correctly shared is the part that genuinely has one definition: both resolvers consume `artifact_naming._CLUSTERED_RE` and `_LEGACY_TIMESTAMP_RE` from the single naming authority rather than re-encoding either grammar. Note the diagnosis this corrects: the backlog item frames the defect as "a second copy", but the duplication was never the harm; the harm was a MISSING FILENAME TIER in a fallback that fabricates instead of failing, and fixing that leaves two deliberately different, commented functions.
