## Project conventions discovered (Step 0)

- AN EXECUTED PLAN IS APPEND-ONLY, NOT IMMUTABLE, and that distinction is the whole mechanism of E-01. `AGENTS.md` forbids changing what such a plan RECORDS and in the same breath permits appending a dated history line pointing at later work. So "the contradiction stays readable in an executed plan" is answerable without rewriting anything, and rewriting V-02's text would in any case destroy the audit trail of a review round that erred.
- PLAN HISTORY IN THIS REPOSITORY IS NEWEST-FIRST, and readers depend on it: `.aw/records/plans/README.md` states a new record "is inserted directly under the `## Workflow history` heading, so the FIRST record is the most recent", and names `plan_readiness.extract_newest_history_entry` as the reader, recording that a reader which "sliced to end of file and took the last bullet is the bug that fix replaced". Hence E-01's placement constraint.
- A HISTORY LINE'S LEADING TOKEN DISTINGUISHES A TRANSITION FROM A NOTE. `ipd_lifecycle._PLAN_STATUS_VOCAB` holds the ten tokens that are a STATUS transition, and `ipd_lifecycle._plan_status_events` skips any line whose token is not one of them, documenting that "annotations never masquerade as transitions". So a note token is the correct choice for E-01 and a status token would be a false lifecycle claim.
- THERE IS NO `aw ipd note`. The annotation verb exists for two other types (`aw backlog note`, `aw specs note`) and not for plans, so E-01 is a hand edit by necessity rather than by choice (F-07).
- THE TWO `plan-review` VARIANTS ARE HELD IN DELIBERATE PARITY IN THEIR OWN WORDS (`plan-review-long/README.md`: "Kept in deliberate parity with the single-file"), and review has already ruled on this exact file pair: plan `x7i14a` PR-801 found a one-sided edit to the single-file form and required the long form's twin section be edited identically, recording that "a one-sided `Evidence` edit is drift by construction". E-03 follows that precedent rather than re-litigating it.
- `spec-review.md` REFERENCES `plan-review`'s SHARED HALVES RATHER THAN COPYING THEM, by design and with a test enforcing it. Its own "What is SHARED and must not be re-stated here" table says "Anything else you find duplicated here is a defect; fix it by deleting the copy", and `tests/test_spec_review_attestation.py::test_the_body_does_not_apply_the_ipd_ev_rubric` FAILS the body if it mentions an E/V bijection, on the stated ground that "a spec carries no E/V checklists". The sweep rule is about E/V items, so `spec-review.md` is correctly out of scope and its omission is a considered decision, not an oversight.
- `.aw/system/managed-sections.json` RECORDS A NORMALIZED sha256 PER INSTALLED FILE (`manifest.hash_content` -> `normalize_for_hash`), so a raw `sha256sum` answers the wrong question. Measured with the real function at authoring: `plan-review/plan-review.md`, `plan-review-long/02-review-and-revise.md` and `verify-execution/verify-execution.md` are ALREADY stale, while `verify-execution/intent-audit.md` currently MATCHES, so E-04 introduces a NEW mismatch whose consequence is that `aw uninstall` classifies the file as user-drifted and PRESERVES it. Do NOT hand-edit that file: it is installer-owned, written by `manifest.record` as the content the installer last wrote.

The maintainer ruled on 2026-09-26 that this repository keeps no tests pinning production source text or structure, and plan `96xtmi` deleted them in bulk.
