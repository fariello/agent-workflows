## Goal

Make the coordinator worktree's teardown stop DESTROYING the reachability of a commit it did not land, and make the repository able to NAME the surviving commit through an ordinary git ref instead of leaving `git fsck` archaeology as the only route.

WHAT THIS GOAL DOES NOT CLAIM, stated because the adjacent fix is easy to conflate with this one. It does NOT make a contended or raced transition SUCCEED, and it must not be validated as if it did: when a peer holds an uncommitted edit to the plan file the correct outcome is still a refusal, and this plan keeps every byte of that behavior, including the branch staying unmoved and the peer's content staying verbatim. It also does NOT restore the executing agent's released bytes to the working tree; that is `4er1ev`'s subject and its journal mechanism is untouched here. What changes is only whether the commit those bytes live in can still be FOUND afterwards.

AND IT IS A REACHABILITY FIX, NOT A RECOVERY WORKFLOW. After this plan an operator who hits a failed landing is told a ref name and a command that works; deciding what to do with the recovered commit stays theirs. The honest one-line summary is "the abandoned commit stops being garbage".

## Project conventions discovered (Step 0)

- A COORDINATOR-OWNED THROWAWAY WORKTREE IS THE ESTABLISHED MUTATE-THEN-LAND MECHANISM and it ships. `commit_lock.coordinator_worktree` yields a worktree on its own short-lived branch and tears both down unconditionally; `ipd_lifecycle._finalize_transaction` and `runner_shared.perform_coordinator_backlog_close` are its two live callers. This plan changes the TEARDOWN's reachability behavior and adds nothing to the mechanism.
- `commit_isolated` IS A DELIBERATE SIBLING, NOT A DUPLICATE, and must be left alone. Its own docstring and `coordinator_worktree`'s explain why: `commit_isolated` uses `--detach` (git permits one worktree per branch) and therefore advances the ref itself under a compare-and-swap, which is exactly the step that must not precede a peer-protecting fast-forward. It also backs `git_commit_helper.offer_commit`, the shared self-commit path `AGENTS.md` names as immune by construction to sweeping a co-worker's work into a commit.
- A SINGLE SOURCE FOR A DERIVED STRING IS THE HOUSE PATTERN when a writer and a reader must agree. `artifact_core.finalize_commit_subject` records the reasoning explicitly: the pre-commit gate and the run viewer's discrepancy classifier both MATCH what the transaction produces, and a hand-written copy in any one of them drifts silently. E-04's `abandoned_ref_name` follows it.
- GIT'S EXIT CODE, NEVER ITS PROSE, DECIDES AN ARM. `ReconcileLanding`'s docstring states it: rc 1 is the would-be-overwritten refusal and rc 128 is divergence, and string-matching git's wording differs between them and across versions. E-04's classification uses `merge-base --is-ancestor`'s rc for the same reason.
- FAIL-SOFT IS CORRECT FOR HOUSEKEEPING INSIDE A FAILING TRANSACTION, and the repository already does this deliberately. `_rollback_precommit`'s docstring records that escalating a rollback to `PHASE_UNKNOWN_OUTCOME` over a regenerable generated view "would block an operator for no safety gain"; retention and pruning are the same class of concern, which is why E-04 and E-05 record a failure rather than raising.
- THE GITIGNORED SIDECAR TRAP, worth knowing when writing anything into a coordinator worktree: `lane_containment` classifies `.aw/records/history.jsonl` as discardable because it is gitignored and non-authoritative. This plan writes only git REFS, not files, so it is not exposed to that trap; stated so an executor does not go looking for a file-based store.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Open questions

### OQ-01: Should the retained-ref namespace be `refs/aw/abandoned/coordinator/<sha12>`, or does the maintainer want a different ref layout?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE AND MEASUREMENT, not left to the executor. The backlog item explicitly leaves the design open ("keep the branch on a failure arm under a recoverable name and report it; or write a tag/ref the operator can `git show`; or have the report name `worktree_commit` and the journal path explicitly"), so a choice had to be made and justified. A retained BRANCH was measured WORSE on three counts (visible in `git branch -a`, carried by `git push --all`, enumerated by `worktree_lease`'s `refs/heads/` sweep; F-10). A TAG would appear in `git tag` and is carried by `--follow-tags`, and the execution contract forbids creating tags outside a release GO, so it is excluded outright. NAMING ONLY THE SHA (the item's third option) does not fix reachability at all, since F-03 measures gc collecting it, so it is necessary but insufficient and is folded into E-06 as the fallback when retention failed. `refs/aw/*` was measured to satisfy every requirement: gc-immune, `git show`/`git cherry-pick` usable, invisible to every operator view checked, not pushed, and shared across lanes (F-08, F-10, F-11, F-14). The `abandoned/coordinator/` segmentation leaves room for a future sibling (for example `commit_isolated`'s arm, F-13) without a rename. A maintainer who prefers a different layout can say so at review; nothing else in the plan depends on the exact string, because E-04 routes every use through one function.

### OQ-02: Is a 14-day retention window right, and should an unattended repository ever retain forever?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED with the number argued rather than picked, and the alternative priced. UNBOUNDED retention is rejected because a permanent ref pins the commit and its whole tree, and this helper runs on every terminal transition, so the namespace would grow monotonically with no reader and no reaper. 14 DAYS is chosen because git's own `gc.pruneExpire` default is `2.weeks` (verified unset in a fresh fixture, so the default applies), which means the retention can never make a commit's lifetime SHORTER than it already is today while making it strictly longer and NAMEABLE inside the window; any smaller number would need a separate argument for why less than git's own horizon is enough. A reviewer who wants forever-retention should say so, and the cost is that argument's other side: recovery data that nobody reads, pinning objects indefinitely. The mechanism is measured working at three ages (F-09), so changing the constant is a one-line decision rather than a redesign.

### OQ-03: Should `land_worktree_commit` name the retained ref directly, which would be simpler than E-06's separate verified report?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED NO, on a structural fact rather than a preference, and recorded because it is the obvious simplification and it is wrong. `land_worktree_commit` is called INSIDE the `with _clock.coordinator_worktree(...)` block, while the retention happens in that context manager's `finally`, which by definition has not run yet. So at the moment this function composes its message the ref DOES NOT EXIST, and naming it would be an unverifiable claim of exactly the kind F-05 documents as the present defect. The ref name is derivable purely from the sha, so a determined implementation COULD print the name it expects, and that is precisely the trap: on the arm where E-04's fail-soft write failed, the message would name a ref that is absent, which is worse than today's message because it is confidently wrong rather than merely unhelpful. Hence the division E-06 and E-07 encode: this function reports what GIT did, and the transaction reports what it VERIFIED it retained.
