## Goal

Make a silent re-collapse of the color-depth ladder impossible to land without a test going red, no matter which renderer or which seam does it, while adding zero code-structure assertions.

The test of success is not "a guard exists again". It is that the three mutants recorded in F-05 and F-06, each re-collapsing the ladder at a DIFFERENT seam, each turn at least one new assertion red: one inside `Term.lifecycle_depth` (the original defect's exact shape), one inside `Term.style_lifecycle_text` (a different method, which is the item's "third consumer" scenario), and one that deletes the `16` rung so it falls through to `256`.

## Project conventions discovered (Step 0)

- THE MAINTAINER RULING ON THIS AXIS FORBIDS THE OBVIOUS GUARD, which is the single constraint that shapes this entire plan. Backlog `p5qx91` records: "We test outcomes and functionality, never code structure or text in a script. Zero tests that pin code. Do NOT restore single-originating-definition AST/text pins; testing on color-axis should only verify functional rendering outcomes across terminal surfaces." The item for THIS plan restates it ("the obvious guard walks the consumers and asserts none of them rewrites a tier, which is precisely the code-structure pin ... the maintainer ruling on `p5qx91` forbids for this axis specifically"). So the only conforming instrument is an outcome assertion, and the design question is how to make an outcome assertion BROAD, which is what E-03's runtime axis enumeration answers.
- P16 SUPPLIES BOTH THE PROHIBITION AND THIS PLAN'S OWN TEST STANDARD. `GUIDING_PRINCIPLES.md` Section 16 forbids `inspect.getsource`, `ast.parse`, `read_text()` and regex against `agent_workflows/*.py`, forbids count/census pins, and forbids architectural placement pins. It also REQUIRES "Verify test sensitivity with mutation" ("A test is only valid if breaking the underlying behavior makes the test fail"), which is why every assertion here was prototyped against three mutants before authoring (F-05, F-06), and it REQUIRES the accumulate pattern with a trailing `why` for table-driven tests, which E-03 follows.
- P16 ALSO ORDERS THE REMEDIES FOR A LIVE-CHECKOUT DEPENDENCY, and E-04 takes the FIRST one. "First, synthesize the input (the default): Whenever the property does not actually depend on the live checkout, synthesize or anchor the input so the assertion executes everywhere." The tier decision is per-renderer, not per-corpus, so a synthesized four-item fixture is sufficient and makes the guard location-independent. The `livecorpus` marker is explicitly the WRONG trade here, since P16 says to choose it "for blast-radius isolation, never merely to quiet a location problem option one can eliminate".
- THE DISTINCTION BETWEEN A STRUCTURE PIN AND AN OUTCOME ASSERTION IS SETTLED IN-REPO AND THIS PLAN STAYS ON THE LEGAL SIDE. P16's ruff `F811` clarification holds that a check is an OUTCOME assertion when it "reports a condition under which the shipped module's behavior is already wrong", and a forbidden pin when it "reports only that source looks different from a remembered shape". Reading `lifecycle_style.ALL_STAGES` and `term.COLOR_DEPTHS` to build a sweep is the former: the constants are published data, and every assertion is on bytes a call returned. No assertion in this plan would notice a refactor that kept the output identical, which is the operative test.
- CITE CODE BY SYMBOL, NOT BY LINE. Spec `ipd-structure-and-linting` Section 10.2 and advisory `IPD-C801` require a symbol or a quoted content string; `nw088c` records the same lesson after a line citation rotted. `term.py` and `tests/test_term.py` are actively edited by concurrent lanes, so every citation here names a function, method, class, or quoted string.
- THE SUITE IS RUN BARE. `AGENTS.md` requires `python3 -m pytest` with no added flags, because `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow and not livecorpus'`. `-o addopts=""` is used ONLY for the per-file count in E-02, the sanctioned exception.
- `tests/test_term.py` CARRIES NO `slow` MARKER TODAY and already spawns subprocesses: `ColorDepthEndToEndLadderTests` drives `python3 -m agent_workflows` and runs in 5.82s inside a file that totals 30 passing tests in 10.19s. So E-04 follows established practice in this file rather than introducing subprocess testing to it, and the fixture-based design keeps the added cost near 4s.

## Deferred / out of scope (with reason)

- **THE API CHANGE THE ITEM FLOATS (resolve the tier only in `term.resolve_color_depth`; consumers receive it).** DEFERRED, with the item's own framing accepted: it "is an API change to a widely used class, so it needs its own design decision". SECOND, the cost is 63 production construction sites that pass no `depth=` today plus 120 in tests (F-03). THIRD, it is a breaking change to a public class, which is a different risk class from adding tests and does not belong in a `low`/`chore` item. What this plan does instead is make the OUTCOME of any such re-collapse fail, which is strictly cheaper and is available today. A reviewer who thinks the construction-level fix is the right long-term answer should file it as its own item; the guards added here remain correct and useful underneath it, since they assert output and not shape.
- **THE GENERIC COLOR AXIS (`Term.colorize`, `color256`, `status_256`, `badge`, `format_path`) IGNORING THE DEPTH PIN.** EXCLUDED FROM THE FIX, FILED AS A CARRIER IN E-06. Resolving that conflict changes the appearance of every non-lifecycle surface in the package for any user who pins a tier, which is a maintainer decision about user-visible behavior, not an executor's. Folding it into this plan would also silently convert a `chore` into a release-gated `bug` under the repository's own rule. E-06 files it with the conflict stated and does NOT pre-classify it.
- **EXTENDING THE CLI GUARD TO EVERY SUBCOMMAND.** OUT OF SCOPE on measured cost (F-09: 108.25s for 10 commands at 2 tiers, versus 3.9s for the fixture-backed form) and on value: the tier decision is per-renderer, so the marginal command adds runtime without adding a distinct property. ## Open questions

### OQ-01: Should the ladder be made unexpressible at construction time (the item's "one direction worth evaluating") instead of guarded by output assertions?

- Blocking: no
- Status: resolved
- Owner: plan author
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE, NOT FROM PREFERENCE, and resolved AGAINST the direction the item floats, which is why the reasoning is given in full. The item suggests giving `Term` no way to express the coercion by resolving the tier only in `term.resolve_color_depth`. It is rejected for THIS plan on three measured grounds. (1) IT WOULD NOT HAVE CAUGHT THE DEFECT IT WAS RAISED BY (F-07), which is decisive: `resolve_color_depth` was correct at all four rungs when the bug shipped, and the collapse happened in a CONSUMER that read the correct answer and rewrote it. Removing a constructor parameter does not remove a consumer's ability to rewrite what it receives. (2) COST AND RISK (F-03): 63 of 65 production `Term(` sites pass no `depth=`, plus 120 test constructions, and it is a breaking change to a public class, which does not fit a `low`/`chore` item inherited from an item that itself says the direction "needs its own design decision". (3) THE GUARDS ARE AVAILABLE NOW AND ARE ORTHOGONAL: they assert OUTPUT, so they remain valid and useful even if the API is later changed, whereas the API change alone would leave the class untested. THE READING UNDER WHICH THE ANSWER FLIPS, stated so a reviewer can take it up: if the maintainer wants the defect class ELIMINATED rather than CAUGHT, the construction-level change is the only instrument that does that, since P16 forbids the structural pin that would otherwise police it. That is a legitimate position and it is filed in Deferred as its own design item rather than being pre-empted here; it is not blocking, because this plan's guards are strictly additive and would be kept under either answer.

### OQ-02: Does the depth pin govern the GENERIC color axis, or only lifecycle rendering?

- Blocking: no
- Status: deferred
- Owner: maintainer
- Resolution or deferral rationale: DEFERRED TO A HUMAN BECAUSE THE REPOSITORY'S OWN RECORDS CONFLICT AND THE ANSWER CHANGES USER-VISIBLE OUTPUT, which is exactly the class of decision an agent must not make alone. The measurement is not in doubt (F-08): at pin `none` the generic axis still emits `\x1b[1;38;5;46m` and `\x1b[38;5;33m`, so `aw check`, `aw doctor`, `aw ipd lint`, `aw index plans`, `aw ipd board`, `aw backlog check`, `aw specs check` and `aw attention` all print 256-color bytes to a user who pinned `none`. What is in doubt is whether that is a DEFECT. Spec `uonrjg` Section 3 lists "generic command outcome icons that are not lifecycle states" as a NON-GOAL, so the spec owning the ladder does not reach this axis; DECISIONS D42 states the obligation generally ("degrade through 256/16/none") with no lifecycle limit; and `config.CONFIG_SCHEMA`'s own help text promises to "Pin the terminal color depth (256, 16, or none) instead of detecting it" without qualification, which a user would reasonably read as covering everything. Under the repository's "every live bug gates the next release" rule, calling it a bug attaches a release gate, so classifying it unilaterally would be consequential as well as wrong. THIS IS NOT BLOCKING FOR THIS PLAN: it is deferred by SCOPE, and E-04's token-scoped `none` assertion is correct under BOTH readings, since it asserts only that no LIFECYCLE word is painted above its tier and makes no claim about generic tokens. E-06 files the carrier with this conflict stated as the question, deliberately as `followup` rather than `bug`, so the maintainer rules on the reading before a gate is attached.
