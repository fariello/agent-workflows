## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- A FINDING-CODE ROW RECORDS ITS OWN BINDING STATE, AND THE THREE STATES ARE ALREADY DEFINED. `run_evidence` ships `BOUND`, `UNBOUND_BY_DEPENDENCY` and `UNBOUND_UNBUILT` with the reason stated at the definition: "An unbound code that HONESTLY REPORTS ITSELF UNBOUND is safe ... A code silently wired to a predicate that does not answer its question is a fail-OPEN checker". This plan therefore does not invent a vocabulary for "bound"; it uses the one that exists, and it may only write `BOUND` where a shipped predicate genuinely answers THAT code's question.
- THE `RUN-*` BLOCK DELIBERATELY INTRODUCED THIS CONVENTION FOR OTHERS TO FOLLOW. Its comment says the policy "has to be readable in ONE place and enumerable by a test", names the parallel `EV-*` taxonomy as the counterexample ("docstring prose plus inline literals, so no test can enumerate them and a reworded message drifts silently"), and states that it "deliberately INTRODUCES the convention `EV-*` should have had". An `IPD-EXEC-*` table in the same module, with the same record type and the same accessors, is the intended use of that convention rather than a new one.
- A BOUND ROW MUST NAME ITS PREDICATE AND AN UNBOUND ROW MUST NAME WHAT IT WAITS ON, enforced at runtime. `validate_finding_table` fails `RC-BINDING` when a `BOUND` row carries no predicate, when a `BOUND` row also declares `waiting_on`, when an unbound row claims predicates, or when an unbound row does not say what it waits on. The new table's validator must enforce the identical rule, because the rule is the whole reason the `binding` field is trustworthy.
- PREDICATES ARE RECORDED AS `module.symbol` STRINGS, NOT AS IMPORTS, and the stated reason is that "a test can prove each one still resolves, which is what stops the mapping rotting silently". That also keeps `run_evidence` free of the dependency edge; F-08 measured that neither `run_evidence` nor `ipd_lint` currently loads the other.
- `ipd_lint`'s CODES ARE MODULE CONSTANTS, so a consumer branches on a name rather than a literal: `C_EXEC_STATE` (`IPD-S401`), `C_VALID_STATE` (`IPD-S402`), `C_CROSS_STATE` (`IPD-S403`), `C_CHECKPOINT` (`IPD-S404`). Pending plan `qo9khm` (finstruct) consumes exactly these constants for the same reason, which is the precedent for naming them rather than the numbers.
- `C_CHECKPOINT` IS A CATCH-ALL AND MUST NEVER BE TREATED AS THE PRE-TRANSITION E/V CODE. `ipd_lint.check_checkpoint` attaches `IPD-S404` to the three answerable pre-transition messages AND to `status '<x>' is incompatible with checkpoint '<cp>'` (emitted UNCONDITIONALLY, before the `pre-transition` branch) AND to `<OQ>: unresolved blocking question at pre-execution`. The shipped comment above `runner_shared.RETRYABLE_FINALIZE_FINDING_TEXTS` says keying on this code is "the obvious and WRONG trigger", and plan `qo9khm`'s review MEASURED that admitting it widens two never-retry classes. This plan RECORDS the predicate (`check_checkpoint`) and never claims the CODE `IPD-S404` is equivalent to an `IPD-EXEC-*` code.
- SPEC `25kzda` IS READ AS A FILE BY TESTS, so its wording is already a pinned contract in several places and an amendment is detectable. `tests/test_runner_shared.py` globs `*-25kzda-*.spec.md` under the approved directory and asserts on its content; that glob-and-assert-one-match shape is the pattern E-04 follows.
