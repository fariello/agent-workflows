- Date: 2026-10-01
- Kind: child
- Concern: Nothing records WHICH lane an execution actually ran in, so every consumer that needs that identity must INFER it from a branch name. ## Goal

Turn "which lane did this execution run in" from a question the repository INFERS into one it READS. The runner already computes the exact answer and throws it away as far as any checked-in consumer is concerned; this plan records it on the begin receipt, which is the one store already anchored on the checkout (`receipt_dir` resolves through `checkout_control_root`, fixed under backlog `dh0uno`) and therefore already readable from inside a lane. The immediate beneficiary is `check.scope-drift`. `iqtt8d` (executed) already stopped it measuring the CANONICAL lane by default; this plan removes the cases its candidate-selection heuristic still gets wrong (F-13: an abandoned sibling holding work beats a live lane that has none yet, and a reused low attempt number loses to an abandoned higher one), and in both of them today's result is a false `error`-severity finding. The durable benefit is that the reconstruct-a-branch-name-from-an-id6 hazard, now measured twice, gets a recorded fact to read instead of a name to rebuild.

THIS PLAN DOES NOT WIDEN A GATE BY ITSELF, AND THE DISTINCTION MATTERS FOR REVIEW. `check.scope-drift` is registered `error` severity and does gate (F-6), so a change that makes it resolve MORE lanes can convert silence into a failing check. For receipts on disk TODAY that cannot happen here: none carries a `lane` block, so `check_scope_drift` takes the unchanged fallback path for every one of them, and E-07 measures that the findings set and `aw check` exit codes are identical before and after. For receipts written AFTER this lands the change can move a finding in EITHER direction, and both are corrections: it can remove a false finding that the heuristic attributed from an abandoned sibling (F-13, the measured case), and it can add a true finding for a recorded lane the heuristic did not select. That is the same risk `iqtt8d` already accepted and measured for the inference route.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- RECONSTRUCTING A LANE BRANCH FROM AN `id6` IS AN EXPLICITLY DOCUMENTED HAZARD, and it is the convention this whole plan serves. `worktree_lease.lane_branch_name`'s docstring says callers "must NOT reconstruct this by hand from an id6, because allocation may attempt-scope the name ... Read `handle.branch` instead"; `lane_id_from_branch` exists because that mistake was measured under `resumedupe txc9l1`; and `allocate_isolation_worktree`'s docstring repeats the instruction ("Read `handle.branch`, `handle.path`, and `handle.disposition` rather than assuming the name").
- AN ADDITIVE RECEIPT FIELD HAS A WORKING LOCAL PRECEDENT AND A STATED RULE. Schema v2 added `frozen_region_digest` while still WRITING `plan_content_digest`, and `receipt_is_current` falls back to the old whole-file rule when the new field is absent, "deliberately - a pre-Phase-2 receipt must not be spuriously ACCEPTED by a rule it was never bound under". This plan's `lane` block copies that shape: write it, never require it, and let absence select the old path.
- A RECEIPT IS GITIGNORED, SINGLE-USE, AND CHECKOUT-ANCHORED, which is what makes it a cheap place to record this. `.aw/.gitignore`'s `/state/` entry covers `.aw/state/ipd-lifecycle/`, so no receipt is committed and no migration touches git history; a clean finalize UNLINKS the receipt (the "Consume the begin receipt" step in `_complete_after_commit`), so the population is naturally short-lived; and `receipt_dir` anchors on the checkout through `checkout_control_root` (backlog `dh0uno`), so a receipt is readable from inside a lane, unlike a lane owner record.
- RUN STATE IS NOT A SUBSTITUTE FOR THE RECEIPT, which is why this plan adds a receipt field rather than reading what the runner already persists. `execute_item_core` writes `worktree_branch`/`worktree_lane_id`/`worktree_base` into run state, but `.aw/records/runs/` is gitignored (`.aw/.gitignore` line `records/runs/`) and is keyed by RUN id, so a check rule holding only a plan id6 has no supported route to it.
- A RECEIPT MUTATION IS WRITTEN ATOMICALLY AND MUST PRESERVE `base_head`. `_atomic_write_json` writes via a temp file plus `os.replace` so "a crash mid-write cannot produce a partial/valid receipt", and `refreeze_receipt` is the in-tree example of mutating a receipt while deliberately keeping `base_head`, for the reason its docstring records.
- BOTH RUNNERS NOW SHARE ONE BEGIN AND ONE EXECUTE LOOP. `oc_runipd.driver_begin` and `agy_runipd.driver_begin` are byte-identical one-line delegations to `runner_shared.driver_begin` (unified by `rununify 05`, `ct4w0a`), and both hosts execute an item through `runner_shared.execute_item_core`. A change at that one site reaches both hosts, and `runner_shared` may not import a runner, which is why its host-specific dependencies are INJECTED (`818uru` OQ-02).
- `check.scope-drift` COLLAPSES TO ONE FINDING PER PLAN unconditionally, with the rationale recorded in `check_scope_drift`'s docstring (350 findings from six causes). This plan adds no rule and must not disturb that shape.
- `_receipt_is_live` and `_plan_execution_tree` both FAIL SAFE through a whole-body exception guard, each docstring stating the cost (an environment where git cannot run silently disables the rule) and justifying it by CI being the authoritative boundary. Preserve the behavior and the reasoning.
