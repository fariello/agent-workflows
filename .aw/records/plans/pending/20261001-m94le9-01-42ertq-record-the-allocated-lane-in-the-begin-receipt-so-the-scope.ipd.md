# IPD: Record the allocated lane in the begin receipt so the scope advisory reads the lane identity instead of inferring it from branch names

- Date: 2026-10-01
- Kind: child
- Concern: Nothing records WHICH lane an execution actually ran in, so every consumer that needs that identity must INFER it from a branch name. `check_engine._plan_execution_tree` infers it by handing the plan's `id6` straight to `worktree_lease.inspect_lane`, which reconstructs the canonical branch `aw/lane/<id6>` and therefore measures the WRONG TREE whenever `allocate_worktree` attempt-scoped the execution into `aw/lane/<id6>_attemptN`. That is the exact hazard `worktree_lease.lane_branch_name`'s own docstring forbids ("must NOT reconstruct this by hand from an id6, because allocation may attempt-scope the name ... Read `handle.branch` instead") and is the second measured instance of it, the first being the one `lane_id_from_branch` was added to close under `resumedupe txc9l1`. The runner ALREADY HOLDS the answer: `allocate_worktree` returns a `WorktreeHandle` carrying the exact `branch`, `lane_id` and `base_commit`, and `runner_shared.execute_item_core` immediately persists all three into run state as `worktree_branch`/`worktree_lane_id`/`worktree_base`. It is written where the advisory cannot read it, because `.aw/records/runs/` is gitignored run-local state keyed by run id, not by plan id.
- Scope: Make the ALLOCATED LANE IDENTITY a recorded fact on the begin receipt rather than an inferred one. Add an additive, OPTIONAL `lane` block to the begin receipt (schema v3: `branch`, `lane_id`, `base_commit`, `disposition`, `recorded_at`) written by a NEW `ipd_lifecycle` updater that MUST NOT touch `base_head` or any digest; call that updater from `runner_shared.execute_item_core` at the single self-finalize allocation site, immediately after the `attempt["worktree_*"]` fields are written, because the lane does not exist when `driver_begin` runs; and make `check_engine._plan_execution_tree` PREFER the recorded branch when the receipt carries one, falling back UNCHANGED to today's `inspect_lane(repo_root, plan_id)` behavior when it does not. ## Goal

Turn "which lane did this execution run in" from a question the repository INFERS into one it READS. The runner already computes the exact answer and throws it away as far as any checked-in consumer is concerned; this plan records it on the begin receipt, which is the one store already anchored on the checkout (`receipt_dir` resolves through `checkout_control_root`, fixed under backlog `dh0uno`) and therefore already readable from inside a lane. The immediate beneficiary is `check.scope-drift`, which stops measuring an abandoned sibling lane whenever allocation attempt-scoped the execution. The durable benefit is that the reconstruct-a-branch-name-from-an-id6 hazard, now measured twice, gets a recorded fact to read instead of a name to rebuild.

THIS PLAN DOES NOT WIDEN A GATE BY ITSELF, AND THE DISTINCTION MATTERS FOR REVIEW. `check.scope-drift` is registered `error` severity and does gate (F-6), so a change that makes it resolve MORE lanes can convert silence into a failing check. For receipts on disk TODAY that cannot happen here: none carries a `lane` block, so `_plan_execution_tree` takes the unchanged fallback path for every one of them, and E-07 measures that the findings set and `aw check` exit codes are identical before and after. The widening arrives only for receipts written AFTER this lands, by executions whose lane is recorded, which is the intended outcome and is the same risk `iqtt8d` already accepted and measured for the inference route.

- BOTH RUNNERS NOW SHARE ONE BEGIN AND ONE EXECUTE LOOP. `oc_runipd.driver_begin` and `agy_runipd.driver_begin` are byte-identical one-line delegations to `runner_shared.driver_begin` (unified by `rununify 05`, `ct4w0a`), and both hosts execute an item through `runner_shared.execute_item_core`. - `_receipt_is_live` and `_plan_execution_tree` both FAIL SAFE through a whole-body exception guard, each docstring stating the cost (an environment where git cannot run silently disables the rule) and justifying it by CI being the authoritative boundary. Preserve the behavior and the reasoning.

Clearing it would mean teaching teardown and the interrupt-reclamation path to reach into the receipt store, which is a wider change touching `teardown_isolation_worktree` and `reclaim_lanes_on_interrupt` and would couple reclamation to the lifecycle store for a condition that is already handled by degrading to silence. Resolved from repository evidence to the extent the repository can answer it: a live receipt with no resolvable lane is ALREADY an ordinary state on this checkout (F-10 measures two, `cup9r7` and `gyd8sq`, whose lanes read `ABSENT`), so this plan introduces no new condition and the existing handling is the precedent. The residual question is purely whether the extra coupling is worth the tidiness, which is a risk-appetite call for the maintainer.
