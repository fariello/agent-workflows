So the gate's PASS today is not "docs are clean", it is "nobody looked", and the two are indistinguishable in the rendered report. That is the precise harm: a `GO` verdict currently carries a `docs_checks PASS` row that asserts a check which never ran.
  THE ONE LIVE FINDING IS A FALSE POSITIVE OWNED BY AN APPROVED SIBLING PLAN, WHICH IS WHY THIS PLAN HAS A REAL DEPENDENCY RATHER THAN NONE (F-03). The finding fires against the plain-prose heading `## The aw router skill` in `docs/skill-selection.md`, not against any command invocation. `docs_check`'s own module docstring promises to check "every `aw <subcommand>` referenced in a FENCED command block", while `check_doc` applies `_AW_CMD_RE` to raw lines with no notion of a code span, so prose is scanned as if it were a command. Measured: restricting the scan to fenced blocks and inline code spans yields ZERO unknown subcommands across `docs/`, while the prose scan yields exactly that one. Plan `t9lcdu` (Set `gzmr54`, `- Status: approved`) already owns BOTH halves of that fix (its E-03 restricts the scan, its E-04 rewrites the heading) and declares `agent_workflows/docs_check.py` and `docs/skill-selection.md` in its `- Scope-Paths:`. This plan therefore must NOT touch the checker or the document, and must NOT land before `t9lcdu`, because wiring the gate first would make the release report NO-GO on a known false positive and teach the first operator who saw it to distrust the gate.
  WIRING ALONE IS INSUFFICIENT BECAUSE THE INJECTION CONTRACT IS ALSO TYPE-BROKEN, AND THE BREAK IS INVISIBLE UNTIL THE GATE ACTUALLY CARRIES DATA (F-04). `gate_docs_checks` is annotated `doc_findings: Sequence[str]` and stores the list verbatim into `evidence={"findings": findings}`, but `check_docs_dir` returns `List[DocFinding]`, a dataclass. Passing the real findings straight through therefore produces a `GateResult` whose `to_dict()` is NOT JSON-serializable: driven, `json.dumps(gate.to_dict())` raises `TypeError: Object of type DocFinding is not JSON serializable`, while the same call with `str()`-normalized findings succeeds. Since `ReleaseReadinessReport.to_dict` exists precisely to be serialized, a naive wiring would convert a vacuous pass into a crash at the moment the gate first has something to report, i.e. exactly when it matters. `DocFinding.__str__` already renders the canonical `doc:line: [check] message` form, so the fix is to normalize at the boundary and keep the declared `Sequence[str]` contract honest rather than widening it.
  AN ABSENT DOCS TREE MUST NOT READ AS CLEAN, WHICH IS THE SECOND WAY THIS GATE CAN LIE (F-05). `check_docs_dir` is built on `rglob` and returns `[]` for a directory that does not exist (driven against a fresh nonexistent path: no exception, empty list). A gate that computes its own findings therefore inherits a fail-OPEN mode: point it at a tree with no `docs/` and it reports `docs checks pass`. The gate must distinguish "checked, clean" from "could not check", or the wiring reintroduces the same false-pass class it exists to remove.
  WHY `followup` AND WHY NO RELEASE GATE IS INVENTED. The item is `- Work-Kind: followup` and carries no `- Blocks-Release:`, and this plan preserves both. Nothing a user runs today returns a wrong answer or waits longer: `build_report` has NO production caller at all (the only non-doc reference tree-wide is `tests/test_release_readiness_child_pin.py`, which drives `gate_leak_scan`/`gate_ipd_lint` and never calls `build_report`), and there is no `aw` subcommand that renders a readiness report (the 68 top-level subcommands include `release`/`releases`, which own release RECORDS, and `check`, which is typed to artifact types; none builds this report). So the false `PASS` is latent rather than user-perceptible, which is what keeps it off the `bug` classification under the AGENTS.md perceptibility test, and it would be wrong to escalate it on a hunch. It is equally wrong to call it harmless: the moment a reviewer or a workflow consumes this report, the row lies.
