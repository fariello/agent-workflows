## Goal

Make `aw oc run` and `aw agy run` return spec `25kzda` 5.6's exit 3 when a human gate stopped the run, so a caller can distinguish "a human must approve something" from "an item failed". Today both return 1 for both conditions, which means an unattended caller cannot route the two outcomes differently. The aggregator that decides this correctly already ships, is already tested, and is already the spec's transcription; the only thing missing is that nothing calls it.

  THE MAPPING, stated exactly, since every clause is load-bearing and each is measured in the Findings:

  1. A NON-MAPPING ENTRY becomes `AggregatedItem(item_id="<malformed>", contribution_hint=CONTRIBUTION_FAILURE)`.   2. `status == "queued"` UNDER `stopped=True` becomes `AggregatedItem(..., benign_skip=True)`. This is the deliberate-stop concession spec `c4gd2h` A1/A4 require, carried over VERBATIM in meaning from `deliberate_stop_exit_code`: the item never ran, so it is excused, and `benign_skip` is the aggregator's own word for exactly that (its docstring: "a skip that spec 5.6 counts as benign"). Measured to yield exit 0 (F-07 scenario E).
  3. `status == "queued"` UNDER `stopped=False` takes the general rule below and therefore contributes FAILURE, which is what happens today: a `queued` item in a run that did NOT stop is work the run failed to reach.
  4. AN ITEM THAT MET ITS ACTION'S SUCCESS BAR (`item_reached_success(entry)` True) becomes `AggregatedItem(..., verified=True)`. Reuse that predicate; do NOT re-derive the bar. It is question (2) of the five-question classification recorded at `runner_shared.SUCCESS_STATES`, and that note names a measured incident (`run-20260904T042705Z-1025943`) caused by one site hardcoding a different bar.
  5. A HUMAN-GATED ITEM becomes `AggregatedItem(..., needs_input=True)`, and the gate predicate is `bool(entry.get(NEEDS_INPUT_KEY)) and not item_reached_success(entry)`. THE SECOND CONJUNCT IS THE WHOLE CORRECTNESS OF THIS PLAN and is not defensive padding: `NEEDS_INPUT_KEY` has THREE write sites and one of them fires on SUCCESS (F-05), so dropping it regresses a passing spec review from exit 0 to exit 3.
  6. EVERYTHING ELSE becomes `AggregatedItem(..., contribution_hint=CONTRIBUTION_FAILURE)`, matching the aggregator's documented signal for "a plain failure" in `NON_MASKABLE_CLASSES`.

## Project conventions discovered (Step 0)

- CODE IS CITED BY SYMBOL, NOT BY BARE LINE OFFSET (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`). This matters concretely here because `runner_shared.py` is 36,535 lines and both driver files exceed 4,000, so every offset in this plan is attached to a symbol or a quoted string and never stands alone.
- THE SUITE RUNS BARE. `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow'`. Every measurement here was taken with a bare `python3 -m pytest`; the baseline at HEAD `925458df` is `3102 passed, 2 skipped` (F-12).
- SPEC 5.6's EXIT TABLE IS TRANSCRIBED IN EXACTLY ONE PLACE AND MUST STAY THERE. `run_evidence._CLASSIFICATION_EXITS` carries the comment "THE ONLY PLACE INTEGERS APPEAR", and the surrounding block explains that contributions are three-valued precisely so integers do not leak into the logic. This plan therefore writes NO exit-code literal into `runner_shared` or either driver; the integer is obtained by calling the aggregator.
- THIS PACKAGE SHIPS TWO DISAGREEING EXIT TABLES AND THE DIVERGENCE IS DELIBERATE AND DOCUMENTED. `run_evidence`'s block note states it: spec 5.6's 3 is "human input required" while `run_cli.EXIT_BLOCKED` is also 3 but means "blocked: unknown-outcome / retry budget exhausted / not runnable", and at 4 the two disagree outright. `run_cli`'s table governs the READ-ONLY inspection commands (`aw runs show|evidence|verify-ledger`); spec 5.6's governs the RUN aggregate, which is what this plan wires. Reconciling them is explicitly recorded as owned by nobody, and this plan does not adopt it.
- A SHARED CHECKOUT MEANS NO SPECULATIVE FILE MUTATION. Every measurement in this plan that required new behavior was taken IN MEMORY, in a scratch `python3 - <<PY` heredoc that imported the shipped modules and composed the proposed projection as a local function. `git status --short` was empty throughout and no tracked file was edited to measure anything.
