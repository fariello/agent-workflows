## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- THE CONTEXT-THREADING IDIOM IS ESTABLISHED AND MUST BE REUSED: `ctx = context or select_output(args)`, used verbatim by `cli._run_find`, `cli._run_check` and `cli._run_search`. `_run_noun_verb` already accepts a `context` parameter and `_dispatch` already passes it, so E-03 consumes an argument that is already arriving rather than widening a signature.
- THE DISPATCH SITE IS THE RIGHT PLACE FOR A ONCE-PER-INVOCATION SIDE EFFECT, and the repository already decided this for the sibling concern. `_run_noun_verb`'s own comment records it: the self-commit offer is placed "ONCE here at the dispatch site (PR-012: never inside a shared backend, so `aw group research` fires exactly once from here and NOT again in the backend)". The same hazard applies verbatim to emitting a payload, which is why E-03/E-05 emit at the two call sites and E-04 only SUPPRESSES inside the backends.
- `HumanRenderer` CANNOT REPRODUCE TODAY'S HUMAN OUTPUT, which is why this plan keeps the prose prints instead of routing the human path through the renderer. Its layout is a fixed seven-section banner form (`AW <command>`, an outcome banner, `Changes:`/`Would change:`, and so on) with no way to emit a line like `renamed <old> -> <new>`; `term.format_preview` renders `  {kind:<4}  {path}` and the renderer never passes its `target_path` argument. There IS an escape hatch, `result.data["human_rendered"]`, used by `cli._run_check` and `doctor`, but using it would mean rebuilding every prose line as a string and routing it through the renderer for zero behavioral gain and a real regression risk. Keeping the prints is strictly safer and is what makes byte-equality achievable.
- THE SCHEMA VALIDATOR IS THE ARBITER OF RECORD VALIDITY, not this plan's judgement: `agent_schema.assert_valid_agent_record` is called at the end of `CommandResult.to_agent_record`, so an invalid record raises at emit time rather than shipping. E-06(g) asserts conformance explicitly anyway, following `tests/test_status_set.py`'s precedent, because a record can be schema-valid and still wrong for this command.
- THE SUITE RUNS BARE. `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow and not livecorpus'`. Run `python3 -m pytest` with no added flags; use `-o addopts=""` only when per-test counts from a narrowed run are genuinely needed.

## Open questions

### OQ-01: Should a mutation PREVIEW record carry `complete: true` or `complete: false`?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: `complete: true`, and `docs/cli-output-contract.md` Section 5's example is CORRECTED rather than the rule being bent (E-01). Resolved from measurement, not taste. The document says both things about this exact command (F-07) and the schema validator accepts both, so the question cannot be settled by running anything and must be settled by decision. Three measured tiebreakers all point one way: the only shipped preview-emitting mutation, `aw adopt --agent`, emits `complete: true`; the reviewed golden authored for `cmd: "rename"` carries `"complete":true`; and Section 11.3 is a RULE while Section 5 is an EXAMPLE. The semantic argument agrees: a dry run that successfully computed and reported everything it would do is COMPLETE as an answer to the question asked, and `complete: false` is reserved for a truncated or partial result (the stream-truncation convention uses it for `omitted > 0`). ALTERNATIVE REJECTED: honour Section 5 and emit `complete: false`, which would make every preview look partial and would contradict `aw adopt`, forcing a consumer to special-case these two verbs. REVERSIBLE: yes, but only cheaply BEFORE consumers exist, which is now; that is a reason to settle it in this plan rather than defer it.

### OQ-02: Should diagnostics appear on an exit-0 record, as the research path requires?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: YES, carry them, and do NOT let them change the verdict. Measured (F-04): `aw research mv --apply` emits nine `frontmatter-invalid` lines and exits 0 today. Three options existed. (a) DROP THEM in the payload: refused, because it makes the machine surface strictly less informative than the prose it replaces, and the frontmatter problems are real and actionable. (b) LET THEM DRIVE THE VERDICT to `findings`/exit 1: refused, because this Set changes no exit code (that is Order 01's and this plan's shared invariant) and flipping a previously-successful command to exit 1 would break every existing caller, including the two live tests that drive these spellings. It would also be a behavior change smuggled in under an output fix. (c) CARRY THEM AS DIAGNOSTICS ON AN EXIT-0 RECORD: chosen. It is legal in the schema (`to_agent_record` emits a `findings` integer independently of `exit`, and `assert_valid_agent_record` does not require `findings == 0` at exit 0), it preserves the information, and it keeps the verdict untouched. The honest consequence, which a reviewer should accept explicitly: a consumer must read `exit`/`outcome` for the verdict and must NOT infer failure from a non-zero `findings`. That is already what `docs/cli-agent-protocol.md` instructs ("Trust the terminal record's `outcome`, `exit`, `verified`, and `complete` for the verdict"). REVERSIBLE: yes; a later plan could decide these findings should gate, which would be a deliberate behavior change with its own review.

### OQ-03: Should the record's `cmd` be the canonical verb or the spelling the user ran?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED: the SPELLING THE USER RAN. `aw research mv` and `aw rename research` reach the same backend and perform the same mutation, but a consumer correlating a record to the process it launched needs `cmd` to identify the command it issued; reporting `rename` for a `research mv` invocation would make the record unmatchable to its own invocation. This also follows the existing records: `command_surface` declares `research set-assign` and `research mv` as their own commands with their own flags and exit contracts, so they are distinct commands in the repository's own inventory, not aliases. The `target` field carries the TYPE (`plans`, `research`), which is where the type belongs, so nothing is lost. E-05 requires the chosen values be stated in V-05 so a reviewer can check them against the declarations rather than infer them.
