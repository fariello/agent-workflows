## Goal

Stop the runner blaming a lane for a test that was already failing before that lane existed. After this plan, an integration refuses only when the merged tree fails something the pre-work baseline did not, and a refusal names exactly which ids are NEW.

## Project conventions discovered (Step 0)

- The three-valued unknown discipline is already the house rule for this exact data and is stated in `SuiteBaseline`'s own docstring: "an empty tuple with `state == \"absent\"` means UNKNOWN, not 'nothing was failing'". `suite_baseline_context` implements the same inversion-avoidance on the prompt side, stating absence as UNKNOWN in prose. This plan must not introduce a fourth spelling of that rule.
- THE EXIT CODE IS THE AUTHORITY AND A FAILING-ID LIST IS NEVER THE AUTHORITY. This is the house rule most at risk from this plan, it is pinned by a test class whose docstring says it is the case its file exists for (`tests/test_suite_adjudication.py::TheExitCodeIsTheAuthorityAndNotTheList`), and it was learned the expensive way: plan `32ij2j` compared failing sets as a subset over an always-empty string and would have integrated a lane that broke everything. A list may make a refusal SPECIFIC; it may never manufacture a pass (F-7).
- A FAILING-ID LIST IS TRUNCATED AT 40 AND UNORDERED IN PRACTICE, so it is not a set you may subtract without checking its length: `SUITE_FAILURE_LINE_LIMIT` is 40, the extractor returns in first-seen order, and `addopts` supply `-n auto --dist=worksteal` plus random ordering (F-8).
- THE REVALIDATION VERDICT IS CACHED ON THE MERGED TREE ID, not on the item, so any per-item input to the verdict must enter the cache key or be recomputed per item (F-9).
- `make_integration_validation_runner` FAILS CLOSED ON FIVE DISTINCT PATHS and distinguishes "the gate measured and refused" from "the gate could not measure" via the `measured` flag added by `l2mzxn` after a near-identical incident. A change to the verdict must leave all five and both flags intact.
- The repository's standing preference is to CONSUME an existing vocabulary rather than mint a parallel one. `runner_shared` already separates "the gate measured and refused" (`INTEGRATION_REFUSAL_CONFLICT` / `merge-refused`) from "the gate could not measure" (`INTEGRATION_REFUSAL_UNMEASURED` / `merge-unchecked`), the latter added 2026-09-21 by `l2mzxn` after a near-identical incident stranded three verified lanes. This plan adds NO third kind: a no-regression red becomes a PASS, not a new refusal class.
- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).

## Proposed changes (ordered, validatable)

1. A pure new-failure predicate over (merged failing ids, `SuiteBaseline`) returning new ids plus `regressed`/`no-regression`/`unknown`, where an empty merged list on a red suite and a truncated list are both `unknown` (E-01).
2. Normalized node-id comparison that cannot collapse two different failures into one, and treats an unparseable line as NEW (E-02).
3. `make_integration_validation_runner` consumes the predicate at EXACTLY ONE return path, leaving the five fail-closed paths and the exit-5 path untouched, and fixes the baseline-blind cache (E-03).
4. The revalidation record carries the comparison inputs and outputs for audit, additively (E-04).
5. A regression file pinning the three verdicts, FOUR anti-fail-open controls, and the five unchanged paths with their `measured` flags (E-05).

### OQ-03: Does the tree-keyed revalidation cache need the baseline in its key, or a per-item recomputation?

- Blocking: no
- Status: resolved
- Owner: executor
- Finding: F-9
- Resolution or deferral rationale: RESOLVED TO (b), CACHE THE MEASUREMENT AND RECOMPUTE THE JUDGEMENT PER ITEM, with the executor free to take (a) instead PROVIDED they record why. Resolved rather than left open because the problem must be fixed either way (an unmodified cache is a wrong verdict, which is not an option), because both routes are inside this plan's declared scope, and because E-03 and V-03 already force whichever choice is made to be stated and proven - so leaving it open would hold the plan for a decision that cannot be got wrong silently. THE PROBLEM IS MEASURED, not speculative: `make_integration_validation_runner` caches `{passed, reason, measured}` under `cache[tree_id]` and serves it wholesale to any item reaching the same merge result, while this plan makes the verdict RELATIVE to a PER-ITEM baseline - and run `run-20260922T024054Z-2245533` contains two items with DIFFERENT baselines (`ld8lb3` at `301a1d8fbc15`, `65cuw0` at `ee20e831f5f1`). So an unmodified cache can serve a comparison computed against another item's baseline, which is a wrong verdict in whichever direction the baselines differ. TWO FIXES. (a) Add the baseline identity to the cache key: smallest diff, keeps one entry per (tree, baseline) pair, but re-runs the SUITE when two items share a tree and differ only in baseline, which costs a full suite run (~107s measured) for a comparison that needs none. (b) Cache the raw merged failing-id set and the raw suite verdict, then recompute the comparison per item: preserves the one-run-per-merge-result property the cache exists for and makes the cached value a MEASUREMENT rather than a JUDGEMENT, which is the more honest shape, at the cost of a slightly larger change to the cache entry. CHOSEN: (b), because the cache's stated purpose is "ONE run per distinct merge result" and (a) partially defeats it by re-running a ~107s suite for a comparison that needs none, and because caching a MEASUREMENT and deriving JUDGEMENTS from it is the same discipline `SuiteBaseline` already follows and the same one that keeps the `measured` flag meaningful. Note (b) also keeps the existing `measured` semantics intact, since what gets cached stays a fact about the tree rather than a verdict about an item. Either route satisfies E-03; taking (a) requires recording why, and V-03 demands the choice be shown working on the real `301a1d8fbc15` / `ee20e831f5f1` pair regardless.
