# IPD: Make a release-gate exemption expressible as a typed attested field, so a deliberately ungated bug is distinguishable from an oversight

- Date: 2026-09-28
- Kind: child
- Concern: A live `Work-Kind: bug` item that genuinely should NOT gate a release cannot say so. `check_engine.check_live_bug_gate` flags any live gating-kind item whose `- Blocks-Release:` is absent (ERROR, I-07), and its own recovery text invites the author to "file an explicit exemption if this bug genuinely does not gate the release" - but no such mechanism exists anywhere in the tree (`rg Gate-Exempt` returns nothing). The marker plan `rgaasb` E-04 prescribed, a literal `- Blocks-Release: -`, TRADES ONE ERROR RULE FOR ANOTHER: `releases._ITEM_BLOCKS_RELEASE_RE` matches the dash as `\S+`, `releases.resolve_release` cannot resolve it, and `releases.check_blocks_release` reports `check.blocks-release-dangling` (also ERROR, also I-07). So an exemption is inexpressible: an item is either ungated and flagged, or dash-gated and flagged. The consequence is that a deliberate, reasoned de-gate is byte-for-byte indistinguishable from an oversight, which pushes a future executor toward re-gating a decision a human already made - exactly what E-04's "DO NOT BLANKET-APPLY" instruction existed to prevent.
- Scope: Add a TYPED, ATTESTED exemption as a sibling front-matter pair on a backlog item - `- Release-Exempt-Kind:` (a closed enum reusing `attention_contract.GATE_KINDS`) plus `- Release-Exempt-Ref:` (validated per kind by the shipped `attention_contract.validate_gate_ref`) - modelled directly on the existing `Gate-Kind`/`Gate-Ref` typed pair. Teach `check_live_bug_gate` to treat a VALID exempt pair as satisfying, add the conditional-presence validation both directions (a malformed pair is a finding; an exempt pair alongside a live gate is a contradiction), wire both `aw backlog set` dispatch paths and `aw backlog new`, and amend the two docs surfaces plus the I-07 catalog row. Does NOT touch `check.blocks-release-dangling`, does NOT make `- Blocks-Release: -` mean anything new, does NOT extend the exemption to specs or plans, and does NOT re-gate or exempt any existing item.

## Goal

Make a release-gate exemption a POSITIVE, TYPED, ATTRIBUTED assertion on the item, so `check.live-bug-ungated` can tell a reasoned de-gate from an oversight and stays trustworthy at ERROR severity. After this plan, an author who has decided a bug does not gate the release records that decision in a machine-readable pair that the checker honors and a reader can audit; an author who simply forgot is still flagged. Nothing about what `- Blocks-Release:` MEANS changes, and no existing item's gate state moves.

## Project conventions discovered (Step 0)

- CODE IS CITED BY SYMBOL, NOT BY BARE OFFSET (spec `ipd-structure-and-linting` Section 10.2, advisory `IPD-C801`). This plan cites every touch point by `module.function` or by a quoted content string for that reason; the backlog item's own reasoning is cited by quoted phrase, not offset.
- THE TYPED TWO-PART PAIR IS AN ESTABLISHED SHAPE HERE, which is why this plan adopts it rather than inventing one. `attention_contract` defines `GATE_KINDS` as a closed six-value enum and `validate_gate_ref` as a per-kind validator bounded by `is_safe_descriptive`, and `backlog.validate_item` enforces the pair's presence conditionally (present-and-valid iff `blocked`, absent otherwise) through four named rules. E-01/E-02 mirror that structure and IMPORT that enum and validator instead of forking them.
- AN ATTESTATION IS RECORDED, NOT ASSUMED, and the repository has two working precedents. `runner_shared`'s `--allow-uncovered-orchestrator-work` is the tree's first `RunPolicyFlag` whose `kind` is `"str"` precisely because "a bare boolean would record that someone clicked past the gate and nothing about whether they should have"; and `status_set.apply_status_change` folds `--by-human` into the history actor string so an attested approval is "machine-greppable rather than buried in free-text prose". The exemption pair follows the same principle: a typed ref plus a history record, not a bare sentinel.
- THE UNATTESTED SENTINEL IS THE ANTI-PATTERN TO AVOID, and it already exists here to learn from: `ipd_schema.SCOPE_PATHS_GRANDFATHERED`, `PLAN_PRIORITY_GRANDFATHERED` and `ITEM_DEPENDENCIES_UNRESOLVED` are bare magic values carrying no actor and no reason. E-03's refusal to honor a MALFORMED pair is what keeps this field from becoming a fourth one.
- BOTH `aw backlog set` SPELLINGS MUST BE WIRED. `backlog.run_set` handles the `--status` spelling and `status_set.apply_status_change` handles the positional one; `backlog.decide_gate_default`'s docstring states that a default wired into one spelling and not the other "would fire inconsistently, which is worse than not shipping it because it teaches a false expectation". E-04 and E-05 are split along that fork for that reason: one item per dispatch path.
- THE SUITE RUNS BARE: `pyproject.toml` `addopts` already supplies `-q -n auto --dist=worksteal -m 'not slow'`. Run `python3 -m pytest` with no added flags; a second `-q` suppresses the `N passed` line this plan's validation requires, and `-n0` makes the run several times slower.

### OQ-01: Should the exemption be a typed two-part pair, or a single free-text reason field?
