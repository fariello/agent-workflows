## Goal

Make an evidence-satisfied backlog close leave the SAME durable, portable, machine-readable trace no matter which of the two `aw backlog set` spellings a caller used, so the one shared close predicate returns the same verdict at rest that it returned at the moment of the close, from any checkout. Today only one spelling records the citation, the recorded form does not survive being read from a different directory, and a citation containing a space is written in a shape the reader cannot parse, so a legitimate close is reported as a dropped release gate by an error-severity rule in a fail-closed CI step.

## Project conventions discovered (Step 0)

- Cite code by SYMBOL (`module.function`) or by a quoted content string, with a line number only appended to one of those and never alone: an offset expires before this plan executes (spec `ipd-structure-and-linting` Section 10.2; advisory `IPD-C801`).
- THE TWO SPELLINGS OF `aw backlog set` ARE TWO DIFFERENT CODE PATHS, and `cli.py` forks on `args.status is not None`: with `--status` into `backlog.run_set`, without it into `status_set.run_set_command`. This repository has fixed the resulting asymmetry at least three times (plan `47ttnv` wired the close predicate onto the positional path; `43p53n` and the gate-defaulting plans each closed a one-sided write), which is why the backlog item lists it as a scope warning and why this plan treats "one shared helper, called from both" as the only acceptable shape.
- A FIELD NEEDS FOUR THINGS TO EXIST, recorded by `f7igdu`'s F-05: a reading regex plus a parser slot, a `validate_item` shape rule, a writer, and a README line. Without the parser slot an unknown bullet is PRESERVED verbatim by `_render_item` (because it is not in `_TEMPLATE_OWNED_KEYS`) but is invisible to every consumer, and `validate_item` silently accepts a malformed one. This plan's E-05 and E-06 exist because the reader and the fourth corner, validation, currently disagree with the parser.
- `validate_item` IS DELIBERATELY A SHAPE CHECKER WITH NO REPO ROOT, so it does not test whether a citation RESOLVES; `f7igdu` chose that explicitly because "a citation can legitimately point at an artifact that was later archived or renamed". E-06 therefore tests READABILITY, not existence, and that distinction is a constraint rather than a preference.

- THE LEAK SANITIZER IS A REAL GATE ON TRACKED CONTENT, not advisory: `.pre-commit-config.yaml`'s `local-leaks` hook runs `python3 -m agent_workflows check-local-leaks` over the TRACKED tree, and `leak_sanitizer`'s `home-path`/`users-path`/`handle` rules are `severity='fail'`. - `verdict.path`, NOT `args.evidence`, IS THE KEY FOR AN EVIDENCE WRITE, because `evaluate_blocking_close` tries `DE-GATED`, then `HANDOFF`, then `SATISFIED`, and returns on the first that holds. `f7igdu` E-03 established this and `tests/test_backlog_handoff_close.py::test_case_6d_handoff_and_degated_closes_leave_no_close_evidence` pins it.

## Open questions

### OQ-01: Should the reader be widened to match the writer, or the accepted citation narrowed to a whitespace-free path?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE AT AUTHORING: WIDEN the reader. The question is decidable without asking a human because the repository has already decided what a legitimate citation is, and it is the resolver, not the reader's regex. MEASURED: `check_engine.resolve_evidence_artifact` returns True for `.aw/records/a b.md`, because it tests only `attention_contract.is_safe_descriptive` (which permits a space; it refuses control characters, and returns False for a value containing a newline), repo containment, existence, and membership of the records tree. So a path containing a space IS an accepted citation TODAY, and narrowing would REFUSE a close the shipped resolver considers legitimate, which is a reduction in behavior this plan has no mandate to make. The reader's `(\S+)` is therefore not a deliberate grammar but an accident of a quick regex, and it disagrees with BOTH the writer and `backlog._CLOSE_EVIDENCE_RE`'s `(?P<value>.+?)`, which is two votes to one. Widening also leaves `validate_item` with nothing new to refuse, which is why E-06 is written to collapse into a test plus a comment on this branch. The counter-argument was weighed and rejected: a whitespace-free grammar would be simpler to validate at rest, but buying that simplicity by refusing a currently-legitimate close trades a real capability for a cosmetic one. E-05 still requires the executor to STATE the choice and the rejected alternative in the execution note, because the decision must be readable from the executed plan rather than only from here.

### OQ-02: Should `set_close_evidence_line` take the repo root as a parameter, or should normalization happen at each call site?

- Blocking: no
- Status: resolved
- Owner: none
- Resolution or deferral rationale: RESOLVED FROM REPOSITORY EVIDENCE AT AUTHORING: thread the repo root into the helper. The only fact the decision turned on was how many callers the helper has, and that is a one-grep question answered at authoring rather than deferred: `grep -rn "set_close_evidence_line" agent_workflows/ tests/` returns exactly TWO matches, its definition in `backlog.py` and its single call site in `backlog.run_set`. No test calls it directly and no other module imports it. So changing the signature costs one call site inside this plan's own `- Scope-Paths:`, and no caller outside the plan's scope can break. That settles it in favor of ONE normalization point, because the alternative (normalize at each call site) would create TWO such points the moment E-03 adds the positional caller, which is precisely the divergence class F-02 is an instance of and that the backlog item warns about by name. E-02 remains written to permit "a sibling helper it delegates to", which is a free implementation choice (a two-argument wrapper over a root-aware core) rather than a second normalization point, so the executor retains that latitude without reopening this decision.
