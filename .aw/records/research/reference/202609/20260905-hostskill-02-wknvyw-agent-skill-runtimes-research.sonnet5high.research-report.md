### Discovery: automatic vs. manual registration

Every host surveyed does **automatic filesystem discovery** within its scanned directories — none of them require the user to individually "register" each skill file the way, say, VS Code extensions require installation. The manual step, where one exists, is almost always about *scope* or *consent*, not discovery:
- Gemini CLI requires per-activation consent even after a skill is discovered (see §3).
- Cursor requires an opt-in sync step to make personal (`~/.cursor/skills/`) skills available to Cloud Agents; `~/.agents/skills/` explicitly never syncs to Cloud Agents at all.
- Claude Code requires a non-interactive run with `CLAUDE_CODE_SYNC_SKILLS=1` to pull claude.ai-account-level skills onto a local machine at all.
- Windsurf's Claude-compat paths (`.claude/skills/`) are opt-in behind a "Claude Code config reading" setting, while `.agents/skills/` is on by default.

### File format and size limits

All hosts converge on the same minimal core: a `name` and a `description` in YAML frontmatter, a Markdown body, optional `scripts/`, `references/`, `assets/` directories. Beyond that they diverge in how strict they are about *extra* fields:

- **Claude Code** accepts a long, Claude-specific field list locally (documented: `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`). Outside Claude Code — i.e. for claude.ai skill uploads, the Skills API, and `package_skill.py`-based packaging — **only six spec fields are allowed, and an unrecognized field is a hard packaging error**: *"Unexpected key(s) in SKILL.md frontmatter: argument-hint. Allowed properties are: allowed-tools, compatibility, description, license, metadata, name."* A field like the toolkit's `semantic-digest` would trip this validator on that distribution path (**VERIFIED**, code.claude.com/docs/en/skills).
- **OpenCode**: "Only these fields are recognized: `name` (required), `description` (required), `license`, `compatibility`, `metadata`. **Unknown frontmatter fields are ignored**" (**VERIFIED**, opencode.ai/docs/skills.md).
- **Cursor**: documents a fixed field table (`name`, `description`, `paths`, `disable-model-invocation`, `icon`, `color`, `metadata`) but doesn't state what happens to an unrecognized key; no hard-failure behavior is documented the way Claude Code's upload path has.
- **Codex**: documents only `name` and `description` as required; doesn't document rejecting extra keys.
- **Windsurf**: explicitly tolerant — *"Agent-specific frontmatter fields like Claude Code's `context: fork` and `allowed-tools` are ignored by Windsurf. These are safely skipped without causing errors"* (REPORTED, agensi.io guide, cross-checked against Windsurf's own docs' silence on the matter — Windsurf's own page doesn't discuss unknown-field handling directly, so I'm treating the "safely skipped" claim as REPORTED, not VERIFIED, though it's consistent with every host that does document its behavior).

Net: **a non-standard frontmatter key like `semantic-digest` is very unlikely to break parsing on any host examined except one specific Claude Code distribution path (claude.ai upload / Skills API / `package_skill.py`), where it is documented as a hard, blocking validation error.** Everywhere else it is either explicitly ignored or simply undocumented (and, per direct testing culture in this ecosystem, generally tolerated).

### Script execution

Every host that documents scripts at all treats them the same way: **the bundled script is not run by some dedicated "skill execution" subsystem — the SKILL.md body just instructs the agent to run it, and the agent runs it through its own ordinary shell/bash tool**, subject to that host's ordinary tool-permission machinery. None of them run a script automatically just because it exists in the skill folder; all require the model to decide to invoke it (or the user to invoke it manually), and all funnel it through the same approval/sandbox layer that governs any other shell command that host's agent might run. Working directory is consistently "the session's current working directory," not the skill's own directory, in every host that documents it (Claude Code makes this explicit and provides `${CLAUDE_SKILL_DIR}` specifically so scripts can be referenced by an absolute path regardless of cwd).

## 2. Is there a cross-host standard, or competing conventions?

There are **two distinct, coexisting standards**, and conflating them is a common source of confusion in the ecosystem's own secondary literature:

**AGENTS.md** — a single flat Markdown file (like a README, but for agents) carrying always-loaded, project-wide instructions (build/test commands, conventions). **VERIFIED**, agents.md and OpenAI's own announcement (openai.com/index/agentic-ai-foundation): it began as an OpenAI-led, cross-vendor convention around August 2025, with early participation credited to OpenAI Codex, Sourcegraph/Amp, Google Jules, Cursor, and Factory. On **December 9, 2025**, OpenAI and Anthropic donated it to a newly formed **Agentic AI Foundation (AAIF)** under the Linux Foundation, alongside Block, with support from Google, Microsoft, AWS, Bloomberg, and Cloudflare — so it is now vendor-neutral by governance, not just by informal convention. A secondary/arxiv source (REPORTED, not independently verified by me) puts adoption at 60,000+ repositories and 20+ supporting tools as of December 2025. A competing, less-adopted convention called `agent.md` (note: singular) exists, associated with Geoffrey Huntley and Sourcegraph (REPORTED, Medium); by the reporting author's own account they were sticking with `AGENTS.md` for its larger installed base while watching `agent.md`.

**Agent Skills / SKILL.md** — the on-demand, packaged-procedural-knowledge standard this whole report is about, at **agentskills.io**. **VERIFIED** across the many official per-host pages already cited: it originated inside Claude/Claude Code, and Anthropic published it as an open standard on **December 18, 2025** (multiple corroborating secondary sources agree on this date; Anthropic's own Claude Code docs describe it as "the Agent Skills open standard" without restating the exact date on the page I fetched, so treat the exact date as REPORTED-but-consistent across many independent secondary sources, not independently primary-sourced by me). Both AGENTS.md and Agent Skills are meant to be complementary, not competitors: AGENTS.md is the always-on orientation file, SKILL.md packages are the load-on-demand procedures.

These are genuinely different specs solving different problems, and the toolkit under discussion actually already uses AGENTS.md correctly for its always-on pointer (per its README, "adds a pointer to your AGENTS.md") — the SKILL.md/`.agents/skills/` design described in the prompt would be a *second*, additional mechanism layered on top of that, not a replacement for it.

**What real multi-host projects do about the `.agents/skills/` vs. host-native-path split:** rather than picking one path and hoping, the pattern actually observed in the wild is **either (a) rely on the growing number of hosts that already alias `.agents/skills/` natively, or (b) symlink**:

- `britt/agent-skills` (a real, actively released skills catalog — **REPORTED**, its own GitHub Releases page, v3.2.0) explicitly did this: *"Codex CLI and Cursor can now read every skill natively. All skills are symlinked under `.agents/skills/` — the shared open-standard path those tools already look for... Nothing is duplicated; `skills/` stays the one canonical copy, everyone else just gets a window into it."*
- `microsoft/apm`, issue #1520 (**REPORTED**, a real, open GitHub issue on a real Microsoft-org repo, dated ~May 27, 2026): proposes moving the Windsurf target's *deploy* path from `.windsurf/skills/` to `.agents/skills/` specifically "so windsurf joins the existing 5-target convergence (copilot, cursor, codex, gemini, opencode)" — independent confirmation, from a project actively building cross-host tooling, that those five hosts were already treated as converged on `.agents/skills/` by the time this issue was filed.
- `addyosmani/agent-skills`, `docs/opencode-setup.md` and `docs/cursor-setup.md` (**REPORTED**, real repo docs): explicitly document copying/symlinking into whichever discovery path a given host actually scans when a default install location misses it, e.g. *"If the skills land somewhere OpenCode does not scan, copy or symlink them into one of the discovery paths listed below."*
- Package-manager-style tools (`skills-lock`, `helix.skills.json`/lockfile, the `npx skills` family) all ship an explicit per-agent target map (`claude-code` → `.claude/skills/`, `cursor`, `opencode`, `windsurf`, `github-copilot`, `amp`, and a literal **`universal`** target defined as `.agents/skills`) — i.e. the tooling ecosystem has already operationalized "`.agents/skills` is the universal/fallback target" as a first-class concept, not just a docs aspiration.

So: the field-level answer to "is `.agents/skills` a convention no shipped host actually reads" is **no, that's now false** — it was arguably true in the first weeks after the Agent Skills standard shipped (Dec 2025), when only Claude-compat paths existed, but by the time of this research (Sept 2026) it has become the majority convention among hosts that support skills at all, with Claude Code (the format's originator), Amazon Kiro, and Google Antigravity as the notable holdouts.

## 3. What does the host put in context, and does a POINTER work?

**What's loaded, and when — this is consistent, described-the-same-way ("progressive disclosure") across every host with documentation on the point:**

1. At session start (or extension/skill-list refresh), only **name + description** (sometimes plus a file path, as Codex does) are injected into the model's context — this is the "always visible" listing.
2. When the model (or the user, via slash-command/@-mention) decides a skill applies, the **full SKILL.md body** is read into context.
3. Any files the body itself references (`references/*.md`, `scripts/*`, `assets/*`) are read **only if and when the model decides to open them**, per the SKILL.md's own instructions.

This three/four-stage model is explicitly named this way by multiple hosts (Codex's official docs literally head a section "progressive disclosure"; Windsurf's docs cite `agentskills.io/what-are-skills#how-skills-work`; Microsoft's Agent Framework docs describe a four-stage `Advertise → Load → Read resources → Run scripts` pipeline with named tools for each step). **This is not a workaround the toolkit invented — it is exactly the mechanism every host's own docs recommend building SKILL.md around.** Cursor's docs say almost verbatim what the toolkit is trying to do: *"Keep your main SKILL.md focused and move detailed reference material to separate files... Reference scripts in your SKILL.md using relative paths from the skill root."* Claude Code's docs: *"Reference supporting files from SKILL.md so Claude knows what each file contains and when to load it."*

**Enforced limits, and what happens on overflow:**
- Claude Code: the skill *listing* (not body) is capped at ~1% of the model's context window by default (`skillListingBudgetFraction`), with a hard 1,536-character-per-entry cap on the combined description+`when_to_use` text; when the listing overflows its budget, Claude Code *silently drops descriptions*, starting with least-used skills, and logs a debug-only warning — this is a silent, ranked truncation, not a rejection.
- Codex: the initial skills list is capped at 2% of the context window, or 8,000 characters if the window size is unknown; when many skills are installed, Codex shortens descriptions first, and for very large skill sets may **omit some skills from the list entirely and show a warning** — again, silent/degraded, not a hard failure, but explicitly can mean a skill simply never gets a chance to be selected.
- No host documents a hard *rejection* of an oversized SKILL.md body itself (as opposed to the listing) — the closest thing to a size-based failure mode anywhere in this research is Claude Code's recommendation to keep the body "under 500 lines" and its separate compaction rule that re-attached, previously-invoked skills after context compaction share a combined 25,000-token budget and can be dropped entirely if many were invoked in one session.

**Does a pointer reliably get followed?** This is the toolkit's central bet, and it is also the weakest-evidenced part of this whole report, honestly: **no host publishes a success-rate or reliability benchmark for "the agent opens the file a plain-prose instruction told it to open."** What I can say, calibrated by source quality:

- The *mechanism* is real and well-supported: every host that documents scripts/references at all documents the agent opening a same-skill-package file on its own initiative when the SKILL.md body tells it to (all the "Reference supporting files..." guidance quoted above). This is a routine, expected, host-endorsed pattern, not a fringe trick.
- The toolkit's specific pattern is a step further than that, though: `SKILL.md` doesn't point at a file *in its own package* (`reference/canonical-body.md` does exist in-package per the prompt, but it itself "points at" the *authoritative workflow body elsewhere in the repo*, i.e. a **second hop**, and outside the skill directory). I found no host documentation, and no controlled study, addressing multi-hop or out-of-package pointer-following specifically. This reduces to a general instruction-following question (will the model reliably act on an imperative sentence buried in a loaded document) rather than a skills-specific mechanism, and general instruction-following reliability is not something any vendor publishes hard numbers on.
- The one piece of concrete, if anecdotal, evidence I found of the *in-package* version working as designed: a real GitHub Discussion on the standard's own repository (agentskills/agentskills #162, **REPORTED**) shows a user confirming, with an actual tool-call trace (`Read(.claude/skills/foo-docs/references/troubleshooting.md)`), that "at least with Claude Code + Opus, the skill is able to apply progressive disclosure for sub-files" when told to via a relative link in the SKILL.md body. The known failure mode raised in that same thread is *not* "the agent refuses to open the file" — it's the opposite: once it does decide to open a referenced file, **it loads the whole thing** with no further progressive disclosure inside that file, which is a context-cost problem, not a reliability-of-following-the-pointer problem.
- Net: **I found no evidence of hosts failing to follow an explicit, well-written pointer instruction to an in-repo file, but I also found no rigorous evidence that they reliably do so under adversarial or degraded conditions** (long context, competing instructions, weaker models). Anyone relying on this design should treat it as "consistent with how every host says SKILL.md is supposed to work" rather than "proven reliable" — the honest answer here is closer to UNKNOWN-leaning-plausible than VERIFIED.

**Safety controls around skill files:**
- **Prompt-injection / trust framing**: none of the hosts researched described skill content as inherently more or less trusted than any other file the agent reads — a SKILL.md is just more context, subject to the same general prompt-injection exposure as any other file the agent opens (this is a known, general, unsolved-by-any-vendor problem class, not specific to skills; I found no host claiming a skills-specific defense here beyond ordinary tool permissions).
- **Script-execution consent**: every host funnels script execution through its normal tool-approval layer (Claude Code's `allowed-tools`/permission settings and the Bash-tool permission prompt; Codex's approval-policy × sandbox-mode two-axis model — `untrusted`/`on-request`/`never` crossed with `read-only`/`workspace-write`/`danger-full-access`; Cursor and Windsurf running scripts through the same tool-call flow as any other agent action).
- **Activation consent, as distinct from execution consent**: Gemini CLI is the one host I found that documents a *separate, skill-specific* consent gate: *"Installation consent: When installing from a remote URL, you will be asked to confirm the source. Activation consent: Every time a skill is triggered during a session, the agent must ask for permission to activate it and gain access to its resources"* (**VERIFIED**, google-gemini/gemini-cli docs). This is a stronger, skills-specific control than anything documented for the other hosts, which generally treat "the skill loaded" and "a tool call from within it needs approval" as the only two checkpoints.
- **Workspace-trust interaction**: Claude Code explicitly notes that a project skill's `allowed-tools` field applies "whenever you or Claude invoke the skill, including in a `-p` run in a folder you've never trusted" — i.e. workspace trust does *not* gate a skill's self-granted tool permissions, which the docs themselves flag as a reason to review third-party skills' `allowed-tools` before running them.

## 4. Is a per-package digest script justified?

**Short answer: no host calls a script that lives inside a skill package to validate it, and the real convention that exists for this problem operates at the repository level, not the per-skill level.**

- **No host invokes a bundled script for validation.** Every validation mechanism I found is an *external* tool run *against* the skill files, not a script the skill folder ships and self-executes: `claude plugin validate <dir>` (Claude Code, checks frontmatter parses); `gh skill --dry-run` / `--fix` (GitHub CLI, validates against the Agent Skills spec plus repo hygiene checks like tag/secret/code scanning); OpenCode's and others' silent-ignore-unknown-fields behavior (a parser-level check, not an executed script). None of these are "a script that ships inside the skill folder and is run by the skill folder."
- **The real convention for integrity/verification is a single repository-level lockfile with content hashes, generated and checked by tooling that lives outside any individual skill** — directly the "single repository-level manifest" alternative the prompt's author suspected. Concretely, multiple independent, real tools in this space (**REPORTED**, several actual GitHub repos/packages: `luisalima/skills-lock`, `vercel-labs/skills` issue #549 describing the intended `skills-lock.json` workflow, a Rust `skil` crate with `.skill-lock.json`, and a Helix-agents `skill-cli` with `helix.skills.lock`) converge on the same shape: one JSON file at the repo root, one entry per skill, each entry carrying a pinned source/version and a **SHA-256 integrity hash over that skill's file tree**, checked with a `--frozen`/`--check` flag in CI. This is explicitly modeled on `package-lock.json`/`Cargo.lock`, and is described by its own authors as filling a real, previously-missing gap ("Most agent skills repos on GitHub have NO lock file. They publish skills with no integrity verification" — REPORTED, leadmagic.io).
- **Given that**, a `scripts/verify_digest.py` per skill package that "only compar[es] an argument against a baked-in constant," with nothing in the shipped code calling it, matches neither pattern actually in use: it isn't invoked by any host (hosts don't call scripts inside skill packages except at the model's own initiative, driven by SKILL.md prose, and nothing in the described design instructs the model to run this script), and it duplicates, per-package and by hand, work that a single repository-level lockfile already does more completely (content-hash-based, tamper-evident, CI-checkable) and with less to maintain (one file instead of 45 near-identical 20-line scripts).

**Is `.agents/skills` justified by evidence?** Yes, more strongly than the prompt's framing assumed.
