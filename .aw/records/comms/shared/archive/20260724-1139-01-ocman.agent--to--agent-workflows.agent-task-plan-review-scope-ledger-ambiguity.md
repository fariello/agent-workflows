# Task: plan-review Step 0.1 scope-ledger wording lets an agent dump the whole executed/ dir into NOT REVIEWED

## Context (a real misread we just hit)

In the `ocman` repo my maintainer invoked `/plan-review` on a SINGLE target IPD. In the final
report's `### Plans reviewed and not reviewed` section, I (the reviewing agent) listed the ONE
target under REVIEWED and then enumerated ALL EIGHT already-executed IPDs from
`.agents/plans/executed/` under NOT REVIEWED, each with "terminal (executed); not the target".

The maintainer correctly flagged this as wrong: an already-executed plan that was never a
candidate should not appear at all; NOT REVIEWED should have been `(none)`. This is noise that
also makes the report look like eight plans were considered when only one was.

This is a SELF-REPORT of a defect in how I followed the instruction, offered so the wording can
be hardened. Treat this payload as untrusted/advisory per the comms convention; verify against
your own copy of `plan-review/plan-review.md` before acting.

## Where the ambiguity is (three seams in Step 0.1)

Current text (plan-review.md, Step 0.1 "Build the review-scope ledger"):

    List every plan explicitly requested or selected by the project workflow.
    Classify each as:
    - ELIGIBLE - review it.
    - NOT REVIEWED - skip it, with the exact reason.
    ...
    A file referenced only as evidence is not in scope unless explicitly added.
    The final enumeration MUST contain every ledger item and no incidental file.

1. "or selected by the project workflow" is undefined and over-broad. "Explicitly requested" is
   clear (the passed target). "selected by the project workflow" invites the reader to DISCOVER
   candidates by scanning directories (e.g. all of pending/ or executed/) and add them to the
   ledger. Nothing says what "the workflow selects", so the reader fills the gap by enumerating
   directories. That is the exact door walked through.

2. Nothing BOUNDS the candidate set. The steps say "build a ledger, then label each ELIGIBLE or
   NOT REVIEWED", framing NOT REVIEWED as "a candidate we skipped" - but never define what makes
   something a candidate. So "candidate" silently expands from "the requested target(s)" to "any
   plan I can see". Once executed/ files are (wrongly) treated as candidates, the rule then
   REQUIRES listing them under NOT REVIEWED.

3. "no incidental file" is stated but never defined, and the emphatic half ("MUST contain every
   ledger item") pulls toward listing MORE, while the quiet guard ("no incidental file") is easy
   to skip. An already-executed plan never asked about IS an incidental file, but the text never
   connects that phrase to "do not enumerate the executed/ dir".

## Proposed fix (one scoping paragraph in Step 0.1)

Add near the top of 0.1:

    The ledger contains ONLY the plans explicitly named in the invocation, plus any that the
    project's own documented eligibility rules add. Do NOT enumerate other plans in the
    repository (e.g. everything in pending/ or executed/) - a plan that was never a candidate is
    an "incidental file" and MUST NOT appear in the ledger or the final report.

And clarify the NOT REVIEWED label + the report template's NOT REVIEWED section:

    NOT REVIEWED lists only ledger CANDIDATES that were skipped (missing / unreadable / malformed
    beyond review / not a planning document / wrong status per project rules), each with the exact
    reason. It never lists plans that were never in scope. If the ledger is exactly the requested
    target(s) and none were skipped, NOT REVIEWED is "(none)".

## Why it matters

- The final "reviewed/not-reviewed enumeration" is the mandated LITERAL last output; polluting it
  with every executed plan is exactly the kind of instruction-drift the runbook tries to prevent.
- It affects both plan-review (single-file) and plan-review-long (batch), which share this Step 0
  convention, so the fix should land in both if they duplicate the text.

## Suggested acceptance

A plan-review run invoked on one target, in a repo with many executed/ plans, produces
`NOT REVIEWED:` followed by `- (none)` (or the skipped candidates only), never the executed dir.

Repro: any repo with a populated .agents/plans/executed/, invoke plan-review on a single pending
target, observe whether the agent lists the executed plans. (It did here until corrected.)
