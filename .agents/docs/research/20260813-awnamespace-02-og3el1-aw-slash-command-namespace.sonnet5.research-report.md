# AI coding agent slash commands: namespacing research for `/aw <verb>`

All sources accessed August 13, 2026 unless a different access/publication date is noted inline. Documented facts are attributed to specific URLs; anything not directly stated in official documentation is explicitly marked as inference or unverified.

## 1. Executive summary and recommendation

Across the seven target hosts, true space-separated subcommand syntax (`/aw migrate` as two tokens where `aw` is a real command group) does not exist anywhere as a first-class, host-native mechanism. Two other mechanisms get close. First, **colon-namespacing via subdirectories** is real and currently works on **Gemini CLI** (`.gemini/commands/aw/migrate.toml` → `/aw:migrate`), confirmed in current official docs, though Gemini CLI itself is being sunset for free/Pro/Ultra individual users on June 18, 2026 in favor of the closed-source Antigravity CLI, whose own custom-command surface does not (per available documentation) offer the same subdirectory-to-colon namespacing. Claude Code's *plugin* system also produces colon-namespaced commands (`/plugin-name:command-name`), but only for commands distributed through the Claude Code plugin/marketplace mechanism, not for files dropped into a project's `.claude/commands/` directory - current official Claude Code docs state explicitly that subdirectories under `.claude/commands/` affect only the displayed description, not the invocable command name, which contradicts older docs and several third-party writeups still circulating. Second, **argument-based dispatch** - one real command (`/aw`) whose body reads a positional argument such as `$1`, `$ARGUMENTS`, or `{{args}}` and branches internally - is supported by OpenCode, Claude Code, and Gemini CLI, and would render as literal `/aw migrate` for the user, matching the requested shape exactly, at the cost of putting all the verb-dispatch logic inside one prompt template instead of one file per verb.

The **recommended portable design** is a hybrid: ship an argument-dispatching `/aw` command (using each host's native positional-argument syntax) on every host that supports it (OpenCode, Claude Code, Gemini CLI), and fall back to flat, hyphenated per-verb files (`/aw-migrate`, `/aw-setup`, ...) on every host that has no argument-substitution mechanism in its custom-command system (Cursor, GitHub Copilot/VS Code, Windsurf, and - based on currently available docs - Antigravity). This degrades gracefully, requires no plugin/marketplace distribution model, and keeps the per-host shim generation logic the framework already has (one shim per host) largely intact; it just changes what a "shim" contains on argument-capable hosts (one dispatcher file instead of N files). Gemini CLI's real colon-namespacing (`/aw:migrate`) is close enough to the target shape to offer natively there instead of the dispatcher pattern, and should be treated as a bonus rather than the baseline, both because it is genuinely nicer and because Gemini CLI's own future is unsettled as of this research.

## 2. Per-host findings

### 2.1 OpenCode

**1. Mechanism.** Markdown files in `.opencode/commands/` (project) or `~/.config/opencode/commands/` (user/global); the filename (without `.md`) becomes the command name. Frontmatter fields: `description`, `agent`, `model`, `subtask`. Commands can also be defined in `opencode.json`/`opencode.jsonc` under a `command` key. [Commands | OpenCode, https://opencode.ai/docs/commands/, fetched August 13, 2026, page states "Last updated: Aug 12, 2026"]

**2. Namespacing.** Current official docs describe no subdirectory-to-namespace mechanism at all - the docs state plainly "The markdown file name becomes the command name," with no mention of subdirectories affecting the invocable name. [https://opencode.ai/docs/commands/, accessed August 13, 2026] An older, unmerged GitHub feature request (#299, June 2025) proposed subdirectory namespacing modeled on Claude Code's documented-but-apparently-unimplemented behavior (`.opencode/commands/frontend/component.md` → `/project:frontend:component`), but this is a feature request, not documented current behavior, and the current docs supersede it. [https://github.com/anomalyco/opencode/issues/299, accessed August 13, 2026] Verdict: **(c) flat prefix only** is the only documented mechanism; **(b) argument-based dispatch is real and separately supported** (see below), which is not one of the three mechanisms as strictly namespacing but does deliver the desired invocation string.
- (a) Subdirectory namespacing: **not supported** per current docs.
- (b) Argument-based dispatch: **supported**. Commands support `$ARGUMENTS` (all args as one string) and positional `$1`, `$2`, `$3`, etc. A single `.opencode/commands/aw.md` could read `$1` as the verb and branch. Exact invocation: `/aw migrate` (this literally works, since OpenCode passes everything typed after the command name into the argument placeholders). [https://opencode.ai/docs/commands/, accessed August 13, 2026]
- (c) Flat prefix: `/aw-migrate` as a separate file `aw-migrate.md`, always available as a fallback.

**3. Collision surface.** Built-in commands include `/init`, `/undo`, `/redo`, `/share`, `/help`. Custom commands can override built-ins of the same name; OpenCode's command loader documentation shows commands loaded in order (built-in defaults, then config-defined commands, then MCP prompts, then skills), with later sources taking precedence and skills skipped if a command of the same name already exists. `aw` is not a reserved/built-in name as of this research. [https://opencode.ai/docs/commands/ and mirrored docs at https://anomalyco-opencode.mintlify.app/commands, accessed August 13, 2026]

**4. Arguments & discovery.** `$ARGUMENTS`, `$1`/`$2`/`$3` positional substitution, `!command` for shell-output injection, `@file` for file-content inclusion, all documented. Autocomplete: typing `/` in the TUI lists available commands with their descriptions; no special namespaced-family grouping is documented. [https://opencode.ai/docs/commands/, accessed August 13, 2026]

**5. Portability verdict.** The friendliest achievable shape for OpenCode that matches `/aw <verb>` exactly is the argument-dispatch pattern: one `.opencode/commands/aw.md` file whose body branches on `$1`. This is a real, exact match to the target syntax on this host.

### 2.2 Claude Code (Anthropic)

**1. Mechanism.** Two co-existing formats as of this research: the legacy format, Markdown files in `.claude/commands/` (project) or `~/.claude/commands/` (personal), where the filename becomes the command name and optional YAML frontmatter configures `description`, `allowed-tools`, `argument-hint`, `model`; and the current recommended format, `.claude/skills/<name>/SKILL.md`, which supports the identical `/name` invocation plus autonomous (non-slash) invocation by Claude. Official docs state "Custom commands have been merged into skills... For new work, prefer skills." Both formats continue to work. [Slash Commands in the SDK, https://code.claude.com/docs/en/agent-sdk/slash-commands, fetched August 13, 2026]

**2. Namespacing.** This is the most important and most commonly misreported finding in this research. Multiple community sources (a DeepWiki writeup, a plugin marketplace README, and older cached documentation) describe subdirectories under `.claude/commands/` as producing colon-namespaced invocation strings, e.g. `.claude/commands/frontend/component.md` → `/project:frontend:component`. [https://deepwiki.com/FlorianBruniaux/claude-code-ultimate-guide/5.3-custom-commands-and-slash-commands, accessed August 13, 2026] This behavior was reported as broken in a filed bug (`anthropics/claude-code` issue #2422, June 2025): "the documented namespace syntax... doesn't work in practice... The namespaced command is not recognized." [https://github.com/anthropics/claude-code/issues/2422, accessed August 13, 2026] The **current official SDK documentation resolves this ambiguity directly**: under "Organization with Namespacing," it shows an example directory tree and states plainly, **"The subdirectory appears in the command description but doesn't affect the command name itself."** [https://code.claude.com/docs/en/agent-sdk/slash-commands, fetched August 13, 2026] A separate, actively maintained community doc (hyperskill's marketplace repo) independently confirms the same current behavior: "Organize commands in subdirectories. The subdirectories are used for organization and appear in the command description, but they do not affect the command name itself." [https://github.com/hyperskill/claude-code-marketplace/blob/main/docs/slash-commands.md, accessed August 13, 2026] **Conclusion: raw subdirectories under `.claude/commands/` or `.claude/skills/` do not produce namespaced invocation on Claude Code today**, despite older docs and several still-circulating community writeups claiming otherwise.

A genuinely different, working colon-namespace mechanism exists for **plugin-distributed** commands: Claude Code plugins (installed via `/plugin marketplace add` and the `/plugin` menu) expose their commands as `/plugin-name:command-name`, and this is confirmed as **not optional** - a filed bug (`anthropics/claude-code` #15882, reported against docs claiming the prefix was optional) states "the plugin prefix (aka namespace) is never optional... the slash command then always is `/foo:foo` and never `/foo`." [https://github.com/anthropics/claude-code/issues/15882, accessed August 13, 2026] A third-party guide independently confirms current plugin-namespace behavior: "Plugin commands use namespaced syntax with the format `/plugin-name:command-name`... For example, the commit-commands plugin provides `/commit-commands:commit` rather than just `/commit`." [https://www.sean-weldon.com/blog/2026-01-06-how-to-install-and-discover-claude-code-plugins-through-mark, accessed August 13, 2026] If `agent-workflows` were distributed as a Claude Code plugin named `aw`, this would genuinely produce `/aw:migrate`, `/aw:setup`, etc. - but this requires the marketplace/plugin distribution model (a `.claude-plugin/marketplace.json` and `.claude-plugin/plugin.json`), which is a materially different distribution mechanism than dropping files into an existing repository, and is a much bigger architectural commitment than the current flat-file-shim model.

- (a) Subdirectory namespacing (raw commands/skills directory): **documented as not affecting the command name** - current official behavior.
- (a-variant) Plugin-namespace (`/plugin-name:command-name`): **real and confirmed, but requires plugin/marketplace distribution**, not a plain repo-installed file.
- (b) Argument-based dispatch: **supported**. `$ARGUMENTS`, and positional `$0`, `$1`, etc. (`$0` is the first word after the command name per current SDK docs, differing from OpenCode's `$1`-is-first convention - worth flagging as a portability gotcha, see Section 4). A single `.claude/commands/aw.md` (or `.claude/skills/aw/SKILL.md`) with `argument-hint` reading `$0` as the verb produces literal `/aw migrate` invocation. [https://code.claude.com/docs/en/agent-sdk/slash-commands, fetched August 13, 2026]
- (c) Flat prefix: `/aw-migrate` as `aw-migrate.md`, always available.

**3. Collision surface.** Claude Code ships bundled skills (e.g. `code-review`, `verify`) alongside built-ins; official docs note that naming a custom command the same as a bundled skill causes the custom command to "shadow" the bundled one. No evidence `aw` is reserved. [https://code.claude.com/docs/en/agent-sdk/slash-commands, fetched August 13, 2026]

**4. Arguments & discovery.** Positional (`$0`, `$1`, ...) and `$ARGUMENTS` substitution, `argument-hint` frontmatter field for autocomplete display, `!`command`` shell injection, `@file` references, `allowed-tools` restriction. The SDK's `system/init` message exposes the full discovered `slash_commands` list programmatically. [https://code.claude.com/docs/en/agent-sdk/slash-commands, fetched August 13, 2026]

**5. Portability verdict.** Same as OpenCode: the argument-dispatch pattern (`.claude/commands/aw.md` or `.claude/skills/aw/SKILL.md`, reading `$0`) is the exact match to `/aw <verb>`. True colon-namespacing is possible only via the heavier plugin-distribution path, which is a separate design decision, not a drop-in file-format change.

### 2.3 Cursor

**1. Mechanism.** Two systems, with Cursor actively migrating from the first to the second. Legacy: plain Markdown files in `.cursor/commands/` (project) or `~/.cursor/commands/` (global); filename becomes command name. A community-maintained JSON Schema for this format states explicitly: "No frontmatter supported" - the entire file content is the prompt body. [https://claude-plugins.dev/skills/@pr-pm/prpm/creating-cursor-commands, accessed August 13, 2026 - third-party, not an official Cursor source, flagged accordingly] Current/recommended: Skills, `SKILL.md` files under `.cursor/skills/<skill-name>/`. Cursor also auto-loads skills from `.agents/skills/`, `~/.agents/skills/`, `~/.cursor/skills/`, and (for cross-tool compatibility) `.claude/skills/` and `.codex/skills/`. A built-in `/migrate-to-skills` command (Cursor 2.4+) converts eligible legacy commands to skills automatically. [Skills | Cursor Docs, https://cursor.com/help/customization/skills (canonical URL; also reachable via https://cursor.com/docs/context/commands), fetched August 13, 2026]

**2. Namespacing.** Official docs state directly, for Skills: "You can also organize skills into subfolders... Cursor walks the skills root recursively, so category folders work for grouping related skills. **The skill's name comes from the folder that contains `SKILL.md`, not the category above it.**" [https://cursor.com/help/customization/skills, fetched August 13, 2026] This is functionally identical to Claude Code's current documented behavior: nesting is for organization/grouping only and does not produce a namespaced invocation string. No official Cursor documentation describes any colon- or path-based namespace syntax for either legacy commands or skills.
- (a) Subdirectory namespacing: **not supported** (explicitly documented as organizational-only).
- (b) Argument-based dispatch: **undocumented / unverified**. No official Cursor source found in this research describes a `$ARGUMENTS`- or `$1`-style placeholder syntax for legacy commands or skills. The official skills doc states only that typing `/skill-name` "runs" the skill; it does not document a positional-argument substitution mechanism. Third-party sources are inconsistent on this point (some show `argument-hint`-style frontmatter that does not appear in the official schema found). Treat argument-based dispatch as **not confirmed available** on Cursor pending clearer official documentation.
- (c) Flat prefix: `/aw-migrate` via `.cursor/commands/aw-migrate.md` or `.cursor/skills/aw-migrate/SKILL.md` - **confirmed working, and the safest choice for this host**.

**3. Collision surface.** Not documented in official sources found; no evidence of reserved `/aw` name.

**4. Arguments & discovery.** Not clearly documented for arguments (see above). Discovery: typing `/` in chat surfaces both prompt-file-style commands and skills together; skills can also be attached as context via `@skill-name`. [https://cursor.com/help/customization/skills, fetched August 13, 2026]

**5. Portability verdict.** **(c) flat prefix only** is the safe, documented answer for Cursor: `/aw-migrate`, `/aw-setup`, etc., one file per verb, either as legacy commands or (preferred, per Cursor's own migration path) as Skills.

### 2.4 GitHub Copilot (VS Code Chat / Copilot CLI)

**1. Mechanism.** "Prompt files" (also called slash commands in VS Code's own docs): Markdown files with the `.prompt.md` extension in `.github/prompts/` (workspace, default location, configurable via the `chat.promptFilesLocations` setting) or in VS Code user-profile storage (global). YAML frontmatter supports `description`, `name` (overrides the filename as the invocation name if present), `argument-hint`, `agent`, `model`, `tools`. [Use prompt files in VS Code, https://code.visualstudio.com/docs/agent-customization/prompt-files, fetched August 13, 2026, page dated 8/12/2026] Important current caveat directly from the docs: "Agents running on the Agent Host don't use prompt files. To use an existing prompt with the Copilot agent, convert it to an agent skill" - VS Code is mid-migration from prompt files to Agent Skills, with an experimental one-time migration tool (`chat.customizations.promptMigration.enabled`). [same source] The standalone GitHub Copilot CLI (distinct from the VS Code extension) does **not** currently support custom slash commands from `.github/prompts/` at all - this is tracked as an open, unimplemented feature request as of this research. [https://github.com/github/copilot-cli/issues/618, filed and still open as of the source snapshot dated November 18, 2025; https://github.com/github/copilot-cli/issues/1113, filed January 25, 2026, also open]

**2. Namespacing.** No subdirectory-to-namespace mechanism is documented anywhere in the official VS Code prompt-files reference. The command name is either the `name` frontmatter field or the filename; no mention of subdirectory structure affecting the invocation string at all (subdirectories are not even discussed as an organizational feature in the fetched official page). [https://code.visualstudio.com/docs/agent-customization/prompt-files, fetched August 13, 2026]
- (a) Subdirectory namespacing: **not supported / not documented in any form**.
- (b) Argument-based dispatch: **partially supported, informally**. The docs show `/create-react-form formName=MyForm` and `/create-api for listing customers` as valid invocations, i.e. free text typed after the command name is appended to the prompt - but there is no documented positional-placeholder syntax analogous to `$1`/`$ARGUMENTS`. The closest structured mechanism is `${input:variableName}` / `${input:variableName:placeholder}` template syntax, which the docs describe as a way to prompt the *model* to ask the user for missing information conversationally, not a deterministic pre-substitution the way OpenCode/Claude Code/Gemini CLI handle it. A single `/aw` prompt file could plausibly work by instructing the model "the first word typed after this command is the verb; branch accordingly" - but this relies on model-level instruction-following rather than a host-guaranteed substitution mechanism, so it is meaningfully less reliable than the OpenCode/Claude Code/Gemini CLI equivalents. Treat as **usable but not host-guaranteed**.
- (c) Flat prefix: `/aw-migrate` via `.github/prompts/aw-migrate.prompt.md` - confirmed, reliable, and the safe default.

**3. Collision surface.** Not documented; VS Code notes that "Agent skills also appear as slash commands alongside prompt files" (so a future migration to Agent Skills would share the same namespace as prompt files), and that if a `name` field collides, behavior is not explicitly specified in the fetched docs.

**4. Arguments & discovery.** Autocomplete: typing `/` in the VS Code Chat view shows custom prompts "at the top of the IntelliSense list" with a bookmark icon, distinct from built-in system commands. [https://learn.microsoft.com/en-us/visualstudio/ide/copilot-chat-context?view=visualstudio, accessed August 13, 2026 - this is the Visual Studio variant of the docs, cited for the autocomplete-behavior detail since it closely mirrors VS Code's own described UI] `argument-hint` frontmatter shows placeholder guidance in the chat input.

**5. Portability verdict.** **(c) flat prefix only** is the reliable, documented answer: `/aw-migrate`, `/aw-setup`, etc. The plain Copilot CLI (as opposed to VS Code) currently has **no working custom-slash-command mechanism at all** as of this research - flag this explicitly as a host where the entire feature is unavailable outside the VS Code extension context.

### 2.5 Windsurf

**1. Mechanism.** "Workflows": Markdown files under `.windsurf/workflows/` (workspace scope, discovered recursively in the current workspace and any parent directories up to the git root) or `~/.codeium/windsurf/global_workflows/` (global scope, not committed). Frontmatter supports `name` and `description`. Invocation: `/[workflow-name]`. Workflow files are capped at 12,000 characters each. [Workflows, official documentation, fetched via https://docs.windsurf.com/windsurf/cascade/workflows which redirects to https://docs.devin.ai/desktop/cascade/workflows, fetched August 13, 2026]

**Notable current-state finding:** the Windsurf documentation domain (`docs.windsurf.com`) now redirects to `docs.devin.ai`, and the fetched page repeatedly refers to the host application as "Devin Desktop" rather than "Windsurf," including a note that "Workflows are specific to Cascade - the Devin Local agent does not support them," and a migration path ("Devin: Open Cascade Migration Wizard") from Workflows to a separate "Skills" mechanism. This indicates Windsurf has been integrated into, or rebranded under, Cognition's Devin product line as of this research; the underlying mechanism documented here (Cascade Workflows) still appears current and functioning, but the product-identity layer around it has changed since the framework's target-host list was presumably written. This should be flagged to the maintainer as a naming/product-continuity risk independent of the namespacing question. [https://docs.devin.ai/desktop/cascade/workflows, fetched August 13, 2026 via redirect from docs.windsurf.com]

**2. Namespacing.** No subdirectory-to-namespace mechanism is documented. Workflows are discovered recursively from multiple `.windsurf/workflows/` directories (current workspace, sub-directories, and parent directories up to the git root) purely for *discovery* purposes - "deduplicated and displayed with the shortest relative path" when the same name exists in multiple discovered locations - but the invocation name itself is `/[workflow-name]`, derived from the file's `name` field or filename, with no indication that a subdirectory path becomes part of the invocation string. [same source]
- (a) Subdirectory namespacing: **not documented / apparently not supported** - subdirectories affect discovery/precedence, not the command name.
- (b) Argument-based dispatch: **not documented**. No `$ARGUMENTS`- or `$1`-style placeholder syntax appears anywhere in the fetched official docs or examples (the example workflows use inline shell commands like `` `gh pr checkout [id]` `` where `[id]` is written as literal placeholder text for the model to infer from context, not a host-substituted argument). Treat as **not confirmed available**.
- (c) Flat prefix: `/aw-migrate` via `.windsurf/workflows/aw-migrate.md` - confirmed, safe default.

**3. Collision surface.** A documented precedence order exists across four levels: System (Enterprise, highest priority) > Workspace > Global > Built-in (lowest priority) - "if an organization deploys a system-level workflow with a specific name, it will override any workspace, global, or built-in workflow with the same name." [same source] No evidence `aw` is reserved as a built-in.

**4. Arguments & discovery.** No structured argument mechanism documented (see above). Workflows can call other workflows by name from within their own instructions (e.g., a step reading "Call /workflow-2"), which is a form of composition but not argument passing in the traditional sense.

**5. Portability verdict.** **(c) flat prefix only**: `/aw-migrate`, `/aw-setup`, etc.

### 2.6 Gemini CLI / Gemini Code Assist

**Critical currency note, stated up front:** Google announced on May 19, 2026 that Gemini CLI and the Gemini Code Assist IDE extensions would stop serving Google AI Pro, Ultra, and free-tier Gemini Code Assist individual users on June 18, 2026, with the closed-source Antigravity CLI positioned as the successor. [An important update: Transitioning Gemini CLI to Antigravity CLI, Google Developers Blog, https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/, accessed August 13, 2026, dated May 19, 2026] This is corroborated by multiple independent outlets reporting the cutover actually happened on schedule. [The Register, https://www.theregister.com/ai-ml/2026/05/20/bye-bye-gemini-cli-google-nudges-devs-toward-antigravity/5243605, dated May 20, 2026; Tech Times, https://www.techtimes.com/articles/318660/20260618/gemini-cli-shutdown-takes-effect-go-based-antigravity-cli-arrives.htm, dated June 18, 2026] **Organizations with a Gemini Code Assist Standard or Enterprise license, Gemini Code Assist for GitHub via Google Cloud, or a paid Gemini/Gemini Enterprise Agent Platform API key retain uninterrupted access to legacy Gemini CLI** per Google's own announcement. [same Google Developers Blog source] Third-party sources disagree on the exact successor CLI's binary name (`agy` vs. `av` appear in different secondary sources) and this research could not confirm the binary name against an official Google source directly - **flag this specific detail as unverified**.

**1. Mechanism (legacy Gemini CLI, still authoritative for enterprise-licensed users and for any repo that pins an older Gemini CLI version).** Command definition files in TOML format under `~/.gemini/commands/` (user scope) or `<project>/.gemini/commands/` (project scope). Required `prompt` field (string, single- or multi-line); optional `description` field. [Custom Commands, official gemini-cli docs, https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/custom-commands.md, accessed August 13, 2026; mirrored at https://google-gemini.github.io/gemini-cli/docs/cli/custom-commands.html and https://geminicli.com/docs/cli/custom-commands/]

**2. Namespacing.** This is the clearest, best-documented true-namespacing mechanism found in this entire research task. Official docs state directly: **"The name of a command is determined by its file path relative to its commands directory. Subdirectories are used to create namespaced commands, with the path separator (/ or \) being converted to a colon (:)."** Worked example given in the docs themselves: a file at `<project>/.gemini/commands/git/commit.toml` becomes the command `/git:commit`. [same source, accessed August 13, 2026] Applied directly to this project: a file at `.gemini/commands/aw/migrate.toml` becomes `/aw:migrate`; `.gemini/commands/aw/setup.toml` becomes `/aw:setup`; and so on for every verb, each as its own file inside a shared `aw/` subdirectory.
- (a) Subdirectory namespacing: **fully supported and officially documented**. Exact invocation string: `/aw:migrate` (colon, not space).
- (b) Argument-based dispatch: **also supported, separately**. `{{args}}` expands to everything typed after the command name; there is also a shell-injection syntax `!{...}` and a directory/file-inclusion syntax `@{path}`, with a documented processing order (file inclusion, then shell commands, then argument substitution). [https://geminicli.com/docs/cli/custom-commands/, accessed August 13, 2026] This means a single `.gemini/commands/aw.toml` with `prompt = "...verb: {{args}}..."` would produce literal `/aw migrate` (space-separated) invocation, exactly matching the target syntax, as an alternative to the colon-namespaced per-verb-file approach.
- (c) Flat prefix: also trivially available (`.gemini/commands/aw-migrate.toml` → `/aw-migrate`) if neither of the above is wanted.

**3. Collision surface.** If a project-scoped command and a user-scoped (global) command share the same name, the project-scoped one wins. [https://jsdev.space/gemini-cli-custom-commands/, accessed August 13, 2026 - third-party but consistent with the general project-over-global precedence pattern documented officially for command discovery] `/commands list` and `/commands reload` are built-in meta-commands for inspecting and refreshing custom commands without restarting the CLI. [https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/custom-commands.md, accessed August 13, 2026] No evidence `aw` is reserved.

**4. Arguments & discovery.** Both structured positional-style dispatch (`{{args}}`) and true namespacing (subdirectory → colon) are available and can be combined (e.g., `.gemini/commands/aw/migrate.toml` could itself use `{{args}}` for a migrate-specific sub-argument, giving `/aw:migrate <target>`). MCP server prompts are also automatically exposed as slash commands using the MCP prompt's own name and description. [https://cloud.google.com/blog/topics/developers-practitioners/gemini-cli-custom-slash-commands, accessed August 13, 2026]

**5. Portability verdict.** Gemini CLI (legacy) offers the single best match to a true `/aw <verb>`-style family found across every host researched, via `/aw:migrate` (colon) - and, if literal space-separated syntax matters more than the colon, the `{{args}}` dispatch pattern gives that too. The major caveat is availability going forward: this mechanism is confirmed working today only for the shrinking population of enterprise-licensed users and anyone pinning a pre-June-18-2026 Gemini CLI version; it should not be treated as a durable long-term target without separately confirming Antigravity CLI's custom-command surface (see 2.7 and the note below), since Google's own transition messaging points users toward Antigravity CLI going forward.

### 2.7 Antigravity

Antigravity did not exist as a distinct, separately-shipped product at the start of this research's relevant timeframe in the way the other six hosts did; it has grown from an IDE (per third-party retrospective coverage, "started in late 2025 as an AI-first IDE... In May 2026 it grew into Antigravity 2.0... The new CLI is the terminal front end for that same platform") into Google's designated successor to both the Gemini CLI and the Gemini Code Assist IDE extensions. [https://inventivehq.com/blog/gemini-cli-deprecated-antigravity-cli-migration, accessed August 13, 2026 - third-party retrospective, treated as context rather than an authoritative spec source]

**1. Mechanism.** Antigravity follows the open "Agent Skills" standard rather than a bespoke command-file format. A skill is a directory containing a `SKILL.md` file (with YAML frontmatter `name` and `description`) plus optional supporting scripts/references. Skills are placed at `<workspace-root>/.agents/skills/<skill-folder>/SKILL.md` (project scope) or `~/.gemini/antigravity/skills/<skill-folder>/` (global scope, per one source) or `.antigravity/skills/` (per a different source) - **the exact canonical global/legacy-compat directory name is inconsistent across the secondary sources found in this research and could not be pinned to a single official page**; official Google documentation found does confirm the `.agents/skills/` project-scope path specifically. [How to Build Custom Skills for Antigravity Using Agent Skills Standard, https://dev.to/volodymyr_nehir/how-to-build-custom-skills-for-antigravity-using-agent-skills-standard-4ab9, accessed August 13, 2026 - third-party; corroborated for the `.agents/skills/` path specifically by Google's own codelab, https://codelabs.developers.google.com/antigravity/how-to-create-agent-skills-for-antigravity-cli, accessed August 13, 2026, and by official product docs, Google Antigravity Docs - Plugins & Skills, https://antigravity.google/docs/cli/plugins, accessed August 13, 2026]

**2. Namespacing.** Official Google Antigravity documentation states: "Skills are declarative, human-readable markdown files... Once registered, Skills convert automatically into slash commands inside the TUI, allowing you to invoke them manually (e.g., typing `/refactor-ui`)... Any markdown skill in this directory is automatically imported as a global slash command whenever you launch `agy` in any directory." [Google Antigravity Docs - Plugins & Skills, https://antigravity.google/docs/cli/plugins, accessed August 13, 2026] The example given (`/refactor-ui`) is a flat, hyphenated name with no colon or path segment, and no official Antigravity documentation found in this research describes subdirectory structure inside `.agents/skills/` mapping to a namespaced invocation string the way Gemini CLI's TOML commands do. Antigravity's IDE-mode default behavior is also emphasized as autonomous/progressive-disclosure ("the agent uses progressive disclosure - it reads the metadata of your available skills and autonomously activates the right one," per a third-party walkthrough) rather than purely manual slash invocation, though the CLI docs confirm manual `/skill-name` invocation also works.
- (a) Subdirectory namespacing: **not documented as supported**; skill name appears to be the containing-folder name, consistent with the Cursor/Claude Code Skills pattern, but this research found no explicit official statement equivalent to Cursor's or Claude Code's "subdirectory doesn't affect the name" clarification - **treat as likely-flat-only by analogy to the shared Agent Skills standard, but unconfirmed for Antigravity specifically**.
- (b) Argument-based dispatch: **not documented**. No placeholder-substitution syntax (`$1`, `$ARGUMENTS`, `{{args}}`, or equivalent) was found in any official Antigravity source in this research.
- (c) Flat prefix: `/aw-migrate` via `.agents/skills/aw-migrate/SKILL.md` - the only mechanism confirmed by official documentation and by Google's own worked example format.

**3. Collision surface.** Not documented in sources found.

**4. Arguments & discovery.** `/skills` is a built-in command that lists currently discovered skills. [Authoring Google Antigravity Skills, https://codelabs.developers.google.com/getting-started-with-antigravity-skills, accessed August 13, 2026] No documented argument-passing mechanism beyond whatever free text the user types after the command, which - as with GitHub Copilot - relies on the model interpreting that text rather than a host-guaranteed substitution.

**5. Portability verdict.** **(c) flat prefix only**, by the same logic as Cursor, Windsurf, and GitHub Copilot: `/aw-migrate`, `/aw-setup`, etc. Given Antigravity's role as Gemini CLI's designated successor, this is also the most consequential finding in the entire report for the framework's future: **the true colon-namespacing available today on legacy Gemini CLI does not appear to carry forward to Antigravity** based on currently available documentation, so any design that leans on Gemini CLI's namespacing as a long-term anchor should be treated as provisional.

## 4. Back-compat and deprecation recommendation

**Migration approach.** Introduce the new `/aw <verb>` family without removing the old flat commands in the same release:
1. On OpenCode, Claude Code, and Gemini CLI, add a single new dispatcher file (`aw.md`/`aw.toml`) per host that reads the first positional argument and re-executes (or textually re-includes) the corresponding existing flat command's prompt body, so `/aw migrate` and the legacy `/migrate` (or whatever the current flat name is) both work and stay in sync from one underlying instruction source.
2. On Cursor, GitHub Copilot, Windsurf, and Antigravity, there is no dispatcher option, so the "new" family is really just a **rename with an alias period**: keep the existing flat files exactly as they are, and additionally ship new flat files under the `aw-` prefix (`aw-migrate.md` alongside the existing `migrate.md`) whose body is a one-line pointer/duplicate of the original, so users can start typing the new convention immediately while old scripts/muscle memory referencing the old name keep working.
3. Deprecation path: once telemetry or a reasonable fixed window (e.g., two minor versions) shows the old flat names are no longer being invoked, remove the old aliases and keep only the `aw`/`aw-*` family. On hosts with true dispatch (OpenCode, Claude Code, Gemini CLI), this is a config/content change only. On alias-only hosts (Cursor, Copilot, Windsurf, Antigravity), this means deleting the old files, which is a breaking change for anyone who pinned the old names in muscle memory, scripts, or (for VS Code) any `chat.promptFilesRecommendations` configuration - call this out in release notes specifically for those four hosts.

**Host-specific complications for aliasing:**
- **Claude Code**: naming a new command/skill identically to one of Claude Code's own *bundled* skills (`code-review`, `verify`) causes silent shadowing rather than an error, per official docs - worth a one-time check that neither the old nor new `aw`-family names collide with Claude Code's bundled skill names before shipping.
- **GitHub Copilot / VS Code**: the platform's own migration story (prompt files → Agent Skills, with an experimental automated migration tool) is mid-flight as of this research; whatever alias files are shipped for VS Code today may need to be re-shipped in the Agent Skills format later, since "Agents running on the Agent Host don't use prompt files" per current docs.
- **Windsurf / Devin Desktop**: the product identity itself is in flux (docs domain now redirects to Devin's docs, and Devin's own docs describe a parallel migration from Workflows to a separate Skills mechanism, with a dedicated "Cascade Migration Wizard"). Any aliasing work here should be treated as provisional and re-checked against Devin Desktop's own migration timeline rather than assumed stable.
- **Gemini CLI**: aliasing work here has a hard external deadline unrelated to this framework's own choices - legacy Gemini CLI (where the colon-namespace mechanism lives) is already unavailable to non-enterprise users as of June 18, 2026, per Google's own announcement. Any `/aw:verb`-style shim shipped for Gemini CLI should be treated as serving only the remaining enterprise-licensed population, with Antigravity as the actual forward-looking target - and Antigravity's own custom-command surface, per Section 2.7, does not currently offer equivalent namespacing.

## 5. Open risks, unknowns, and hosts where this is not fully viable

- **Cursor argument-substitution is unconfirmed.** This research found no official Cursor documentation describing a `$ARGUMENTS`-equivalent mechanism for either legacy commands or Skills. If a follow-up check of Cursor's own docs or changelog turns up such a mechanism, the argument-dispatch pattern (and therefore literal `/aw migrate`) might become viable there too; until then, treat Cursor as flat-prefix-only.
- **Windsurf/Devin Desktop product continuity.** The documentation domain redirect (`docs.windsurf.com` → `docs.devin.ai`) and the repeated "Devin Desktop" framing in currently-live docs is a signal this research surfaced but did not fully resolve - it is unclear from the fetched pages alone whether "Windsurf" remains the correct product name for shim-targeting purposes, or whether the framework's host list should be updated to reflect a Devin-branded surface. Recommend a direct, dedicated check of Cognition's current branding before finalizing any Windsurf-specific shim naming.
- **Gemini CLI's future for the framework's actual user base.** The framework's namespacing dream case (`/aw:migrate`) is real today only on a CLI that most individual users can no longer access as of June 18, 2026. Building meaningfully around Gemini CLI's colon-namespace mechanism risks building for a shrinking or already-departed audience; Antigravity is the documented successor but does not currently offer equivalent namespacing per the sources found here.
- **Antigravity's directory-path inconsistency.** Three different secondary sources gave three different candidate paths for Antigravity's global-scope skills directory (`~/.gemini/antigravity/skills/`, `.antigravity/skills/`, and implicitly others via the CLI's own migration-import logic from legacy Gemini CLI paths). Only the project-scope `.agents/skills/` path was confirmed by an official Google source. Anyone implementing an Antigravity shim should verify the global-scope path directly against a current Antigravity CLI install rather than relying on this research's secondary sources.
- **GitHub Copilot CLI (the standalone terminal tool, not the VS Code extension) has no custom-command mechanism at all** as of this research - both relevant feature requests were open/unimplemented at time of access. If the framework's host list includes the standalone Copilot CLI specifically (as opposed to VS Code's Copilot Chat), this host should be marked as **not viable for any shim** until GitHub ships the feature.
- **Antigravity CLI's exact binary name is unconfirmed** (`agy` vs. `av` conflict across secondary sources) - immaterial to the namespacing question itself, but worth resolving before writing any user-facing installation instructions that reference the binary by name.
