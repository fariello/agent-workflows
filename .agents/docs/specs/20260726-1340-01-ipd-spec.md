# Spec: authoring and executing an Implementation Plan Document (IPD)

- Date: 2026-07-26
- Status: canonical reference; produced by IPD `20260726-ipdcomplete-02-h409oe-ipd-spec-and-always-loaded-directive` (Set `ipd-completeness-guardrails`, Order 2)

This is the single entry point for how to author and execute an IPD in this toolkit. It CONSOLIDATES the conventions by REFERENCE to their authoritative homes (it does not restate or fork them). When authoring or executing an IPD you MUST follow it, including the mandatory implementation checklist and the completion rule below.

## Authoritative homes (the sources this consolidates)

- IPD TEMPLATE and its section structure, the mandatory `## Detailed Implementation Checklist (TODO)`, the completion rule, and the split-into-a-Set guidance: `.agents/workflows/assess/templates/ipd.md` (DECISIONS D111).
- STATUS vocabulary + readiness lifecycle (`draft` -> `to-review` -> `reviewed` -> `approved` -> terminal `executed`/`superseded`/`not-executed`; standing `reusable`), and the plan-file naming `YYYYMMDD-HHMM-NN-<slug>.md`: the template's status comment block and `.agents/plans/README.md` (DECISIONS D45/D47/D52).
- PLAN LIFECYCLE + directory disposition + the `Set:`/`Order:` mechanism for ordered sets, and the retire (`superseded`/`not-executed`) rule: the AGENTS.md `AGENT-PLANS` block and `.agents/plans/README.md`.
- EXECUTION CONTRACT (path-scoped commits, never `git add -A`/`-a`, never push, paste ACTUAL runner output, no em/en dashes, STOP-and-report on scope growth, no tags/Releases/PyPI outside release-review): the AGENTS.md agent-workflows managed block and `CONTRIBUTING.md`.

## What an IPD MUST contain

Author from the template (`assess/templates/ipd.md`), or generate a conformant skeleton with `aw ipd scaffold` and assign ids with `aw ipd sync`. The EXACT structural contract is machine-checkable and owned by the canonical schema (`agent_workflows/ipd_schema.py`) and the structure specification `.agents/docs/specs/20260802-1904-01-ipd-structure-and-linting.spec.md`; `aw ipd lint` enforces it. Do not restate or fork that contract here. In brief:

- Metadata block (a bullet `- Field: value` list after the H1 title, NOT YAML front matter; "YAML front matter" means only actual `---` YAML, which the parser ignores): required `Date`, `Kind` (`child` or `orchestrator`), `Concern`, `Scope`, `Status`, `Author`; `Set` and `Order` together when in an ordered Set (`Order: 0` for an orchestrator, `>= 1` for a child); `Approval` when and only when `Status: approved`; `Highest E allocated` once any `E-*` exists (the allocation watermark); the `Quarantine`/`Quarantine owner`/`Quarantine follow-up` trio only on a quarantined nonterminal plan.
- The H2 SECTION ORDER is exact and per-kind (child and orchestrator differ), enumerated in the schema. In BOTH kinds `## Detailed Implementation Checklist (TODO)` is the H2 IMMEDIATELY AFTER `## Goal` and `## Validation and cross-check ...` is the H2 IMMEDIATELY BEFORE `## Approval and execution gate`. (There is no "near the top/end"; placement is exact.)
- `## Workflow history` (append one dated line per workflow touch; never rewrite prior lines).
- `## Detailed Implementation Checklist (TODO)` (mandatory): the EXECUTION checklist. Only executable leaves are checkboxes; each carries a unique `E-NN` id, `Depends on:` (`none` or comma-separated `E-*`), `Expected outcome:`, and `Execution state:` (`pending`|`performed`|`blocked`|`failed`). `E-* checked` means the action was PERFORMED, not that it was verified (F-07). The terminal lifecycle transition is NOT an `E-*` item (F-08); it is a post-gate transaction (see the lifecycle line).
- `## Validation and cross-check` (mandatory): a SEPARATE evidence pass. Exactly one `V-NN validates E-NN` row per `E-NN` (a 1:1 bijection), each with `Required evidence:`, `Observed evidence:`, and `Result:` (`pending`|`pass`|`blocked`|`failed`). `V-* pass` means the evidence was INSPECTED and supports the expected outcome. Both the CREATOR (authors both checklists) and the REVIEWER (assesses both) are responsible for it (DECISIONS D115).
- `## Open questions`: each question is an `### OQ-NN:` with `Blocking:` (`yes`|`no`), `Status:` (`open`|`resolved`|`deferred`), `Owner:`, and a resolution/deferral rationale. A blocking question may not be deferred and must be resolved before `pre-execution` (F-09).
- The other sections (`## Goal`, `## Findings`, `## Proposed changes (ordered, validatable)`, `## Deferred / out of scope (with reason)`, `## Scope check`, `## Required tests / validation`, `## Spec / documentation sync`; plus the orchestrator's `## Child IPDs...`, `## Completion criteria...`, `## Cross-IPD validation`) appear in the schema-defined order for the kind.
- `## Approval and execution gate` carries `Size assessment:` (`standard`|`exception`) with a `Cohesion rationale:`, plus the completion rule below.

## Completion rule (the hard gate)

Before claiming done or transitioning a plan to `executed/`:

1. EVERY execution `- [ ]` item MUST be `- [x]` AND its matching `## Validation and cross-check` item MUST be verified with CONCRETE evidence (tests run with the ACTUAL output pasted; never claim a pass not run).
2. If any item cannot be completed, STOP and report it explicitly rather than transitioning the plan.
3. A checklist is a MITIGATION, not a guarantee (a box can be ticked without the work); the reviewer step and the paste-actual-output rule still apply. An agent-asserted `executed` is a CLAIM, not proof (see `.agents/comms/README.md`).

## Keep IPDs small (split into an ordered Set)

Size thresholds are WARNINGS and review triggers, not caps: the defaults are more than 5 task-group sections or more than 18 executable `E-*` leaves (spec Section 8). Exceeding a threshold does not invalidate the plan; it requires `Size assessment: exception` plus a substantive `Cohesion rationale:` in the gate, which the semantic reviewer weighs. Prefer splitting work that spans several code regions/files, mixes distinct concerns, or has independently-executable phases into an ordered `Set:`/`Order:` of small, independently-executable, independently-verifiable plans. When the parts need coordination, add a `00` ORCHESTRATOR IPD (the `00` slug is reserved for it) that defines the child sequence, dependencies, whole-Set completion criteria, and cross-IPD validation; use the orchestrator template alongside the IPD template. State cross-chunk dependencies in each chunk's execution contract ("requires `Order N` executed first; if its symbols are absent, STOP"). Splitting is good hygiene for any model and especially valuable when the executing model is a faster/weaker tier; authors MUST NOT pad a small plan toward the thresholds nor split a cohesive plan merely to stay under them.

## Lifecycle in one line

`draft` -> `to-review` -> `reviewed` (via `/plan-review`) -> `approved` (human) -> execute, validate, sync docs -> then, as a POST-GATE transaction (NOT an `E-*`/`V-*` checklist item, F-08): append the workflow-history line, set the terminal `Status:`, `git mv` from `.agents/plans/pending/` to `.agents/plans/executed/` (or `superseded/`/`not-executed/` with a `RETIRED ...` header; never delete), and make the path-scoped lifecycle commit. Recurring plans live in `reusable/`.
