# Spec: authoring and executing an Implementation Plan Document (IPD)

This is the single entry point for how to author and execute an IPD in this toolkit. It CONSOLIDATES the conventions by REFERENCE to their authoritative homes (it does not restate or fork them). When authoring or executing an IPD you MUST follow it, including the mandatory implementation checklist and the completion rule below.

## What an IPD MUST contain

Author from the template (`assess/templates/ipd.md`); do not drop its sections. In brief:

- Front matter: `Date`, `Concern`, `Scope`, `Status` (born `to-review` for a real proposal; `draft` only for an explicit stub), `Author`, optional `Set:`/`Order:`, and `Approval:` once a human signs off.
- `## Workflow history` (append one dated line per workflow touch; never rewrite prior lines).
- `## Goal`, `## Findings`, `## Proposed changes (ordered, validatable)`, `## Deferred / out of scope`, `## Scope check`, `## Required tests / validation`, `## Spec / documentation sync`, `## Open questions`.
- `## Detailed Implementation Checklist (TODO)` (mandatory): tickable `- [ ]` items grouped by task, naming EXACT file basenames + function/symbol names (+ line anchors), the LITERAL verification command, and a reminder to paste real output. This is the primary progress tracker for an agent with no external todo tool.
- `## Approval and execution gate` with the completion rule below.

## Completion rule (the hard gate)

Before claiming done or transitioning a plan to `executed/`:

1. EVERY `- [ ]` checklist item MUST be `- [x]` AND independently verified (tests run with the ACTUAL output pasted; never claim a pass not run).
2. If any item cannot be completed, STOP and report rather than transitioning the plan.
3. A checklist is a MITIGATION, not a guarantee (a box can be ticked without the work); the reviewer step and the paste-actual-output rule still apply. An agent-asserted `executed` is a CLAIM, not proof (see `.agents/comms/README.md`).

## Keep IPDs small (split into an ordered Set)

When an IPD would exceed roughly 4-6 tasks, span several code regions/files, or mix distinct concerns, SPLIT it into an ordered `Set:`/`Order:` of small, independently-executable and independently-verifiable plans instead of one large plan. State cross-chunk dependencies in each chunk's execution contract ("requires `Order N` executed first; if its symbols are absent, STOP"). Good hygiene for any model; close to REQUIRED when the executing model is a faster/weaker tier.

## Lifecycle in one line

`draft` -> `to-review` -> `reviewed` (via `/plan-review`) -> `approved` (human) -> execute, validate, sync docs -> set terminal `Status:` and `git mv` from `.agents/plans/pending/` to `.agents/plans/executed/` (or `superseded/`/`not-executed/` with a `RETIRED ...` header; never delete). Recurring plans live in `reusable/`.
