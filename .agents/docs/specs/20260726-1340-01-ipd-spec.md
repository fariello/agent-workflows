# Spec: authoring and executing an Implementation Plan Document (IPD)

- Date: 2026-07-26
- Status: canonical reference; produced by IPD `20260726-1326-02` (Set `ipd-completeness-guardrails`, Order 2)
- Author: opencode (its_direct/pt3-claude-opus-4.8-1m-us)

This is the single entry point for how to author and execute an IPD in this toolkit. It CONSOLIDATES the conventions by REFERENCE to their authoritative homes (it does not restate or fork them). When authoring or executing an IPD you MUST follow it, including the mandatory implementation checklist and the completion rule below.

- IPD TEMPLATE and its section structure, the mandatory `## Detailed Implementation Checklist (TODO)`, the completion rule, and the split-into-a-Set guidance: `.agents/workflows/assess/templates/ipd.md` (DECISIONS D111).
- STATUS vocabulary + readiness lifecycle (`draft` -> `to-review` -> `reviewed` -> `approved` -> terminal `executed`/`superseded`/`not-executed`; standing `reusable`), and the plan-file naming `YYYYMMDD-HHMM-NN-<slug>.md`: the template's status comment block and `.agents/plans/README.md` (DECISIONS D45/D47/D52).
- PLAN LIFECYCLE + directory disposition + the `Set:`/`Order:` mechanism for ordered sets, and the retire (`superseded`/`not-executed`) rule: the AGENTS.md `AGENT-PLANS` block and `.agents/plans/README.md`.
- EXECUTION CONTRACT (path-scoped commits, never `git add -A`/`-a`, never push, paste ACTUAL runner output, no em/en dashes, STOP-and-report on scope growth, no tags/Releases/PyPI outside release-review): the AGENTS.md agent-workflows managed block and `CONTRIBUTING.md`.

## What an IPD MUST contain

Author from the template (`assess/templates/ipd.md`); do not drop its sections. In brief:

- Front matter: `Date`, `Concern`, `Scope`, `Status` (born `to-review` for a real proposal; `draft` only for an explicit stub), `Author`, optional `Set:`/`Order:`, and `Approval:` once a human signs off.
- `## Workflow history` (append one dated line per workflow touch; never rewrite prior lines).
- `## Goal`, `## Findings`, `## Proposed changes (ordered, validatable)`, `## Deferred / out of scope`, `## Scope check`, `## Required tests / validation`, `## Spec / documentation sync`, `## Open questions`.
- `## Detailed Implementation Checklist (TODO)` (mandatory), placed near the BEGINNING: the EXECUTION checklist, tickable `- [ ]` items grouped by task covering every required action, decision, deliverable, and validation, naming EXACT file basenames + function/symbol names (+ line anchors), the LITERAL verification command, and a reminder to paste real output. Primary progress tracker for an agent with no external todo tool.
- `## Validation and cross-check` (mandatory), placed near the END: a SEPARATE verification checklist whose items map 1:1 to the execution checklist and require CONCRETE per-item evidence (command output, `file:line`, artifact path) before reporting success; incomplete/blocked/skipped/unverified work is reported EXPLICITLY here. It must be specific enough to catch the common failure of claiming completion without having done every step. Both the CREATOR (authors both checklists) and the REVIEWER (assesses both) are responsible for it (see the plan-review workflow, DECISIONS D115).
- `## Approval and execution gate` with the completion rule below.

## Completion rule (the hard gate)

Before claiming done or transitioning a plan to `executed/`:

1. EVERY execution `- [ ]` item MUST be `- [x]` AND its matching `## Validation and cross-check` item MUST be verified with CONCRETE evidence (tests run with the ACTUAL output pasted; never claim a pass not run).
2. If any item cannot be completed, STOP and report it explicitly rather than transitioning the plan.
3. A checklist is a MITIGATION, not a guarantee (a box can be ticked without the work); the reviewer step and the paste-actual-output rule still apply. An agent-asserted `executed` is a CLAIM, not proof (see `.agents/comms/README.md`).

## Keep IPDs small (split into an ordered Set)

Strong guidance, not an inflexible rule: prefer FIVE or fewer major steps; avoid more than roughly TEN major steps or 12-18 total actionable checklist items in one IPD. When an IPD would exceed that scale, span several code regions/files, mix distinct concerns, or have independently-executable phases, SPLIT it into an ordered `Set:`/`Order:` of small, independently-executable and independently-verifiable plans instead of one large plan. When the parts need coordination, add a `00` ORCHESTRATOR IPD (the `00` slug is reserved for it) that defines the child sequence, dependencies, whole-Set completion criteria, and cross-IPD validation; use the orchestrator template alongside the IPD template. State cross-chunk dependencies in each chunk's execution contract ("requires `Order N` executed first; if its symbols are absent, STOP"). Good hygiene for any model; close to REQUIRED when the executing model is a faster/weaker tier.

## Lifecycle in one line

`draft` -> `to-review` -> `reviewed` (via `/plan-review`) -> `approved` (human) -> execute, validate, sync docs -> set terminal `Status:` and `git mv` from `.agents/plans/pending/` to `.agents/plans/executed/` (or `superseded/`/`not-executed/` with a `RETIRED ...` header; never delete). Recurring plans live in `reusable/`.
